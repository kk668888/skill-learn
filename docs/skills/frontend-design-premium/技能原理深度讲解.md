# 技能原理深度讲解

> **套件**：`frontend-design-premium`
> **来源**：`skills/frontend-design-premium/frontend-design-premium/`
> **上游仓库**：[TryHand-Co-Ltd/frontend-design-premium](https://github.com/TryHand-Co-Ltd/frontend-design-premium) v1.4.1（Apache-2.0）
> **本文定位**：讲**这一整套**的整体设计。单个技能的细节归它的 `-中文版.md` 与 `-详细设计讲解.md`

---

## 0. 一句话原理

**把"审美"和"产品行为"拆给两个技能，再用一个磁盘文件（`DESIGN.md`）补上 agent 缺失的记忆——三层各管一件事，谁也不许越界。**

```
上游 frontend-design  →  审美方向（好看、不模板化）
项目 DESIGN.md        →  持久品味记忆（跨会话、跨 agent）
本技能 premium        →  生产行为契约（一致性、状态、安全、可访问性、验证）
```

## 1. 这个套件的特殊之处

它只有 **1 个技能**，这与本项目另外三套（grill 4 个、superpowers 14 个、openspec 12 个）都不同。但它仍值得作为一个独立套件，因为它的设计重心**不在技能内部，而在技能与外部的关系上**：

| 关系 | 说明 |
|------|------|
| **对外部技能的强依赖** | 必须与 `frontend-design` 组合使用。缺了它，本技能**应当停止**（原文明确要求"停下来报错"，而不是近似替代） |
| **对外部文件的读写** | 读项目根的 `DESIGN.md` 与 `UX-CONTRACT.md`，并在必要时**创建**它们 |
| **对外部业务文档的读取** | 读 PRD / ADR / `CONTEXT.md` / 领域契约作为**证据** |
| **对外部工具链的依赖** | 两个 Python 脚本（审计 + 上游解析），以及项目自己的 formatter / typecheck / 测试 / build |

**换句话说**：这个套件的"原理"有相当一部分是**它的边界与依赖**，而不是它的内部步骤。这正是单技能套件仍需要一份套件级文档的理由——

| 文档 | 管什么 |
|------|--------|
| **本文（套件级）** | 三层职责怎么切、与外部世界的依赖关系、核心概念、与其他套件的横向对比 |
| `-中文版.md` | `SKILL.md` 原文说了什么 |
| `-详细设计讲解.md` | 单技能内部的九个设计决策、各自的代价、失效场景 |

## 2. 三层职责边界

这是整套设计里最需要记住的一张表——三层各管一件事，原文对越界有明确禁令：

| 层 | 拥有什么 | 不拥有什么 |
|----|---------|-----------|
| **上游 `frontend-design`** | 主题相关的**审美方向**：配色、字体、版式、动效、文案创意 | 产品行为、一致性、可访问性、验证 |
| **项目 `DESIGN.md`** | **视觉意图、理由，以及它定义的规范值** | 工作流 / 状态 / 导航 / 反馈 / 恢复 / locale / 可访问性行为 |
| **项目 `UX-CONTRACT.md`** | **可观察的前端行为**：工作流、状态、导航、反馈、恢复、locale、可访问性 | 视觉意图与规范值 |
| **本技能 premium** | **生产行为契约**，以及强制执行上述边界 | 审美方向（那是上游的） |

原文对最后两层的边界有一句精确的表述：*"Do not duplicate or let them drift."*（不要让二者重复，也不要让它们漂移。）

**三处"不许越界"的禁令值得单列**：

1. *"Never overwrite an existing visual identity for one feature."* —— 不许为一个功能覆盖既有视觉识别
2. *"do not hand-copy the same value into independent systems"* —— 不许把同一个值手抄进互相独立的系统
3. *"Do not rewrite a contract merely to legitimize existing drift."* —— 不许为了给既存漂移正名而改写契约

三条共同的敌人是**局部最优**：一处功能的便利，换全局一致性的损失；一次手快的复制，换来两份真相各自漂移。而第 3 条更狠——它堵的是**用修改规范的方式掩盖违规**，那是把问题从代码搬进了契约，污染的是权威来源本身。

## 3. 核心概念

| 概念 | 含义 |
|------|------|
| **register（注册类型）** | 目标页面的性质分类：**产品/管理页**（走完整契约）vs **营销落地页**（只加四类打磨）。见 §0a 闸门 |
| **canonical owner（规范归属者）** | 某个 UI 行为的**唯一**权威实现。已存在则复用/扩展；不存在且会反复出现则**创建一个共享原语**并记录决策；未解出则**阻塞实现** |
| **high-risk（高风险类别）** | 七类"错误默认值不可补救"的决策（权限/金钱/隐私/不可逆/法律文案/非幂等副作用/共享状态转换）。**没有默认值**，必须来自权威来源或升级 |
| **premium contract（生产契约）** | §4 那套不可协商的规则：跨屏一致性、表格、交互状态、滚动条、对话框、按钮语义、表单、搜索、locale、可访问性 |
| **durable token（持久 token）** | 需要通过**一条有文档的路径**从 `DESIGN.md` 通到运行时 CSS/主题适配器的值，而非手抄的常量 |
| **behavior ledger（行为台账）** | 记录多屏行为一致性的矩阵（见 `references/consistency-system.md`） |
| **upstream digest** | frontmatter 中记录的、被测试过的上游内容摘要；配五态机（MATCH/UNTESTED/MISSING/UNTRUSTED/INCOMPATIBLE）管理上游漂移 |
| **trust boundary（信任边界）** | 业务文档是**证据**而非**指令**——只有本技能、上游技能、用户请求才是指令源 |

## 4. 设计哲学

从原文各处的措辞里能提炼出四条：

1. **清晰分工优于功能堆叠**——审美归上游、行为归本技能、记忆归 `DESIGN.md`。每一层都明确"不拥有什么"，而不只是"拥有什么"。
2. **不可补救的错误不许猜**——高风险七类必须来自权威或升级；可低成本撤销的选择才允许智能默认。
3. **证据优于宣称**——*"report actual results rather than inferring them from static inspection"*；用 grep 搜违规项而不是凭记忆判断"我没犯错"。
4. **渐进优于革命**——明确禁止大爆炸式重设计，改为"盘点 → 规范化 → 加固 → 按风险迁移 → 强制 → 退役"；也不为一个功能覆盖既有识别。

## 5. 与另外三套的横向对比

| | frontend-design-premium | grill | Superpowers | OpenSpec |
|---|---|---|---|---|
| **管什么** | 前端**审美 + 生产行为契约** | 想清楚（含非编码） | 工程纪律（怎么做） | 需求资产（做什么） |
| **技能数** | 1（+ 2 个外部依赖面） | 4 | 14 | 12 |
| **产物** | `DESIGN.md` + `UX-CONTRACT.md` + 代码 | `CONTEXT.md` + ADR | design doc + plan + 代码 | `specs/` + changes/ |
| **行动门禁** | §0aa 归口闸门未解出 → **阻塞**；§3a 高风险 → 升级上报 | 共识需用户确认 | `<HARD-GATE>` | `Planning boundary` |
| **验证方式** | 静态审计脚本 + 真实浏览器 + grep 违规项 | 前沿为空 | TDD 红绿 + 两阶段评审 | `verify-change` |

**四处值得注意的同构**（四个独立作者，四个不同项目）：

1. **都要求"先想清楚再动手"**——本技能的 §0a/§3a 闸门、grill 的共识确认、Superpowers 的 HARD-GATE、OpenSpec 的 Planning boundary。
2. **都把共识落成磁盘文件对抗对话易逝性**——`DESIGN.md` / `CONTEXT.md` / design doc + plan / `specs/`。
3. **"证据优于宣称"出现了三次**——本技能 §6、`superpowers:verification-before-completion`、`openspec:verify-change`。
4. **"不信任乐观自评"出现了两次**——本技能 §6 要求 grep 搜违规（而非判断），`superpowers:subagent-driven-development` 的评审提示词写着 `CRITICAL: Do Not Trust the Report`。

## 6. 已知的两处源码缺陷

读源码时核实到的，与我们的复制无关（`diff -r` 校验源码与插件缓存字节一致）：

| 缺陷 | 影响 |
|------|------|
| `scripts/validate_skill.py` **不存在** | §0 兼容性说明把它写成发布/CI 的强制校验入口，但该文件未随技能发布。**发布校验实际无法执行** |
| `VERSIONING.md` **不存在** | §0 把它写成"升级流程见 `VERSIONING.md`"，但文件缺失。**上游升级流程无文档** |

两个都是上游（TryHand）发布时漏带的文件。它们削弱的是**决策二那套上游漂移管理机制**——机制描述得很完整，但执行链条上的两个环节是空的。
