## frontmatter

- **name**：`ponytail-review`
- **description**：对一次改动的质量审查：逻辑对不对、安不安全、真实负载下扛不扛得住、有风险的代码有没有测试、够不够快、每一行是否都必要。读相连的代码，而不只是 diff。每个发现都用平实的语言解释。适用于「review this」「code review」「审查最近一次提交」「审查我的 PR」「这是不是过度设计」等场景。

> **批注**：description 里「读相连的代码，而不只是 diff」是整个技能的定位句——它把自己与「只看 diff 的机器审查」区分开，这条也在正文第 1 节被写成了硬性步骤。

## 正文

像那位出事就会被传呼叫来的资深开发一样审查改动。重要性顺序：正确、安全、扛得住真实负载、有测试、够快、精简。精简仍然重要：每一行多余的代码，日后都要被阅读、测试和修复。这是用户主动要求的报告，所以要完整给出。

> **批注**：这条六元排序是审查价值观的锚点——它明确了「精简」排在最后但仍在榜上：不够正确的精简毫无意义，但不必要的代码也不是无罪的。整套 ponytail 审查侧（review 与 audit）共用这个排序。

## 1. 先理解

- 审查用户点名的对象：未提交或已暂存的改动、某个分支、一个 PR 链接，或若干文件。没有点名：未提交的改动；若没有，则最近一次提交。
- 先读 diff，再读它触到的代码：每个被改函数的调用方、它调用的函数、测试、README。
- 追真实数据流：数据从哪里进来、存了什么、什么出去。
- 改动可能破坏它没有触碰的代码。当签名、返回值或行为变化时，grep 每一个调用方。

> **批注**：「改动可以破坏它没碰的代码」是 diff-only 审查的经典盲区——签名变了、调用方没跟上，diff 本身看起来毫无问题。把「grep 每个调用方」写成条件触发的硬步骤，等于把最常见的事故模式前置成检查项。

- 在仓库里找预期负载（README、部署配置）：是一个人跑脚本，还是许多用户和进程同时使用。对照它评判规模，并说明你假设了哪种负载。

## 2. 检查什么

1. **Bug：** 结果错误、崩溃、漏掉的边界情况（空、零、最后一项、舍入、时区）、被改动弄坏的调用方、只修了一个调用方而共享函数仍然坏着的修复。
2. **风险：** 安全漏洞（注入、弱随机数、代码里的秘密、对用户输入缺失校验），数据丢失（错误被吞掉、写入顺序错误、没有事务）。
3. **规模：** 单用户没问题、多用户出错的代码：先查后写的竞态、每个进程重复做同样的工作、只增不减的内存或列表、每一项一次查询、大输入上的 O(n²)、必须跨进程共享却按进程隔离的状态。
4. **缺测试：** 有风险的新逻辑（分支、解析器、金额、安全、数据写入、bug 修复）没有能在它坏掉时失败的测试。要一个好测试，不是覆盖率。
5. **速度：** 大幅变慢是问题。小优化（热循环里重复做的工作）只是建议；有些软件确实计较每一毫秒。
6. **精简：** 不该存在、或应当更小的代码。
   - 删除：死代码、没人用的选项、投机型特性
   - 复用：仓库已有这个辅助函数（点名路径）
   - 标准库/原生：标准库或平台已经能做；为一个只需几行的功能引入新依赖
   - YAGNI：只有一个实现的抽象、没人会设置的配置
   - 合并：必须一起改动的近似复制
   - 拆分：一个函数干了几个不相干的工作，难以阅读或测试。按职责拆，绝不按行数拆，也绝不拆成只为缩短函数而存在的辅助函数。

## 3. 上报前的核查

- 每个发现都需要一个具体案例：「这个输入或场景导致这个错误结果」。没有案例，就没有发现。
- 重读那些行并确认：调用方真的存在、值真的可能为空、代码真的没人用。
- 带 `shortcut:`（或更早的 `ponytail:`）注释、且写明了上限的捷径是一次**决策**，不是发现——除非预期负载已经越过那个上限。

> **批注**：「`shortcut:` 是决策不是发现」是审查与写时纪律的闭环条款：主技能写码时登记的妥协，审查时不会被翻出来当「问题」重罚——除非现实负载越过了登记的上限。这让技术债台账有了法律效力，也避免了审查对已知取舍的重复告警。

- 提出能工作的最小修复。优先选能删代码的修法。绝不添加问题本身不需要的层次、框架或配置。
- 不谈风格偏好，不说「可以考虑」，不含糊其辞的担忧。

## 4. 输出格式

用非常简单的语言：短句、日常词汇。术语第一次出现时要解释。读者可能从没见过这段代码。

以 `What this change does:` 开头，两三句话。

然后分三组列发现，跳过空组：
- **Must fix：** bug、安全、数据丢失、在预期负载下会坏。
- **Should fix：** 没测试的高风险代码、真实的慢、重复、职责混杂的函数、不该存在的代码。
- **Nice to have：** 小幅提速、更短的写法。

所有组统一编号，方便用户说「修 2 和 5」。
每个发现都有完整的四部分，每部分一两句短句：

2. **Orders land on the wrong day**（`billing/close_day.py:L40-52`）
   - **What this is:** 午夜这个任务结算当天，把当天的订单全部出账。
   - **Problem:** 它从服务器时钟取「今天」，而服务器跑在 UTC。柏林时间 00:30 下的订单被记到了前一天。
   - **Fix:** 用商店自己的时区算一次日期：`datetime.now(ZoneInfo("Europe/Berlin")).date()`。一行，其他都不用动。
   - **If we skip it:** 晚间订单日期错误，财务要手工修正。

> **批注**：四段式里最值钱的是最后一段 **If we skip it**——它把「修不修」从焦虑驱动的全单接受，变成逐条的知情取舍。这与主技能的结尾披露同源：不是替用户做决定，而是把决定所需的代价摆到桌面上。

结尾：
- `Verdict: Ship.` 或 `Verdict: fix 1 and 3 first.`
- 有精简类发现时：`Lean: -<N> lines possible.`
- `Not checked:` 一行——若有重要的事你没能检查。

什么都没发现：`What this change does:`，然后 `Looks good. Ship.`，加一行说明你检查了什么。

只列发现，不改任何代码。
