## 1. 它解决什么问题

AI 审查代码有两个系统性失败模式。

**其一是 diff 盲区**：只看 diff 的审查看不见 diff 之外的世界。改动把函数签名改了，diff 本身完美自洽，但三个调用方从此编译不过；「先修了一个调用方、共享函数还坏着」的半吊子修复，在 diff 视角里甚至是「修复」。事故恰恰住在这层视野之外。

**其二是噪音淹没**：没有准入标准的审查会把风格偏好、「可以考虑」式的模糊担忧、和不痛不痒的猜测一股脑倒给用户。用户面对二十条无法行动的意见，等于没有审查——真问题被稀释在假勤奋里。

所以这不是「让模型仔细点」能解决的问题，而是**报告的生产规则**问题：读什么、按什么准入、用什么格式输出。

> **设计立场**：它假设「审查的价值以可行动性计」，而不是以发现数量计。这决定了它的一切输出约束——统一编号、三组分级、四段式发现、Verdict 收尾——全都服务于「让用户能说修 2 和 5」。

## 2. 核心设计决策

### 决策一：先理解，再看 diff

**选了什么**：第 1 节是硬性前置——读 diff 之前先读它触到的代码：调用方、被调函数、测试、README；签名或行为变化时必须 grep 全部调用方；从部署配置里找预期负载并声明假设。

**为什么**：没有上下文的 diff 审查只能发现「局部错误」，而代价最高的错误全是「关联错误」。把 grep 调用方写成条件触发的强制项（签名/返回值/行为变化时），等于把最高频的事故模式变成检查单第一行。

**备选方案**：纯 diff 审查（更快、上下文成本固定且低）。**被否决的原因**：恰好漏掉所有跨文件事故；这也是它区别于普通「review this diff」提示的根本之处。

**代价**：审查成本不再是 O(diff)，而是 O(改动影响面)。大改动的审查会显著变慢变贵。

### 决策二：发现必须有具体触发案例

**选了什么**：「这个输入或场景导致这个错误结果」——没有案例，就没有发现。上报前还要重读代码确认前提（调用方真的存在、值真的可能为空）。

**为什么**：这是审查的**可判定准入**。LLM 审查的典型产出是「可能存在并发问题」这类不可证伪的担忧；强制构造具体案例，等于要求模型先在心里完成一次复现，构造不出来的发现自动出局。

**这一点与 grilling 的「前沿」、TDD 的「先看失败」同构**：都把主观感觉换成客观条件。

**代价**：确实存在但难以构造最小案例的隐患（深层架构问题）会被漏报。

### 决策三：`shortcut:` 是决策，不是发现

**选了什么**：带注释且写明上限的捷径不进发现清单，除非预期负载已越过上限。

**为什么**：主技能写码时用 `shortcut:` 登记妥协，审查时若把这些再翻出来重罚，写时登记就失去了意义——没人会再诚实地登记。这条豁免让「登记 → 豁免 → 越限才重提」成为完整的债务生命周期。

**代价**：它信任登记的质量。措辞含糊的 `shortcut:`（没写清上限）仍可能被误豁免。

### 决策四：四段式发现 + 统一编号 + Verdict

**选了什么**：每个发现固定四段——是什么 / 问题 / 修法 / 跳过的代价；全报告统一编号；结尾必须给 Verdict（放行或先修哪几条）和 Not checked。

**为什么**：四段式把「不修」从被defaults的焦虑变成逐条知情选择（与主技能的结尾披露同源）；统一编号让报告可被局部采纳；Verdict 强制模型表态，堵住「列了一堆问题但不给结论」的骑墙；Not checked 则是审查版的诚实边界。

**代价**：格式是刚性的——小改动的审查也要走完整四段，报告显得重；修法被压缩到一两句，复杂问题的修复方案只能给方向。

### 决策五：给没见过代码的人写报告

**选了什么**：短句、日常词汇、术语首次出现必须解释；开头两三句「这个改动做了什么」。

**为什么**：审查报告的读者常常不是作者本人——评审者、接手者、甚至非工程角色。术语不解释，报告只在作者和模型之间有效。

**代价**：对资深读者显得啰嗦；「简单语言」与精确表达之间存在张力。

## 3. 机制如何运转

```
确定审查对象（点名 → 未提交改动 → 最近提交）
   ↓
先理解：diff + 相连代码 + 调用方 grep + 预期负载声明
   ↓
按六元清单检查：Bug / 风险 / 规模 / 缺测试 / 速度 / 精简
   ↓
逐条准入：有具体触发案例？前提已复核？
   shortcut: 已登记且未越限？→ 豁免
   ↓
输出：What this change does
   → Must fix / Should fix / Nice to have（统一编号，四段式）
   → Verdict + Lean + Not checked
```

关键约束在**准入层**：检查清单可以产生二十条怀疑，但只有能构造出具体案例、且前提被复核过的才允许上报。宁缺毋滥是这个技能与「AI 审查噪音」的分界线。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 超大 diff / 大规模重构 | 无法读全影响面，漏报关联错误；只能靠 Not checked 兜底 | 「先理解」的成本是 O(影响面)，超过预算时覆盖必然缩水 |
| 仓库缺少负载描述 | 规模类发现（竞态、扩展性）失去评判基准，可能误报或漏报 | 预期负载靠 README/部署配置声明，缺失时模型只能猜 |
| 用户只要风格审查 | 报告「太重」，格式化输出与诉求错位 | 技能明确拒绝风格意见，这是特性也是边界 |
| 动态调用 / 反射密集代码 | grep 调用方漏掉动态引用，误判「无人调用」 | 静态文本搜索看不见运行时组装的调用 |
| 与人工评审并存 | 重复告警或结论冲突（模型说放行、人说不放行） | Verdict 是模型在自身视野内的表态，覆盖不了人掌握的领域上下文 |

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| 与 ponytail-audit 同源 | 同一套六元清单与准入规则；review 面向一次改动，audit 面向整仓并加排序与 20 条上限 |
| 检验 ponytail 主技能的产出 | 主技能写最小改动，review 用同一价值观验收——「写 → 审」闭环 |
| 与 ponytail-debt 共享 `shortcut:` 语义 | 写时登记、审查豁免、debt 收割，三技能构成债务的完整生命周期 |
| 与 TDD 类流程互补 | 「缺测试」是它的四大发现类别之一；它事后验收测试存在性，TDD 约束测试产生时序 |
| 与 grilling/brainstorming 不重叠 | 那两个管「想清楚再做」，review 管「做完后的验收」，阶段不同 |
