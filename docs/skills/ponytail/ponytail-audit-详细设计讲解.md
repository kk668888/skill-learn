## 1. 它解决什么问题

整仓审计面对一个 diff 审查没有的困难：**仓库大于任何一次上下文预算**。逐文件扫描既读不完、也会把发现碎片化——单看每个文件都「还行」，跨文件的重复实现、互相矛盾的两处规则、只增不减的共享状态，全部漏网。

同时，审计报告有自己特有的失败模式：**倾倒式输出**。把两百条观察按目录顺序倒出来，等于没审——用户要的是「先修什么」，不是「有什么」。此外还有身份问题：模型对现有代码没有立场，容易把「都写出来了总有理由」当成结论，于是永远审不出「这东西不该存在」。

> **设计立场**：它假设「审计者的价值在于排序和取舍，不在于穷举」；并且「审计者应当以接手者自居」——没有历史包袱、出事负全责的人，才敢对存量代码说「删」。

## 2. 核心设计决策

### 决策一：地图先行，代价深处优先

**选了什么**：先读 README、部署与构建配置、依赖清单、入口点、测试建立全貌；然后端到端追主流程（输入、金额、认证、写入、后台任务、跨进程共享）；大仓库**在出错代价最高的地方深入**，明确声明没读的部分。

**为什么**：这是采样问题唯一诚实的解法。均匀逐文件读 = 预算摊薄 = 每处都浅；按代价分配深度，把预算押在用户输入、金额、数据写入这些出事最疼的路径上。「声明没读的部分」把采样的盲区显式化，防止报告被误读为全覆盖。

**备选方案**：工具化全量扫描（linter 组合 + 汇总）。**被否决的原因**：那是另一个产品；这里的审计靠阅读理解跨文件语义（同一规则两处实现不一致、调用方与返回值约定不符），静态规则覆盖不了。

**代价**：没被采样到的路径发现不了问题；「深处」的判断本身可能错——模型认为不重要的模块可能正藏着雷。

### 决策二：接手者人格

**选了什么**：正文第一句把审计者设定为「刚刚接手仓库、出事会被传呼的资深开发」。

**为什么**：与 review 的「被传呼者」一字之差，但「刚接手」专门对抗模型的默认倾向——尊重存量、假设存在即合理。接手者没有沉没成本，可以把「两个辅助函数做同一件事」「只有一个实现的接口」直接定性为待处理项。

**代价**：人格设定是软约束；在「删这段有政治阻力」的真实组织语境里，报告仍然只管技术判断。

### 决策三：精简盘点作为一等公民

**选了什么**：六元清单的第六项（精简）在 audit 里给出完整子分类：删除、复用、标准库/原生、YAGNI、合并、拆分；输出结尾附 `Lean: -N lines, -M dependencies possible.` 统计行。

**为什么**：「能删什么」是整仓视角独有的产出——diff 审查看不见两个辅助函数互为副本。把精简做成结构化盘点（而不是一句「有点冗余」），配合统计行，让「减法」变成可执行的工单。

**代价**：YAGNI 类发现（单实现接口、纯转发包装层）误报率天然偏高——有些「只有一个实现」是刻意的扩展点设计，审计无法从代码本身分辨意图。

### 决策四：20 条上限 + 省略计数

**选了什么**：发现最多 20 条，跨组统一编号；更小的没列进来时，必须说明省略了多少。

**为什么**：上限强制排序——要进前 20，就必须比已在榜上的更 重要。这与 review 的「无上限但必须人人带案例」是同一准入哲学在不同体量下的两个化身：整仓的候选发现太多，不加硬上限就会退化成倾倒。省略计数则保证「被裁掉的」不被假装成「不存在」。

**代价**：第 21 条之后的问题从报告里消失（只剩一个计数）；排序偏差直接决定什么被看见。

### 决策五：Verdict 必须表态，「健康」也是结论

**选了什么**：结尾一行 Verdict：健康，或先修什么；什么都没发现时输出 `Healthy. Nothing to fix.` 加一行检查范围说明。

**为什么**：「健康」必须是一个允许且明确给出的结论，否则审计会被迫制造发现来证明自己的存在——这是审查类工具最隐蔽的失败模式。强制表态同时堵住骑墙输出。

**代价**：Verdict 是模型视野内的一行判断，覆盖不了采样盲区与领域上下文；「健康」可能给用户虚假的安全感，靠 Not checked 行部分对冲。

## 3. 机制如何运转

```
确定范围（点名目录/包 → 整仓）
   ↓
画地图：README / 部署配置 / 依赖 / 入口点 / 测试
   ↓
端到端追主流程：输入 → 存储 → 输出
（金额、认证、写入、后台任务、跨进程共享 = 深入优先级）
   ↓
六元清单检查：Bug / 风险 / 规模 / 缺测试 / 速度 / 精简（完整子分类）
   ↓
准入：具体案例？前提复核（含全树 grep 与动态引用）？shortcut 豁免？
   ↓
排序取前 20（跨组统一编号）+ 省略计数
   ↓
What this repo does + 负载假设
→ Must fix / Should fix / Nice to have（四段式）
→ Verdict + Lean 统计 + Not checked
```

最容易违反的是**准入与上限**：候选发现一多，模型天然想都报。上限不是格式约束，是排序义务——它逼模型回答「哪个问题最值得用户的时间」。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 超大仓库 | 采样覆盖不足，深处判断失误时整片区域漏审 | 「代价深处优先」是赌注式采样，赌错方向全盘皆输 |
| 动态调用 / 反射密集代码 | 「无人使用」误判，建议删除实际在用的代码 | 全树 grep 只见静态文本，看不见运行时组装的引用 |
| 刻意的扩展点设计 | 单实现接口、转发包装层被报为 YAGNI，误伤架构预留 | 子分类无法从代码分辨「偷懒的单实现」与「刻意的接缝」 |
| 仓库演进后旧报告未重跑 | 审计结论过期，指向已修复的问题 | 一次性快照，没有时效机制 |
| 组织语境复杂 | 「该删」的结论技术正确但不可执行 | 审计只管技术判断，删除的决策成本在报告视野之外 |

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| 是 ponytail-review 的整仓版 | 共享六元清单、准入规则与四段式发现；差异在地图先行、20 条上限与 Lean 统计 |
| 与 ponytail-debt 互认语义 | 已登记且未越限的 `shortcut:` 不入发现清单；debt 台账是审计的已知债务底册 |
| 被 ponytail-gain 指名 | gain 记分板把「这个仓库还能删什么」指向 audit，构成展示 → 行动的通路 |
| 验收 ponytail 主技能的长期产出 | 主技能逐次最小改动，audit 周期性盘点存量——防止「每次都最小」累积出「整体冗余」 |
| 与 OpenSpec 串联 | 审计产出的 Should fix 可以转化为变更提案，进入规格化流程 |
