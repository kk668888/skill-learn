# ponytail 系列技能原理拆解

> 源码：`skills/ponytail/`（来自 [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail) v5.3.2，MIT，作者 Dietrich Gebert）
> 涉及技能：ponytail、ponytail-review、ponytail-audit、ponytail-debt、ponytail-gain、ponytail-help
> 套件定位：*"Makes your AI agent think like the laziest senior dev in the room. The best code is the code you never wrote."*

## 0. 一句话原理

**用可判定的「梯子」把 YAGNI 从口号变成流程，再用「登记 → 豁免 → 收割」的债务生命周期让每一次偷懒留痕、可审、可还。**

它对抗的 LLM 缺陷：把「专业」表演成「多写」——没人要求的抽象、为几行代码引入的依赖、手搓平台自带的控件；以及反面：把「偷懒」滑坡成「砍掉校验的少做」。

## 1. 架构：一个内核 + 五个卫星

六个技能分三层：

```
【行为内核】会话级激活（/ponytail，档位 lite / full / ultra）

  ponytail ──── 梯子六级命中即停 + 结尾披露 + shortcut: 登记
      ↓ 产出最小改动
【验收层】同一价值观：correct > safe > load > tested > fast > lean

  ponytail-review（单次 diff）──┐
                               ├──┬→ 豁免已登记且未越限的 shortcut
  ponytail-audit（整仓排序）───┘  │
                                  ↓ 发现
【记账与展示层】
  ponytail-debt ── 收割 shortcut: 注释为台账（债务的唯一事实源）
  ponytail-gain ── 基准收益记分板（诚实边界：拒绝 per-repo 推算）
  ponytail-help ── 速查卡（全家导航 + 配置链）
```

**为什么这样分层**：与 grill 的「薄入口 + 内核」不同，ponytail 是**内核 + 卫星**。内核改变写码行为本身；卫星各自独立触发、运行上互不依赖。它们之间的组合不靠转发调用（对比 grill-me 的一行转发），而靠**语义约定**：review 豁免 debt 台账里登记过的捷径，gain 把按仓库数字的追问指向 debt，help 把新用户导向全家。

**这种松耦合的代价**：没有任何机制强制「写完必须 review」「audit 必须先读 debt」——闭环靠 description 里的触发词互相引导，靠用户养成习惯。卫星可以单独用，但单独用时价值减半：不登记捷径就无账可收，不跑 review 就没有验收。

## 2. 内核与卫星的三个咬合点

整套设计最值得学的是三个跨技能咬合，它们把六个文件变成了一个系统：

**① 登记 → 豁免（ponytail ⇄ review/audit）**
写代码时，刻意妥协必须写 `shortcut: <上限>, <何时升级>` 注释；审查时，「已登记且未越限」的捷径从发现清单里豁免。没有豁免条款，登记等于自首，没人会诚实地写；有了它，登记变成免责——**写时纪律因此有了经济激励**，这是债务体系能自转的关键一齿。

**② 收割 → 回收（ponytail-debt ⇄ audit）**
debt 把散落各处的注释收割成台账，并给「没写升级触发器」的债打 `no-trigger` 标记；当现实负载越过注释里登记的上限，review/audit 的豁免自动失效，债以发现的身份回到报告里。**债务的到期机制不在任何调度器里，就在注释文本本身**——上限和触发器写得越具体，回收越准时。

**③ 展示 → 诚实（ponytail-gain ⇄ debt）**
「ponytail 给我省了多少」是反事实问题——未写出的代码没有基线。gain 的解法是把问题**拆掉**：只复述可溯源的基准数字，按仓库折算一律拒绝，并指认唯一合法的数字来源是 debt 的计数台账。展示层不生产数字，只搬运被测量过的数字。

### 内核三机制为什么存在（速览）

单技能的取舍细节归 [ponytail-详细设计讲解.md](./ponytail-详细设计讲解.md)，这里只列套件视角的分工：

| 机制 | 管什么 | 没有它会怎样 |
|------|--------|--------------|
| 梯子 | 方案选择的裁决顺序 | YAGNI 退化为口号，具体分歧仍按训练偏好走 |
| 绝不裁剪清单 | 正确性义务的豁免区 | 「最小」在压力下滑坡成「砍校验的最小」 |
| 结尾披露 | 懒惰留痕 | 用户无从评估「最小」背后的风险存量 |

## 3. 三套系统的收敛与分歧

| | ponytail | Superpowers | grill |
|---|---|---|---|
| 管什么 | **体量**（写多小） | **过程**（怎么写） | **需求**（写什么） |
| 核心动作 | 梯子命中即停 | 先测试后代码 | 前沿整批问 |
| 完成判定 | 最小完整 + 披露 | 链路走完（TDD 循环闭合） | 前沿空 + 共识确认 |
| 落盘资产 | `shortcut:` 注释 + 台账 | design doc + plan | CONTEXT.md + ADR |
| 诚实机制 | 结尾披露 / gain 不编数字 | verification-before-completion | 决策必带推荐答案 |

**收敛点**（独立发明的同构物，说明是这类工作流的稳定解）：

1. **可判定代替主观**——梯子命中即停 ≈ 前沿为空 ≈ 测试由红转绿；三套都不信任「我觉得可以了」。
2. **留痕对抗易逝**——`shortcut:` 注释、plan 文档、CONTEXT.md 都是对话外部的磁盘资产；ponytail 的披露要求甚至把「没做什么」也留了痕。
3. **裁量权归用户**——lite 档「点名更小的选项让用户选」、grilling 的推荐答案、Superpowers 的计划审批，都是把决定摆到桌面而非代做。

**分歧点**（同装时需要仲裁的地方）：

- **动手前的第一问**：TDD 要「先写失败测试」，ponytail 要「先找可复用的」——两者争夺动手后的第一个动作。仲裁思路：先按 ponytail 定**做什么**（也许复用后根本不用写），再对要写的部分走 TDD。
- **完成标准**：TDD 的完成是「测试绿」，ponytail 的完成是「最小且完整」——测试全绿但实现臃肿，在 Superpowers 眼里是完成、在 ponytail 眼里是未完成。

## 4. 与你的关联（L2 自检素材）

你在本项目刚亲历过这条链路：收录六个 SKILL.md → 生成全套中文文档 → 把 v5.3.2 锁进离线包（`fingerprintTree` 全树指纹 = 套件价值观里的「最小且可核验」）→ 规格同步时校验器强制保留旧场景名。期间每个决定都有落盘记录——这正是套件教的「懒惰必须留痕」。

**自检题**（不翻文档回答，答得上就是 L2 达标）：

1. 为什么「登记 → 豁免」让写时纪律有了经济激励？没有豁免条款时，理性的模型会怎么选？
2. `shortcut:` 注释里的「上限」和「触发器」各自承担什么？只写上限不写触发器，债会怎样？（提示：`no-trigger`）
3. gain 为什么拒绝计算「你这个仓库省了多少」？这个反事实问题和 grilling 的「前沿」有什么同构关系？
