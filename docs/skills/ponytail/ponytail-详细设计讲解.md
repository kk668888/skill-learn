## 1. 它解决什么问题

LLM 写代码有一条与训练信号同源的系统性偏见：**更多 = 更好**。分层完整、带抽象、可配置的实现在训练语料里更像「高质量代码」，于是模型把「专业」表演成「多写」——没人要求的包装层、只有一个实现的接口、为三行代码引入的新依赖，都是这条偏见的产品。

这不是「提示词里写一句请精简点」能解决的问题：**形容词没有裁决力**。当「复用现有辅助函数」和「新写一个更通用的工具类」摆在一起，模型需要的是一个可执行的裁决顺序，而不是一个方向性的形容词。口号在具体分歧面前总会输给训练偏好。

更隐蔽的代价在维护侧：每一行多余代码今后都要被阅读、测试和修复。过度工程不是免费的炫技，是分期偿还的负债。

> **设计立场**：它假设「任务真正需要的代码量通常远小于模型的第一反应」，且「代码库现状优先于通用最佳实践」。这决定了它的方法论是**按序检查**（沿固定次序找最省的可行解），而不是自由发挥式的删减。

## 2. 核心设计决策

### 决策一：用「梯子」把 YAGNI 从原则变成流程

**选了什么**：六级检查顺序——①该不该存在 → ②代码库已有 → ③标准库/平台原生 → ④已装依赖 → ⑤一行 → ⑥最小实现。

**为什么**：YAGNI 作为原则人尽皆知，但没有裁决顺序时它只是口号。梯子把每次「写不写、写什么」变成逐级判定：每一级都有明确的「命中即停」出口，模型不需要判断力也能得出节制的结论。第一级排在最前是点睛之笔——**砍需求的优先级高于换实现**，多数过度工程的问题在「这东西根本不该有」就结束了。

**备选方案**：在系统提示里写「保持精简、避免过度设计」。**被否决的原因**：无判定序，遇到具体分歧仍按训练偏好走。README 的基准数据（无技能时任务产出 335 行手搓日历组件，有技能时复用输入控件 10 行解决）演示的正是口号与流程的差距。

**代价**：梯子是「改代码」场景的产物。绿地项目、全新领域里②③④级全部空转，梯子退化为「直接写最小实现」，缺少参照系。

### 决策二：对方案懒惰，对阅读绝不懒惰

**选了什么**：动笔之前必须列出改动触达面（调用方、测试、夹具、配置、导出）并评估破坏面；修 bug 先 grep 全部调用方再在共享代码修根因。

**为什么**：懒惰的真实失败模式不是「写多了」，而是「少看见了」——最小 diff 如果漏掉了必须同步修改的调用方，比不写还糟。最小改动的前提是**完整的影响清单**，所以阅读义务被写成了硬性前置。

**代价**：前置阅读成本是固定的，哪怕一行改动也要过一遍触达面清单。极小改动上这套流程显得重。

### 决策三：绝对豁免清单（Never cut）

**选了什么**：信任边界校验、防数据丢失的错误处理、安全性、无障碍性、硬件标定、用户点名的要求——永不参与裁剪。

**为什么**：没有豁免清单，「最小」会在压力下滑坡成「砍掉校验的最小」。清单把「节制」的适用范围钉死在方案选择层，正确性义务完全不在此列。

**代价**：灰色地带（性能、日志、可观测性）仍靠模型自觉判断；清单能防住最危险的滑坡，防不住全部。

### 决策四：非平凡逻辑必须留下检查

**选了什么**：分支、循环、解析器、金额、安全逻辑、新脚本/新应用，必须配一个小测试或 assert 自检；琐碎改动豁免。

**为什么**：这是对「懒惰」最危险误读的事前防御——把测试定义为懒惰的收尾义务，而不是懒惰的对立面。官方基准里高风险逻辑带测试比例 98%（无技能 68%），主要是这条在起作用。

**代价**：它只要求「事后有一个检查」，不要求「先看测试失败」。过程纪律明显弱于 TDD——这是与 superpowers 同装时最需要仲裁的差异（见第 5 节）。

### 决策五：`shortcut:` 注释把技术债登记在案

**选了什么**：刻意妥协必须写成 `shortcut: <上限>, <何时升级>` 格式的注释，并有专门的 ponytail-debt 技能收割成台账。

**为什么**：推迟的决定最大的风险不是推迟本身，而是被遗忘。把「上限」和「升级触发器」强制写进注释，欠债就从口头的「以后再说」变成了可 grep 的结构化记录。

**代价**：依赖写时纪律；注释措辞不合规（缺上限或缺触发器）时，台账质量随之下降——debt 技能只能给这些行打 `no-trigger` 标记。

### 决策六：结尾披露 + 三档可调强度

**选了什么**：每次回复尾部申报跳过了什么、没检查什么、有什么风险；档位 lite/full/ultra 调节介入强度，另有 off 关闭。

**为什么**：懒惰必须留痕，否则用户无从评估「最小」背后的风险存量和「未被检查」的盲区。档位设计承认「全有或全无」不现实——lite 档甚至只要求「点名更小的选项，让用户选」，把最终裁量权还给用户。

**代价**：披露依赖模型自觉遵守；用户不读尾部，这层保护就归零。

## 3. 机制如何运转

```
接到编码任务
   ↓
动笔之前：读任务 + 读涉及的代码
   列触达面（调用方/测试/夹具/配置/导出）→ 这才是范围
   ↓
沿梯子下行，命中即停：
   ①不该存在？→ 一行点名，不做
   ②库内已有？→ 按现有用法复用
   ③标准库/平台原生？→ 用它（自家组件优先）
   ④已装依赖？→ 用它（不为几行加依赖）
   ⑤一行能懂？→ 一行
   ⑥最小实现
   ↓
非平凡逻辑？→ 留一个小测试 / assert 自检
刻意妥协？→ 写 shortcut: <上限>, <何时升级>
   ↓
回复尾部披露：跳过了什么 / 没查什么 / 风险
```

最容易违反的一步是**①排在最前**：模型的本能是接受需求然后想「怎么写」，而梯子要求先问「该不该写」。其次是触达面清单——跳过它直接改代码，得到的是「短但漏」的 diff，这比过度工程更难被发现。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 绿地项目 / 全新领域 | ②③④级空转，「最小实现」缺参照系，可能产出过瘦的地基 | 梯子的复用检查全部依赖既有代码与依赖，无库可查时只剩「写少点」 |
| 安全敏感代码 | 校验被当作「没人要求的功能」质疑掉 | 豁免清单依赖模型自觉识别「这是安全代码」；识别错了没有机制兜底 |
| 用户确实需要完备方案 | 边界处理被当作过度设计质疑，来回拉扯 | full 档先验地假设「需求大于实际需要」，这个先验在确实复杂的需求上是错的 |
| 大型重构 | 逐次最小 diff 可能在架构上绕远路 | 「最短可工作 diff」是局部最优；整体最优路径的第一步往往不小 |
| 与强流程技能同装 | TDD 要求先写失败测试，ponytail 要求先找复用，节奏冲突 | 两套纪律管辖同一时段（动手前），没有更高层规则仲裁时互相拉扯 |
| 性能敏感路径 | 「小优化只是建议」的立场会漏掉真实的性能需求 | 梯子按体量排序，不按执行成本排序 |

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| 被 ponytail-review / ponytail-audit 检验 | 两个审查技能用同一套价值观（correct > safe > load > tested > fast > lean）检查产出，形成「写 → 审」闭环 |
| 与 ponytail-debt 配套 | 写时登记 `shortcut:` 注释，事后收割为台账，防止欠债失忆 |
| 与 superpowers TDD 互补但有张力 | TDD 管过程（先测试后实现），ponytail 管体量（能复用就不写）；同装时需明确先后——先按 TDD 定流程，再按梯子裁体量 |
| 与 OpenSpec 不冲突 | OpenSpec 的规划门禁管「做什么」（规格先行），ponytail 管「怎么做得最小」；两者作用在不同阶段 |
| 与 brainstorming / grilling 串联 | 先把需求想清楚（问对问题），ponytail 才能把「该做的最小部分」识别对——需求模糊正是梯子第一级的判据难题 |
