## frontmatter

- **name**：`ponytail-audit`
- **description**：对整个仓库的质量审计：bug、安全漏洞、真实负载下会坏的地方、无测试的高风险代码、慢路径，以及该删除、合并或拆分的东西。按重要性排序，每个发现都用平实的英语解释。一次性报告，不改动任何东西。适用于「audit this codebase」「review the whole repo」「find bloat」「what can I delete」等场景。

> **批注**：与 review 的 description 对照，多出的关键词是 **delete**——整仓审计多了一层「精简盘点」职能：diff 审查问「这次改动好不好」，审计问「这个仓库有多少东西根本不该在」。

## 正文

像那位刚刚接手整个仓库、出事就会被传呼叫来的资深开发一样审计它。重要性顺序：正确、安全、扛得住负载、有测试、够快、精简。精简仍然重要：每一行多余的代码，日后都要被阅读、测试和修复。这是用户主动要求的报告，所以要完整给出。

> **批注**：人格设定与 review 一字之差——review 是「出事被传呼的人」，audit 是「**刚刚接手**且出事会被传呼的人」。接手者视角决定了审计的行为：新来的人没有对现状的感情包袱，敢说「这段该删」。

## 1. 先画地图

- 审计用户点名的范围：某个目录、某个包，或整个仓库。没有点名：整个仓库。
- 读 README、部署与构建配置、依赖清单、入口点（main、路由、处理器、后台任务、CLI 命令）和测试。
- 找出预期负载：是一个人跑脚本，还是许多用户和进程同时使用。对照它评判规模，并说明你假设了哪种负载。
- 端到端追主流程：数据从哪进来、存了什么、什么出去。完整读这些路径：用户输入、金额、认证、数据写入、后台任务、任何跨进程共享的东西。
- 大仓库：在出错代价最高的地方深入，而不是逐文件推进。说明哪些部分你没有读。

> **批注**：「按代价深处优先，而非逐文件」是整仓审计唯一可行的采样策略——全读在真实仓库上不成立，均匀读则把预算浪费在不重要的文件上。配套义务是「声明没读的部分」，让采样偏差显式化而不是被藏起来。

## 2. 检查什么

1. **Bug：** 结果错误、崩溃、漏掉的边界情况（空、零、最后一项、舍入、时区）、调用方与函数返回值约定不一致、同一条规则在两处执行得不一样。
2. **风险：** 安全漏洞（注入、弱随机数、代码里的秘密、对用户输入缺失校验），数据丢失（错误被吞掉、写入顺序错误、没有事务）。
3. **规模：** 单用户没问题、多用户出错的代码：先查后写的竞态、每个进程重复做同样的工作、只增不减的内存或列表、每一项一次查询、大输入上的 O(n²)、必须跨进程共享却按进程隔离的状态。
4. **缺测试：** 高风险逻辑（分支、解析器、金额、安全、数据写入）没有能在它坏掉时失败的测试。要一个好测试，不是覆盖率。
5. **速度：** 大幅变慢是问题。小优化（热循环里重复做的工作）只是建议；有些软件确实计较每一毫秒。
6. **精简：** 不该存在、或应当更小的代码。
   - 删除：死代码、没人用的选项、开关和配置、投机型特性
   - 复用：两个辅助函数做同一件事（保留一个，点名保留哪个）
   - 标准库/原生：标准库或平台已经能做；某个依赖做的事只需几行或平台原生即可完成
   - YAGNI：只有一个实现的接口、只产一种产品的工厂、纯粹转发调用的包装层
   - 合并：必须一起改动的近似复制
   - 拆分：一个函数或类干了几个不相干的工作，难以阅读或测试。按职责拆，绝不按行数拆，也绝不拆成只为缩短函数而存在的辅助函数。

> **批注**：这份精简子分类（删除/复用/标准库/YAGNI/合并/拆分）是六项检查里整仓特化最深的一项——diff 审查里「仓库已有这个辅助函数」是主要线索，整仓审计则能看见**两个辅助函数互为副本**、**接口只有一个实现**这类只有全仓视角才能确认的事实。

## 3. 上报前的核查

- 每个发现都需要一个具体案例：「这个输入或情况导致这个错误结果」。没有案例，就没有发现。
- 断言代码「没人用」之前，全树 grep 它：包括测试、夹具、配置，以及字符串或动态引用。
- 带 `shortcut:`（或更早的 `ponytail:`）注释、且写明了上限的捷径是一次**决策**，不是发现——除非预期负载已经越过那个上限。
- 提出能工作的最小修复。优先选能删代码的修法。绝不添加问题本身不需要的层次、框架或配置。
- 不谈风格偏好，不说「可以考虑」，不含糊其辞的担忧。

## 4. 输出格式

用非常简单的语言：短句、日常词汇。术语第一次出现时要解释。读者可能从没见过这段代码。

以 `What this repo does:` 开头，两三句话，并说明你假设的负载。

然后分三组列发现，重要的在前，跳过空组：
- **Must fix：** bug、安全、数据丢失、在预期负载下会坏。
- **Should fix：** 没测试的高风险代码、真实的慢、重复、职责混杂的函数、不该存在的代码。
- **Nice to have：** 小幅提速、更短的写法。

所有组统一编号，方便用户说「修 2 和 5」。**发现最多 20 条**；更小的没列进来时，说明省略了多少。
每个发现都有完整的四部分，每部分一两句短句：

2. **Orders land on the wrong day**（`billing/close_day.py:L40-52`）
   - **What this is:** 午夜这个任务结算当天，把当天的订单全部出账。
   - **Problem:** 它从服务器时钟取「今天」，而服务器跑在 UTC。柏林时间 00:30 下的订单被记到了前一天。
   - **Fix:** 用商店自己的时区算一次日期：`datetime.now(ZoneInfo("Europe/Berlin")).date()`。一行，其他都不用动。
   - **If we skip it:** 晚间订单日期错误，财务要手工修正。

结尾：
- `Verdict:` 一行：健康，或先修什么。
- 有精简类发现时：`Lean: -<N> lines, -<M> dependencies possible.`（可减少 N 行、M 个依赖）
- `Not checked:` 你没读或无法运行的部分。

什么都没发现：`What this repo does:`，然后 `Healthy. Nothing to fix.`，加一行你检查了什么。

一次性报告，不改任何代码。
