## 1. 它解决什么问题

技术债最经典的失败模式不是欠债，而是**赖账**：一次「先这样，以后再改」的妥协，由于没有任何机制提醒「以后」到了，悄悄变成永久架构。欠条只存在于当时的对话里，人一换、季度一过，债就凭空消失了。

把债记进 issue tracker 是常见的补救，但它引入新的失败模式：**账与码分家**——issue 里写着「临时方案」，代码里看不出哪一段是临时的；代码重构了，issue 没人关；账面和现实渐渐互不相干。

所以这不是「提醒团队还债」能解决的问题，而是**债务的载体**问题：记录必须长在代码上，收割必须可自动化。

> **设计立场**：它假设「债务治理的瓶颈是遗忘，不是意愿」——只要升级触发器足够显眼，团队多半会还债；于是整个设计都在对抗遗忘这一个敌人。

## 2. 核心设计决策

### 决策一：债随代码走（注释即登记）

**选了什么**：债务的唯一载体是代码里的 `shortcut: <上限>, <何时升级>` 注释；台账只是注释的派生物。

**为什么**：注释和被妥协的代码物理共生——代码被读到，债就被读到；代码被删，债自动销账。不需要同步，不存在账实分离。这与「issue tracker 永远滞后于代码」形成根本对照。

**备选方案**：外部台账系统（issue/看板）。**被否决的原因**：账与码分家，且登记成本高到没人坚持。注释方案的登记成本是零——主技能写码时顺手完成。

**代价**：注释的表达力有限（一个上限、一个触发器）；复杂的债务背景仍需外链。

### 决策二：收割而非维护

**选了什么**：本技能不维护任何状态——每次用 grep 现场收割注释，输出一次性台账。

**为什么**：既然注释是唯一事实源，台账就应该是纯派生物。不维护状态意味着不可能账实不符：每次收割都是全量重算。这也是「一次性报告」纪律（one-shot）的由来。

**代价**：每次收割都全仓 grep；超大仓库上成本不低，且台账不能增量追加备注。

### 决策三：窄模式过滤（前缀 + 冒号）

**选了什么**：grep 模式限定注释前缀（`#`、`//`、`/*`）+ `shortcut:`/`ponytail:`；显式跳过非推迟的命中（如键盘快捷键说明）。

**为什么**：`shortcut` 是高频英文词，裸词搜索会把散文和无关代码全部卷进台账，信噪比崩塌后台账就没人看了。前缀约定把「按规范登记的债」和「恰好用了这个词的普通文本」硬分开。

**代价**：依赖注释风格统一；不写注释前缀的特殊语法（如某些模板语言的行内注释）会漏收。

### 决策四：`no-trigger` 标记点名腐烂风险

**选了什么**：没写升级路径或触发条件的标记，在台账里打 `no-trigger` 标签，结尾统计 `N markers, M with no trigger`。

**为什么**：`shortcut: <上限>, <何时升级>` 的后半段才是防赖账的关键——有触发器，债才会在该还的时候自己跳出来。没有触发器的债在结构上等价于永久化，但表面上还挂着「已登记」的假象。点名它，等于把「假登记」从真登记里揪出来。

**代价**：无法自动判断一个触发器写得是否认真——「以后重构时」这种废话触发器也能通过格式检查。

### 决策五：只读，写文件需确认

**选了什么**：默认只读不改；用户要持久化时，经确认才写台账文件（如 `PONYTAIL-DEBT.md`）。

**为什么**：一次性纪律（one-shot）与 ponytail 全家一致；而写文件是副作用，需要越过一道人工闸门——与整套体系的「用户确认前不动手」同构。

**代价**：写出的台账文件本身会过期（代码变了文件不会），若被当成事实源二次维护，反而重新引入「账实分离」。

## 3. 机制如何运转

```
主技能写码时刻：
  刻意妥协 → 写 shortcut: <上限>, <何时升级> 注释   ← 债的唯一登记点
        ↓（任意时刻）
/ponytail-debt 收割：
  git grep（排除 .git / gitignore，限定注释前缀）
   ↓
每条命中 → 过滤非推迟命中（键盘快捷键等）
   ↓
按文件分组的台账行：位置 / 简化了什么 / ceiling / upgrade
   ├─ 缺触发条件 → no-trigger 标签
   └─ 需要负责人 → git blame 补充
   ↓
结尾统计：N 条标记，M 条无触发；或 Clean ledger
```

机制里最脆弱的一环在**登记时刻**，而不是收割时刻：收割是确定性的 grep，登记却依赖主技能写码时的纪律。登记偷懒（不写触发器），收割再严格也只能标 `no-trigger`。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 团队不使用主技能 / 不写标记注释 | 无源可收，台账恒空 | 整个体系的前提是「债以注释形式登记」，前提不成立则机制空转 |
| 登记措辞不合规 | 台账里 `no-trigger` 堆积，债务可见但不可行动 | 格式检查只能验证结构，验证不了触发器的质量 |
| 注释语法特殊的技术栈 | 部分标记漏收，账面偏乐观 | grep 前缀模式需要按栈补齐，漏配即漏账 |
| 台账文件被二次维护 | 写出的快照过期，账实分离回归 | 派生物被误当事实源，恰好复活了这个技能要消灭的失败模式 |
| 历史巨量存量债 | 首次收割输出过长，失去排序价值 | 台账只分组不排序不限量，与 audit 的 20 条上限哲学不同 |
| 触发器写得太模糊 | 债登记了但永远不会「到期」 | 「以后重构时」式触发器无法判定是否已触发 |

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| 登记：ponytail 主技能 | 写码时刻强制 `shortcut:` 注释——debt 的全部输入都来自这里 |
| 豁免：ponytail-review / audit | 审查对已登记且未越限的捷径免报；「越限」的判定依据正是注释里的 ceiling |
| 与 git blame 组合 | 台账行可追加 blame 取得负责人，债务分配到人 |
| 被 ponytail-gain 引用 | gain 的诚实边界声明：唯一真实的 per-repo 数字来自 debt 的台账，其余一律不编 |
| 与 OpenSpec 串联 | 台账中越限或集中的债务可转化为变更提案，进入规格化还债流程 |
