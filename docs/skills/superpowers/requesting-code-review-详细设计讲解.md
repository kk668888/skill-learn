## 1. 它解决什么问题

它对付的是**问题级联**：一个未被发现的问题，会成为后续工作的地基。

这个失败模式有一个残酷的数学性质——**修复成本随时间非线性增长**。第 3 个任务里发现第 1 个任务的错误，你往往不是"改一行"，而是要撤销建立在它之上的一切。更糟的是**它不会自己暴露**：错误的实现通常能跑，只是跑得不对；后续代码会绕着它长出各种补偿性设计，把错误固化进结构里。

**为什么不能靠实现者自查解决**：这是关键。写代码的人和审代码的人如果共享同一套假设，那么**错误的假设会被两边同时认可**。你审自己的代码时，脑子里跑的是"我当时想做什么"，而不是"这段代码实际做了什么"——你会不自觉地用意图填补实现的缺口。

**设计立场**：把评审交给一个**没有你上下文**的独立主体。它的价值恰恰来自"不知道你在想什么"——它只能看**产物本身**。

> 这个立场解释了原文那句看起来很怪的措辞：*"precisely crafted context ... never your session's history."*（精心构造的上下文，永远不是你的会话历史。）正常直觉是"给评审者越多背景越好"，而这里刻意**不给**你的思路过程。因为你的思路过程正是偏见的载体。

## 2. 核心设计决策

### 决策一：隔离会话历史——让评审者只看到产物

**选了什么**：派一个全新 subagent，只喂给它四样东西：做了什么（`{DESCRIPTION}`）、应该做什么（`{PLAN_OR_REQUIREMENTS}`）、变更范围（两个 SHA）。**不喂**你的推理过程、你踩过的坑、你的取舍纠结。

**为什么**：因为"为什么我这么写"这个信息会**为代码辩护**。如果你告诉评审者"这里用了轮询是因为 WebSocket 一直断",他就很难再客观地问"轮询在这里真的合适吗"。意图一旦给出，人（和模型）会自然地从意图出发去理解代码，而不是从代码出发去质疑意图。

**附带收益**：原文提到的第二点——保护你自己的 context。评审会产生大量细节输出，不该占据主会话。这在长流程里是实打实的资源考量。

**代价**：评审者**确实**会缺少判断所需的背景，可能给出脱离语境的建议（例如建议"用 WebSocket 替代轮询"，而你不知道他们试过）。这就是为什么决策五（允许反驳）是必需的，而不是可选的。

**备选方案**：*把会话摘要一并提供* —— 被否决。摘要的写法本身就会被你的偏见塑形，等于把偏见换个形式递进去。

### 决策二：用 git SHA 范围界定评审对象

**选了什么**：不用"请你评审我的改动"这种描述，而是给出 `{BASE_SHA}` 和 `{HEAD_SHA}`，让评审者自己 `git diff`。

**为什么**：把评审对象变成一个**可精确复现的区间**，而不是一句自然语言描述。
- 描述会漏（"我改了 auth 那块"——到底哪几个文件？）
- 描述会有主观筛选（你会不自觉地把不太自信的部分说得含糊）
- SHA 区间是客观的，且评审者能自己展开看全貌

**代价**：**依赖提交历史的整洁度**。如果一次提交里混了多件不相关的事（临时调试、顺手重命名），评审者会在噪声里工作，评审质量下降。这条把"提交要有原子性"从风格偏好变成了**前置条件**。

### 决策三：强制严重度分级

**选了什么**：所有问题必须归入三档——Critical（必须修）、Important（继续前修）、Minor（记下来以后说）。

**为什么**：**不分级的意见清单等于没有优先级的风向标**。设想一份 15 条意见的清单，其中 1 条是数据丢失风险、14 条是命名建议——如果不分级，实现者要么全改（浪费），要么挑着改（可能漏掉那 1 条）。分级的本质是**把"该先处理什么"这个判断从实现者的临场决定变成评审者的显式输出**。

**配套的还有一个反向约束**（写在附属模板里）：*"Categorize issues by actual severity. Not everything is Critical."*（按实际严重度分级，不是所有东西都是 Critical。）这防的是**分级通胀**——如果评审者倾向于把一切标成 Critical 以显得认真，分级就退化成噪声，实现者会开始忽略标签（"狼来了"）。

**代价**：分级是主观判断，且评审者有系统性高估的倾向（说"这是 Critical"比说"这是 Minor"显得更负责）。所以校准这件事只能靠提示词约束，无法强制。

### 决策四：用模板而不是开放提示

**选了什么**：附属文件 `code-reviewer.md` 里是一份固定的 prompt 模板，定义了五个检查维度和固定的输出格式。

**为什么**：保证**覆盖面的一致性**。开放式地让评审者"看看有什么问题"，结果高度依赖它当时的注意力分配——可能这次重点看架构、下次重点看测试，两次评审不可比。

模板强制每轮都过一遍：计划对齐 → 代码质量 → 架构 → 测试 → 生产就绪。这五个维度也不是随手列的，它们对应"这段代码可能在哪几个层面出问题"，覆盖了从"做错了"到"做对了但做得不好"的整个谱系。

**代价**：模板会僵化。项目特有的关注点（比如这个项目特别在意 i18n、或特别在意某个历史坑）不在五个维度里，评审者不会自动去看。模板能保证下限，不能提高上限。

### 决策五：明确要求给出裁决，并明确允许反驳

**选了什么**：两个看似矛盾的条款同时存在——① 评审必须给出明确裁决（`Ready to merge? Yes | No | With fixes`）；② 实现者可以且应当反驳错误的评审意见。

**为什么需要裁决**：没有裁决的评审只是**意见列表**，它把"到底能不能继续"的决策成本又推回给实现者。裁决把结论显式化，让"继续/不继续"成为一个已经做过的判断，而不是一堆需要自己掂量的材料。

**为什么需要反驳条款**：因为决策一的代价是真实的——评审者确实可能缺上下文而误判。如果不允许反驳，团队会陷入两个坏结局之一：要么遵循错误的建议（把代码改坏），要么默默忽略所有评审（机制名存实亡）。**把反驳写成正式权利**，反而保住了评审的权威性——因为只有能被质疑的评审，才值得被信任。

> 原文里有一句关键的措辞：*"Push back if reviewer is wrong (**with reasoning**)"*——注意括号里那三个字。反驳必须是技术性的，不是"我觉得没问题"。这把反驳从情绪行为约束成了技术行为。

## 3. 机制如何运转

```
完成任务
   ↓
取 BASE_SHA / HEAD_SHA（界定评审区间）
   ↓
填充 code-reviewer.md 模板（DESCRIPTION / PLAN / 两个 SHA）
   ↓
派独立 subagent（不带会话历史）
   ↓
评审员返回：优点 → 问题（Critical/Important/Minor）→ 建议 → 评估
   ↓
按档处置：
   Critical  → 立即修
   Important → 继续前修
   Minor     → 记下，以后说
   认为评审错了 → 带技术理由反驳
   ↓
进入下一个任务
```

**最容易被违反的约束**：把"继续前修 Important"执行成"继续前记下 Important"。这一条没有可见后果（代码照样跑），所以省略它不会立刻暴露——和 TDD 的两个验证步骤是同一类问题：**不产生产物的步骤最容易被跳过**。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **同一模型既写又审** | 共同的盲点被双方同时认可，评审形同虚设 | 评审的价值来自"不同的视角"，而同一模型对同一类问题有同样的盲区 |
| **提交历史脏**（一个 commit 混多件事） | 评审在噪声中工作，抓不住重点 | 决策二依赖 SHA 区间是干净的变更单元 |
| **分级通胀** | 真正的 Critical 被淹没，"狼来了"效应 | 评审者有高估严重度的倾向，只能靠提示词约束 |
| **超大 diff** | 评审质量断崖下降 | 注意力是有限资源，越长的 diff 越容易只被扫读 |
| **评审变成表演** | 走了流程，问题照旧 | 机制只能保证"评审发生"，无法保证"反馈被采纳" |
| **非 git 项目** | SHA 机制完全失效 | 对象界定依赖版本控制系统 |
| **评审者缺关键上下文** | 给出脱离语境的建议 | 决策一的固有代价；缓解手段是决策五（允许反驳） |
| **没有明确的 plan / requirements** | `{PLAN_OR_REQUIREMENTS}` 占位符填不出东西，"计划对齐"维度失效 | 评审的一半价值是"做的是不是要做的"，缺了需求就只能评质量 |

> **第一条值得单独说**：Superpowers 在 `subagent-driven-development` 里明确安排了**模型分级**（机械任务用便宜模型、评审用最强模型）——这不只是成本优化，也是**缓解同源盲点**的手段。但要说彻底解决，"换模型"只能做到部分缓解：如果实现和评审都由 AI 完成，某些类型的错误（尤其是"读过同样的训练数据所以有同样的错误直觉"）仍会同时过关。这可能是整条自动化流程最根本的局限。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **与** `receiving-code-review` **成对** | 一个负责发起，一个负责接收。两者对"评审意见"的立场一致：**是待评估的建议，不是命令**——发起方允许反驳，接收方要求验证 |
| **被** `subagent-driven-development` **调用** | 作为每个任务后的**固定环节**（两阶段评审的第二阶段） |
| **被** `executing-plans` **调用** | 在每个任务后或自然检查点触发 |
| 与 `test-driven-development` 的分工 | TDD 保证**单元行为**正确，评审检查**整体设计与需求对齐**——后者是测试无法覆盖的层面（测试通过 ≠ 设计合理） |
| 与 `verification-before-completion` 的分工 | 评审是**他人验证**，后者是**自我验证**；两者互补，不能互相替代（自己宣称完成不能代替被评审） |
