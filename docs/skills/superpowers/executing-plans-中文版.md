## frontmatter

- **name**：`executing-plans`
- **description**：当你有一份写好的实现计划，要在**独立会话**中带评审检查点地执行时使用。

## 概述

载入计划，批判性地审查它，执行所有任务，完成后汇报。

**开始时要宣告：**"我正在使用 executing-plans 技能来实施这份计划。"

**注意：** 告诉你的协作伙伴，Superpowers 在**能访问 subagent** 时效果好得多。在有 subagent 支持的平台（如 Claude Code 或 Codex）上运行时，它的工作质量会显著更高。**如果 subagent 可用，请改用 `superpowers:subagent-driven-development` 而不是本技能。**

> **批注**：一个技能在正文里主动写明"有更好的选择时别用我"，这是很少见的做法。它把自己的定位说得很清楚——**fallback（退化方案）**，服务于那些不支持 subagent 的平台。这句话同时也在向用户传递一个信息：你看到的执行质量偏低，可能不是模型的问题，而是环境缺了 subagent 这一步。把能力边界明说，比让用户自己困惑要好。

## 流程

### 第 1 步：载入并审查计划

1. 读取计划文件
2. **批判性地审查**——找出你对这份计划的疑问或顾虑
3. 如果有顾虑：在开始之前先向你的协作伙伴提出来
4. 如果没有顾虑：创建 TodoWrite，然后继续

> **批注**：第一步不是"执行"，而是"审查"，这个顺序是刻意的。理由在于**视角切换**：写计划的会话有当时的完整上下文，而执行会话是**冷启动**的——它没有那些上下文，看这份计划时反而像第一次读。**这个"劣势"此刻变成了优势**：冷读者最容易发现计划里那些"写的人自己懂、别人看不懂"的缺口。而且这是发现问题的**最低成本时刻**——代码一行都还没写。

### 第 2 步：执行任务

对每个任务：

1. 标记为 in_progress
2. **严格照每一步执行**（计划里已经是小块步骤）
3. 按计划要求运行验证
4. 标记为 completed

### 第 3 步：完成开发

所有任务完成并验证之后：

- 宣告："我正在使用 finishing-a-development-branch 技能来完成这项工作。"
- **必需的子技能：** 使用 `superpowers:finishing-a-development-branch`
- 遵循该技能，验证测试、呈现选项、执行选择

## 什么时候该停下来求助

**遇到下列情况立刻停止执行：**

- 撞上阻塞（缺少依赖、测试失败、指令不清）
- 计划有致命缺口，无法开始
- 你不理解某条指令
- 验证反复失败

**要请求澄清，而不是猜测。**

## 什么时候该回到前面的步骤

**回到第 1 步（审查）当：**

- 协作伙伴根据你的反馈更新了计划
- 根本性的方案需要重新考虑

**不要硬闯阻塞**——停下来问。

## 记住

- 先批判性地审查计划
- 严格照计划步骤执行
- 不要跳过验证
- 计划里说要引用某个技能时，就去引用它
- 卡住就停，不要猜
- **未经用户明确同意，绝不在 main/master 分支上开始实施**

## 集成

**必需的工作流技能：**

- **`superpowers:using-git-worktrees`** —— 确保隔离的工作区（创建一个，或验证已有的）
- **`superpowers:writing-plans`** —— 生成本技能所执行的计划
- **`superpowers:finishing-a-development-branch`** —— 所有任务完成后收尾
