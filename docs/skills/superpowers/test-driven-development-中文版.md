## frontmatter

- **name**：`test-driven-development`
- **description**：当实现任何功能或修 bug 时使用，须在编写实现代码之前。

## 概览

先写测试。看着它失败。写最小量的代码让它通过。

**核心原则**：如果你没有亲眼看着测试失败，你就不知道它测的是不是对的东西。

**违反规则的字面，就是违反规则的精神。**

> **批注**：第二句是刻意的反灵活条款。几乎所有规则都留了"看情况"的口子，而所有规则也都是从这个口子里失效的——所以这里提前把它焊死。详见[详细设计讲解](./test-driven-development-详细设计讲解.md)决策五。

## 何时使用

**总是适用：**
- 新功能
- 修 bug
- 重构
- 行为变更

**例外（须先问你的搭档）：**
- 用完即弃的原型
- 生成的代码
- 配置文件

想着"这次就跳过 TDD 吧"？停下。那是合理化。

> **批注**：例外清单有个共同特征——它们**不是"代码"**（生成的代码、配置）或**不会留下**（原型）。它没有给"简单改动""赶时间""我很确定"留任何位置。这正好堵住了最常见的三个借口。

## 铁律

```
没有失败的测试，就不许有生产代码
```

先写了代码才写测试？**删掉它，从头再来。**

**没有例外：**
- 不许"留着当参考"
- 不许在写测试时"改编"它
- 不许看它
- 删就是删

从测试出发重新实现。就这样。

> **批注**："删就是删"针对的是一个很具体的自欺路径：你说"我留着它当参考"，实际发生的是你会照着它写测试——那**就是**事后补测试，只是分了两步走。禁止保留、禁止查看，是为了让这个后门根本不存在。

## Red-Green-Refactor

```
RED（写一个失败的测试）
  → 验证它失败 →（失败方式不对则回到 RED）
GREEN（写最小量代码）
  → 验证它通过 →（不过则回到 GREEN）
REFACTOR（清理）
  → 保持绿色 → 下一个
```

### RED —— 写一个失败的测试

写一个最小的测试，展示应该发生什么。

**好：**

```typescript
test('retries failed operations 3 times', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```

名称清晰、测真实行为、只测一件事。

**坏：**

```typescript
test('retry works', async () => {
  const mock = jest.fn()
    .mockRejectedValueOnce(new Error())
    .mockRejectedValueOnce(new Error())
    .mockResolvedValueOnce('success');
  await retryOperation(mock);
  expect(mock).toHaveBeenCalledTimes(3);
});
```

名称含糊、测的是 mock 而不是代码。

**要求：**
- 一件事
- 名称清晰
- 真实代码（除非无法避免，否则不用 mock）

### 验证 RED —— 看着它失败

**强制执行。永远不许跳过。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试失败（不是报错）
- 失败信息符合预期
- 失败原因是功能缺失（而不是拼写错误）

**测试通过了？** 你在测已有行为。修测试。

**测试报错了？** 先修错误，重跑，直到它以正确的方式失败。

> **批注**：这一步是整个技能的灵魂。"失败"和"报错"被明确区分开——报错说明测试自己有问题，只有"以预期的方式失败"才证明测试真的在检验那个缺失的功能。详见[详细设计讲解](./test-driven-development-详细设计讲解.md)决策二。

### GREEN —— 最小量代码

写最简单的代码让测试通过。

**好：**

```typescript
async function retryOperation<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try {
      return await fn();
    } catch (e) {
      if (i === 2) throw e;
    }
  }
  throw new Error('unreachable');
}
```

刚好够通过。

**坏：**

```typescript
async function retryOperation<T>(
  fn: () => Promise<T>,
  options?: {
    maxRetries?: number;
    backoff?: 'linear' | 'exponential';
    onRetry?: (attempt: number) => void;
  }
): Promise<T> {
  // YAGNI
}
```

过度设计。

不要加功能、不要重构别的代码、不要超出测试范围去"改进"。

### 验证 GREEN —— 看着它通过

**强制执行。**

```bash
npm test path/to/test.test.ts
```

确认：
- 测试通过
- 其他测试仍然通过
- 输出干净（没有错误、警告）

**测试失败？** 改代码，不改测试。

**其他测试失败？** 现在就修。

### REFACTOR —— 清理

只在绿了之后：
- 消除重复
- 改善命名
- 提取辅助函数

保持测试绿色。不要新增行为。

### 重复

为下一个功能写下下一个失败的测试。

## 好的测试

| 品质 | 好 | 坏 |
|------|-----|-----|
| **最小** | 只测一件事。名称里有"and"？拆开。 | `test('validates email and domain and whitespace')` |
| **清晰** | 名称描述行为 | `test('test1')` |
| **体现意图** | 演示期望的 API | 让人看不出代码该做什么 |

## 为什么顺序很重要

**"我先写实现，之后补测试来验证它能跑"**

事后写的测试会立刻通过。立刻通过什么都证明不了：
- 可能测错了东西
- 可能测的是实现细节而非行为
- 可能漏掉了你忘记的边界情况
- 你从未见过它抓住 bug

测试先行强迫你**看到测试失败**，从而证明它确实在检验某些东西。

**"我已经手工测过所有边界情况了"**

手工测试是临时的。你以为你测全了，但其实：
- 没有记录测过什么
- 代码一变就没法重跑
- 压力下容易漏掉情况
- "我当时试过它能用" ≠ 全面

自动化测试是系统性的。它们每次都以同样的方式运行。

**"删掉 X 小时的工作太浪费了"**

沉没成本谬误。时间已经花掉了，无法追回。你现在有两个选择：
- 删掉并用 TDD 重写（再花 X 小时，高置信度）
- 留下它再补测试（30 分钟，低置信度，大概率有 bug）

真正的"浪费"是**留着你不能信任的代码**。没有真实测试的可运行代码就是技术债。

**"TDD 是教条，务实就意味着灵活变通"**

TDD **就是**务实的：
- 在提交前发现 bug（比事后调试快）
- 防止回归（测试会立刻抓到破坏）
- 记录行为（测试展示了代码该怎么用）
- 使重构成为可能（随便改，测试会兜住）

所谓"务实"的捷径 = 在生产环境里调试 = 更慢。

**"事后补测试能达到同样目的——重要的是精神而不是仪式"**

不对。事后测试回答的是"**这段代码做了什么**"；测试先行回答的是"**它应该做什么**"。

事后测试会被你的实现带偏。你测的是你造出来的东西，不是需求要的东西。你验证的是你记得的边界情况，不是新发现的。

测试先行强迫你在实现之前发现边界情况。事后测试只验证"你记得全"（而你没有）。

30 分钟的事后测试 ≠ TDD。你得到了覆盖率，失去了"测试确实有效"的证明。

## 常见的合理化

| 借口 | 现实 |
|------|------|
| "太简单了不用测" | 简单的代码也会坏。写测试只要 30 秒。 |
| "我之后补测试" | 立刻通过的测试什么都证明不了。 |
| "事后补测试效果一样" | 事后测试 = "它做了什么？"；测试先行 = "它该做什么？" |
| "我已经手工测过了" | 临时 ≠ 系统。没有记录，无法重跑。 |
| "删掉 X 小时太浪费" | 沉没成本谬误。留下未验证的代码就是技术债。 |
| "留着当参考，我先写测试" | 你会改编它。那就是事后补测试。删就是删。 |
| "我需要先探索一下" | 可以。探索完就把它扔掉，从 TDD 开始。 |
| "测试难写 = 设计不清晰" | 听测试的话。难测 = 难用。 |
| "TDD 会拖慢我" | TDD 比调试快。务实 = 测试先行。 |
| "手工测试更快" | 手工无法证明边界情况。每次改动你都得重测。 |
| "现有代码没有测试" | 你正在改进它。给现有代码补上测试。 |

> **批注**：这张表不是"提醒"，而是一个**预先写好的反驳库**。借口总是在具体情境中冒出来——那时正是判断力最弱的时候。把这 11 条在冷静时写死，就把"要不要跳过"从一次**判断**降级成一次**查表**。这是整个技能里最独特的设计。

## 红旗 —— 停下，从头再来

- 测试之前先写了代码
- 实现之后才补测试
- 测试立刻通过
- 解释不了测试为什么失败
- 测试是"之后"加的
- 用"就这一次"为自己开脱
- "我已经手工测过了"
- "事后补测试能达到同样目的"
- "重要的是精神不是仪式"
- "留着当参考"或"改编现有代码"
- "已经花了 X 小时，删掉太浪费"
- "TDD 是教条，我要务实"
- "这次不一样，因为……"

**以上任何一条都意味着：删掉代码，用 TDD 从头开始。**

## 示例：修 bug

**Bug：** 空的 email 被接受了

**RED**
```typescript
test('rejects empty email', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('Email required');
});
```

**验证 RED**
```bash
$ npm test
FAIL: expected 'Email required', got undefined
```

**GREEN**
```typescript
function submitForm(data: FormData) {
  if (!data.email?.trim()) {
    return { error: 'Email required' };
  }
  // ...
}
```

**验证 GREEN**
```bash
$ npm test
PASS
```

**REFACTOR**
如果多个字段都需要校验，提取出校验逻辑。

## 验证清单

标记工作完成之前：

- [ ] 每个新函数/方法都有测试
- [ ] 每个测试在实现之前都亲眼看着它失败过
- [ ] 每个测试的失败原因都是预期的（功能缺失，而非拼写错误）
- [ ] 为通过每个测试写的都是最小量代码
- [ ] 所有测试通过
- [ ] 输出干净（没有错误、警告）
- [ ] 测试使用真实代码（mocks 仅在无法避免时使用）
- [ ] 边界情况与错误情况都有覆盖

有勾不上的？你跳过了 TDD。从头再来。

## 卡住的时候

| 问题 | 解法 |
|------|------|
| 不知道怎么测 | 写出你期望的 API。先写断言。问你的搭档。 |
| 测试太复杂 | 设计太复杂。简化接口。 |
| 必须 mock 一切 | 代码耦合太重。用依赖注入。 |
| 测试的准备代码太庞大 | 提取辅助函数。还是复杂？简化设计。 |

> **批注**：这张表把"测试难写"重新定义成了**设计信号**而非障碍——测试写不顺，说明接口设计有问题，而不是"这个不好测所以跳过"。这是把 TDD 当作**设计工具**，而不只是验证手段。

## 与调试的集成

发现 bug？先写一个复现它的失败测试。走 TDD 循环。这个测试既证明修复有效，也防止回归。

**永远不要在没有测试的情况下修 bug。**

## 测试反模式

添加 mocks 或测试工具时，阅读 `testing-anti-patterns.md` 以避免常见陷阱：
- 测 mock 的行为而不是真实行为
- 往生产类里加只给测试用的方法
- 不理解依赖关系就 mock

## 最终规则

```
生产代码 → 存在一个先失败过的测试
否则 → 不是 TDD
```

除你的搭档许可外，没有例外。
