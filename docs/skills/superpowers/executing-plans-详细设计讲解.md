## 1. 它解决什么问题

这个技能处理的是一个**已经被上游解决过的问题的下半场**。

`writing-plans` 已经把计划写到了"零占位符"的程度——精确文件路径、每步完整代码、2-5 分钟的步骤粒度。所以执行阶段的核心风险**不再**是"不知道该做什么"，而是另外三个：

**其一，执行会话是冷启动的。** 写计划的会话积累了整套理解，而执行会在**另一个会话**里发生（这正是它的定位：`in a separate session`）。那些理解不会被带过来。执行者拿到的是计划的**文本**，不是计划背后的**思考**。

**其二，AI 会在执行中即兴。** 计划里写"A 方案"，执行时它可能觉得"B 方案更好"就改了。这种偏离单次看往往"更优"，但会毁掉计划的**整体一致性**——而计划的价值恰恰在于它是一套自洽的整体。

**其三，卡住时的默认反应是猜。** LLM 极难承认"我卡住了"；它倾向于产出一个看起来合理的猜测，而不是停下来说"这里我不确定"。而冷启动的执行者**缺乏做这个猜测所需的信息**——它的猜测比计划作者的猜测更不可靠。

> **设计立场**：它假设计划是**可信的上游产物**，执行阶段的任务是**忠实还原**而非重新设计。这个假设是整套设计的基石——一旦计划本身有问题，这个技能的所有纪律（严格照做、不即兴）都会把错误**忠实地放大**。所以它才需要"第 1 步先审查"来兜底。

## 2. 核心设计决策

### 决策一：第一步是"批判性审查"，不是"开始执行"

**选了什么**：载入计划后，先找疑问和顾虑；**有顾虑就先提出来，不要开始**。

**为什么**：这是**把冷启动的劣势转成优势**。前文说执行会话缺少上下文——但反过来看，冷读一份计划时，那些"作者自己懂、别人看不懂"的缺口会最刺眼。写计划的人无法用这个视角看自己的产物。

更关键的是**成本**：这是唯一一个"发现问题时零成本"的时刻。代码还没写，计划改一句就行。一旦进入第 2 步，同样的发现就要以一整轮返工为代价。

**备选方案**：让执行者先读懂计划、有疑问边做边问。**被否决的原因**——那样顾虑会在执行中途以"阻塞"的形式暴露，而那时已经投入了工作；更糟的是，执行者可能**不问**，直接绕过缺口继续做。

**代价**：多一道前置步骤。对于一份确实没问题的计划，这一步是纯粹的开销。

### 决策二：严格照做，不即兴

**选了什么**：`Follow each step exactly`——照计划的原样执行。

**为什么**：计划的价值在于**它是自洽的一套**。单点"优化"会破坏自洽性——而破坏往往不是立即可见的，它会在若干个任务之后以"两块代码对不上"的形式浮现，届时很难归因到当初那次即兴。

另外，**计划已经粒度足够细**（`writing-plans` 要求 2-5 分钟一步，每步含完整代码），细到这个程度时，即兴已无必要——若还需要执行者临场设计，说明计划没写到位，那是上游问题，该回到 `writing-plans` 而不是让执行者补锅。

**代价**：如果计划确实有局部瑕疵但被第 1 步漏过，执行者会忠实地执行一个次优方案。

### 决策三：卡住就停，不许猜

**选了什么**：四种情况立刻停止（阻塞、致命缺口、指令不清、验证反复失败），并且 `Ask for clarification rather than guessing`。

**为什么**：**猜错的代价远大于停下等待的代价**。停下只是浪费时间；猜错则是浪费了工作 + 制造了错误的代码 + 让后续任务建立在错误地基上。

而且这里有一个**信息论层面的理由**：执行者是冷启动的，它对全局的掌握弱于计划作者。同一个模糊点，让掌握更多信息的人来裁决，质量一定更高。**执行者越"聪明"地猜，越可能猜出一个在局部自洽、在全局错误的方案**——这比明显的错误更危险。

**代价**：在无人值守场景下，"停下等待"意味着整条流水线挂起。这是真实的成本，也是这个技能**只适合有人在环**的原因之一。

### 决策四：明确自曝"有 subagent 时请用别的"

**选了什么**：在概述里直接写明——`If subagents are available, use superpowers:subagent-driven-development instead of this skill.`

**为什么**：**它能识别自己的质量上限，并主动把用户导向更优解**。这句话不是谦辞，而是因为两者的差距有结构性原因：本技能在**同一个上下文里**顺序执行所有任务，`subagent-driven-development` 则是每个任务一个全新上下文。差别不是"稍好"，而是**长计划下是否会发生上下文污染**。

**代价**：技能的存在感被自己削弱。但从用户利益看，这个取舍是对的——**一个知道自己何时不该被使用的技能，比一个声称万能的技能更可信**。

### 决策五：收尾转交，不自己完成

**选了什么**：所有任务完成后，**必须**转交 `finishing-a-development-branch`（原文标了 `REQUIRED SUB-SKILL`）。

**为什么**：**合并/PR/丢弃是一个需要有决策权限的人来拍板的动作**，不属于"执行"的范畴。把它放进执行技能里，等于让执行者自己决定要不要合并——而执行者对"这次改动值不值得合并"没有独立判断的立场（它是执行者）。

这条与 `grilling`、`OpenSpec` 的规划门禁同源：**动作的性质不同，就需要不同的关卡**。

### 决策六：阶段划分——审查 / 执行 / 收尾

**选了什么**：三步拆分，且第 2 步内部对每个任务只做"标记 → 照做 → 验证 → 标记完成"，**没有**任务间的评审环。

**为什么**：任务间的评审环是 `subagent-driven-development` 的机制，这里没有——因为它**没有独立评审者**（没有 subagent 就没有干净的评审上下文）。同一个会话既做又评，评审会被"我刚写的代码"污染，价值大打折扣。所以这里**用"计划的细致"替代"评审的独立"**：既然计划已细到每步有预期输出，那么"按计划验证"本身就承担了一部分规格合规检查的功能。

> **一处值得留意的措辞**：本技能的 description 承诺 `with review checkpoints`，但正文里并未规定"每 N 个任务停下来评审"的节奏——正文中唯一的停止条件是**阻塞**，不是**检查点**。实际可用的检查点只有：第 1 步的审查、每个任务后的验证、以及最后的转交。如果你期待的是"每几个任务停下来让人看一眼"，正文并未提供这个机制。

## 3. 机制如何运转

```
载入计划文件
   ↓
【第 1 步】批判性审查
   ├─ 有顾虑 → 停下，向伙伴提出 → 等回应（可能回到第 1 步重审）
   └─ 无顾虑 → 建 TodoWrite
   ↓
【第 2 步】逐任务执行
   ├─ 标记 in_progress
   ├─ 严格照步骤做
   ├─ 按计划运行验证
   ├─ 标记 completed
   └─ 卡住？ → 立刻停止，提问（不许猜）
   ↓
【第 3 步】全部完成并验证
   └─ 转交 finishing-a-development-branch（合并/PR/丢弃由人决定）
```

**最容易违反的约束是"卡住就停"**。原因很直接：停下来在当下是**负收益**（工作没有推进），而猜测在当下是**正收益**（看起来推进了）。这个正负号只在几轮之后才反转——那时才发现地基是错的。**这个延迟的惩罚，正是它需要被写成硬规则的原因**。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **计划本身有错** | 错误被忠实放大到全部任务 | 第 1 步只审查一次，且审查发生在**没有代码可验证**的阶段；有些缺陷读文本看不出来 |
| 计划有**未被察觉的缺口** | 执行者要么照做（产出不完整），要么就此停下空等 | 它被要求"不猜"，但不猜就意味着必须有人回答——**无人值守时流水线挂起** |
| **长时间无人值守** | 撞上阻塞后一直停着 | 技能的默认行为是等人，没有超时或降级策略 |
| 计划**粒度不够细** | 执行者被迫临场设计，开始即兴 | 本技能不校验计划质量，只是假设它合格；细粒度是 `writing-plans` 的责任 |
| **会话很长 / 任务很多** | 上下文污染累积，后期任务质量下降 | 它不做上下文隔离（这正是它推荐 `subagent-driven-development` 的原因） |
| 用户把 `review checkpoints` **理解为"定期停下汇报"** | 期待落空，觉得技能没按承诺走 | 正文未规定任务间的评审节奏（见决策六的说明） |
| 计划里**引用的技能不存在** | 执行到该步时中断 | 原文要求"计划说引用技能时就引用"，但技能可用性未在上游校验 |

> **第一条与第二条合起来是同一个结构性弱点**：这个技能的可靠性**完全继承自计划的质量**，而它对计划的把关只有"读一遍并提疑问"。之所以能接受这个弱点，是因为链条上游的 `writing-plans` 用了极重的手段保证质量（零占位符、每步完整代码、计划自审）。**把这个技能单独拿出来用——配一份随手写的计划——它的表现会很差**，而这不是技能本身的问题，是它假设的前提没被满足。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **上游** `writing-plans` | 计划由它生成；本技能不校验计划质量，直接继承 |
| **上游** `using-git-worktrees` | 提供隔离工作区与干净的测试基线 |
| **下游** `finishing-a-development-branch` | REQUIRED——收尾必须转交，不自行决策 |
| **替代** `subagent-driven-development` | 二者互斥：本技能用于**独立会话 / 无 subagent**；那个用于**当前会话 / 有 subagent**。原文明确推荐后者 |
| 与 `test-driven-development` 的关系 | 本技能不内联 TDD——TDD 要求写在计划的每一步里（"写失败测试"是一步、"跑它确认失败"是另一步） |
