## 1. 它解决什么问题

它对付的是**收尾时刻的默认行为**。

实现做完了，测试全过。接下来呢？这个问题在技术上**没有正确答案**——合并、开 PR、先留着、扔掉，全都可能是对的，取决于这次工作的性质和你的意图。但 LLM 面对这种"没有正确答案"的岔路口时，行为是确定的：**它会挑一个最像是"正常流程"的选项往下走**。

后果是双向的：
- **做多了**：不该合并的合并了，或者自作主张提交了 PR、推到了远端——这些动作**可见于他人**，撤回的社交成本很高。
- **做少了**：该清理的没清理，留下一地的分支和 worktree；或者反过来，**自作主张把工作区删了**。

第二条尤其严重。收尾阶段是整条链路里**唯一会执行不可逆删除的地方**（删分支、删 worktree）。在这里，"挑一个默认选项往下走"的代价不是返工，而是**丢失工作成果**。

**设计立场**：收尾是一个**必须由人拍板的决策点**。没有默认行为，没有"最合理的那个"，只有摆在你面前的选项。技能的责任是**把选项列清楚、把环境判断好、把不可逆动作排到最后**，但选哪个必须由你说。

## 2. 核心设计决策

### 决策一：用封闭菜单，而不是开放式提问

**选了什么**：恰好 4 个选项（detached HEAD 时 3 个），逐字给出，并明确要求"不要添加解释"。

**为什么**：开放式提问（"接下来该怎么做？"）有两个问题：

1. **把设计工作推回给用户**。用户请你做完这个任务，现在还要替你构思收尾的选项——等于最后一步的认知负担全是他的。
2. **回答的形态不可控**。用户可能说"推上去吧"，而这句话没有明确 merge 还是 PR，于是又是一轮澄清。

封闭菜单同时解决了两个问题：选项是现成的（零构思成本），措辞是固定的（零歧义）。

"不要添加解释"这条看起来吹毛求疵，实际是在**保护菜单的形态**。菜单的价值在于可以**一眼扫完并做出选择**；一旦每个选项后面跟一段说明，它就变成了一篇需要阅读理解的短文，扫视优势消失。

**代价**：菜单是**硬编码的四个**，因此无法表达组合意图。真实场景里常见的是"先推送开 PR，同时本地也合一份"、"先留着，等我明天想清楚"这类中间态——菜单里没有位置放它们。用户只能选一个最接近的，然后手动补做剩下的事。

**备选方案**：
- *开放式提问* —— 被否决。见上。
- *给出更多选项（比如 6-7 个）* —— 被否决。选项越多，扫视优势越弱，且每多一个就要多维护一条执行路径。
- *默认合并，同时提供撤销* —— 被否决。merge + 推送到远端是**可见于他人**的动作，撤销的代价不是技术性的而是社交性的（别人已经看到了）。不能默认执行。

### 决策二：菜单形状随环境变化

**选了什么**：先检测 `GIT_DIR` 与 `GIT_COMMON` 的关系，据此决定给 4 个还是 3 个选项。

**为什么**：detached HEAD 的情境下没有"本地合并"这个动作可做——它是被外部环境管理的（CI、IDE、某种 workspace 机制），没有可合并的目标分支。给出一个执行必然失败的选项，比少给一个更糟：**用户在菜单上看到它，就会以为自己有这条路径**。

这条决策体现了"菜单是**承诺**"的意识：列出的每一项都必须是可兑现的。

**代价**：环境判断本身可能出错（`GIT_DIR`/`GIT_COMMON` 的比对在 submodule 里也会成立——这个坑 `using-git-worktrees` 里已经遭遇过一次）。判断错了就会给出错误形状的菜单。

### 决策三：清理规则不对称——Option 2/3 永不清理

**选了什么**：只有 Option 1（本地合并）和 Option 4（丢弃）会清理 worktree；Option 2（开 PR）和 Option 3（保持现状）**永远保留**。

**为什么**：清理的前提是"这个东西没人要了"。三种情况下这个前提不成立：

- **Option 2**：PR 开出去之后，评审意见会回来，你需要**在原 worktree 里继续改**。清理掉等于把迭代的地基抽了。
- **Option 3**：用户明确说了"我自己稍后处理"——那当然不能动。
- **Option 1**：合并成功 = 工作已经进入主分支，临时工作区完成了使命。
- **Option 4**：丢弃 = 主动宣布不要了。

这个不对称的关键在于：**"完成"不等于"可以清理"**。Option 2 的 PR 也是"完成"，但它的生命周期还没结束。技能把"清理"绑定在"这条工作线是否还需要活动的工作区"上，而不是绑定在"任务是否做完"。

### 决策四：provenance check——只清理自己创建的

**选了什么**：Step 6 用**路径前缀**判断 worktree 的归属——落在 `.worktrees/`、`worktrees/` 或 `~/.config/superpowers/worktrees/` 之下才清理；否则交给宿主环境。

**为什么**：这是 `using-git-worktrees` 那条"never fight the harness"的另一面。**清理对方创建的东西，和创建对方不知道的东西，造成的危害是同一种**——宿主环境的内部状态（会话绑定、退出时的清理责任、界面指示）会和实际的 git 状态脱节，此后表现为莫名其妙的错误。

**代价**：判定依据是**路径前缀匹配**，这是一个薄弱的证明。任何恰好建在 `.worktrees/` 下的 worktree——比如用户为了别的原因手工建的——都会被判定为"Superpowers 所有"并被删掉。**路径不是来源**，但技能没有更好的手段（git 不记录"是谁创建的"）。

这个漏洞之所以可接受，是因为默认路径（`.worktrees/`）本身就是 Superpowers 约定的位置，落在那里说明大概率是自己建的。**这是一个用约定换来的近似判定。**

### 决策五：Option 4 要求打字确认，而不是 y/n

**选了什么**：丢弃前必须**输入 `discard` 这个词**。

**为什么**：针对**确认疲劳**。用户在一串交互里会对"是否继续"形成肌肉记忆——看到确认框随手回车。要求输入一个特定的词，强制这次交互必须被**有意识地阅读并复述**：你不可能在没看内容的情况下打出一个你没预期的单词。

这是整份技能里唯一的破坏性操作，值一个特殊的确认仪式。

**代价**：在自动化或脚本化流程里，这个确认**无法完成**——没有人能打出那个词。所以本技能整体上是**交互式场景专用**的。

### 决策六：不可逆动作严格排在可逆动作之后

**选了什么**：Option 1 的顺序是 merge → **在合并结果上验证测试** → 清理 worktree → 删除分支。

**为什么**：这一切都在保护**回退路径**。合并是可能失败的（冲突、测试挂掉）；如果先清了 worktree、删了分支，失败时就无路可退。

原文在「常见错误」里记录了一个更具体的技术原因：**先删分支会失败**，因为 worktree 仍然引用着那个分支。所以顺序不是"随便排的偏好"，而是由 git 的内部约束决定的：**分支被 worktree 引用时不能删**。

**代价**：步骤多、顺序固定，在实现上更容易写错——而写错的后果（CWD 在 worktree 内部时 `git worktree remove` 静默失败）原文里也专门列了一条。

## 3. 机制如何运转

```
任务完成
   ↓
Step 1  验证测试
   ├─ 失败 → 停下（不进 Step 2）
   └─ 通过 ↓
Step 2  检测环境（GIT_DIR vs GIT_COMMON）
   ├─ 普通仓库 / 具名分支 → 4 选项菜单
   └─ detached HEAD      → 3 选项菜单（无 merge）
   ↓
Step 3  确定基准分支
   ↓
Step 4  呈现菜单（逐字，不加解释）
   ↓
Step 5  执行所选
   ├─ 1 本地合并  → merge → 验证 → 【清理】→ 删分支
   ├─ 2 开 PR     → push → gh pr create → 【保留 worktree】
   ├─ 3 保持现状  → 汇报 → 【保留 worktree】
   └─ 4 丢弃      → 打字确认 → 【清理】→ 强制删分支
   ↓
Step 6  清理（仅 Option 1 和 4）
   ├─ 在 .worktrees/ 等约定路径下？ → 自己建的，清理 + prune
   └─ 其他路径？                    → 宿主的，不动
```

**最容易违反的约束**：Step 1 的"测试失败就停下"。它的位置在流程最前端，且后继动作（呈现菜单）本身是无害的——于是很容易想"先把选项给用户看，反正他还没选"。但一旦菜单出现，用户就进入了"选择"的心智，而带着失败测试的选择没有一个是对的。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **非 GitHub 仓库** | Option 2 直接失败 | `gh pr create` 硬编码依赖 GitHub CLI。GitLab / Bitbucket / 自建 Gitea 都无法执行 |
| 用户工作在 `.worktrees/` 下的**手工 worktree** | 被误判为 Superpowers 所有并被删除 | provenance 判定是路径前缀匹配，而**路径不等于来源** |
| 用户想要**组合动作**（先 PR 再本地合并） | 无法表达，只能选一个 + 手动补做 | 菜单是封闭的 4 项，没有组合位 |
| **无人协作**（自动化 / subagent 收尾） | 卡在菜单上；discard 的打字确认也不可能完成 | 整份技能建立在"有一个人来做选择"之上 |
| **非 git 项目** | 完全不可用 | 全部命令基于 git |
| detached HEAD **但用户确实想本地合并** | 没有这个选项 | 菜单按环境裁剪（决策二），裁剪的依据是"技术上可行"，不是"用户可能想要" |
| worktree 目录**已被手动删除** | `git worktree remove` 失败，但留下陈旧登记 | 技能用 `git worktree prune` 兜底，然而该命令排在失败的那条之后 |

> **最值得注意的是第二行。** provenance check 是这份技能里**唯一一处用近似手段做安全判断**的地方——它需要在"该不该删"这个问题上给出答案，而 git 并不记录"谁创建了这个 worktree"。
>
> 于是它退而求其次，用路径前缀当证据。这个近似在**约定被遵守**时是正确的（自建 worktree 确实都在那几个目录下），但在**约定被违反或碰巧**时就会误判。而误判的后果是**删除用户的工作**——恰恰是这份技能存在的全部理由所在。
>
> 换个角度看，这暴露了一个设计上的不对称：技能对"删除"这件事的防护做得非常严（打字确认、合并成功后才清理、顺序严格），但**"该不该删"的判定依据却很薄**。前者防的是"手滑"，后者防的是"看错",而真正会造成损失的其实是后者。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **与** `using-git-worktrees` **成对** | 一个建、一个按来源判定清理。两者的 provenance 约定必须一致（都用 `.worktrees/` 等路径） |
| **被** `subagent-driven-development` **调用** | 它是该技能的终态：全部任务完成 → 最终代码评审 → 调用本技能 |
| **被** `executing-plans` **调用** | 同上，批量执行模式走完也要收尾 |
| **依赖** `verification-before-completion` 的思路 | Step 1 的"先验证测试再给选项"是同一原则（证据先于宣称）在收尾场景的应用 |
| 与 `grilling` 的同构 | 两者都把一段流程的**终点**做成显式确认点：`grilling` 是"确认共识后才行动"，本技能是"选完选项后才行动" |
