# Superpowers 原理拆解

> 源码：`~/.claude/plugins/cache/superpowers-marketplace/superpowers/5.1.0/`（v5.1.0，作者 Jesse Vincent / obra）
> 官方定位：*"A complete software development methodology for your coding agents"*——给编码代理的一整套开发方法论。

## 0. 一句话原理

**用"任何任务开始前必须先调技能"的强制规则，把人类软件工程的纪律塞进 AI 的执行路径里。**

它不是工具，是纪律。14 个技能各自负责开发流程的一段，靠 description 自动触发，链式传递。

## 1. 主链路总览

```
想法
 │
 ▼
① brainstorming ──→ 产出 design doc（docs/superpowers/specs/）
 │                    用户逐段确认 + 终审
 ▼
② using-git-worktrees ──→ 隔离工作区（新分支 + 跑通测试基线）
 │
 ▼
③ writing-plans ──→ 产出 plan（docs/superpowers/plans/）
 │                  2-5 分钟粒度的任务 + 完整代码
 ▼
④ subagent-driven-development（推荐）
   或 executing-plans
 │    每个任务：实现 → 规格审查 → 质量审查
 ▼
⑤ test-driven-development（贯穿④的实现过程）
 │    RED → 验证失败 → GREEN → 验证通过 → REFACTOR
 ▼
⑥ requesting-code-review ──→ 按严重度报告问题
 │
 ▼
⑦ finishing-a-development-branch ──→ 验证测试 → merge/PR/保留/丢弃
```

旁支技能（按需触发）：`systematic-debugging`（修 bug 时 4 阶段根因分析）、`verification-before-completion`（宣称完成前必须验证）、`receiving-code-review`（如何回应评审意见）、`dispatching-parallel-agents`（并行子代理）。

## 2. 逐步拆解：每步为什么存在

### ① brainstorming —— 为什么不许直接写代码

源文件里的 `<HARD-GATE>`（硬门禁）：

> *Do NOT invoke any implementation skill, write any code... until you have presented a design and the user has approved it.*

**为什么**：
- LLM 的默认行为是"看到需求立刻开写"。写出来的东西往往建立在未检验的假设上——假设错了，代码全废。
- 技能里专门有一节 **Anti-Pattern: "This Is Too Simple To Need A Design"**：*"Simple projects are where unexamined assumptions cause the most wasted work."*（"简单"项目恰恰是未检验假设造成最多浪费的地方。）这是对"太简单不用设计"这种合理化冲动的预防针。
- 流程设计本身也是行为设计：**一次只问一个问题**（避免用户认知过载）、**优先选择题**（降低回答成本）、**提出 2-3 个方案带取舍**（防止锁死第一个想法）、**设计分段呈现、每段确认**（增量验证）。
- 终态被严格限定：*The ONLY skill you invoke after brainstorming is writing-plans*——不许跳到任何实现技能。

**产出**：design doc 存入 `docs/superpowers/specs/`，经过 spec 自审（占位符/矛盾/歧义/范围四查）+ 用户终审两道关。

### ② using-git-worktrees —— 为什么要隔离

在动手前建独立 worktree + 新分支，先跑通测试基线。

**为什么**：后面 subagent 会大量自动执行，出问题不能污染主分支；"测试基线是绿的"保证了后续任何红色都是新代码造成的，不是历史遗留。

### ③ writing-plans —— 为什么计划要写到"羞辱性"的详细程度

源文件原话，计划要假设执行者是：

> *"an enthusiastic junior engineer with poor taste, no judgement, no project context, and an aversion to testing"*

（一个热情但品味差、没判断力、没有项目上下文、还厌恶测试的初级工程师。）

**为什么**：这份计划的真正读者不是人，是**零上下文的 subagent**。会话里积累的理解不会自动传递给它们，所以：
- **精确文件路径**（`Modify: src/path/file.py:123-145`）——不让执行者猜
- **每步完整代码**——计划即预演，"写计划"时就把实现想完
- **2-5 分钟粒度**（"写失败测试"是一步，"跑它确认失败"是另一步）——粒度小到不可能在一步里隐藏误解
- **No Placeholders 铁律**：禁止 "TBD"、"添加适当的错误处理"、"类似 Task N" 这类占位符。**为什么**：占位符 = 把决策推迟到执行时，而执行者恰恰是最没有上下文的人。计划阶段偷的懒，执行阶段加倍偿还。
- "Similar to Task N" 也不许——执行者可能乱序读任务，必须重复完整代码。

### ④ subagent-driven-development —— 为什么每个任务派一个新 subagent

**核心机制**：每个任务派一个**全新的** implementer subagent（由控制者精心构造其指令和上下文），完成后走**两阶段评审**：

```
实现 subagent（写代码+测试+提交+自审）
   ↓
规格合规审查 subagent ──→ 不合规？实现者修复，再审
   ↓ 合规
代码质量审查 subagent ──→ 有问题？实现者修复，再审
   ↓ 通过
标记完成 → 下一个任务
```

**为什么 fresh subagent**：
- **上下文隔离**。subagent 不继承主会话历史——主会话里跑偏的讨论、过时的决定不会污染它。控制者"精确投喂"它需要的上下文。
- **主会话的 context 是稀缺资源**，留给协调而不是装满实现细节。
- 模型分级省钱：机械任务用便宜模型，评审用最强模型——"计划足够好时，大多数实现任务都是机械的"。

**为什么两阶段评审、且顺序固定（先规格后质量）**：
- 规格合规查的是"做的对不对"（有没有少做、多做——示例里 spec reviewer 抓到实现者擅自加了个 `--json` flag，这叫 over-building）；代码质量查的是"做得好不好"。
- **先质量后规格是浪费**：代码写得再漂亮，规格错了全是白干。所以质量评审必须在规格 ✅ 之后才开始（Red Flags 里明确列了这条）。

**为什么连续执行不打扰人**：*"Do not pause to check in... 'Should I continue?' prompts waste their time"*——计划已经过你批准，执行期再反复确认是把决策成本还给你，违背分阶段的意义。只有 BLOCKED、真歧义、全部完成三种情况才停。

### ⑤ test-driven-development —— 为什么"看到测试失败"是强制的

**Iron Law**：

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

先写测试？写了实现？**删掉，重来**。*Delete means delete*——不许留作参考、不许"改编"。

**为什么看它失败如此重要**（这是整个 TDD 技能的灵魂）：
- 测试写完立刻通过 = 什么都没证明。可能测错了东西、可能测的是实现而非行为。
- **只有先看到它以正确的方式失败（功能缺失而非拼写错误），才能证明这个测试真的在检验这个功能。**
- "事后补测试"为什么不行：测试会被你的实现带偏——你测的是"你写了什么"，而不是"需求要什么"。

**为什么这个技能里有一大张"合理化对照表"**（"太简单不用测"、"我先写完再测效果一样"、"删掉几小时工作太浪费"...）：
- 跳过 TDD 的冲动全是**合理化**（rationalization），人和 LLM 都会。技能把每条借口和反驳预先写死，就是在堵住执行时的心理逃逸通道。
- *"Violating the letter of the rules is violating the spirit of the rules."*（违反规则的字面就是违反规则的精神。）——这句是刻意的反灵活：这个技能不接受"变通"。

### ⑥⑦ 评审与收尾 —— 为什么按严重度分级的报告才能阻塞

- 评审问题按严重度分级，**Critical 阻塞推进**——不分级的评审意见清单等于没有优先级的风向标。
- `verification-before-completion` 的哲学：**Evidence over claims**。"我觉得好了"不算数，跑出来的证据才算数。
- `finishing-a-development-branch` 把 merge/PR/保留/丢弃做成显式决策点——收尾本身是个需要人拍板的决定，不许默认行为替你决定。

## 3. 设计哲学（README 原文四条）

1. **Test-Driven Development** — 永远先写测试
2. **Systematic over ad-hoc** — 流程优于猜测
3. **Complexity reduction** — 简洁是首要目标
4. **Evidence over claims** — 验证先于宣称成功

贯穿观察：**Superpowers 的每个技能都在对抗 LLM 的某个具体缺陷**——

| LLM 缺陷 | 对抗它的技能 |
|-----------|--------------|
| 拿到需求就开写 | brainstorming 的 HARD-GATE |
| 上下文漂移、越干越乱 | fresh subagent + 计划零占位符 |
| "我编完了"（幻觉完成） | TDD 验证 + verification-before-completion |
| 合理化走捷径 | TDD 的借口对照表、using-superpowers 的 Red Flags 表 |
| 主观判断"差不多了" | 两阶段评审、严重度分级 |
