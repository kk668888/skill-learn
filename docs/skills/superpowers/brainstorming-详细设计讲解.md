## 1. 它解决什么问题

LLM 面对一个模糊需求时的默认行为是**立刻开始产出**。而它填充空白的方式是**用最可能的推测代替确认**。

这个推测过程不可见：你看到的是一个完整、自信、结构良好的产出，看不到底下垫了多少个"我猜他大概是想要…"。等到发现猜错，成本已经付出——而且往往是**成倍**付出，因为写错的代码、搭错的结构都需要回退。

关键认识：**这个错误不来自模型能力不足，而来自信息不足**。换一个更强的模型也一样猜错，因为它同样没有那些信息。所以这不是"提示词写清楚点"能解决的问题，而是**流程结构**问题——在产出之前，必须有一个强制把假设暴露出来的环节。

`brainstorming` 就是那个环节。

> **设计立场**：它假设"用户往往还说不清自己想要什么，但**看到具体选项就能判断**"。
> 这个假设决定了它的核心动作是**提出 2-3 个方案让你挑**——先创造选项空间，再收敛。
>
> 对照 grill 系列的 `grilling`：那一套假设"用户心里其实有答案，只是没说清楚"，因此是**纯追问式**的（逼出已有信息），几乎不主动发明方案。**两套系统都在对抗同一个失败模式，但一个靠"创造选项"，一个靠"逼出信息"**——这是它们最根本的立场差异。

## 2. 核心设计决策

### 决策一：用 `<HARD-GATE>` 这种仪式化标签表达禁令

**选了什么**：把"不许动手"这条规则包在 `<HARD-GATE>` 里，全大写、XML 风格。

**为什么**：这个标签**不携带任何机器可解析的语义**——没有任何程序会解析它。它的作用完全是修辞上的：

- 在长文档中制造一个**视觉与语义的断点**
- 让"不许越过"看起来像一条**硬约束**，而不是一句建议
- 增加模型绕过它的**心理成本**（对"合理化倾向"做防御）

这是在对抗一个具体现象：**模型会把强约束悄悄降级为建议**。一句"你应该先做设计"，在模型面对"这个太简单了吧"的自我说服时是不堪一击的；而一个带标记的、措辞绝对的 GATE，更难被无声绕过。

**代价**：它是**装饰性**的，没有强制力。一个决心绕过的模型照样可以绕过——它只是增加了概率上的阻力。

**备选方案**：
- *普通段落写规则* —— 被否决。在与"这次不一样"的合理化冲动对抗时，语气强度就是有效性。
- *靠 description 里的 MUST 表达* —— 不够。description 只影响"是否触发这个技能"，管不住"触发之后是否守规矩"。

### 决策二：专门写一节「反模式」来封堵逃避路径

**选了什么**：在 HARD-GATE 之后立刻跟一节 *Anti-Pattern: "This Is Too Simple To Need A Design"*。

**为什么**：这一节是**预判式防御**。它把模型最可能的逃避路径提前命名、提前驳斥：

> *"Simple" projects are where unexamined assumptions cause the most wasted work.*

注意它给的出路**很巧妙**：不是"简单项目也要写长设计"，而是——

> The design can be short (a few sentences for truly simple projects), but you MUST present it and get approval.

**降低服从成本，而不是放宽要求**。这让"跳过设计"失去了唯一的合理性借口：既然简单项目的设计只需几句话，那"太简单所以跳过"就不成立了。这是**把借口的经济学基础抽掉**，而不是硬碰硬地禁止借口。

**代价**：文档变长，且这节对"真的极其简单"的场景仍是净负担——一次改配置也要走完 9 步清单。

### 决策三：一条消息只问一个问题

**选了什么**：*"Only one question per message - if a topic needs more exploration, break it into multiple questions."*

**为什么**：核心考量是**用户注意力的质量**。一次问 6 个问题，用户容易只答前两个、或者对后面的问题给出低质量的回答，而 AI 无法分辨"这个回答含糊"和"用户没认真想"。

一次一问还带来一个隐性好处：**每个回答都能影响下一个问题**。用户的答案可能让某个后续问题变得不必要，或者引出一个原本没想到的方向——批量提问会锁死问题集合，一问一答则保留了这种演化能力。

**代价**：**来回次数显著增加**。如果问题空间有 10 个决策，就是 10 个来回。这在长会话中会累积成可观的时间成本。

> **直接对照**：`grilling` 在这一点上做了**相反**的押注——它的铁律是"一轮问完整条前沿（一次 4-6 个问题）"，理由是前沿上的问题彼此无依赖、用户可以在一次阅读中处理完，用编号和结构化排版控制认知负载。
>
> 两者的赌注可以这样概括：
>
> | | brainstorming | grilling |
> |---|---|---|
> | 押注 | 用户注意力**质量**优先 | 交互**次数**优先 |
> | 手段 | 一次一问，逐题演化 | 批量问，整层推进 |
> | 代价 | 来回多 | 用户可能漏答或答得草率 |
>
> 没有普适的赢家：问题空间大且互相独立时 grilling 更省时；决策彼此纠缠、需要逐个演化时 brainstorming 更稳。

### 决策四：必须提出 2-3 个方案

**选了什么**：*"Propose 2-3 different approaches with trade-offs"*，并且要求**先讲推荐的**。

**为什么**：这是对"锚定效应"的对抗。如果 AI 直接给出一个方案，讨论就变成了**围绕那一个方案修修补补**，而"其实有更好的方向"这件事根本不会被提出。

2-3 个方案的作用不是让你挑，而是**把设计空间显式地摊开**——看到 A、B、C 之后，你可能既选 A 又想到 D。

**为什么"先讲推荐的"**：这是一个微妙的排序决策。先讲推荐方案能让用户最快进入决策状态（可以直接同意），但如果把推荐放最后，用户会被前两个方案的细节带偏、在比较中消耗注意力。**推荐前置 + 理由紧跟**，把最高信息密度放在最前面。

**代价**：提出 3 个方案比提出 1 个要多花可观的 token 和时间，而且其中 2 个注定被否决。

### 决策五：把终态**写死**成"调用 writing-plans"

**选了什么**：*"The ONLY skill you invoke after brainstorming is writing-plans."*——并明确点名禁止 frontend-design、mcp-builder 等。

**为什么**：brainstorming 结束时，模型正处于**"跃跃欲试想动手"**的状态——它刚刚把设计想清楚了，"接下来去实现"对它来说是极其自然的冲动。此时任何开放式的下一步表述，都可能被它自行展开成**实际的实现动作**。

把终态写死成一个具体技能名之后，这条路径变成**机械的、没有解释空间的转发**——模型没有机会在这里做判断，也就没有机会做错的判断。

**代价**：灵活性丧失。如果某个场景确实应该在设计后直接跳到别的技能，这个写死的规则会拦一下（需要人来手动引导）。

### 决策六：分段呈现设计，每段确认

**选了什么**：*"Ask after each section whether it looks right so far."*

**为什么**：对抗**草率批准**。一份完整设计一次性甩给用户，用户要么不读就批准，要么读到第三段才发现第一段就错了——此时前面两段的理解都已白费。

分段确认把"批准"这个动作拆成若干小份，每份的审查成本低到用户真的会看。这是**增量验证**的一般原则在对话里的应用。

**代价**：交互次数增加；而且如果设计本身很短，"分段"就显得形式主义。

### 决策七：两道关——机器可查的归自审，理解归用户

**选了什么**：写完规格后先做**规格自审四查**（占位符 / 内部一致性 / 范围 / 歧义），再由**用户审阅**。原文明确这两步是分开的，且自审"不需要再复审一遍，修完就走"。

**为什么分两道**：四查里的前三项是**格式与逻辑**问题（有没有 TODO、前后是否矛盾、范围是否合适），这些 AI 自己就能可靠地查出来。第四项"歧义"介于两者之间。

而真正需要人来做的，是判断**"这是不是我要的东西"**——这个 AI 无论如何自查都答不了。

所以分工是：**AI 清掉机械缺陷，把干净的版本交给用户做理解层面判断**。如果顺序反过来（先给用户看不干净的版本），用户会被格式问题分心，浪费在"帮我看看"上的注意力。

**四查为什么是这四项**：它们对应四种**不同层级**的缺陷——

| 检查 | 缺陷类型 | 一句话 |
|------|---------|--------|
| 占位符扫描 | **没写完** | 有 TBD／TODO／含糊需求 |
| 内部一致性 | **写错了** | 小节之间互相矛盾 |
| 范围检查 | **写多了/写少了** | 超出或不足一份计划 |
| 歧义检查 | **写糊了** | 同一需求可被两种方式解读 |

其中**歧义**是最贵的一项：含糊的需求会一路带到实现阶段才暴露成返工，而那时代价已经大得多。

### 决策八：范围评估必须**先于**细节提问

**选了什么**：*"Before asking detailed questions, assess scope."* 如果请求描述了多个独立子系统，立刻标记，不要花问题去打磨细节。

**为什么**：这是对**沉没成本**的防御。如果没有这一步，AI 会热情地开始问第一个子系统的细节，问了 8 个问题之后才发现"这其实是四个项目"。此时用户已经投入了大量注意力，很难接受"我们得从头分解"。

前置范围检查把这个问题挪到了成本最低的位置——**一个问题都还没问的时候**。

**代价**：需要在信息很少时就做判断，可能误判（把一个大项目当成一个，或反之）。

### 决策九：可视化伴侣的"独立消息"约束

**选了什么**：提议启用可视化伴侣的消息，**必须只包含那条提议**，不能与任何其它内容合并。

**为什么**：这是把**元决策**和**实质决策**分离。混在一起时，用户会把它当成一个顺口答掉的选项，而不是真正做出"要不要启用这个 token 消耗较大的功能"的判断。

同时这也保护了那次征求同意的**有效性**——用户是真正在被问"要不要"，而不是在回答别的什么时顺手略过。

**代价**：多一次交互往返，而且对纯文本项目（不需要浏览器）来说这一步是空转。

## 3. 机制如何运转

```
探索项目上下文
      ↓
评估范围 ←── 若发现多子系统，先分解，再对第一个子项目走本流程
      ↓
（若涉及视觉问题）独立一条消息提议可视化伴侣
      ↓
提出澄清问题（一次一个）──────┐
      ↓                      │ 每个回答可能
提出 2-3 方案（推荐前置）      │ 改变后续问题
      ↓                      │
分段呈现设计 → 用户逐段确认 ───┘（不通过则退回）
      ↓
撰写规格文档 + 提交 git
      ↓
规格自审四查（就地修复）
      ↓
用户审阅规格 ──要求修改──→ 回到自审
      ↓ 批准
调用 writing-plans（唯一允许的终态）
```

关键约束有两条，都容易违反：

1. **"一条消息只问一个问题"** —— 违反的表现是 AI 忍不住把 3 个相关问题打包问出去。理由总是"它们关联性很强"，但那正是应该拆开的信号。
2. **"终态只能是 writing-plans"** —— 违反的表现是 AI 在设计批准后"顺手"开始写代码。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 需求**极其简单**（改一处配置） | 9 步清单 + HARD-GATE 的流程成本远超收益 | 反模式那一节虽然允许"几句话的设计"，但**流程步骤数不会随之减少**——它降的是内容量，不是仪式量 |
| 用户**不看就批准** | 分段确认退化成橡皮图章，整个验证层失效 | 该机制完全依赖用户真的会读；AI 无法察觉"这次批准没经过思考" |
| 问题空间**大且互相独立** | 来回次数爆炸（10 个决策 = 10 个来回） | "一次一问"的固有代价，且没有"何时该转批量"的判据 |
| 探索中途**才发现要分解** | 前面问的问题白问，用户注意力白费 | 前置范围评估只基于很稀的信息，可能漏判 |
| 规格写成后**后续无人再读** | 规格退化成一个仪式产物，与实现脱节 | 技能能保证"写出来"，无法保证"被使用" |
| 用户**不知道自己要什么** | 2-3 个方案都不合意，但用户也说不清哪里不合意 | 设计立场假设"看到选项能判断"；这个前提不成立时，同一轮会反复空转 |
| 与 `grilling` 类技能**混用** | 提问节奏在"批量"和"一次一问"之间摇摆，用户体验割裂 | 两套技能的节奏铁律直接冲突，同时激活会互相干扰 |

> **最值得注意的是第一条与最后一条。**
>
> 第一条暴露了这个技能的一个**尺度缺陷**：它对"复杂度"的适应只体现在设计文档的篇幅上，流程步骤本身是刚性的。HARD-GATE 那句 "regardless of perceived simplicity" 是刻意的——但它同时也意味着**简单项目要为一个不存在的风险付流程成本**。
>
> 最后一条是跨套件混用的真实风险：`brainstorming` 和 `grilling` 都在解决"实现前想清楚"，但**提问节奏的哲学相反**。同时启用它们，用户会经历"一个问题一个问题答"和"一次答一堆"的来回切换，认知负担反而比只用一套更大。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **后继** `writing-plans` | 唯一允许的终态。设计批准后必须交给它 |
| **前置** `using-superpowers` | 那条"任务前必须先调技能"的元规则，是 brainstorming 能被唤起的前提 |
| **被取代**（部分场景） | grill 系列的 `grill-with-docs` 覆盖了"想清楚"这一层，但不产出实现计划、不管 TDD 与评审——两者目标不同，不是替代关系 |
| **对立** `grilling` | 提问节奏的正面对立：一次一问 vs 整条前沿批量问。这是两套系统最实质的设计分歧 |
| **同族** `writing-skills` | 后者是"写技能"的元技能，本技能是"写设计"的流程技能，都用"先探索后产出"的结构 |
| 与 `using-git-worktrees` 的时序 | 隔离工作区在**设计批准之后、写计划之时**创建，不在 brainstorming 期间 |
