## 1. 它解决什么问题

它对付的是**技能质量的静默失败**。

一个坏掉的程序会报错、会崩、会有测试变红。**一个坏掉的技能不会。** 它安安静静地待在磁盘上，被加载、被读到、被忽略——或者更糟：被读到、被误解、被以一种看起来很合理的方式错误执行。没有任何信号告诉你它坏了。你只会在某次真正需要它的时候，发现纪律没有被执行，而那时你无法回溯到底是哪一环失效了。

这个问题的根源在于：**写技能看起来是"写作任务"**。而写作没有正确性可言——只有清晰和优美。于是"这个技能写好了吗"这个问题，退化成"这份文档读起来清楚吗"。

**设计立场**：把技能文档重新定义为**工程产物**，并给它一个**可检验的正确性标准**——**这个技能是否真的改变了 agent 的行为**。

这个标准看起来朴素，但它是一个根本性的转换：一份读起来极其清晰、逻辑严密、排版精美的技能文档，如果 agent 在没有它的时候也这么做，那么**它的价值是零**。而这个事实**只能通过测试发现**，读文档是读不出来的。

> 这正是"写技能就是为流程文档做 TDD"这句话的全部力量所在——它不是打比方，而是**引入了一个正确性判据**。

## 2. 核心设计决策

### 决策一：用 TDD 类比重新定义整个任务

**选了什么**：把技能创建的每一步都映射到 TDD 的一个概念上（一张 12 行的对照表），并把技能文档称为"生产代码"、压力场景称为"测试用例"。

**为什么**：这是整份技能的**组织原则**，其价值远不止"类比好记"。它做了三件事：

1. **引入正确性判据**。TDD 的核心主张是"没看着测试失败，你就不知道测试是否在测对的东西"。移植过来就是："没看着 agent 在没有技能时犯错，你就不知道这个技能教的是不是对的东西。"
2. **把"写什么"交给测试决定**。RED 阶段的产出不是"确认会失败"，而是一份**逐字记录的借口清单**。这份清单成为 GREEN 阶段的**需求**。技能的内容因此由观察到的失败决定，而不是由作者的想象决定。
3. **让编辑也受约束**。TDD 的纪律是对**每次改动**生效的；类比一旦成立，"只加一节"这种改动也必须先有失败测试——这就堵住了最常见的松动点。

**代价**：类比有边界。代码的失败是**二元的**（测试红或绿），而"agent 是否遵循了技能"往往是**程度问题**。这个差异在第 4 节展开。

### 决策二：铁律，且明确扩展到"编辑已有技能"

**选了什么**：`NO SKILL WITHOUT A FAILING TEST FIRST`，并特别写明"这同时适用于新建技能和对已有技能的编辑"，还列举了三条不许开的例外（简单补充／只加一节／文档更新）。

**为什么**：**"只加一节"是最危险的改动**。它在心理上不像"写一个新技能"那样正式，容易被当成顺手的事。但一个未经测试的新章节可能**改变整个技能的行为**——比如新增一段措辞松动的话，把原本被堵死的漏洞重新打开。

这是纯粹的 TDD 逻辑：新代码需要测试，**新增的代码也是代码**。改动的大小与是否需要验证无关，因为风险来自"新引入的未验证内容"，而不是来自"改了多少行"。

**代价**：编辑成本显著上升。改一个错别字、修一处格式，按字面也需要先跑基线测试——而这在实践中显然不成比例。原文用"不为文档更新开例外"把这条咬得很死，但没有给出**按风险分级**的余地（比如"只修正错别字可以例外"）。这是一个为了杜绝钻空子而牺牲了合理性的设定。

### 决策三：description 只写触发条件，绝不概括工作流

**选了什么**：反复强调三遍——description **只**描述何时使用，**绝不**概括技能的过程或工作流。

**为什么**：这一条背后有**一次真实的对照测试**，是整个技能里最有实证分量的部分：

> 一个 description 写着"任务之间做代码评审"，导致 Claude 只做了**一次**评审——尽管技能里的流程图明确画的是**两次**（规格合规性，然后是代码质量）。
>
> 改成"在执行含独立任务的实现计划时使用"（去掉工作流概括）之后，Claude 正确读了流程图并执行了两阶段评审。

这个发现的意义超出了"该怎么写 description"：**description 会取代正文**。它成了 AI 心里的"技能摘要"，一个它以为足够的替代品。于是你写进 description 的每一个工作流细节，都是在**主动提供一个跳过正文的理由**。

这解释了为什么这条规则的措辞如此绝对——它不是风格偏好，而是被测试证实的因果机制。

**代价**：这个发现是**对特定模型版本的经验观察**。模型对 description 的处理方式会随版本变化，而这个技能把一条经验规律固化成了硬规则。一旦底层行为改变，这条规则会从"关键防护"变成"无意义的约束"，而技能本身没有机制去重新检验它。

### 决策四：禁止 `@` 链接，只允许带标记的交叉引用

**选了什么**：引用其他技能时只用技能名 + 明确标记（`**REQUIRED SUB-SKILL:**`），**绝不**用 `@` 路径语法。

**为什么**：原文给了具体数字——`@` 语法会**立刻强制加载**文件，"在你还没需要它们之前就消耗掉 200k+ 的上下文"。

这一条的真正含义是：**交叉引用应当是"指针"而不是"内容"**。技能之间需要能互相指路（否则用户不知道该看哪个），但绝不能自动带上货。`@` 语法把"指路"变成了"搬运"。

而要求加上 `**REQUIRED SUB-SKILL:**` 这类标记，解决的是另一个问题：纯文字引用（"见 xxx 技能"）不表达**强制性**。读者无法判断这是"相关阅读"还是"你必须先读"。标记把引用分成了有语义等级的两类。

**代价**：不用 `@` 意味着加载是**两步**的——先读到引用，再手动调用。多一跳，而在"严格执行"的场景下这一跳可能被跳过（于是该读的没读）。另外，禁用 `@` 与许多文档工具的惯例相冲突（在 Obsidian 等工具里 `[[链接]]` 是常规做法），跨工具协作时需要额外说明。

### 决策五：四类技能，四套测试标准

**选了什么**：纪律强制型、技术型、模式型、参考型，各自定义"怎么测"和"什么算成功"。

**为什么**：如果只有一套标准，"测试技能"就只对纪律型技能有意义——因为只有它们有明确可判定的"违规"（做了 TDD 还是没有）。其余三类会陷入"不知道怎么算测过了"。

这一节的工作是**为每种类型定义它的失败模式**：

| 类型 | 失败长什么样 | 成功标准 |
|------|-------------|---------|
| 纪律强制型 | 压力下违规 | 最大压力下仍遵循 |
| 技术型 | 用错、漏掉边界 | 能应用到新场景 |
| 模式型 | 该用时没认出来 | 能正确识别何时用/不用 |
| 参考型 | 找不到信息 | 找到并正确应用 |

这个分类的实际用途是：**它让"测试"这个动作对每种技能都变得可执行**。没有它，作者会在"参考型技能怎么测"这一步停下来，然后跳过整个测试环节。

**代价**：模式型和参考型的成功标准仍然相当模糊——"能正确识别何时应用"怎么判定？不如纪律型的"在压力下有没有违规"那样二元可判。这四套标准里，只有第一套是真正硬性的。

### 决策六：把说服原则作为显式依据

**选了什么**：明确引用社会心理学的说服研究（Cialdini；Meincke et al.），并提供了 `persuasion-principles.md` 作为研究基础。

**为什么**：这一节直接承认了一个不舒服的事实——**技能文档本质上是说服文本**。

作者没有假装"好的文档自然会被遵循"，而是承认：**在压力下，合乎逻辑的指令也会被绕过**。因此需要额外的说服手段——权威（引用官方要求）、承诺（要求声明）、稀缺、社会认同、统一性。

这解释了几种看起来奇怪的写法：
- 全大写、`<EXTREMELY-IMPORTANT>` 标签 → **权威信号**
- "REQUIRED SUB-SKILL" → 明确强制等级，不给自由裁量
- 逐字列出借口并反驳 → 让对方在**说出借口时**就认出自己（承诺 + 自我一致性）

原文用一句话划定了伦理边界：*"不是要操控，而是确保关键实践在压力下仍被遵循。"*

**代价**：**这条边界是自我声明的，没有外部校验**。"确保遵循"和"操控"在手法上是同一批（都是利用说服原则），区别只在于**目的是否正当**——而"目的是否正当"由谁判定？这套技能在实践中无法回答这个问题。一个恶意设计者可以用完全相同的技术，让人（或 AI）去做不该做的事。**技能作者引用了一项可用于操控的技术，并以"我的意图是好的"作为区别。**

### 决策七：STOP——禁止批量创建技能

**选了什么**：写完任何技能之后必须停下，完成部署流程；明确禁止"不做测试就批量创建多个技能"。

**为什么**：这是 TDD 里同一模式第三次出现（前两次：一次只写一个测试、一次只动一个变量）。理由也一致：批量操作会让**"哪一个没通过"变得无法判断**。

而在这个场景下还有额外一层：技能的质量问题是**静默的**。一个批量产出的技能集合里，某个技能失效不会产生任何错误信号——它只会在未来某次使用时，让纪律静默地不生效。

**代价**：效率。批量创建在机械性工作上确实更快，而这条禁令不给"这个技能很简单、我确信它没问题"留余地——尽管那种情况确实存在。

### 决策八：Token 效率作为一等约束

**选了什么**：给出字数目标（getting-started 工作流 <150 词、频繁加载的技能 <200 词、其他 <500 词），并提供具体的压缩技法（把细节移到 `--help`、用交叉引用代替重复、压缩示例）。

**为什么**：因为它讨论了**一个不对称的成本结构**：频繁加载的技能会进入**每一次**对话。一个 1000 词的技能，成本是 1000 词 × 你此后的每一次对话。

这个约束反过来塑造了技能的形态——它解释了为什么 Superpowers 的技能普遍**极度精炼**，为什么细节被反复外置到附属文件，为什么 description 要写得那么克制。

**代价**：简洁与完整性直接冲突。压缩到 200 词的技能可能丢掉必要的边界说明，而在实际使用中这个缺失不会立刻暴露。**读文档的人感觉不到少了什么，因为他们不知道少了什么。**

## 3. 机制如何运转

```
RED —— 写失败测试
   ├─ 设计压力场景（纪律型：3 种以上叠加压力）
   ├─ 在没有技能的情况下跑（用 subagent）
   ├─ 逐字记录 agent 的行为与借口
   └─ 从借口里归纳出模式
        ↓
      【这份借口清单 = GREEN 阶段的需求】
        ↓
GREEN —— 写最小技能
   ├─ name / description（Use when...，不概括工作流）
   ├─ 针对 RED 里发现的**具体**违规写内容
   ├─ 一个优秀示例（不是多语言）
   └─ 用同样的场景跑（此时有技能）→ 应当遵从
        ↓
REFACTOR —— 堵漏洞
   ├─ 找出**新的**合理化
   ├─ 加明确回击 / 补进合理化对照表 / 补进红旗清单
   ├─ 更新 description 加入"即将违规"的症状
   └─ 重新测试，直到无懈可击
        ↓
【STOP】不许在未验证时进入下一个技能
```

**最容易违反的约束**：RED 阶段的"**在没有技能时跑**"。跳过它的诱惑极大——你已经知道该写什么了，为什么要先花时间跑一个注定失败的东西？

但跳过 RED 会导致一个具体的后果：**GREEN 阶段失去需求来源**。你不再知道该堵哪些漏洞，于是只能凭想象写一份"看起来完整"的技能。而那种技能的全部问题，恰恰在于**它看起来完整**。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **测试成本高** | 整个流程被跳过，Iron Law 形同虚设 | 铁律靠自律执行，没有任何强制力。设计压力场景 + 跑 subagent + 逐字记录，是重活 |
| 缺少 **subagent 支持** | 无法执行 RED/GREEN 的核心步骤 | 测试方法论要求"用 subagent 跑压力场景"——`executing-plans` 里已明确提到"不是所有平台都有 subagent" |
| **"违规"难以判定**（模式型/参考型技能） | 只能凭感觉判断测没测过 | 只有纪律型技能有二元可判的失败；其余三类的成功标准是程度判断 |
| 压力场景**设计不出来** | RED 阶段空转，或测了个无关的东西 | 原文要求"3 种以上叠加压力"，这需要真实理解 agent 在什么情况下会失守 |
| CSO 那条**经验发现过时** | 硬规则变成无意义约束，或反之失去防护 | "description 概括工作流 → AI 走捷径"是对特定模型版本的观察，模型行为会变 |
| 测试**只覆盖想得到的情况** | 未预料的借口第一次出现时防御为零 | 合理化对照表本质上是**已见借口的清单**，对未见借口无效 |
| **说服技术的伦理边界** | 同样的技术可用于操控 | 边界靠作者自我声明（"不是要操控"），无外部校验 |
| 与**其他文档工具**冲突 | `@` 禁令、`[[ ]]` 惯例不一致 | 禁用 `@` 是本项目的规则，跨工具协作时需额外说明 |

> **最值得注意的是一、二两行的组合。**
>
> 这份技能对**技能文档**施加了和 TDD 对代码一样严格的要求：必须测试、必须看到失败、不许批量。但它的**执行机制和 TDD 完全一样——靠自律**。
>
> 区别在于代价。跳过 TDD 的后果会在几分钟内显现（代码出 bug）；跳过技能测试的后果**可能在几周后才显现**，而且以静默的方式显现（某个技能在关键时刻没生效，而你归因于"AI 今天状态不好"）。
>
> 更麻烦的是**反馈链的断裂**：这份技能自己规定了"技能必须被测试"，但它**没有办法验证"技能作者是否真的做了测试"**。一份没有测试过的技能文档，和一份测试过的，在磁盘上完全一样。这是一个**无法自我执行**的规则。
>
> 第二行揭示了一个更实际的门槛：整套测试方法论依赖 subagent。而在没有 subagent 的环境里（原文在 `executing-plans` 里明确承认这种平台存在），这份技能最核心的 RED/GREEN 步骤**根本无法执行**——留下的只有写作规范。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **依赖** `test-driven-development` | 明确列为 **REQUIRED BACKGROUND**——本技能是它的适配版，不理解 TDD 就无法理解本技能 |
| **产出了**其它所有技能 | Superpowers 的 14 个技能都应由本技能的方法论创建/验证 |
| **解释了**各技能的合理化对照表从哪来 | `systematic-debugging`、`test-driven-development`、`using-superpowers` 里那些对照表，都是本技能 RED 阶段的产物 |
| **被** `using-superpowers` **反向约束** | 后者也是技能，也受本技能规范约束；两者的关系是自指的（元规则也要遵守规则） |
| 与 `grill` 的 `domain-modeling` 呼应 | 两者都强调"**把结论落成持久文件**"——一个落成技能，一个落成术语表/ADR，都是对抗对话易逝性 |
