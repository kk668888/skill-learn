## 1. 它解决什么问题

表面上它对付的是"代码没测试"，但那不是真正的失败模式——真正的失败模式更隐蔽：

**测试写完了，立刻通过，于是你以为它验证了什么，其实什么都没验证。**

一个立刻通过的测试，可能是：测错了对象、测的是实现细节而非行为、或者覆盖了一个你本来就写对的分支。它给你**置信度的错觉**，而错觉比没有置信度更危险——你会基于它放心地重构、放心地合并。

这个失败模式有个关键性质：**它从外部看不出来**。你没法通过读代码判断一个测试"是不是真的在检验东西"——它看起来和有效的测试一模一样。唯一的证据来自它的**历史**：你有没有见过它失败。

更麻烦的是，这个失败模式有一个稳定的产生路径：**先实现，后补测试**。这条路走起来极其自然——实现的时候你满脑子都是"怎么让它工作"，等它工作了再补测试，而这时你对实现的记忆会让测试不自觉地**围绕实现写**，而不是围绕需求写。

**设计立场**（这是理解整个技能的关键）：它假设执行者——不管是人还是 AI——会在压力下**持续地、创造性地合理化**，为跳过环节找理由。所以它不给规则留任何解释空间，并额外准备了一张**预先写好的反驳库**。

> 换句话说：这个技能的设计前提不是"人不懂 TDD 的好处"，而是"人懂，但会在具体情境里说服自己这次可以例外"。对抗后者的方式和对抗前者完全不同——不能靠讲道理，只能靠把后门焊死。

## 2. 核心设计决策

### 决策一：把铁律绝对化，不给任何场景留例外

**选了什么**：`NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST`——没有失败测试就不许有生产代码。原文用的词是 "Iron Law"（铁律）、"No exceptions"。

**为什么不分场景给例外**：因为"这次情况特殊"正是**所有**违规的统一入口。一旦规则变成"通常要这么做，但简单改动可以免"，执行者就获得了一个需要每次重新判断的许可——而判断的时刻恰恰是判断力最弱的时候（赶时间、自以为想清楚了、代码看起来很简单）。

把它绝对化之后，"要不要遵守"不再是一个决策点。原文甚至专门堵了最常见的那句合理化：`"This Is Too Simple To Need A Test"`。

**代价**：真正的探索性编码会被卡住。探索阶段你本来就想先随便试试、快速看结果，而铁律要求你先写测试。

**原文的缓解方式**：承认三类例外——用完即弃的原型、生成的代码、配置文件——但要求**先问搭档**。注意这三类的共同特征：它们要么**不是代码**（生成物、配置），要么**不会留下**（原型）。它没有给"简单""赶时间""我很确定"留位置。把例外限定在"产物属性"上而不是"主观判断"上，是为了让例外本身也无法被合理化利用。

### 决策二：把"亲眼看到失败"设为强制——这是整个技能的灵魂

**选了什么**：写完测试必须**运行它并观察失败**（Verify RED，原文标注 `MANDATORY. Never skip.`），而且失败的方式必须正确。

**为什么这是灵魂**：它是对"测试立刻通过"这个失败模式的**唯一解药**。逻辑链条是：

```
测试通过   → 只能说明"当前状态下它不报错"
             （可能测错对象、可能测的是实现、可能漏了边界）
测试失败   → 说明"这条测试确实依赖某个还不存在的东西"
             → 于是它确实在检验那个东西
```

而且原文对"失败"做了细分：**失败（fail）不等于报错（error）**。报错说明测试自己有 bug（拼写、引用错误），只有"因功能缺失而失败"才证明测试→功能这条链路真实存在。这个区分非常精确，因为一个写错的测试**也会以报错的方式"不通过"**——如果不区分，你会误以为它验证过了。

**它还顺带解决了覆盖率幻觉**：100% 覆盖率完全可以是 100% 空转。覆盖率衡量"执行到的代码行数"，不衡量"这些行的行为被验证了吗"。强制看红，是把"验证的有效性"从不可观测变成可观测。

**代价**：每个循环多两次命令执行；在测试慢的环境里成本显著，这也成了后面失效分析里的第一条实际约束。

### 决策三：`Delete means delete`——正面处理沉没成本

**选了什么**：先写了代码后补测试？**删掉代码，从头再来**。而且不许留作参考、不许"改编"、不许看。

**为什么连"参考"都不许**：这不是洁癖，是针对一条具体的自欺路径——

```
"我留着它当参考，然后按 TDD 补测试"
  ↓ 实际发生的是
你照着已知的实现去写测试
  ↓ 这等价于
事后补测试，只是分了两步走
```

"改编现有代码"同理。所以禁止保留、禁止查看，本质是**让这个后门在物理上不存在**。

**它的深层对抗对象是沉没成本谬误**。原文对这笔账算得很直接：

> *The "waste" is keeping code you can't trust.*（真正的浪费是留着你不能信任的代码。）

它把"删掉几小时工作"重新定义成不是浪费——因为那些时间已经花掉了，无法追回；而现在真正的选择是"再花 X 小时得到高置信度"还是"省 30 分钟但拿到一份不可信的代码"。

**代价**：这是全篇心理冲击最大的一条。对已经完成的工作按下删除键，需要执行者在当下就接受"沉没成本不是成本"——而这件事在情绪上极难。

### 决策四：预先写好"合理化对照表"——最独特的设计

**选了什么**：一张 11 行的表，左列是**借口的原文**（"太简单了不用测"、"我先写完再补测试"、"删掉 X 小时太浪费"⋯），右列是逐条反驳。

**为什么这是全篇最精妙的设计**：注意它对抗的到底是什么。

它的敌人不是"不懂 TDD 价值的人"——那种情况讲道理就够了。它的敌人是**"懂，但在具体情境里说服自己这次例外"**。而对这种敌人，讲道理完全无效：道理你在冷静时全都同意，可借口是在**情境中**产生的，那时你的判断力最弱。

对照表的作用是**把判断降级成查表**：

| 没有对照表 | 有对照表 |
|-----------|---------|
| "这次是不是可以不测？让我想想⋯" | "『太简单了』→ 表里第 1 条 → 简单的代码也会坏" |
| 需要临场做一次价值判断 | 只需字面匹配 |
| 判断力最弱时做判断 | 在冷静时就把结论固化好了 |

**为什么表里写的是"借口原文"而不是抽象原则**：因为它需要能被**字面匹配**到当时脑子里的那句话。如果写成"应当坚持测试先行"，你在心里说的是"这个函数太简单了"，匹配不上；写成"『太简单了不用测』→ 简单的代码也会坏"，才能直接命中。

**代价**：对照表只能覆盖已列出的借口。遇到表外的新借口（比如"这次是 AI 生成的所以⋯"），机制失效。而且 11 条已经接近上限——再长就从"反驳库"变成"说教"，被跳过。

### 决策五：把"字面即精神"写成硬条款

**选了什么**：`Violating the letter of the rules is violating the spirit of the rules.`（违反规则的字面，就是违反规则的精神。）

**为什么必须写出这么一句**：因为"精神 vs 字面"是**所有规则失效的通用后门**。"我遵守的是精神，不是字面"——这句话可以把任何规则软化到失效，而且说话人往往真诚地相信自己在遵守精神。

这个技能里它尤其致命。因为 TDD 的"精神"（写出可信的测试）恰恰**只能通过字面**（看到红）来保证。一旦允许"我理解了精神所以可以省略执行细节"，决策二的整个机制就崩了——而崩掉之后你**看不出**它崩了（测试还是绿的）。

**代价**：放弃了对真实特殊情况的适应能力。如果确实存在一个合理的、原文没预料到的例外，这条规则不允许你自行判断——你只能去问搭档（原文的例外条款正是这么规定的）。

### 决策六：把测试的质量也规则化

**选了什么**：一张 "Good Tests" 表，三个维度——Minimal（一件事，"名称里有 and 就拆开"）、Clear（名称描述行为）、Shows intent（演示期望的 API）。

**为什么**：这是防**第二种自欺**。决策一到五防的是"不写测试"，但还有一条更隐蔽的路径：**写了测试，数量也够，但质量差**——一个测了三件事的巨型测试、一个叫 `test1` 的测试、一个把实现细节写进断言从而一重构就碎的测试。这些都能让覆盖率好看，却提供不了置信度。

把质量标准也写进技能，等于把"什么算做完"从主观判断（"测试写了"）变成了可核对的清单。

## 3. 机制如何运转

```
RED ── 写一个最小的失败测试（一件事、名称清晰、用真实代码）
 │
 ▼
验证 RED ── 运行，确认失败
 │            ├─ 通过了？→ 你在测已有行为，改测试
 │            ├─ 报错了？→ 修测试本身，重跑
 │            └─ 因功能缺失而失败 → 继续
 ▼
GREEN ── 写最小量代码让它通过（不加功能、不重构别的）
 │
 ▼
验证 GREEN ── 运行，确认通过且其他测试仍绿、输出干净
 │
 ▼
REFACTOR ── 消除重复、改善命名（保持绿色，不新增行为）
 │
 └──→ 下一个失败测试
```

**最容易被违反的约束**：两个 `MANDATORY` 标注的验证步骤。它们不产生任何可见产物（没有新代码、没有新测试文件），所以省略它们**从结果上完全看不出来**——这正是它们最危险的地方。

注意 REFACTOR 的位置：它**只在绿了之后**才允许。这不是流程洁癖，而是因为"绿"是重构的安全网；在红的时候重构，你无法区分"重构改坏了"和"本来就没通过"。原文还追加了一句 `Don't add behavior`——重构阶段不许顺手加功能，否则你就把 RED 跳过了。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **存量代码没有测试** | 很难"先红"——你不确定正确行为是什么 | 铁律假设"新功能"，而在遗留代码上往往是先理解行为才能写断言 |
| **测试套件很慢** | 每个循环两次运行的成本高，跳过的诱惑急剧上升 | 决策二强制两次验证，代价与测试耗时成正比 |
| **需求本身模糊** | 写不出断言，于是"先写测试"卡在原地 | 测试先行要求"该做什么"已知；需求不清时它无法启动 |
| **UI / 视觉 / 交互类产物** | 断言困难，"通过"的定义模糊 | 机制依赖可自动判定的失败信号；像素和手感难以断言 |
| **强时间压力下** | 合理化对照表被无视 | 对照表降低判断成本，但不消除动机；压力足够大时人会跳过整张表 |
| **异步 / 时间相关逻辑** | 容易滑向 mock，进而触发反模式 | 需要控制时间与并发，mock 是自然选择，而 mock 会掩盖真实行为 |
| **"我确信这是对的"** | 直接写实现 | 这是最经典的入口，也正是对照表第 3、9 条针对的对象 |
| **测试真的很难写** | 被当作困难绕过，而不是设计信号 | 原文主张"难测 = 难用"，但这需要执行者把障碍读成信号 |

> **最值得注意的是第一条和最后一条。** 铁律的绝对性在**遗留代码**场景下会产生真实摩擦：那里"先写一个失败测试"往往不成立，因为你还不知道正确行为是什么。原文给出的路径是"给现有代码补测试"，但这实际上要求你先**反推**出行为——比新功能难得多。
>
> 最后一条则暴露了一个前提假设：这个技能只能**指出**"难测 = 难用"，无法**迫使**你去改设计。如果你把"难测"读成"这个不好测所以跳过"，机制不会拦住你。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **被** `subagent-driven-development` **要求** | 每个实现 subagent 都必须按 TDD 工作；这是它在自动化流程里的主要落点 |
| **被** `writing-plans` **结构化** | 计划的"2-5 分钟粒度"正是 TDD 微循环：写失败测试 → 跑它确认失败 → 写最小实现 → 跑它确认通过 → 提交 |
| 与 `verification-before-completion` 的分工 | **TDD 验证"代码是否正确"，后者验证"任务是否真的完成"**。两者的铁律形式相同（都是"没有证据不许宣称"），但对象不同：一个针对单元行为，一个针对完成状态 |
| 与 `systematic-debugging` 的衔接 | 发现 bug → 先写一个复现它的失败测试 → 走 TDD 循环。这样测试既证明修复有效，又防止回归 |
| 与 `testing-anti-patterns.md` 的分工 | 反模式清单是**事后验尸工具**：用来判断"我这次是不是其实没做 TDD"（测了 mock、加了测试专用方法等，全是没看红就先 mock 的后遗症） |
