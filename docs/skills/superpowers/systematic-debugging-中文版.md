## frontmatter

- **name**：`systematic-debugging`
- **description**：当遇到任何 bug、测试失败或意外行为时使用——在提出修复方案之前。

> **批注**：注意 description 只写了**何时使用**（encountering any bug... **before proposing fixes**），完全没说这个技能做什么、有四个阶段、要建测试用例。这不是偷懒。`writing-skills` 里有一节专门解释为什么——**如果 description 概括了工作流，AI 会照着 description 走捷径，而不去读技能正文**。正文一旦被跳过，里面那套四阶段流程就形同不存在。"before proposing fixes" 这个时间点是精心选定的：它卡在"看到问题"和"动手改"之间那道缝上，而那正是最容易冲动的位置。

## Overview

随机的修复浪费时间，还会制造新 bug。快速打补丁会掩盖底层问题。

**核心原则：** 在尝试修复之前，**永远**先找到根因。修复症状即是失败。

**违反本流程的字面，就是违反调试的精神。**

> **批注**：最后那句话是刻意布置的**防御性条款**，专门用来堵住一整类辩护——"我当然尊重这个流程的精神，只是这次情况特殊，不必拘泥字面"。TDD 技能里有同一句话，`writing-skills` 把它列为"必须提前写进技能"的加固手法之一：把"精神 vs 字面"这条退路提前封死，后面就无法用它来绕过纪律。

## The Iron Law

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

（没有根因调查，就没有修复。）

如果你还没完成阶段 1，你就不能提出修复方案。

## When to Use

适用于**任何**技术问题：

- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**以下情况尤其要使用：**

- 处于时间压力下（紧急状况会让猜测变得诱人）
- "就改一行就好"看起来显而易见
- 你已经试过多次修复
- 上一次修复没起作用
- 你并不完全理解这个问题

**以下情况不要跳过：**

- 问题看起来很简单（简单的 bug 也有根因）
- 你很急（着急必然导致返工）
- 上级要求你**立刻**修好（系统化比乱试更快）

> **批注**：注意"尤其要使用"这一节把**最想跳过流程的时刻**（时间压力、看起来显而易见、已经试过几次）直接列为最该使用的情况。这是在反向利用人的直觉——把"我这么急，哪有空走流程"这个念头本身当作触发信号。

## The Four Phases

你必须完成每一个阶段，才能进入下一个。

### Phase 1: Root Cause Investigation（根因调查）

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 每次都会发生吗？
   - 如果不能复现 → 去收集更多数据，**不要猜**

3. **检查最近的变更**
   - 什么改动可能导致了这个？
   - git diff、最近的提交
   - 新增的依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，或 API → 服务 → 数据库）：**

   **在提出修复方案之前，先加上诊断性埋点：**

   ```
   对每一条组件边界：
     - 记录进入该组件的数据
     - 记录离开该组件的数据
     - 校验环境/配置的传递
     - 检查每一层的状态

   先跑一次，收集证据，看清"在哪一层断掉"
   然后分析证据，确定出问题的组件
   然后只调查那个具体组件
   ```

   **示例（多层系统）：**

   ```bash
   # 第 1 层：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第 3 层：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这会揭示：** 是哪一层失败了（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误深埋在调用栈里时：**

   完整的反向追踪技术见本目录的 `root-cause-tracing.md`。

   **速览版：**
   - 坏值是从哪里产生的？
   - 是谁用坏值调用了这里？
   - 一路往上追，直到找到源头
   - **在源头修，不要在症状处修**

> **批注**：第 4 条是这一阶段最反直觉的部分——它的要求是**先加埋点、跑一次、只为了"看清哪一层断掉"**，而不是先分析代码。这等于强制在第 1 阶段插入一次纯粹的证据收集动作。为什么值得？因为多组件系统里，最贵的错误是"在错误的层调试"。你可能花两小时研究签名脚本，最后发现身份变量根本没传进 CI 工作流。埋点是**用一次运行换掉盲目搜索**。

### Phase 2: Pattern Analysis（模式分析）

**先找模式，再动手修：**

1. **找出可用的例子**
   - 在同一个代码库里找相似的、能正常工作的代码
   - 有什么和出问题的部分相似，但它是好的？

2. **对照参考实现**
   - 如果是在实现某个模式，**完整**阅读参考实现
   - 不要略读——逐行读
   - 在套用之前完整理解这个模式

3. **找出差异**
   - 能工作和不能工作之间，差别是什么？
   - 列出**每一个**差异，无论多小
   - 不要假设"这不可能有影响"

4. **理解依赖**
   - 它还需要哪些别的组件？
   - 哪些设置、配置、环境？
   - 它做了哪些假设？

### Phase 3: Hypothesis and Testing（假设与验证）

**科学方法：**

1. **形成单一假设**
   - 明确说出来："我认为 X 是根因，因为 Y"
   - 把它写下来
   - 要具体，不要含糊

2. **最小化验证**
   - 做**最小的**可能改动来验证假设
   - 一次只动一个变量
   - 不要一次修多个东西

3. **继续之前先验证**
   - 生效了吗？是 → 进入阶段 4
   - 没生效？形成**新的**假设
   - 不要在旧的上面继续叠加修复

4. **当你不明白时**
   - 说出"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 做更多研究

> **批注**：第 2 条"一次只动一个变量"和第 3 条"不要在旧的上面继续叠加修复"合起来防的是一种极其常见的失控模式——**多个修复叠加之后，即使问题消失了，你也不知道是哪个修好的**，更不知道另外几个是否引入了新问题。这条纪律把"修好了"和"知道为什么修好了"绑定在一起。

### Phase 4: Implementation（实施）

**修根因，不修症状：**

1. **创建失败的测试用例**
   - 尽可能最简单的复现
   - 有框架就用自动化测试
   - 没有框架就写一次性测试脚本
   - **修复之前必须有**
   - 用 `superpowers:test-driven-development` 技能来写规范失败测试

2. **实施单一修复**
   - 针对已确定的根因
   - **一次一个**改动
   - 不要"顺手"做别的改进
   - 不要夹带重构

3. **验证修复**
   - 测试现在通过了吗？
   - 有没有弄坏别的测试？
   - 问题真的解决了吗？

4. **如果修复无效**
   - **停**
   - 数一数：你已经试了几次修复？
   - 如果 < 3：回到阶段 1，带着新信息重新分析
   - **如果 ≥ 3：停下，质疑架构（见下面第 5 条）**
   - 没有架构层面的讨论，**不要**尝试第 4 次修复

5. **如果 3 次以上修复都失败：质疑架构**

   **表明存在架构问题的模式：**
   - 每次修复都在不同地方暴露出新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每次修复都会在别处制造新症状

   **停下，质疑根本假设：**
   - 这个模式从根本上是合理的吗？
   - 我们是不是"纯粹出于惯性才一直坚持它"？
   - 应该重构架构，还是继续修症状？

   **在尝试更多修复之前，与你的协作伙伴讨论**

   这**不是**一个失败的假设——这是**错误的架构**。

> **批注**：第 4/5 条是整份技能里最精巧的设计——它引入了一个**计数器**（3 次）。这个数字把一个模糊的直觉（"我好像一直在修，但问题总是冒出来"）变成了**可判定的信号**。更重要的是它附带的那句重新定性："这不是一个失败的假设——这是错误的架构。" 因为连续失败最自然的解读是"我还没找到根因，再试一次就好"，而这个技能强行把解读切换成"根因可能就是架构本身"。没有这句重新定性，第 4 次、第 5 次修复会源源不断地发生。

## Red Flags - STOP and Follow Process

如果你发现自己有这些想法：

- "先临时修一下，稍后再调查"
- "就试试改 X 看看行不行"
- "一次改几处，然后跑测试"
- "跳过测试，我手动验证一下"
- "大概是 X，我来修一下"
- "我不是完全理解，但这样可能行得通"
- "模式说要 X，但我按自己的方式调整一下"
- "主要问题有这些：[未经调查就列出修复清单]"
- 在追踪数据流之前就提出解决方案
- **"再试一次修复"（已经试过 2 次以上时）**
- **每次修复都在不同地方暴露新问题**

**以上全部意味着：停下。回到阶段 1。**

**如果 3 次以上修复失败：** 质疑架构（见阶段 4.5）

## 你的协作伙伴发出的"你做错了"信号

**留意这些纠正性话语：**

- "那个（情况）没在发生吧？"—— 你没验证就做了假设
- "这能让我们看到……吗？"—— 你本该加证据收集
- "别猜了"—— 你在不理解的情况下提修复方案
- "深入思考一下这个"—— 质疑根本假设，而不只是症状
- "我们卡住了？"（语气沮丧）—— 你的方法行不通

**看到这些时：** 停下，回到阶段 1。

> **批注**：这一节把**人类协作伙伴的反应**也纳入了检测机制。为什么值得？因为 AI 判断自己是否在乱猜的能力并不可靠——合理化总是自我一致的。而伙伴的措辞是**外部信号**，不受 AI 自我评估的偏差影响。把"别猜了"这种话明确标注为"回到阶段 1"的触发器，等于给这套自我纪律装了一个外部的断路器。

## Common Rationalizations（常见合理化）

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根因。对简单 bug 来说，流程反而更快。 |
| "紧急情况，没时间走流程" | 系统化调试**比**猜来猜去地乱试**更快**。 |
| "先试一下这个，然后再调查" | 第一次修复就定下了模式。从一开始就做对。 |
| "等确认修复有效再写测试" | 没测试的修复不会稳固。先写测试才能证明。 |
| "一次修多个能省时间" | 无法判断是哪个起了作用，还会引入新 bug。 |
| "参考实现太长了，我按模式自己改" | 部分理解必然产生 bug。完整读。 |
| "我看到问题了，我来修" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（已失败 2 次以上） | 3 次以上失败 = 架构问题。质疑模式，别再修了。 |

## Quick Reference（速查）

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| **1. 根因** | 读错误、复现、查变更、收集证据 | 理解 WHAT 和 WHY |
| **2. 模式** | 找可用例子、对比 | 找出差异 |
| **3. 假设** | 形成理论、最小验证 | 确认，或形成新假设 |
| **4. 实施** | 建测试、修复、验证 | bug 解决、测试通过 |

## 当流程揭示"没有根因"时

如果系统化调查发现问题确实是环境性的、时序相关的，或来自外部：

1. 你已经完成了整个流程
2. 把你调查过什么记录下来
3. 实施恰当的处理（重试、超时、错误提示）
4. 加上监控/日志，便于日后追查

**但是：** 95% 所谓的"没有根因"，其实是调查不完整。

> **批注**：这一节表面上是在给出路（"确实可能没有根因"），但那句"**但是**"把出路收得很窄——它预设绝大多数"没有根因"都是自己没查完。这是一个高风险的断言（95% 是硬数字，没有引用来源），但它在这里的作用是**防止这一节被当成逃生舱**。如果只写前半段，它就会变成"查不出来时可以说这是环境问题"的许可证。

## Supporting Techniques（配套技术）

以下技术属于系统化调试的一部分，都在本目录中：

- **`root-cause-tracing.md`** —— 沿调用栈反向追踪 bug，找到最初的触发点
- **`defense-in-depth.md`** —— 找到根因之后，在多个层次加校验
- **`condition-based-waiting.md`** —— 用条件轮询替换任意超时

**相关技能：**

- **superpowers:test-driven-development** —— 用于创建失败测试用例（阶段 4 第 1 步）
- **superpowers:verification-before-completion** —— 在宣称修复成功之前验证它真的修好了

## Real-World Impact（真实效果）

来自实际调试会话：

- 系统化方法：15-30 分钟修好
- 随机修复方法：2-3 小时的乱试
- 一次修好的比例：95% vs 40%
- 引入的新 bug：接近零 vs 常见
