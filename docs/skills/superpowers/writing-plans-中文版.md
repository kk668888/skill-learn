## frontmatter

- **name**：`writing-plans`
- **description**：当你已经拥有针对多步骤任务的规格或需求、并且在接触代码之前使用。

## 概述

撰写全面的实现计划时，**假设执行工程师对我们的代码库零上下文、且品味可疑**。把他们需要知道的一切都写下来：每个任务要碰哪些文件、代码、测试、可能需要查的文档、怎么验证。把整份计划拆成一口一个的小任务。DRY。YAGNI。TDD。频繁提交。

假设他们是一位**技术熟练的开发者，但对我们的工具链和问题领域几乎一无所知**。假设他们**不太懂好的测试该怎么设计**。

> **批注**：这段"品味可疑的初级工程师"设定不是修辞夸张，而是一次**身份转换**——它真正的读者不是人，是**零上下文的 subagent**。主会话里积累的对本项目的理解**不会自动传递**给子代理（这正是 subagent-driven-development 的 fresh-context 设计）。所以计划必须自足到"一个只在字面上理解它的人也能执行无误"。这一段是全篇的地基，后面所有苛刻要求都从这里推导出来。

**开始时先声明**:"我正在使用 writing-plans 技能来创建实现计划。"

**上下文：** 如果你在隔离的 worktree 中工作，它应当已经在执行阶段由 `superpowers:using-git-worktrees` 技能创建好。

**计划保存到：** `docs/superpowers/plans/YYYY-MM-DD-<功能名>.md`
- （用户对计划位置的偏好会覆盖这个默认值）

## 范围检查

如果规格覆盖了多个相互独立的子系统，它本应在 brainstorming 阶段就被拆成多个子项目规格。如果没有，建议把它拆成多份计划——每个子系统一份。**每份计划都应能独立产出可运行、可测试的软件。**

## 文件结构

在定义任务之前，先勾勒出将要创建或修改哪些文件、以及每个文件负责什么。**分解决策就是在这里被锁定的。**

- 设计单元时要有清晰的边界和定义良好的接口。每个文件应当只有一个明确职责。
- 你能同时装进上下文的代码，是你推理得最准的代码；文件聚焦时你的编辑也更可靠。**优先选择更小、更聚焦的文件**，而不是职责过多的大文件。
- **一起变更的文件应当放在一起。按职责拆分，而不是按技术分层拆分。**
- 在既有代码库中，遵循既有模式。如果代码库本来就用大文件，不要擅自重构——但如果你正在修改的那个文件已经臃肿难用，把"拆分它"写进计划里是合理的。

这个结构会决定任务如何分解。每个任务都应当产出**自成一体、独立成立**的改动。

## 一口一个的任务粒度

**每一步只做一个动作（2-5 分钟）：**

- "写失败的测试" —— 一步
- "运行它，确认它失败" —— 一步
- "写最小实现让测试通过" —— 一步
- "运行测试，确认通过" —— 一步
- "提交" —— 一步

> **批注**：粒度小到这个程度，意义不在"省时间"，而在**让误解无处藏身**。一个 2 分钟的步骤不可能隐藏"我其实没搞懂这一步要干什么"——因为如果搞不懂，这一步就做不出来。反过来，"实现登录功能"这种大步骤可以让执行者带着一堆误解蒙混过关，直到很久以后才爆雷。注意 "运行它确认失败" 被**单独列成一步**，而不是与"写测试"合并——这是为了强制 TDD 的验证环节真的发生。

## 计划文档头部

**每份计划都必须以这个头部开始：**

```markdown
# [功能名] 实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: 使用 superpowers:subagent-driven-development（推荐）
> 或 superpowers:executing-plans 来逐任务执行本计划。步骤使用复选框（`- [ ]`）语法来追踪进度。

**Goal:** [一句话描述本计划构建什么]

**Architecture:** [2-3 句话说明思路]

**Tech Stack:** [关键技术/库]

---
```

> **批注**：头部那句 `For agentic workers:` 是**写给执行代理看的指令**，不是给人看的说明。它把"该用哪个技能执行"这件事直接写进了计划文件里——因为执行阶段的 subagent 可能根本没参与过设计讨论，它唯一的上下文来源就是这份文件。

## 任务结构

````markdown
### Task N: [组件名]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

- [ ] **Step 1: 写失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Step 2: 运行测试，确认它失败**

Run: `pytest tests/path/test.py::test_name -v`
Expected: FAIL，报 "function not defined"

- [ ] **Step 3: 写最小实现**

```python
def function(input):
    return expected
```

- [ ] **Step 4: 运行测试，确认它通过**

Run: `pytest tests/path/test.py::test_name -v`
Expected: PASS

- [ ] **Step 5: 提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

> **批注**：注意 `Modify:` 后面带的是 `:123-145` 这样的**行号区间**，而不只是文件名。这是"零上下文执行者"原则的直接产物——文件可能很大，说"改这个文件"等于让执行者自己去找，而找错了它也不知道。
>
> 更关键的是每个 Run 步骤都配了 `Expected:` ——**命令和预期结果成对出现**。如果只给命令不给预期，执行者看到报错也不知道那是"正常的失败"还是"环境坏了"，而这两种情况的处理方式完全相反。

## 禁止占位符

每一步都必须包含执行工程师真正需要的内容。以下是**计划失败**——永远不要写：

- "TBD"、"TODO"、"稍后实现"、"补充细节"
- "添加适当的错误处理" / "加上校验" / "处理边界情况"
- "为上写测试"（而不给出实际测试代码）
- "与 Task N 类似"（重复写出代码——执行者可能**乱序**阅读任务）
- 只描述"要做什么"却不展示"怎么做"的步骤（涉及代码的步骤必须给出代码块）
- 引用了任何任务中都未定义的类型、函数或方法

> **批注**：这份清单里最有说服力的是 **"与 Task N 类似"也算失败**。它的理由不是洁癖，而是执行者**可能乱序读任务**——子代理一次只拿到一个任务，或者按自己认为合理的顺序推进。一旦它跳读，"类似 Task N"就变成了指向空白。
>
> 而 "添加适当的错误处理" 这类占位符之所以致命，是因为它**把决策推迟到了执行时刻——而执行者恰恰是上下文最少的那个角色**。写计划的人当时知道"适当"指什么，执行者不知道。**计划阶段偷的懒，执行阶段会加倍偿还。**

## 记住

- 永远给出精确文件路径
- 每一步都给完整代码——如果某一步改动代码，就把代码展示出来
- 给出精确命令及其预期输出
- DRY、YAGNI、TDD、频繁提交

## 自审

写完整份计划之后，用新鲜眼光对照规格检查计划。这是**你自己跑的清单——不是派发子代理**。

**1. 规格覆盖：** 略读规格里的每个小节/需求。你能指出某个任务实现了它吗？列出所有缺口。

**2. 占位符扫描：** 在计划里搜索危险信号——上面"禁止占位符"一节里的任何模式。修掉它们。

**3. 类型一致性：** 你在后面任务里用到的类型、方法签名和属性名，与你在前面任务里定义的是否一致？一个函数在 Task 3 里叫 `clearLayers()`、到 Task 7 里变成 `clearFullLayers()`——**那是个 bug**。

如果发现问题，就地修复。不需要再复审一遍——修完就走。如果你发现某条规格需求没有对应任务，**把任务补上**。

> **批注**："类型一致性"这一项值得单独琢磨：它是四项检查里**唯一一项只能靠通读全篇才能发现**的。占位符和覆盖缺口可以靠搜索和对照发现，但两个任务对同一个函数的命名不一致，只有把前后文放在一起比较才会暴露。而这类不一致在交给执行者之后会变成实实在在的编译错误或运行时 bug。

## 执行交接

保存计划之后，提供执行方式选择：

> **"计划已完成并保存到 `docs/superpowers/plans/<文件名>.md`。两种执行方式：**
>
> **1. Subagent-Driven（推荐）** —— 我为每个任务派发一个全新的子代理，任务之间做审查，迭代快
>
> **2. Inline Execution** —— 在本会话中使用 executing-plans 执行任务，批量执行 + 检查点审查
>
> **选哪种？"**

**如果选择 Subagent-Driven：**
- **必需的子技能**：使用 superpowers:subagent-driven-development
- 每个任务一个全新子代理 + 两阶段审查

**如果选择 Inline Execution：**
- **必需的子技能**：使用 superpowers:executing-plans
- 批量执行 + 检查点审查
