## 1. 它解决什么问题

一次大重构之后，你面对 3 个文件里共 6 个失败的测试。顺序排查意味着：读第一个文件、定位根因、修复、跑测试、再读第二个文件……**每次切换问题都要重新装载上下文**，而这个装载过程不产生任何价值。3 个问题花 3 份时间，纯粹是因为它们是串行发生的。

所以收益是清楚的：**这些调查之间没有依赖，为什么不让它们同时发生？** 并行不是让每个问题变快，而是让 N 个问题的总耗时接近 1 个问题的耗时。

但这条路上有一个非常隐蔽的陷阱：**"独立性"是一个容易误判的属性**。两个失败看起来毫不相干（一个在中止逻辑、一个在批次完成），但它们可能：

- 改**同一份文件**（冲突）
- 依赖**同一个被误解的 API 语义**（系统性错误）
- 共享**同一个状态**（数据库、端口、全局缓存）

而一旦并行分派出去，**这些冲突在事前是不可见的**——每个代理只看到自己的问题域，它不知道别人在改什么（这正是上下文隔离的代价）。等发现时，三份工作已经各自做完。

**设计立场**：并把行的收益是真的，但**独立性必须被显式判定，且判定标准要分两级**。这个技能的核心并不是"怎么并行"（那很简单），而是**"什么时候不许并行"**——原文用了大量篇幅在讲后者。

> 注意这个技能的定位与同套件的 `subagent-driven-development` 恰好相反：那个技能**禁止**并行实现，这个技能**鼓励**并行。二者不矛盾，它们的判据是同一条——**有无共享状态**。

## 2. 核心设计决策

### 决策一：两级判定——先问"独立吗"，再问"能并行吗"

**选了什么**：决策树是两个串联的判断，不是一个。

```
有多个失败？
   ├─ 否 → （不适用）
   └─ 是 → 它们相互独立吗？
             ├─ 否（相关）→ 单个代理调查全部
             └─ 是 → 它们能并行工作吗？
                       ├─ 能 → 并行分派
                       └─ 否（共享状态）→ 顺序代理
```

**为什么必须是两级**：因为它区分了两个**容易混淆**的概念——

| 概念 | 含义 | 例子 |
|------|------|------|
| **逻辑独立** | 修 A 不会顺带修好 B | 中止逻辑 vs 批次完成 |
| **无共享状态** | 改 A 不会破坏 B 的工作环境 | 不同文件 vs 同一文件 |

**逻辑独立是必要条件，不是充分条件**。原文用两个不同的分支（`independent?` → `can work in parallel?`）把这一点显式化，因为**合并成一个判断时，实践者会不自觉地用"逻辑独立"替"无共享状态"**——而后者才是真正决定冲突的。

**代价**：多一步判定，且第二级判定（共享状态）需要实际查看文件依赖关系，比第一级费力得多。

### 决策二：粒度是"问题域"，不是"问题"

**选了什么**：`Dispatch one agent per independent problem domain`——注意是 **domain**（域），不是 **problem**（问题）。

**为什么**：粒度选错两端都出问题：

- **太细**（一个测试失败一个代理）：多个代理会去改**同一份测试文件**，冲突概率极高。第 3 步的示例里，3 个失败在**同一个文件**里，被交给**一个**代理——正是这个道理。
- **太粗**（一个代理修全部）：原文的 Common Mistakes 第一条就是 `❌ Too broad: "Fix all the tests" - agent gets lost`。范围一大，代理要跟踪的上下文就多，"聚焦"这个核心收益消失。

**"问题域"是正确粒度的原因**：它是**修复动作的原子单位**——一个域内的多个失败往往共享根因（都是时序问题），一次修复能同时解决；跨域则互不影响。所以按域切分，既保证了"每个代理的改动是自洽的"，又保证了"代理之间不碰同一处代码"。

### 决策三：必须显式写约束

**选了什么**：每个代理的 prompt 里必须有约束项，例如 `Do NOT change production code` 或 `Fix tests only`。

**为什么**：**代理在隔离上下文里工作，它看不到全局，因此无法自行判断自己的修改边界在哪里**。这不是它不小心，而是结构性的信息缺失——你刻意没给它全局上下文（为了聚焦），那么"别越界"这件事就必须由你**显式告知**。

原文把"没有约束"和"没有上下文"并列列为常见错误，理由是 `Agent might refactor everything`（代理可能会重构一切）。一个只拿到"修复 git 历史里有 bug 的那段"的代理，完全可能顺手重构它认为不好的整个模块——**每一步都合理，整体越界**。

> 这里有个与 `subagent-driven-development` 的共同点：**两处都在用"显式约束"补上下文隔离的代价**。上下文隔离带来聚焦，代价是失去全局判断力，所以边界必须由控制者从外部注入。这是所有"隔离上下文"设计都要付的税。

### 决策四：对输出格式提出明确要求

**选了什么**：`Return: Summary of what you found and what you fixed.`——要求返回根因 + 变更的摘要。

**为什么**：因为**整合阶段完全依赖这份摘要**。第 4 步"审查并整合"要求你"理解改了什么、检查是否冲突"——如果代理只回一句"修好了"，你没有任何依据做这两件事，只能打开 diff 自己看，而那样并行的效率收益就被整合成本吃掉了。

原文的 Common Mistakes 里 `❌ Vague output: "Fix it" - you don't know what changed` 说的就是这个：**输出要求含糊，等于把整合阶段的工作量转移回你自己身上**。

### 决策五：整合必须验证，不能信任

**选了什么**：四步验证——读摘要、查冲突、跑**完整**测试套件、**抽查**。

**为什么**：因为有一类失败模式**不会**在前三步暴露——原文专门点了名：

> `Spot check - Agents can make systematic errors`（抽查——代理可能犯系统性错误）

**"系统性错误"指的是什么**：不是一个代理犯了错，而是**多个代理因为同一个错误前提而犯了同一个错**。比如三者都以为某个 API 是同步的，于是都用了错误的方式处理返回值。

这种错误的特点极其危险：

- **冲突检查查不出**：各改各的文件，互不冲突，检查通过。
- **单份摘要看起来正常**：每个代理的推理在自己的域内都是自洽的。
- **只有在跨域视角下才暴露**：跑完整套件时，可能发现"三个地方用了同一个错误假设"。

所以第四步不是礼貌性的"看一眼"，而是**唯一能捕获这类错误的环节**。

**代价**：并行的速度收益被整合成本部分抵消。原文的 "Verification" 一节有 4 个步骤，说明这个成本不低——**并行不是免费的速度**。

### 决策六：用大篇幅讲"什么时候不要用"

**选了什么**：`When to Use` 里有 `Don't use when` 三条，`When NOT to Use` 又是独立一节，列了四条（与前者部分重复）。

**为什么**：**因为这个技能的误用代价特别高**。用一个不该并行的场景去并行，产出的是"看起来成功、实际互相破坏"的结果——冲突可能在合并时才浮现，而那时每个代理都已"完成"。这比直接失败更糟：**你会以为它成功了**。

一个技能愿意用这么大的篇幅讲自我限制，通常说明它有一个容易被诱惑的收益（"并行更快"），而诱惑的代价藏在后面。

## 3. 机制如何运转

```
多个失败
   ↓
① 识别独立问题域（按"什么坏了"分组）
   ↓
② 为每个域构造聚焦任务：范围 + 目标 + 约束 + 输出要求
   ↓
③ 并行分派（所有代理同时开跑）
   ↓
④ 整合与验证
     ├─ 读每份摘要
     ├─ 查冲突（是否编辑了同一处代码）
     ├─ 跑【完整】测试套件   ← 唯一能发现跨域问题的环节
     └─ 抽查                 ← 唯一能发现系统性错误的环节
   ↓
   全绿 → 完成
```

**最容易违反的约束是第 2 步的"约束项"**。原因很实际：写 prompt 时，描述"要修什么"是自然的，而写"不要动什么"需要你先想清楚边界在哪——**后者是额外的心智负担，而省略它在当下没有任何代价信号**。直到代理重构了半个模块，你才发现那句话不该省。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **假独立**（看似独立，实则有共享状态） | 各代理互不察觉地破坏彼此的前提，合并时冲突 | **最危险的一类**。判定的依据是"看起来不相关"，而共享状态往往是隐含的（同一个被误解的 API、同一份配置、同一个端口）。判定错了，**事前没有任何信号** |
| **失败之间相关** | 白干 + 冲突；且修一个本可以顺带修好别的 | 原文明确排除：`Related failures: Fixing one might fix others` |
| **探索性调试** | 无法切分领域，分派变成瞎猜 | `You don't know what's broken yet`——问题域的定义依赖于"已经知道哪里坏了" |
| **需要完整系统状态** | 每个代理都缺关键信息，各自得出片面结论 | 与"自包含"要求直接冲突：有些问题无法在不看全局的前提下理解 |
| **系统性错误**（多代理同一错误前提） | 冲突检查与摘要审查均通过，坏结果被合入 | 检测依赖**抽查**与**完整套件**，而两者都可能被跳过（尤其当你信任摘要时） |
| **约束项缺失或被忽略** | 代理越界重构，改动范围失控 | 代理在隔离上下文里无法自行判断边界；约束是唯一的外部信息 |
| **摘要不可信** | 整合阶段基于错误认知做决策 | 与 `subagent-driven-development` 面对的是同一个问题：**LLM 的自我汇报有乐观偏见**。本技能没有像那样的"不信任汇报"显式指令，是体系里的一处不对称 |
| **问题数量少 / 规模小** | 分派与整合的开销超过串行成本 | 3 个以上才划算（原文的适用条件写的是 `3+ test files`） |
| **部分失败** | 一个代理失败、另两个成功时，如何处理？**原文未规定** | 技能只描述了全成功路径（"所有修复成功整合"）；没有关于"回滚某个代理的产物"或"部分合入"的指导 |
| **在 `subagent-driven-development` 场景中误用** | 多个实现者基于同一代码库起点各自改动，必然冲突 | 那个技能的 Red Flags 明确禁止并行实现；判据同样是"有无共享状态"——**任务顺序累积 = 有共享状态** |

> **第一条与最后一条是同一个判断的两个方向**，值得放在一起看：
>
> | 场景 | 共享状态 | 结论 |
> |------|---------|------|
> | 修 3 个不同测试文件 | 无 | ✅ 并行 |
> | 实现 5 个有顺序依赖的功能 | 有（同一代码库在累积演进） | ❌ 串行 |
>
> **"任务之间逻辑独立"与"工作不冲突"是两件事**。实现任务的独立性说的是"任务 B 不需要任务 A 的结论"，但 B 的实现者**需要看到 A 已经提交的代码**——这就是共享状态。这个区分是本技能与 `subagent-driven-development` 不矛盾的关键。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **边界** `subagent-driven-development` | 二者判据相同（有无共享状态）但结论相反：那里**禁止**并行实现，这里**鼓励**并行调查 |
| **上游** `systematic-debugging` | 单个问题域的根因分析流程。本技能负责"把 N 个域分出去"，域**内部**怎么做仍是系统化调试 |
| **共享原则** 所有 subagent 类技能 | "不继承会话上下文、由控制者精确投喂"这条原则在三个技能里逐字重复（本技能与 `subagent-driven-development` 的 Overview 段落几乎一致）——这不是复制粘贴的偶然，而是同一套上下文隔离原则的复用 |
| **不使用** `test-driven-development` | 本技能面向调试场景，与 TDD 的计划式流程不同；修复时若不写失败测试，则缺乏回归保护 |
