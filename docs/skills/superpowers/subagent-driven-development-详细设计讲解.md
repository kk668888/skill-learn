# subagent-driven-development · 详细设计讲解

> **源码**：`skills/superpowers/subagent-driven-development/SKILL.md`
> **中文原文翻译**：[subagent-driven-development-中文版.md](./subagent-driven-development-中文版.md)
> **套件整体原理**：[技能原理深度讲解.md](./技能原理深度讲解.md)
> **本文定位**：`中文版` 回答"原文说了什么"，本文回答"**为什么这么设计、还有别的选法吗、什么时候会失效**"

## 1. 它解决什么问题

有一个反直觉的现象：**同一个模型，在长任务的后半段比前半段更容易犯错**。原因不是能力衰减，而是**上下文污染**——前面几十轮的试探、废弃的方案、被推翻的假设都还留在上下文里，它们和当前任务的信息**权重相同**，模型必须自己去分辨哪些还有效。任务越长，这个分辨成本越高，出错概率越大。

第二个问题更隐蔽：**执行者的自我汇报不可信**。LLM 有强烈的"乐观自评"倾向——它会说"已实现进度汇报"，而实际上只加了一个 `console.log`。这不是撒谎，是它的自评标准和你的验收标准不一致。而且**自评天然带着写代码时的思路惯性**，它看自己写的东西和看别人写的，警惕性完全不同。所以"让实现者自审"不能替代"独立评审"，只能作为补充。

第三个问题：**主会话的上下文是稀缺资源**。如果把 14 个任务的实现细节全塞进主会话，那么到第 10 个任务时，协调用的上下文已经被挤掉了——控制者自己开始糊涂。

**设计立场**有三条，撑起了整套机制：

1. **上下文是稀缺资源**——必须隔离、必须节流
2. **执行者的自我报告不可信**——必须独立验证，且验证者要被明确告知"不要相信"
3. **"做"与"评"必须分离**——同一个上下文里既做又评，评审会被自己刚写的代码污染

> 这三条立场决定了这个技能的形态：它不是一个"更快的执行方式"，而是一个**围绕上下文污染和自评偏见设计的质量控制系统**。速度是副产品，不是目标。（原文 "Advantages" 里写的是 "fast iteration"，但那是相对于"独立会话 + 人工检查点"的 `executing-plans` 而言。）

## 2. 核心设计决策

### 决策一：每个任务派一个**全新**的 subagent，不继承任何历史

**选了什么**：`They should never inherit your session's context or history — you construct exactly what they need.`

**为什么**：这是整套设计的地基。全新上下文意味着**零污染**——第 10 个任务的实现者不知道第 3 个任务走过什么弯路，因此不会受其影响。同时它把"控制者"和"执行者"的角色分开了：控制者持有全局、负责裁剪；执行者只持有局部、负责做对。

**备选方案**：

- *让同一个 subagent 连续做多个任务*（上下文延续）—— 被否决。这正是要避开的污染源；而且延续上下文会让它逐渐"自以为是"，开始修改早期任务的产物。
- *不用 subagent，就在主会话里顺序做*（即 `executing-plans`）—— 被否决（在有 subagent 的前提下）。主会话会被实现细节淹没，协调能力下降。

**代价**（三条，都是真实的）：

1. **控制者必须预先做完所有提取工作**。原文要求 `Read plan, extract all tasks with full text, note context, create TodoWrite`——在派发第一个任务**之前**就要读完整个计划。这是纯前置开销。
2. **执行者失去自主探索能力**。它不能"先看看代码库再说"，因为不看计划文件、也没有历史。它拿到的就是控制者给的那些字。
3. **控制者成为单点瓶颈**。投喂遗漏一个上下文，执行者就要走一轮 `NEEDS_CONTEXT` 往返。

### 决策二：**禁止** subagent 自己读计划文件

**选了什么**：Red Flags 里明确写着 `Make subagent read plan file (provide full text instead)`——不允许，要直接粘贴全文。

**为什么**：三重理由。

- **省 IO**：读文件是开销，而控制者已经读过一次了。
- **精确裁剪**：任务 N 不需要看到任务 N+5 的内容。整份计划塞进去既是噪声也占上下文。
- **强制控制者先读懂**：这条最容易被忽略。**要求"你必须能粘贴出任务全文"是没有办法作弊的**——一个没读懂计划的人没法提取出"完整文本 + 场景上下文"。这个约束的实际作用是**逼控制者做功课**，而控制者读懂计划的副产品是：它更可能发现任务之间的冲突。

**代价**：投喂内容的**正确性完全取决于控制者**。它漏了什么，执行者就不知道什么（只能靠 `NEEDS_CONTEXT` 补救）。

### 决策三：两阶段评审，且**顺序不可交换**

**选了什么**：先规格合规，再代码质量。而且这条被写进了两处——主 SKILL.md 的 Red Flags（`Start code quality review before spec compliance is ✅` 是红旗），以及 `code-quality-reviewer-prompt.md` 的开头（`Only dispatch after spec compliance review passes`）。

**两个阶段查的是不同的东西**：

| 阶段 | 查什么 | 典型发现 |
|------|--------|----------|
| 规格合规 | **做的对不对**——有没有少做、**有没有多做** | 缺失"进度汇报"；擅自加了 `--json` 标志 |
| 代码质量 | **做得好不好** | 魔法数字 `100` 应抽成常量；文件职责不清 |

**为什么顺序不可交换**：**代码写得再漂亮，规格错了全是白干**。如果在规格未定时先做质量评审，你会花大量精力把一段**最终要被删掉**的代码抛光。原文的红旗清单把这条列进去，说明实践中很多人会图省事先跑质量评审（因为质量评审的模板现成、看起来更"通用"）。

**为什么"多做"也算不合规**——这是最反直觉的一条，值得展开：

`Added --json flag (not requested)` 在直觉上看是"顺手做了件好事"。但在这个体系里它是**缺陷**，理由有三层：

1. **计划是一个自洽的整体**。某个任务"顺手"加的功能，没有经过计划阶段的取舍——它可能与其他任务的接口冲突，可能引入了没被考虑过的边界情况。
2. **未经要求的功能没有对应的测试要求**。计划里每一步的测试是写好的；多出来的代码没有这个保障。
3. **它是 YAGNI 的违反**，而 YAGNI 是这套方法论的显式原则（`writing-plans` 要求 `DRY. YAGNI. TDD.`）。"以后可能用得上"是最常见的过度设计借口。

所以"多做"的判定标准是**纯粹的**：计划里没有的，就是不合规——哪怕它质量很高。

### 决策四：评审者被**明确要求不信任**实现者

**选了什么**：`spec-reviewer-prompt.md` 里有一整段标题为 `CRITICAL: Do Not Trust the Report` 的指令：

> The implementer finished suspiciously quickly. Their report may be incomplete, inaccurate, or optimistic. You MUST verify everything independently.
>
> **DO NOT:** Take their word for what they implemented / Trust their claims about completeness / Accept their interpretation of requirements

**为什么**：这是整套设计里**最锋利的一处**，也是最容易被误读为"对人不对事"的一处。它的实质是——**把"不信任"写进流程，而不是依赖评审者的个人警觉**。

理由有两层：

- **必要性**：LLM 的自评偏见是**系统性的**，不是偶发的。凡是让一个模型评自己产出的场景，这个偏见都会出现。所以不能靠"提醒它要客观"来对抗，必须**直接告诉评审者"对方可能不可靠"**。
- **独立性**：评审者拿到的是一个全新上下文，它对实现者的唯一信息来源就是那份汇报。如果它采信汇报，那这次"独立评审"就退化成了"把汇报重读一遍"——**上下文隔离白做了**。

注意措辞里的 `suspiciously quickly`（快得可疑）——它甚至在给评审者**预设怀疑态度**，而不是中立的"请核实"。这种刻意的不中立，是因为默认倾向（信任）太强，需要用力反向推。

**代价**：可能产生"为挑刺而挑刺"，或对确实做得很好的实现给出不必要的质疑。这个代价被接受，因为**误报的成本（多一轮往返）远低于漏报的成本（坏代码进入后续任务）**。

### 决策五：任务之间**不**停下来确认

**选了什么**：`Do not pause to check in with your human partner between tasks`——一口气执行完。

**为什么**：**决策成本已经预付**。计划经过了你逐段确认（`brainstorming` 的增量验证 + `writing-plans` 的执行交接），执行期每一次"要不要继续"都是把同一个决策**再收一遍费用**，而且这次你手上的信息并不比批准计划时更多。

原文的理由写得很直接：*"Should I continue?" prompts and progress summaries waste their time — they asked you to execute the plan, so execute it.`

**代价**：如果计划有偏差，你会**连续**得到一堆建立在错误基础上的产出，直到事后才发现。这条规则与决策四（评审者的怀疑）是配套的——**用自动化的两阶段评审替代人工检查点**，把"人的介入"从周期性变成异常触发（只在 BLOCKED / 真歧义 / 全部完成时）。

### 决策六：模型按角色分级

**选了什么**：机械实现用便宜模型、集成/判断用标准模型、架构与评审用最强模型。

**为什么可行**：原文给了一句关键的判断依据——**`Most implementation tasks are mechanical when the plan is well-specified.`**

这句话揭示了一个**上游依赖**：模型分级省钱的可行性，**建立在计划质量之上**。`writing-plans` 要求每步附完整代码、精确路径、预期输出——细到这个程度时，实现确实退化成"照抄 + 跑通 + 提交"，便宜模型够用。**所以模型分级不是独立的优化技巧，而是"零占位符计划"这笔投资的下游红利。** 计划粗糙时，实现者被迫做设计判断，分级立刻失效。

注意评审被划入"最强模型"一档——**判断比生成更需要能力**。

### 决策七：四种状态分级处理，且禁止无效重试

**选了什么**：DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED 四种回报状态，各自有明确处置。外加一条硬规则：

> **Never** ignore an escalation or force the same model to retry without changes. If the implementer said it's stuck, something needs to change.

**为什么**：四种状态的价值在于**把"卡住"这个模糊信号映射到四类完全不同的补救动作**：

| 状态 | 病因 | 补救 |
|------|------|------|
| NEEDS_CONTEXT | 投喂不全 | 补上下文，**同模型**重派 |
| BLOCKED（推理不足） | 模型能力不够 | **换更强模型**重派 |
| BLOCKED（任务过大） | 粒度问题 | **拆小** |
| BLOCKED（计划有错） | 上游问题 | **上报给人** |

如果只有"成功/失败"两种状态，正确的补救动作无从判断——只能盲目重试。**四种状态本质上是把"我卡住了"翻译成"该动哪个变量"。**

而"禁止无效重试"防的是**伪进展**：不改任何条件重试一次，期望不同结果，只会浪费一轮并制造"我在推进"的假象。

### 决策八：禁止并行派发**实现** subagent

**选了什么**：Red Flags 里 `Dispatch multiple implementation subagents in parallel (conflicts)`。

**为什么**：这个体系里每个任务都是**在同一份代码库上顺序累积**的——任务 3 的实现者需要看到任务 2 已提交的代码。并行意味着多个实现者基于**同一个起点**各自改动，合并时必然冲突。而且本技能特意要求每个 subagent 只拿到自己任务的文本（决策二），它**根本不知道别人在改什么**——这恰恰使并行冲突无法被任何一方预防。

> **与 `dispatching-parallel-agents` 的边界**（这是个容易混淆的点）：
>
> | | subagent-driven-development | dispatching-parallel-agents |
> |---|---|---|
> | 能否并行 | **禁止**并行实现 | **鼓励**并行 |
> | 前提 | 任务**顺序累积**在同一代码库 | 问题域**完全独立、无共享状态** |
> | 冲突风险 | 高（改同一批文件） | 低（各自独立文件/子系统） |
>
> 判据就是**有无共享状态**。"修 3 个不同测试文件"可以并行；"实现 5 个有依赖关系的功能任务"不行。**"任务独立"和"工作不冲突"是两件事**——任务之间逻辑上独立，不代表它们不碰同一份代码。

## 3. 机制如何运转

```
【前置】读计划一次 → 提取全部任务全文 + 场景上下文 → 建 TodoWrite

每个任务：
  ┌─────────────────────────────────────────────────────┐
  │ ① 派发实现者（投喂：任务全文 + 场景上下文）              │
  │       ↓ 实现者提问？ → 回答 → 重派                     │
  │ ② 实现者：实现 → 测试 → 提交 → 自审                    │
  │       ↓ 回报 DONE / DONE_WITH_CONCERNS /              │
  │         NEEDS_CONTEXT / BLOCKED                       │
  │       ↓                                              │
  │ ③ 派发【规格合规】评审者（被告知：不要相信汇报）         │
  │       ↓ 有缺失或多做？ → 实现者修复 → 重新评审           │
  │ ④ 派发【代码质量】评审者（取 BASE_SHA/HEAD_SHA）        │
  │       ↓ 有问题？ → 实现者修复 → 重新评审                │
  │ ⑤ 在 TodoWrite 标记完成                               │
  └─────────────────────────────────────────────────────┘
       ↓ 还有任务？
  【收尾】派发最终代码评审 → 转交 finishing-a-development-branch
```

**最容易违反的约束有两条**，原文都做了重点防护：

1. **评审顺序**——写在了 Red Flags 和评审模板两处。因为质量评审的模板更"通用"、更容易顺手先跑。
2. **修复必须由同一个实现者做，且必须重新评审**——`If subagent fails task: Don't try to fix manually (context pollution)`。控制者手上有全局上下文，看起来"顺手改一下更快"，但那样就破坏了这个任务的上下文隔离，也跳过了评审闭环。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **任务紧耦合**（共享设计决策、互相依赖） | 每个 subagent 各自假设、产出互不兼容 | 每个 subagent 只拿到自己任务的文本，看不到兄弟任务；决策树已把这种情况踢回 `brainstorming`，但"基本独立"是**主观判断**，误判后后果严重 |
| **计划质量差** | 零上下文 + 差计划 = 执行者被迫即兴或卡死 | 该技能的可靠性**完全继承自计划**。模型分级、任务粒度、验收标准全部以"计划写得好"为前提 |
| **控制者投喂遗漏** | 走一轮 NEEDS_CONTEXT；若实现者不问而猜，则产出错误 | 兜底机制是"实现者提问"，但**"不问就猜"恰是 LLM 的默认倾向**——兜底依赖一个被普遍违反的行为 |
| **规格文本有歧义** | 规格评审无法判定"少做/多做" | 两阶段评审的判定基准是规格文本的精确度；规格含糊时，评审退化成主观判断 |
| **评审循环不收敛** | 实现者与评审者来回拉锯，成本失控 | 原文只规定"重复直到通过"，没有轮次上限或升级路径 |
| **跨任务一致性漂移** | 命名风格、接口约定、错误处理方式不统一 | 每个 subagent 独立，无人看全局；只有**最后**的最终代码评审能发现，那时修改代价已经很高 |
| **任务数量多** | 主会话上下文仍会膨胀（协调开销） | 隔离的是**实现细节**，不是控制开销：任务全文、状态、评审结论都留在主会话 |
| **评审者自身失误** | 坏代码通过闸门 | 评审者是 LLM，也会犯系统性错误；体系里没有"评审评审者"这一层 |
| **成本敏感场景** | 每个任务 3 个 subagent + 若干评审循环，token 开销可观 | 原文在 "Cost" 一节自己承认了这点，理由是"更早捕获问题比事后调试便宜"——**这个理由成立与否取决于缺陷密度** |
| **计划中后期与早期产出的实际状态不符** | 控制者投喂的"场景上下文"过时 | 任务全文在开工前一次性提取；若前面任务改变了设计，后面的任务描述可能已不准确 |

> **第一、二条是同一个结构性特征的两种表现**：这个技能**把大部分失败风险推给了上游**（计划质量 + 任务独立性），自己只负责"在假设成立时高质量地执行"。它的所有防护（两阶段评审、禁止无效重试、不信任汇报）都在防**执行阶段的漂移**，而不防**前提错误**。
>
> 这不是缺陷，而是**分层**：`writing-plans` 负责让计划可信，`brainstorming` 负责让任务可分离。但这也意味着——**单独使用这个技能、喂它一份粗糙的手写计划，会得到一个"纪律严明但方向错误"的过程**，而且因为评审很严格，你会对产出更有信心。这个组合是危险的。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **上游** `writing-plans` | 计划来源。本技能的全部可靠性建立在其质量之上（零占位符 → 模型分级可行） |
| **上游** `brainstorming` | 通过计划间接依赖：任务的可分离性是在设计阶段确定的 |
| **上游** `using-git-worktrees` | 提供隔离工作区；否则多个 subagent 会直接改到主分支 |
| **下发给 subagent** `test-driven-development` | 每个实现者按 TDD 工作——TDD 是**计划的一步**，不是本技能的机制 |
| **复用** `requesting-code-review` | 代码质量评审的 prompt 模板直接沿用，只追加了文件职责/体量增长的检查项 |
| **下游** `finishing-a-development-branch` | 收尾必须转交，本技能不自行决定合并 |
| **替代** `executing-plans` | 二者互斥，取决于"是否有 subagent 支持 / 是否同会话" |
| **边界** `dispatching-parallel-agents` | 本技能**禁止**并行实现；那个技能**鼓励**并行调查。判据是"有无共享状态" |
