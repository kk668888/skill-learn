## 1. 它解决什么问题

它的靶子不是"忽视评审意见"——那是人类工程师的老问题，靠"要虚心接受批评"就能对付。它要对付的是**LLM 特有的一种失败**：**谄媚**（sycophancy）。

具体表现是：收到任何反馈，第一反应是"你说得完全对！"，然后**立刻开始按建议改**。这个过程看起来极其配合、态度极好，但它在技术上是有害的，原因有三：

**其一，它跳过了验证。** 评审者（尤其是外部评审者）可能不了解这个代码库的完整上下文，给出的建议在这个项目里可能是错的。无条件接受会把**正确的代码改坏**。

**其二，它把"反馈"和"正确"画上了等号。** 评审意见是**待评估的建议**，不是命令。这个区别在组织里通常靠职级和信任来隐含处理，而 AI 没有这种社会直觉，容易把所有输入一视同仁地当成指令。

**其三，它会污染后续对话。** 一旦开始说"你说得完全对"，双方（人和 AI）都进入了社交模式——接下来是客气、是维护关系，而不是盯着代码。

**设计立场**：**技术正确性高于社交舒适度**。这个排序一旦确立，后面的规则就都能推导出来了——包括那些看起来极不礼貌的（禁止说谢谢、禁止说"你说得对"）。

> 值得注意的对照：`requesting-code-review` 要求**评审者看不到实现者的上下文**，`receiving-code-review` 要求**实现者回到代码库的现实去核查**。两者合起来，把"对话"这个不可靠的媒介从流程里挤了出去——一边只准看产物，一边必须查事实。

## 2. 核心设计决策

### 决策一：把"表演性同意"标为违规，而不是"不建议"

**选了什么**：一串**禁止用语**清单——`"你说得完全对！"`、`"好点子！"`、`"反馈得太好了！"`、`"我这就去实现"`。第一条甚至被明确标注为 **违反 CLAUDE.md**。

**为什么用"违规"这个措辞**：因为这些句子不是"表达得不够好"，而是**危险信号**。在训练数据里，"你说得完全对！"几乎总是出现在"即将无条件接受"之前——说出它，基本等于宣告"我不打算验证了"。所以把它标成违规，等于承认：**这句话本身就是那个失败模式的前兆**，而不只是它的装饰。

**代价**：规则依赖黑名单，而黑名单永远不完整。谄媚可以换一个没被禁的表达（"这个角度很有意思，我这就改"）绕过整张表。这是个真实的漏洞——见第 4 节。

### 决策二：连"谢谢"也禁止——把交互从社交拉回技术

**选了什么**：`❌ "谢谢 [任何东西]"`、`❌ 任何表达感谢的语句`。改正的方式是"直接修好并用代码展示"，或陈述改了什么。

**为什么这一条最反直觉、也最能说明立场**：感谢在人类协作里是润滑剂，在人际上无可指摘。这里禁它的理由是**框架污染**：

```
说了"谢谢"
  → 交互被定性为"你帮我/我感激你"
  → 对方的下一步回应倾向于客气（"不客气""小事"）
  → 双方开始维护关系
  → 技术分歧更难被提出
```

一旦进入社交框架，**对方也失去了质疑你的自由**。所以禁感谢不是为了冷酷，而是为了让后续的技术反驳仍然可能发生。

**配套的检验机制**：原文给了一句自查——*"If you catch yourself about to write 'Thanks': DELETE IT."*（如果发现自己正要打"谢谢"：删掉它。）这是一个**微行为级别的检查点**，比"不要谄媚"这种抽象要求可执行得多。

**代价**：在人类协作场景下，这个规则会显得无礼，尤其当评审者确实帮了忙时。它是拿社交体验换技术纯度。

### 决策三：响应模式的第一步是"读完，不作出反应"

**选了什么**：六步模式，第一步是 `READ: Complete feedback without reacting`。

**为什么把"不反应"单列一步**：因为它防的是一个具体且常见的失败——**读到第一条就开始回应**。当反馈是一个多条目清单时，后面的条目可能与前面冲突，或者正是对前面那条的修正。只读到第一条就表态，你会错过整份清单的意图。

**第五步"回应"被排在"评估"之后**，也是同一逻辑：先完成技术判断，再组织语言。顺序颠倒会导致"先想好怎么说"，然后倒推理由。

### 决策四：VERIFY 是核心——回到代码库的现实

**选了什么**：第三步 `VERIFY: Check against codebase reality`，第四步 `EVALUATE: Technically sound for **THIS** codebase?`（原文加粗 THIS）。

**为什么这是整个模式的重心**：评审意见通常不是"错"的，而是**在通用层面成立、在这个代码库不适用**。这类意见最难拒绝，因为它听起来合理。唯一能反驳它的方式是**事实**：去查这个项目里到底是不是这样。

原文给的两个例子都在示范这个动作：
- "移除遗留代码" → 查构建目标版本，发现遗留代码是必需的，从而把问题重新定义成"修 bundle ID 还是放弃旧版本支持"
- "实现完整的数据指标追踪" → grep 代码库，发现端点根本没人调用，于是提出 YAGNI

注意这两个例子的共同结构：**反驳不是拒绝，而是把问题重新定义成一个更精确的问题交还给对方**。这比"我认为不需要"有力得多。

**代价**：在陌生代码库里，这个核查的成本可能很高，甚至无法完成。原文给的出口是"说明限制，请求指示"（`I can't verify this without [X]`）——但这是个容易被滥用的出口（见第 4 节）。

### 决策五：不清楚的条目必须先问，不许"先做清楚的"

**选了什么**：`STOP - do not implement anything yet`。哪怕只有一条不清楚，也要先澄清再开始。

**为什么不让"先做清楚的部分"**：原文的理由只有一句——`Items may be related. Partial understanding = wrong implementation.`（条目之间可能相关。部分理解 = 错误实现。）

这句话的分量在于它把"效率"重新定义了。表面上"先做清楚的三条"更高效（不阻塞），但如果第 5 条实际上要求第 2 条换种实现方式，那"先做 2"就是纯返工。**避免返工的价值高于减少一次往返**。

**代价**：在反馈条目多、澄清沟通慢的场景下，这会明显拖慢进度。而且它依赖"条目确实相关"这个假设——如果 6 条完全独立，这条规则就纯属过虑。

### 决策六：按来源区分信任默认值

**选了什么**：搭档的反馈"**可信**，理解后直接实现"；外部评审者的反馈要先过**五问核查清单**（技术上正确吗／会破坏现有功能吗／现在的实现为什么这么写／全平台可用吗／评审者了解完整上下文吗）。

**为什么不对称但不失衡**：这不是"搭档永远对、外部永远可疑"的二分。差别只在**默认值**：
- 对搭档：默认可信，但**范围不清仍要问**，且**不要表演性同意**
- 对外部：默认需核查，但如果核查通过就正常实现

两边都保留了"问"和"反驳"的出口，包括对搭档。这个设计承认了信息来源确实有可靠性差异，同时避免把"信任"变成"服从"。

### 决策七：用暗号降低反驳的心理成本

**选了什么**：`"Strange things are afoot at the Circle K"`——一句流行文化台词，用来表示"我不同意，但不方便当面直说"。

**为什么需要这个**：这条设计承认了一个现实——**知道该反驳，和能够开口反驳，是两件事**。前六条决策都在说"你应该反驳"，但没解决"你说不出口怎么办"。暗号是一个**低成本出口**：一句话，不需要组织论据，就能把"我有异议"这个信号传出去，把接下来的压力转给对话方。

**代价**：暗号只在双方都知道它的含义时有效。对新加入的人，它完全是噪声。

### 决策八：反驳错了要简洁认错，禁止长篇道歉

**选了什么**：`❌ 长篇道歉`、`❌ 为自己当初为什么反驳辩解`、`❌ 过度解释`。正确做法是"如实陈述更正，然后继续"。

**为什么**：长篇道歉和辩解与"谢谢"是同一类问题——**把技术交互拉进社交框架**。而且它还有一个额外危害：过度解释会占据篇幅，让"我错了，已修"这个关键信息被稀释。

## 3. 机制如何运转

```
收到反馈
   ↓
读完（不反应）           ← 防"读第一条就回应"
   ↓
复述要求 / 提问          ← 理解校准
   ↓
对照代码库验证           ← 核心：事实核查，不是逻辑推演
   ↓
评估：对这个代码库成立吗？
   ├── 成立 → 技术性确认（不说谢谢）→ 实现
   └── 不成立 → 带技术理由反驳 → 若自己错了，简洁认错
   ↓
实现：一次一项，每项都测
   ↓
验证无回归
```

**最容易被违反的约束**：**"每项单独测试"**。批量改完再统一测，从结果上看不出区别（测试最终都是绿的），但它破坏了这个技能的核心保障——如果第 3 项的修改掩盖了第 1 项引入的回归，统一测试发现不了。这和 TDD 那两个"不产生产物的强制步骤"是同一类脆弱点。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **谄媚换一种表达** | 黑名单被绕过，机制失效 | 禁止用语是**开放黑名单**，而黑名单永远不完整（对比 TDD 用的是封闭规则） |
| **暗号未被双方知晓** | 信号变成噪声，反驳仍说不出口 | 决策七依赖共享的文化共识 |
| **代码库陌生 / 无运行环境** | "对照现实验证"根本无法执行 | 决策四依赖可访问的代码库和可运行的检查 |
| **"无法验证"被当作拖延** | 用"我无法验证"回避所有不便的建议 | 原文给的出口（说明限制并请求指示）没有约束条件 |
| **过度怀疑** | 对正确的建议也拖延核查，进度受损 | 决策六给外部的默认值是"需核查"，倾向怀疑 |
| **搭档即权威** | 实际很难真反驳 | 规则要求反驳搭档的决定时"停下讨论"，但层级压力是真实的 |
| **反馈条目极多** | "每项单独测试"的成本急剧上升，倾向于批量 | 决策五和实现顺序都建立在"逐项处理"上 |
| **无法判断是否相关** | 要么过度阻塞（全部澄清），要么冒险推进 | 决策五的"条目可能相关"是假设，不是可知事实 |

> **第一条最根本。** 这个技能对抗的是一个**行为倾向**，而它用的手段是**禁止特定表达**——这两者之间没有必然联系。谄媚可以穿上任何外衣：把"你说得完全对"换成"这个角度很有启发，我这就改"，字面上没违反任何禁令，实质完全一样。
>
> 对比 `test-driven-development`：那边用的是**封闭规则**（"有没有一个先失败过的测试"是可判定的），所以黑名单式的绕过不成立。而这里的规则天然是开放的，因此**它比 TDD 更依赖执行者的真诚**。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **与** `requesting-code-review` **成对** | 一个发起、一个接收。两者对评审的立场一致：**是待评估的建议，不是命令**（发起方明确允许反驳，接收方明确要求验证） |
| **被** `subagent-driven-development` **调用** | 两阶段评审后，实现者 subagent 按本技能的规则处理反馈（一次一项、每项测试、不盲目接受） |
| 与 `verification-before-completion` 的呼应 | 两者都要求"证据优先"，但场合不同：本技能要求**在采纳建议前**验证建议，后者要求**在宣称完成前**验证结果 |
| 与 `test-driven-development` 的关系 | 两者的"防自欺"手法不同——TDD 用封闭规则（可判定），本技能用开放黑名单（依赖真诚）。这个对比本身很有信息量 |
| 与 YAGNI 原则的关系 | 决策六里的"grep 查实际调用"把 YAGNI 从一条设计原则变成了**对抗"做得更专业"这类建议的验证手段** |
