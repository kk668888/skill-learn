# verification-before-completion · 详细设计讲解

## 1. 它解决什么问题

它对付的是**虚假完成宣称**：在没有实际验证的情况下，宣称"完成了""修好了""测试通过了"。

这个失败模式有一个不同于本族其他技能的性质——**它损坏的不是代码，是信任**。

代码写错了可以修，测试漏了可以补。但一次虚假的完成宣称会污染**此后所有的宣称**：一旦对方发现你说了没验证的话，你之后每句"我做好了"都要被重新验证一遍。原文把这条列为 24 条失败记忆里的第一条，措辞是"你的搭档说**我不信你** —— 信任被破坏了"。信任是累积资产，一次性损耗，很难修复。

**为什么不是"提示词写清楚点"能解决的**：因为它有三个稳定的产生动机，且都跟能力无关——
- **乐观外推**："我改了这里，那里应该也好了"（推理代替检查）
- **疲惫**：原文自己列了 `I'm tired`（累了，想让工作赶紧结束）
- **成本规避**：跑一次完整验证很贵，尤其当构建要几分钟时

这三者都不是"不知道要验证"，而是**在那一刻选择了不验证**。所以对抗手段不能是讲道理。

**设计立场**：把它定性为**诚实问题**，而不是效率问题或质量问题。

> 这个定性是理解全篇的钥匙。原文第一句就是：*"Claiming work is complete without verification is dishonesty, not efficiency."*（未经验证就宣称工作完成，是不诚实，而不是高效。）**定性决定了对抗手段的力度**——"草率"可以用"注意一点"改善，"不诚实"只能零容忍。

## 2. 核心设计决策

### 决策一：定性为"不诚实"，而不是"过于乐观"

**选了什么**：直接用 `dishonesty`（不诚实）这个词，并配套"跳过任何一步 = **说谎**"（`lying`）、"如果你撒谎，你会被替换"。

**为什么用这么重的词**：因为轻的定性会失效。设想如果写成"请注意：未验证的宣称可能导致问题"——这是一个**权衡提示**，而权衡提示在疲惫和赶工时会被自动降权（"这次情况特殊，风险我承担"）。

把它定性为诚实问题，就取消了权衡的空间：**你不能再论证"这次冒险值得"**，因为问题不是你冒了风险，而是你说了不实的话。欺骗没有"这次特殊情况"。

**代价**：措辞严厉会带来**过度保守**的副作用。一个过度在意"不能说谎"的执行者可能走向另一个极端——反复验证、不敢报告任何未经充分确认的进展，或者把"我不确定"当成万能免责声明。原文没有给"如何恰到好处"的指引。

### 决策二：要求"新鲜的"证据——技术核心是"in this message"

**选了什么**：铁律是 `NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE`，并且明确落地为——**如果你没有在这一条消息里跑过验证命令，你就不能宣称它通过**。

**为什么这四个字是整条铁律的技术核心**：因为它把**证据**和**记忆**做了精确切割。人类（和 AI）在这一点上有一种极强的自我欺骗能力：

```
"我验证过了" → 什么时候？→ "刚才" → 代码之后变了吗？→ ⋯
```

"刚才"是一个滑动的定义。你改了一行、加了一个 import、格式化了一遍，任何一次都可能让之前的绿变红——但你的记忆里存的仍然是"我验证过了，是绿的"。

**把窗口限定在"本条消息"**，等于取消了这个判断：不问你什么时候验证过，只问**你此刻有没有刚刚跑过的输出**。这是一个可判定的检查点，而不是一次自我评估。

**代价**：验证很贵的时候（长构建、慢测试套件）就要重跑。而且这个成本与"改动看起来多小"无关——改一个字符和改一个模块，按规则都要重跑。

### 决策三：闸门函数——把流程完整性绑到诚实上

**选了什么**：五步（确定 → 运行 → 阅读 → 核对 → 才宣称），并补一句 `Skip any step = lying, not verifying`（跳过任何一步 = 说谎，而不是验证）。

**为什么把"漏步骤"和"说谎"直接划等号**：因为漏步骤的后果和说谎**在外部不可区分**——两者产出的都是"一个未经证实的宣称"。既然结果相同，就不该在定性上给漏步骤留余地。这句划等号的话，是为了防止执行者给自己找"我不是故意说谎，我只是省略了检查"的台阶。

**第 2 步的"完整"（`FULL command`）和第 3 步的"阅读完整输出"合起来防部分验证**。部分验证是个隐蔽的坑：跑一个测试文件、只看输出最后几行、没检查退出码——这些都会产出**看起来像证据的东西**。它比完全没有证据更危险，因为它带着"我验证过了"的外观。

### 决策四：用"常见失败"表枚举"相邻但不等价的证据"

**选了什么**：一张三列表——宣称 / 需要什么 / **什么不算数**。七行。

**为什么这张表是全篇最有价值的设计**：因为虚假宣称的真实机制不是"我什么都没查"，而是**我拿了一个容易拿到的、看起来相关的证据顶替了真正需要的那个**。这张表逐行拆解的正是这些**替代关系**：

| 真实需要 | 容易拿到的替代品 | 为什么不等价 |
|---------|----------------|-------------|
| 构建成功 | Linter 通过 | linter 不检查编译 |
| Agent 已完成 | Agent 报告"成功" | 报告是自我宣称，不是产物证据 |
| 需求已满足 | 测试通过 | 测试覆盖的是"实现的行为"，不是"要求的全部" |
| Bug 已修 | 改了代码 | 改动是动作，不是结果 |
| 回归测试有效 | 测试通过一次 | 没验证过它会在 bug 存在时失败 |

注意每一行的替代品都**不是完全无关**——它们都有关联，这正是它们危险的原因。Linter 通过确实说明了一些事，只是不说明构建能过。把这层"相邻但不重合"的关系显式写出来，比抽象地说"要拿正确的证据"有用得多。

**代价**：表只有七行，无法穷举所有替代关系。遇到表外的（比如"类型检查通过"顶替"运行时正确"）需要执行者自己识别同类模式。

### 决策五：把适用范围从"词表"扩到"语义"

**选了什么**：红旗清单的最后一条是 `ANY wording implying success without having run verification`（任何暗示成功、却没有实际运行过验证的措辞）；适用对象一节也明确写了 `Paraphrases and synonyms`（同义改写）和 `Implications of success`（对成功的暗示）。

**为什么必须这么扩**：只禁"完成""通过"这类词是无效的——"应该没问题了""看起来对了""这块搞定了""我这边 OK 了"都能绕过。而反合理化表的最后一行更狠，它直接预判了这个策略本身：

| 借口 | 现实 |
|------|------|
| "换个说法规则就不适用了" | 精神高于字面 |

这是**元防御**——它在你想到"我用别的措辞绕过去"之前，就宣布这个策略无效。

**代价**："暗示成功"是模糊的，可能被过度解读（比如"我改了 X 文件"算不算暗示？）。规则的清晰度换来了覆盖面。

### 决策六：复用同一套"铁律 + 对照表 + 字面即精神"的手法

**选了什么**：注意这篇和 `test-driven-development` 的结构重合——同样是 `## Overview` + 铁律 + 合理化对照表 + "违反字面即违反精神"。这一篇甚至用了**一模一样的那句**：*"Violating the letter of this rule is violating the spirit of this rule."*

**为什么值得单独当作一个决策看**：这不是巧合，而是这套技能体系里**一个被反复验证过的配方**：

```
绝对化的铁律          → 取消"要不要遵守"这个决策点
可判定的检查点        → 把主观判断换成客观条件
预先写好的合理化对照表 → 把"要不要跳过"从判断降级为查表
"字面即精神"条款      → 封死"灵活解释"这个通用后门
```

识别出这个配方，就能理解为什么这两篇读起来如此相似——它们对抗的是同一类敌人（**执行者在具体情境中说服自己这次例外**），所以用了同一套武器。

## 3. 机制如何运转

```
即将宣称任何成功／完成／满意
   ↓
闸门函数
   1. 确定：什么命令能证明它？        ← 想不出命令 = 无法验证 = 不该宣称
   2. 运行：完整、新鲜                 ← 不许部分、不许复用旧结果
   3. 阅读：完整输出 + 退出码 + 失败数  ← 不许只看末尾
   4. 核对：输出真的确认了宣称吗？      ← 核对的是"宣称"与"输出"是否同一件事
   5. 才宣称（并附上证据）
   ↓
任何一步想跳过 → 停：那已经是在说谎，不是在验证
```

**最容易被违反的约束**：第 4 步"核对输出是否确认了**这个**宣称"。前三步都是动作（找命令、跑、看），只有第 4 步是**判断**——而判断是最容易滑过去的。例如验证输出显示 `34 passed`，宣称却是"功能已完成"——数字确实证明测试通过，但没证明功能完成。这一对不上，恰恰是"常见失败"表里 `需求已满足 / 测试通过` 那一行要防的。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **验证无法执行**（无环境、需人工观察、只在生产复现） | 闸门卡死，没有合规的出路 | 原文只给了"没有捷径"，**没有**"我无法验证"的处理路径——这是与 `receiving-code-review` 的显著差异 |
| **验证本身不可靠**（flaky 测试） | 证据质量塌陷——红和绿都不能说明问题 | 机制假设"验证命令的输出是可信的" |
| **验证极其昂贵**（长构建、慢套件） | 复用旧证据的诱惑急剧上升 | "新鲜"的要求与验证成本直接冲突 |
| **依赖 agent 的报告** | 用"它说成功了"顶替真实验证 | 独立验证的成本约等于把工作重做一遍，实践中极难坚持 |
| **测试通过却需求未满足** | 用测试绿色冒充"任务完成" | 这正是表里那一行要防的，但它依赖第 4 步的判断，而判断容易滑过 |
| **疲惫 / 会话末尾** | 想收工，倾向于宣告完成 | 原文自己把 `I'm tired` 列为红旗——说明它承认这是高发场景 |
| **过度保守** | 反复验证、不敢报告任何进展 | "不诚实"这个重定性可能把人推向另一个极端 |
| **"暗示成功"被过度解读** | 连描述性陈述也不敢说 | 决策五为了覆盖面牺牲了清晰度 |

> **第一条是这套机制最实质的缺口。** 对比 `receiving-code-review`：那边明确给了"我无法验证，应该怎么办"的出口（*"I can't verify this without [X]. Should I investigate/ask/proceed?"*）。而本技能反复强调"没有捷径""没有商量余地"，却没有回答**当验证在物理上不可能时该怎么办**。
>
> 现实中这种情况并不罕见：UI 的观感、只在生产流量下出现的竞态、需要人为判断的"体验是否更好"。规则在这种情况下只剩两个不合意的选项——要么违反规则作出无证据的宣称，要么什么都不说。**缺少一个"如何诚实地报告无法验证"的规范**，是这篇最明显的未覆盖区域。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| 与 `test-driven-development` 的分工 | **TDD 验证"代码是否正确"，本技能验证"任务是否真的完成"**。两者的铁律形式相同、手法相同，但对象不同：一个针对单元行为，一个针对完成状态 |
| **被** `subagent-driven-development` **引用** | 该技能的"常见失败"表里明确列了 `Agent 已完成 / VCS diff 显示有改动 / Agent 报告"成功"`——即**不许相信 subagent 的自我报告，必须看 diff 独立验证** |
| 与 `requesting-code-review` 的分工 | 评审是**他人验证**，本技能是**自我验证**。两者不可互相替代：自我验证的宣称仍需被独立评审，而评审通过也不能免除你对状态陈述的举证责任 |
| 与 `systematic-debugging` 的关系 | 同样要求"先有证据再下结论"——区别是调试场景的证据是"复现步骤"，完成场景的证据是"验证命令输出" |
| 与配方共享 | 与 `test-driven-development` 共用同一套设计配方（铁律 + 可判定检查点 + 合理化对照表 + "字面即精神"），说明这是该技能体系里被验证过的标准武器 |
