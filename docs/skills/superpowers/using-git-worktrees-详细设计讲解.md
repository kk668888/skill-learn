## 1. 它解决什么问题

它解决的是**污染的不可逆性**。

Superpowers 的主链路里，紧跟在它后面的是 `subagent-driven-development`——一个会连续自动执行几十个实现任务、中途几乎不停下来问你的过程。这个过程有两个特征：

1. **改动量大且不可预测**。subagent 会写代码、装依赖、跑构建、生成产物。你无法事先知道它会碰哪些文件。
2. **不可中途回退**。一旦在主分支上直接开干，发现方向错了，你得从一堆混杂的改动里分辨哪些是这次的、哪些是之前的。

`worktree` 提供的不是"整洁"，而是**可丢弃性**：整个工作区是一个可以整体删掉的目录，主分支从头到尾没有被碰过。**"这次做得不对，整个扔掉"** 这个选项的存在，才是它真正买来的东西。

**设计立场**：隔离应当是**默认的**，但**必须经用户同意**。这两条看起来矛盾，实际上划定了这份技能的位置——它既反对"直接在 main 上改"，也反对"不问就建一堆目录"。

## 2. 核心设计决策

### 决策一：检测优先于创建（Step 0）

**选了什么**：在创建任何东西之前，先判断"是否已经处在隔离环境中"。

**为什么**：防的是**嵌套**。如果宿主环境（Claude Code 的 `EnterWorktree`、某个 IDE、CI 的 workspace）已经把你放进了一个隔离工作区，而你不加检查地再建一个 git worktree，结果是在 worktree 里套 worktree——分支关系、清理归属、`git worktree list` 的输出全部错乱。

**代价**：Step 0 引入了判断逻辑，而判断逻辑会出错。原文自己就记录了一个真实的坑：判定"是否在 linked worktree 中"的标准手法是比较 `--git-dir` 与 `--git-common-dir`，但**这个信号在 submodule 内部同样成立**——两个完全不同的原因产生同一个信号。技能为此专门加了 submodule 防护。这暴露了一个结构性问题：**用一个布尔信号去回答一个二义性问题**，只能靠补丁逐个补漏。

### 决策二：原生工具优先于 git（"Never fight the harness"）

**选了什么**：Step 1a 先找是否有 `EnterWorktree`、`WorktreeCreate`、`/worktree` 命令或 `--worktree` 标志；有就用它，只在完全没有时退到 `git worktree add`。

**为什么**：原文给出的理由很具体——*"在已经有原生工具的情况下使用 `git worktree add`，会制造出你的宿主环境看不见、也无法管理的幻影状态。"*

这是全篇最重要的一条，因为它描述的不是"效率差异"，而是**状态一致性**。宿主工具在创建 worktree 时会同时登记自己的内部状态（会话与目录的绑定、退出时的清理责任、界面上的指示）。绕过它直接跑 git 命令，git 那边多了一个 worktree，而宿主那边完全不知道——**两边对"现在有几个工作区"的认知不一致**。之后无论是清理、切换还是报错，都会因为这个不一致而表现得莫名其妙。原文把它标为"头号错误"，是有道理的。

**代价**：Step 1a 的实现是**启发式探测**——"它可能是名为 `EnterWorktree`、`WorktreeCreate` 的工具，或 `/worktree` 命令，或 `--worktree` 标志"。这种靠名字猜能力的做法很脆弱：宿主改个工具名、或者提供一个功能等价但名字不含 worktree 的机制，探测就失败了，于是退化到 git 方案——恰好是技能最想避免的那条路。

**备选方案**：
- *一律用 `git worktree add`* —— 被否决。见上，制造幻影状态。
- *一律用原生工具* —— 不可行。并非所有宿主都有。

### 决策三：目录位置用"优先级链"而不是固定路径

**选了什么**：指令中的偏好 → 已有 `.worktrees/` → 已有 `worktrees/` → 已有全局目录 → 默认 `.worktrees/`。

**为什么**：worktree 放哪儿不是技术问题而是**约定**问题——不同项目有不同习惯，硬编码一个路径会违反项目既有约定，而"跟随既有约定"本身是有价值的（团队里所有人看到同一个位置，减少认知负担）。

优先级链的形式比"默认值 + 覆盖"更细致的地方在于：它把"**已存在**"排在"**默认**"之前。所以一个项目如果历史上用 `worktrees/`（不带点），技能会沿用，而不是硬塞 `.worktrees/`。这是对既有状态的尊重。

**代价**：优先级链带来一个**顺序本身就成了规范**的问题——而原文在这里出现了自相矛盾（见第 4 节第一行）。

### 决策四：`git check-ignore` 硬校验

**选了什么**：创建项目本地的 worktree 之前，必须验证目标目录已被 git 忽略；没被忽略就先加进 `.gitignore` 并提交。

**为什么**：worktree 目录里是一份**完整的仓库副本**（含 `.git`）。如果它在仓库内且未被忽略，`git add .` 会把整个副本吞进版本库——几千个文件、递归嵌套的引用。这是个一旦发生就非常难清理的错误。

**为什么必须是硬校验而不是提醒**：因为**默认状态就是危险的**。`.worktrees/` 不在任何默认的 `.gitignore` 模板里。也就是说，一个全新项目按技能的默认路径建 worktree，**开箱即错**。这个决策把"危险默认"转成了"必须显式通过检查"。

**代价**：修改并提交 `.gitignore` 是一次**对仓库的写入**——为了建隔离工作区，反而先在主分支上留了一个提交。轻微的自相矛盾，但可接受。

### 决策五：基线测试，且失败时必须征得同意

**选了什么**：创建后跑测试确认基线是绿的；**如果失败，报告并询问是否继续**。

**为什么**：基线的作用是**归因**。绿的基线意味着此后出现的任何红色都是新代码造成的。没有这个参照点，一个预先存在的失败会混进你的调试过程。

而"失败时必须问"这一条更关键：它承认**基线失败不一定是阻断性的**——你可能就是要在一个已经挂着的仓库上工作（比如你的任务正是修那个失败的测试）。所以它不武断地禁止继续，而是把决定权交还给人。

**代价**：在无人协作的场景（自动化流程、subagent 独自执行）里，"询问"会卡住——没有人在那儿回答。此时这个安全阀会变成一个死锁点。

### 决策六：为沙箱拒绝预留退化路径

**选了什么**：如果 `git worktree add` 因权限错误失败（沙箱拒绝），明确告知用户并**就地工作**。

**为什么**：这是一个**承认环境可能不允许**的设计。在受限沙箱里，创建目录到仓库外（或写 `.git` 元数据）常常被拒绝。如果没有这条路径，AI 可能会反复重试同一个注定失败的命令，或者更糟——悄悄换一种方式绕过沙箱限制。

这条路径的做法是：明确说出来，然后退到一个合法的替代方案（就地工作）。**它把"做不到"变成了一个可报告的结局，而不是一个卡死。**

## 3. 机制如何运转

```
开始
 ↓
Step 0  检测是否已有隔离
   ├─ GIT_DIR != GIT_COMMON 且非 submodule？
   │      → 已在 worktree，跳到 Step 3
   └─ 否则（普通仓库 / submodule）
          ↓
       用户已声明偏好？
          ├─ 是 → 遵从
          └─ 否 → 征求同意
                 ├─ 拒绝 → 就地工作，跳到 Step 3
                 └─ 同意 ↓
Step 1  创建
   ├─ 1a 有原生 worktree 工具？ → 用，跳到 Step 3
   └─ 1b 退化到 git worktree add
          ├─ 选目录（优先级链）
          ├─ check-ignore 校验（项目本地）
          ├─ git worktree add  ← 权限失败？→ 沙箱退化，就地工作
          └─ cd 进新 worktree
                 ↓
Step 3  项目初始化（按 lock 文件自动检测）
                 ↓
Step 4  跑基线测试
   ├─ 通过 → 汇报就绪
   └─ 失败 → 报告 + 询问是否继续
```

**最容易违反的约束**：Step 0。它是唯一一个"什么都不做"的步骤，因此在赶时间时最容易被跳过——而跳过它的后果（嵌套 worktree、幻影状态）不会立刻显现，只会在清理阶段变成一个难以理解的错误。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **原文内部自相矛盾**：目录优先级 | 用户声明与既有目录冲突时，行为不确定 | 「目录选择」一节说"指令偏好优先于既有目录"；而「红旗」一节写的是"existing > global legacy > **instruction file** > default"。两处顺序不同 |
| 项目**不是 git 仓库** | 整个技能不可用 | 全篇建立在 `git rev-parse` / `git worktree` 之上 |
| 宿主工具**名字不含 worktree** | 误判为"无原生工具"，退化到 git 方案 | Step 1a 靠名字启发式探测（`EnterWorktree`/`WorktreeCreate`/`/worktree`/`--worktree`） |
| **全局路径是作者特定约定** | 跨项目几乎不会命中，优先级链第 3 级形同虚设 | `~/.config/superpowers/worktrees/` 是 Superpowers 自己的遗留路径 |
| **无人协作**时分基测试失败 | 卡在"询问是否继续"上 | 该安全阀依赖有人回答 |
| 反馈周期**很长**的项目 | 建 worktree + 装依赖 + 跑基线成本极高，可能被整体跳过 | 初始化（`npm install` 等）和基线测试都不是廉价操作 |
| 沙箱**拒绝创建目录** | 隔离目标完全落空，退回就地工作 | 退化路径只保证"不卡死"，不保证"达到隔离" |

> **最值得注意的是第一行——这是一处真实的不一致，而不是设计取舍。**
>
> 「目录选择」一节写的是：
> ```
> 1. Check your instructions for a declared worktree directory preference.
> 2. Check for an existing project-local worktree directory
> 3. Check for an existing global directory
> 4. default to .worktrees/
> ```
> 而「红旗」一节写的是：`Follow directory priority: existing > global legacy > instruction file > default`
>
> 两者对"用户声明"和"既有目录"谁优先，给出了**相反**的答案。第一节明确说 *"Explicit user preference always beats observed filesystem state"*（显式用户偏好永远高于观察到的文件系统状态），而红旗那行把 instruction file 排到了 existing 和 global legacy **之后**。
>
> 这类矛盾在纪律型技能里代价不小：**执行者可能两处都读到，然后按先读到的那个执行**——结果是不同会话行为不一致。它也印证了第 2 节决策三里提到的问题：优先级链一旦分散在多处表述，就容易各自漂移。**单一事实来源**（把顺序只定义一次，别处引用）本该是这里的做法。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **被** `subagent-driven-development` **前置要求** | 它明确要求先把隔离工作区准备好，再开始逐任务派发实现 subagent |
| **被** `executing-plans` **前置要求** | 同上，批量执行模式也需要隔离 |
| **与** `finishing-a-development-branch` **成对** | 本技能负责建，收尾技能负责按 provenance 判断该不该删——**只有它自己建的才清理** |
| **被** `writing-plans` **间接依赖** | 计划里标注了"如果在隔离 worktree 中，应在执行时创建" |
| 与 `brainstorming` 的位置关系 | 在链路里排在设计之后、计划之前——**设计已定才开始隔离**，避免为一个还不知道要做什么的任务先建目录 |
