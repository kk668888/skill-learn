## 1. 它解决什么问题

它对付的是**猜测式修复**——看到报错，凭直觉改一处，跑一下，还报错，再改一处。

这种模式的三重代价在原文开篇一句话里就点明了：*"Random fixes waste time and create new bugs. Quick patches mask underlying issues."*

- **浪费时间**：原文给了数字——系统化 15-30 分钟，乱试 2-3 小时。
- **制造新 bug**：一次改多处，无法判断哪一处起了作用，也无法判断哪一处引入了新问题。
- **掩盖底层问题**：这是最重的一条。补丁让症状消失，于是**根因失去了被发现的机会**——问题潜伏下来，直到在更贵的地方爆发。

**为什么这个问题特别难治**：因为它的驱动力来自一个**不对称**——症状是可见的、具体的、就在眼前（"这一行报错"），而根因是抽象的、需要调查的。人（和 LLM）天然倾向于处理眼前那个具体的东西。"我先把它弄不报错"在当下永远感觉是对的。

**设计立场**：把**"理解"设为"修复"的前置条件**。不是"建议你先调查"，而是把顺序本身变成规则——没有完成根因调查，你就**不许**提修复方案。这个约束的作用是把"我知道我还没搞懂，但我先试一下"这个念头从可选项中删掉。

## 2. 核心设计决策

### 决策一：用铁律（Iron Law）而不是建议

**选了什么**：`NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST`——全大写，放在独立的代码块里，紧跟一句"如果你还没完成阶段 1，你就不能提出修复方案"。

**为什么**：诊断类技能面对的是**意志力最弱的时刻**。生产挂了、上级在催、你已经有三个猜想——这时候"建议"是没有约束力的。铁律的价值不在信息量（它说的和后面四阶段说的是同一件事），而在**形式**：它是一道门槛，而不是一条提示。

配套的是那句 *"违反本流程的字面，就是违反调试的精神"*。这一句专门封堵一类辩护——"精神我懂，只是这次情况特殊，没必要拘泥字面"。`writing-skills` 把这种写法列为纪律型技能的**标准加固手法**：不等对方提出辩护，先把辩护的退路标注为无效。

**代价**：这种绝对化措辞在**确实不需要**流程的场合会显得教条。原文用"不要跳过"一节来软化（列举了"问题看起来简单"等情况），但那本质上是把一个例外清单塞进铁律里，两者并没有真正调和——它仍然是"一律不许"，只是提前回答了最常见的三个反驳。

**备选方案**：
- *写成"强烈建议"* —— 被否决。在压力下不构成约束。
- *写成"先估算修复成本，超过阈值才走流程"* —— 被否决。**成本估算本身就需要理解问题**，而这个技能的前提恰恰是你还不理解。这是一个自我指涉的循环：要判断"该不该调查"，你得先调查。

### 决策二：切成四个固定阶段，每阶段有独立完成标准

**选了什么**：根因调查 → 模式分析 → 假设验证 → 实施，**必须按序完成**。

**为什么**：把一件"想清楚再动手"的模糊要求，拆成四个各自可判定的段落。关键在于**每阶段都有自己的成功标准**（原文速查表给出了）：阶段 1 是"理解 WHAT 和 WHY"，阶段 2 是"找出差异"，阶段 3 是"确认或形成新假设"，阶段 4 是"bug 解决、测试通过"。

没有这个切分，"调查"就变成一个没有边界的状态——你永远可以说"我再看看"，也可以永远说服自己"看够了"。四个阶段给了一个**可以宣布完成**的中间点。

**为什么是四段而不是更细**：阶段 2（模式分析）的存在最容易被低估。它看起来可有可无——为什么不直接从"调查"跳到"假设"？理由是：**在不知道"正常长什么样"之前，你无法判断什么是异常**。找相似的可工作代码、逐行对比差异，是在给"差异"建立参照系。跳过它，假设就只能建立在想象上。

**代价**：阶段 2 在**没有相似代码可参考**的场景（全新领域、第三方库内部）会空转，实操中容易被草草略过。

### 决策三：在多组件系统中，强制"先加埋点跑一次"

**选了什么**：阶段 1 第 4 条要求——**先不要分析代码**，而是在每条组件边界上加日志，跑一次，用证据指出"哪一层断掉"。

**为什么**：多组件系统里，最贵的错误是**在错误的层调试**。你可能花两小时研究签名脚本，最后发现身份变量根本没传进 CI。埋点是**用一次运行换掉盲目搜索**——把"在 N 个组件里猜哪个出问题"变成"从输出里读出哪个出问题"。

注意它的措辞顺序："Run once to gather evidence showing WHERE it breaks → THEN analyze evidence → THEN investigate that specific component"。三个 THEN 把"收集 → 分析 → 深入"的顺序锁死，防止你一边加日志一边就开始改代码。

**代价**：需要增加临时埋点代码，而且要先跑一次"只为诊断"的构建/部署。在反馈周期很长的系统（CI 十几分钟、需要发布才能测）里，这一条的成本很高。

### 决策四：阶段 3 只允许单一假设、最小验证

**选了什么**："一次只动一个变量"、"不要在旧的上面继续叠加修复"、不明白时要说"我不理解"。

**为什么**：防的是**多变量叠加**。如果一次改三处然后问题消失了，你获得了三个信息为零的结果：不知道是哪一处修好的（下次遇到同样问题你写不出正确的修复），也不知道另外两处是否引入了新问题。

"一次只动一个变量"这条把"修好了"和"知道为什么修好了"绑定在一起——这正是调试的产出应该是什么。一个不知道为什么被修好的 bug，等于一个还没被修好的 bug。

**代价**：收敛速度慢。如果三个改动其实是一组，一个一个试要跑三轮。

### 决策五：用计数器（3 次）把"该怀疑架构了"变成可判定信号

**选了什么**：修复失败时数次数，"如果 ≥ 3：停下，质疑架构"，并附上一句重新定性：*"这不是一个失败的假设——这是错误的架构。"*

**为什么**：这是整份技能里最精巧的设计。连续失败最自然的解读是"我还没找到根因，再试一次就好"——而在这个解读下，第 4 次、第 5 次修复会源源不断地发生，每次都消耗一轮完整的调查。

计数器做了两件事：
1. **把模糊的直觉变成数字**。"我好像一直在修"是感觉，"已经 3 次了"是事实。感觉可以被合理化（"这次不一样"），数字不行。
2. **强行切换解读框架**。那句"这是一个错误的架构"是关键——它不给"再试一次"留空间，把"反复失败"重新归因为**对象错了**，而不是**努力不够**。少了这一句，计数器只是一个数字；有了它，计数器才是一道转向指令。

**代价**：**3 是个启发式阈值，不是真理**。三次不同方向的胡乱尝试，和一个方向上三次有信息量的递进，是完全不同的两件事，而计数器把两者一视同仁。原文给了一个更可靠的判据（"每次修复都在不同地方暴露新问题"），但那需要判断力；计数器不需要判断力，代价是可能误报。

### 决策六：把外部信号纳入触发器

**选了什么**：单列一节"你的协作伙伴发出的信号"，把"别猜了"、"我们卡住了？"这类话语明确标注为**回到阶段 1 的触发器**。

**为什么**：AI 判断"自己是否在乱猜"的能力并不可靠——**合理化总是自我一致的**，一个正在猜测的 AI 会真诚地认为自己是在理性推理。这时候内部的自我检查失效了。

而人的措辞是**外部信号**，不受这个偏差影响。把"别猜了"这种具体短语登记为触发器，等于给自我纪律装了一个**外部断路器**：不依赖 AI 的自我觉察，依赖人的即时反馈。

**代价**：这个机制**假设有人类在场并且愿意纠正**。在无人监督的自主运行（比如 subagent 批量执行、CI 里的自动化调试）中，这个断路器完全不存在——而恰恰是这种场景最容易陷入长时间的猜测循环。

### 决策七：预先写下合理化对照表和红旗清单

**选了什么**：一张 8 行的"借口 | 现实"对照表，一张 11 条的红旗清单。

**为什么**：这些内容不是凭空写的，而是**测试的产物**。附属文件 `test-pressure-1/2/3.md` 是对抗性测试场景（生产故障每小时亏 90 万美元、沉没成本加疲惫、权威加同伴压力），`CREATION-LOG.md` 记录了这个过程。

流程是：先跑一遍**没有技能**的基线，把 AI 说的借口逐字记下来（RED），再针对这些**具体借口**写反驳（GREEN），然后继续测、继续堵漏（REFACTOR）。所以那张对照表里的每一条，都对应一个真实出现过的说法。这是"辩解词表"而不是"想象中的辩解词表"。

**代价**：对照表越全，技能正文越长——而这份技能是要被完整读进上下文的。而且它建立在一个前提上：**借口是有限的、可枚举的**。如果出现一个表里没有的新借口，这一层防御就绕过去了。

## 3. 机制如何运转

```
报告一个问题
     ↓
【铁律检查】完成阶段 1 了吗？
     ├─ 没有 → 不许提修复方案，回到阶段 1
     └─ 有 ↓
阶段 1  根因调查   读错误 → 复现 → 查变更 → 加埋点跑一次 → 追数据流
     ↓  成功标准：理解 WHAT 和 WHY
阶段 2  模式分析   找可用例子 → 对照参考 → 列差异 → 理依赖
     ↓  成功标准：找出差异
阶段 3  假设验证   单一假设 → 最小改动 → 先验证再继续
     ↓  成功标准：确认，或形成新假设
阶段 4  实施       写失败测试 → 单一修复 → 验证
     ↓
  修复失败？
     ├─ 次数 < 3  → 回阶段 1
     └─ 次数 ≥ 3  → 停下，质疑架构，找人类讨论
```

**最容易违反的约束**：从阶段 3 回到阶段 1 的那一跳。修复失败后，最自然的动作是"基于刚才的结果修一下再试"——也就是在阶段 3 里原地迭代。而技能要求的是**退回阶段 1 重新收集证据**。这一跳反直觉，且每次违反都不会立刻造成后果，所以违反会持续累积。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| bug **极其简单**（如拼写错误） | 流程开销大于收益，可能被整体放弃 | 四阶段是为"无法理解的问题"设计的；理解成本已接近零时，它变成纯粹仪式 |
| 问题**无法稳定复现** | 卡在阶段 1 第 2 步，或被迫跳过该步 | 流程把"可复现"设为前提；对竞态、环境、时序问题这个前提不成立（"去收集更多数据"是弱指引） |
| **根因在外部依赖里** | 查清了也修不了，最终只能加规避代码 | 流程假设"你能改到根因所在的那层代码"。第三方库/云服务内部的根因无法直接修 |
| 把 **3 次当机械阈值** | 三次方向各异的乱试，换来一次不必要的架构重构 | 计数器是启发式。真正的判据是"每次修复都在不同地方暴露新问题"，那需要判断力 |
| **无人协作**（subagent / CI 自动化） | "伙伴信号"断路器失效，猜测循环无外部阻断 | 该机制依赖有人类在场并愿意纠正 |
| 时间压力**极大** | 铁律被跳过，回到猜测——而这正是技能定义的"最该使用"的场景 | 铁律靠自律执行，没有任何强制力。它是文档，不是门禁 |
| 所谓的**"没有根因"** | 被当作逃生舱，提前结案 | 技能用"95% 是调查不完整"来收窄这个出口，但这是个无出处的断言，无法核验 |

> **最值得注意的是第一行和最后一行的组合**。这份技能在两端各有一个弱点：
>
> **容易被放弃**——它没有任何强制力。原文把"紧急情况"列为最该使用它的场景，但恰恰在紧急情况下，人最可能直接把它扔到一边。
>
> **容易被提前结案**——"当流程揭示'没有根因'时"这一节，本意是给出路，但它同时也是一个出口。技能用一句很强的断言（"95% 的'没有根因'都是调查不完整"）来堵住这个出口，但这句话本身没有依据。**一个无法核验的数字，在压力下会被轻易绕过**——"这次大概属于那 5% 吧"。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **依赖** `test-driven-development` | 阶段 4 第一步要写失败测试用例，技能明确要求用 TDD 技能来完成 |
| **被** `verification-before-completion` **收尾** | 修完之后，用它来验证"真的修好了"而不是"我觉得修好了" |
| **被** `using-superpowers` **路由** | 后者的"技能优先级"规则规定：修 bug 时调试技能排在领域技能之前 |
| 与 `writing-skills` 的互为印证 | 本技能的 `test-pressure-*.md` 是 `writing-skills` 那套 RED-GREEN-REFACTOR 测试方法论的**活样本** |
| 与 `grilling` 的同构 | 两者都要求"先穷尽理解再行动"，且都用可判定条件（"前沿为空"／"完成阶段 1"）来界定这个中间点 |
