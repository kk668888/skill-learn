> **触发**：即将宣称工作已完成／已修复／已通过时，在提交或创建 PR 之前

## frontmatter

- **name**：`verification-before-completion`
- **description**：即将宣称工作已完成、已修复或已通过时，在提交或创建 PR 之前使用——要求在作出任何成功宣称之前先运行验证命令并确认输出；永远是证据先于断言。

## 概览

未经验证就宣称工作完成，是**不诚实**，而不是高效。

**核心原则：** 永远是证据先于断言。

**违反这条规则的字面，就是违反这条规则的精神。**

> **批注**：第一句的措辞很重——它没有说"这是草率"或"这是乐观"，而是直接定性为**不诚实**。这个定性决定了后面所有规则的力度：草率可以用"注意一点"来改善，不诚实只能用零容忍来处理。详见[详细设计讲解](./verification-before-completion-详细设计讲解.md)决策一。

## 铁律

```
没有新鲜的验证证据，就不许作出完成宣称
```

如果你在**本条消息里**没有运行过验证命令，你就不能宣称它通过。

> **批注**："在本条消息里"这四个字是整条铁律的技术核心。它把"证据"和"记忆"明确切开——你上次跑过、你记得它是绿的，这些**都不是证据**。这个限定还顺手堵住了一个很有说服力的借口："我刚刚才验证过。"刚刚有多刚？只要不是这一次，代码就可能已经变过了。

## 闸门函数

```
在宣称任何状态或表达满意之前：

1. 确定：什么命令能证明这个宣称？
2. 运行：执行**完整**的命令（新鲜的、完整的）
3. 阅读：完整输出，检查退出码，数失败项
4. 核对：输出是否确认了这个宣称？
   - 否：陈述实际状态，附上证据
   - 是：陈述宣称，并附上证据
5. 只有到这时：才作出宣称

跳过任何一步 = 说谎，而不是验证
```

> **批注**：第 2 步的"**完整**"（`FULL`）和第 3 步的"阅读完整输出"合起来防的是**部分验证**——只跑一个测试文件、只看输出末尾、忽略非零退出码。这类做法会产出"看起来像证据的东西"，比完全没有证据更危险。而最后那句"跳过任何一步 = 说谎"是把流程完整性直接绑到诚实上：不是"漏了一步效果打折扣"，而是"漏了一步就不是在验证"。

## 常见失败

| 宣称 | 需要什么 | 什么不算数 |
|------|---------|-----------|
| 测试通过 | 测试命令输出：0 个失败 | 上一次运行、"应该会过" |
| Linter 干净 | Linter 输出：0 个错误 | 部分检查、外推 |
| 构建成功 | 构建命令：退出码 0 | Linter 通过、日志看起来正常 |
| Bug 已修 | 跑原始症状的测试：通过 | 改了代码、假定已修 |
| 回归测试有效 | 验证过红-绿循环 | 测试通过了一次 |
| Agent 已完成 | 版本控制的 diff 显示有改动 | Agent 报告"成功" |
| 需求已满足 | 逐条核对的清单 | 测试通过 |

> **批注**：这张表的价值在于每一行都是**一个看起来相关、但不是同一件事的证据**。`Linter 通过` 对 `构建成功`、`Agent 说成功` 对 `Agent 真的完成了`、`测试通过` 对 `需求满足`——三组都是"相邻但不等价"。不把它们明确分开，人（和 AI）会自然地用容易拿到的那一个顶替需要的那一个。

## 红旗 —— 停下

- 使用"应该"、"大概"、"似乎"
- 在验证之前表达满意（"太好了！"、"完美！"、"完成了！"等）
- 即将在未验证的情况下提交／推送／开 PR
- 相信 agent 的成功报告
- 依赖部分验证
- 想着"就这一次"
- 累了，想让工作赶紧结束
- **任何暗示成功、却没有实际运行过验证的措辞**

> **批注**：最后一条"任何暗示成功的措辞"是把规则从**词表**升级成**语义**。只禁"完成"两个字是没用的，因为"应该没问题了"、"看起来对了"、"这块搞定了"都能绕过。禁"暗示"虽然模糊，但它把举证责任转移了：不是"你有没有说禁词"，而是"你有没有暗示成功而没跑验证"。

## 反合理化

| 借口 | 现实 |
|------|------|
| "现在应该能用了" | 去**运行**验证 |
| "我很有把握" | 把握 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 通过了" | Linter ≠ 编译器 |
| "Agent 说成功了" | 独立验证 |
| "我累了" | 疲惫 ≠ 借口 |
| "部分检查就够了" | 部分什么都证明不了 |
| "换个说法规则就不适用了" | 精神高于字面 |

> **批注**：最后一行是这张表的**元防御**——它预判了"我会用别的措辞绕过你的规则"这个策略，并提前宣布无效。这和 `test-driven-development` 里那句"违反字面即违反精神"是同一手法，两处都用了它。

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] "所有测试通过"
❌ "现在应该过了" / "看起来是对的"
```

**回归测试（TDD 红-绿）：**
```
✅ 写 → 运行（通过）→ 撤销修复 → 运行（**必须失败**）→ 恢复 → 运行（通过）
❌ "我写了一个回归测试"（没有做红-绿验证）
```

> **批注**：回归测试这一条要求了**四步验证**，其中"撤销修复后必须失败"是关键——它证明这个测试真的在检验那个 bug，而不是恰好通过。这和 TDD 的"亲眼看到失败"是同一个原理，只是应用在"验证修复"的场景。

**构建：**
```
✅ [运行构建] [看到：退出码 0] "构建通过"
❌ "Linter 通过了"（linter 不检查编译）
```

**需求：**
```
✅ 重读计划 → 创建清单 → 逐条核对 → 报告缺口或完成
❌ "测试通过，阶段完成"
```

**Agent 委派：**
```
✅ Agent 报告成功 → 检查版本控制 diff → 验证改动 → 报告实际状态
❌ 相信 agent 的报告
```

## 为什么这件事重要

来自 24 条失败记忆：
- 你的搭档说"我不信你" —— 信任被破坏了
- 未定义的函数被发布出去 —— 会崩溃
- 缺失的需求被发布出去 —— 功能不完整
- 在虚假的完成上浪费时间 → 转向 → 返工
- 违反了："诚实是核心价值观。如果你撒谎，你会被替换。"

> **批注**：这一节是整篇的情绪支点。前面全是规则，这里给出了**代价的实证**——"来自 24 条失败记忆"意味着这些规则是从真实事故里反推出来的，而不是先验设计。"信任被破坏"被列在第一位，说明最贵的损失不是返工，而是**你以后说的每句话都要被重新验证**。

## 何时适用

**始终在以下动作之前：**
- 任何形式的成功／完成宣称
- 任何表达满意
- 任何关于工作状态的正面陈述
- 提交、创建 PR、任务完成
- 进入下一个任务
- 委派给 agent

**规则适用于：**
- 确切的措辞
- 同义改写和近义表达
- 对成功的暗示
- 任何暗示完成／正确的沟通

## 底线

**验证没有捷径。**

运行命令。读取输出。**然后**才宣称结果。

这一点没有商量余地。
