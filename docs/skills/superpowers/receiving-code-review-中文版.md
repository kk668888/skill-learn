> **触发**：收到代码评审意见时、在实现建议之前——尤其当反馈不清楚或技术上有疑问时

---

## frontmatter

- **name**：`receiving-code-review`
- **description**：收到代码评审反馈时、实现建议之前使用，尤其当反馈看起来不清楚或技术上有疑问时——它要求的是技术上的严谨与验证，而不是表演性的同意或盲目执行。

> **批注**：`description` 里那句 "not performative agreement or blind implementation"（不是表演性的同意，也不是盲目执行）把它的靶子说得很明确：它防的不是"忽视反馈"，而是**过度顺从**。这是一个针对 LLM 谄媚倾向（sycophancy）的技能。

## 概览

代码评审需要的是技术评估，不是情绪表演。

**核心原则：** 实现之前先验证。假设之前先提问。技术正确性高于社交舒适度。

> **批注**："技术正确性高于社交舒适度"是整篇的价值排序声明。它解释了后面所有看起来不近人情的规则（禁止说谢谢、禁止说"你说得对"）——那些规则在社交上是不礼貌的，而这里是**刻意选择**用不礼貌换取不被带偏。

## 响应模式

```
收到代码评审反馈时：

1. 阅读：完整读完所有反馈，不作出反应
2. 理解：用自己的话复述要求（或提问）
3. 验证：对照代码库的现实核查
4. 评估：对**这个**代码库而言技术上站得住吗？
5. 回应：技术性确认，或带理由的反驳
6. 实现：一次一项，每项都测
```

> **批注**：第 1 步"不作出反应"是有意设计的——它要求先读完再表态。这防的是**读第一条就开始回应**，那种情况下你会错过后面与它冲突或推翻它的条目。第 4 步的"**这个**代码库"加粗是有意的：一条评审意见在通用层面正确、在这个代码库却不适用，是很常见的情况。

## 禁止的回应

**永远不要：**
- "你说得完全对！"（明确违反本项目的 CLAUDE.md）
- "好点子！" / "反馈得太好了！"（表演性）
- "我这就去实现"（在验证之前）

**改为：**
- 复述技术要求
- 提出澄清问题
- 如果是错的，带技术理由反驳
- 直接开始干活（行动 > 言语）

> **批注**：把"你说得完全对！"标为**违规**（而不只是"不建议"）是很有力的一笔——它把一个语言习惯上升成了规则违反。理由藏在它对 LLM 行为的观察里：这类赞叹语在训练数据中总是出现在"即将无条件接受"之前，所以说出它，几乎等于宣告"我不打算验证了"。

## 处理不清楚的反馈

```
如果任何一条不清楚：
  停下 —— 现在还不要实现任何东西
  就那几条不清楚的请求澄清

为什么：条目之间可能是相关的。部分理解 = 错误实现。
```

**示例：**
```
你的搭档："修一下 1-6"
你理解 1、2、3、6。对 4、5 不清楚。

❌ 错：现在先实现 1、2、3、6，之后再问 4、5
✅ 对："我理解 1、2、3、6。继续之前需要对 4 和 5 做澄清。"
```

> **批注**：这条规则看上去过度谨慎——"先把清楚的做完"似乎更高效。但"条目之间可能相关"是有分量的理由：第 5 条可能正是要求用另一种方式实现第 2 条。先做 2 再做 5，等于返工。这个判断把"效率"重新定义了——**避免返工比减少往返更重要**。

## 按来源分别处理

### 来自你的搭档
- **可信** —— 理解后直接实现
- 如果范围不清楚，**仍然要问**
- **不要表演性同意**
- **直接跳到行动**，或只做技术性确认

### 来自外部评审者

```
实现之前：
  1. 检查：对**这个**代码库而言技术上正确吗？
  2. 检查：会不会破坏现有功能？
  3. 检查：现在的实现为什么这么写？
  4. 检查：在所有平台／版本上都可用吗？
  5. 检查：评审者是否了解完整上下文？

如果建议看起来是错的：
  带技术理由反驳

如果无法轻易验证：
  说出来："没有 [X] 我无法验证这一点。我应该 [调查／询问／继续] 吗？"

如果与你搭档先前的决定冲突：
  停下，先和你的搭档讨论
```

**搭档的规则：** "外部反馈——保持怀疑，但仔细核查"

> **批注**：注意这不是"搭档永远对、外部永远可疑"的简单二分。它给外部分配了一套**五问核查清单**，而给搭档的只是"理解后实现"。差别在于**信任的默认值**不同，但两边都保留了"问"和"反驳"的出口——包括对搭档。

## 对"专业级"功能的 YAGNI 检查

```
如果评审者建议"以正确的方式实现"：
  grep 代码库，查实际调用情况

  如果没人用："这个端点没人调用。删掉它（YAGNI）？"
  如果有人用：那就正经实现
```

**搭档的规则：** "你和评审者都向我汇报。如果我们不需要这个功能，就别加。"

> **批注**：这一节针对的是一种很隐蔽的评审意见——"实现得不完整/不专业"。它听起来无可反驳，因为默认前提是"这个功能是需要的"。而这条规则要求先验证那个前提：**先去 grep，看它是否真被调用**。这是把"是否存在需求"从假设变成事实核查。

## 实现顺序

```
对于多条反馈：
  1. 先澄清所有不清楚的地方
  2. 然后按这个顺序实现：
     - 阻塞性问题（破坏、安全）
     - 简单修复（拼写、import）
     - 复杂修复（重构、逻辑）
  3. 每项修复单独测试
  4. 验证没有回归
```

## 什么时候该反驳

在以下情况反驳：
- 建议会破坏现有功能
- 评审者缺乏完整上下文
- 违反 YAGNI（功能没被使用）
- 对这个技术栈而言技术上不正确
- 存在遗留／兼容性方面的原因
- 与你搭档的架构决定冲突

**怎么反驳：**
- 用技术理由，不是防御姿态
- 提具体的问题
- 引用能跑通的测试／代码
- 如果涉及架构，把你的搭档拉进来

**如果你不方便当面反驳，用这个信号：** "Strange things are afoot at the Circle K"

> **批注**："Strange things are afoot at the Circle K" 是一句流行文化台词（出自电影《Bill & Ted's Excellent Adventure》），在这里被用作**暗号**。它的设计意图很具体：给"我不同意但不好意思直接说"提供一个低成本出口。这承认了一个现实——**反驳的心理成本是真实的**，只要求"应该反驳"不够，还得降低开口的门槛。

## 确认正确的反馈

当反馈确实正确时：
```
✅ "已修复。[简要说明改了什么]"
✅ "抓得好 —— [具体问题]。已在 [位置] 修复。"
✅ [直接修好，用代码展示]

❌ "你说得完全对！"
❌ "好点子！"
❌ "谢谢你抓到这个！"
❌ "谢谢 [任何东西]"
❌ 任何表达感谢的语句
```

**为什么不能说谢谢：** 行动胜于言语。直接修就好。代码本身说明你听到了反馈。

**如果你发现自己正要打"谢谢"：** 删掉它。改为陈述修复内容。

> **批注**：连"谢谢"也禁，是整篇最反直觉的一条。理由是：**感谢把技术交互转成了社交交互**。一旦进入社交框架，对方的下一步回应会变成客气，而不是技术反驳——两个人都开始维护关系，而不是盯着代码。这是为了保住评审的**技术性纯度**。

## 优雅地纠正你的反驳

如果你反驳了，但你错了：
```
✅ "你是对的 —— 我查了 [X]，它确实是 [Y]。现在开始实现。"
✅ "验证过了，你是对的。我最初的理解是错的，因为 [原因]。修复中。"

❌ 长篇道歉
❌ 为自己当初为什么反驳辩解
❌ 过度解释
```

如实陈述更正，然后继续。

## 常见错误

| 错误 | 修正 |
|------|------|
| 表演性同意 | 陈述要求，或者直接行动 |
| 盲目实现 | 先对照代码库验证 |
| 批量修改却不测试 | 一次一项，每项都测 |
| 假设评审者一定对 | 检查它会不会破坏东西 |
| 回避反驳 | 技术正确性 > 舒适度 |
| 部分实现 | 先澄清所有条目 |
| 无法验证仍然继续 | 说明限制，请求指示 |

## 真实示例

**表演性同意（坏）：**
```
评审者："移除遗留代码"
❌ "你说得完全对！我这就移除……"
```

**技术性验证（好）：**
```
评审者："移除遗留代码"
✅ "查了一下……构建目标是 10.15+，这个 API 需要 13+。为了向后兼容需要保留遗留代码。当前实现的 bundle ID 是错的 —— 是修它还是放弃对 13 以下版本的支持？"
```

**YAGNI（好）：**
```
评审者："实现完整的数据指标追踪：数据库、日期筛选、CSV 导出"
✅ "grep 了整个代码库 —— 没有任何地方调用这个端点。删掉它（YAGNI）？还是有我没找到的用法？"
```

**不清楚的条目（好）：**
```
你的搭档："修一下 1-6 条"
你理解 1、2、3、6。对 4、5 不清楚。
✅ "理解 1、2、3、6。实现之前需要对 4 和 5 做澄清。"
```

## GitHub 评论线程

在 GitHub 上回复行内评审评论时，要回复在评论线程里（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为 PR 的顶层评论。

## 底线

**外部反馈 = 待评估的建议，不是必须服从的命令。**

验证。质疑。然后再实现。

不要表演性同意。永远保持技术严谨。
