## 1. 它解决什么问题

在 Superpowers 的链路里，设计批准之后、代码之前，插入了"写计划"这一步。它要解决的不是"我不知道要做什么"，而是一个更具体的问题：

**执行实现的那个角色，不拥有设计讨论时积累的上下文。**

这是 `subagent-driven-development` 的 fresh-context 设计的直接后果——每个任务派一个**全新的子代理**，它不继承主会话的历史（这是刻意的，为了防止上下文漂移污染）。好处是干净，代价是：**设计讨论中产生的一切共识，对它都是不存在的信息。**

于是产生了一个尖锐的交接问题：主会话里"我懂了"，子代理那里"我什么都不知道"。中间必须有一样东西把理解传递过去——而那样东西就是**计划文件**。

**设计立场**：计划不是给人看的路线图，而是一份**可脱离对话独立执行的工件**。判断它合格与否的标准不是"我读着挺清楚"，而是"**一个只在字面上理解它、且没参与过任何讨论的人，能否不出错地执行完**"。

这个立场解释了这份技能里几乎所有看起来过分苛刻的要求。

> **一个直接对照**：OpenSpec 的 `tasks.md` 只有任务组和复选框（`- [ ] 1.1 添加主题上下文提供者`），没有代码。那是**清单式**计划——它假设执行者（同一个会话里的 AI）拥有规格和设计的全部上下文。
> `writing-plans` 走的是**穷举式**极端：每一步都要给出完整代码。两者不是谁更先进，而是**服务于不同的执行模型**——清单式适合"上下文连续的同会话执行"，穷举式适合"上下文隔离的子代理执行"。

## 2. 核心设计决策

### 决策一：把读者设定成"品味可疑的初级工程师"

**选了什么**：原文的措辞是——

> *an enthusiastic junior engineer with poor taste, no judgement, no project context, and an aversion to testing*

（一个热情但品味差、没判断力、没有项目上下文、还厌恶测试的初级工程师。）

**为什么**：这是一个**刻意的夸张**，目的是让作者不敢偷懒。

如果计划的读者设定是"一个聪明且熟悉本项目的同事"，那么作者会自然而然地省略掉大量"他肯定知道"的东西——而这些省略恰恰就是执行者踩坑的地方。

把读者设定压到最低，作者的自我审查就会变严：每写一句"这个不用解释吧"，都会想起"可是读者厌恶测试、也没有判断力"。

**但它真正在防的是什么**：不是执行者愚蠢，而是**作者的口头假设**。计划里最危险的句子是那些**作者以为已经说清楚了、实际有歧义**的句子。压低读者设定，是把这些句子逼出来的手段。

**代价**：计划变得冗长。而冗长本身有成本——计划太长，可能没有人（或控制器）真的通读它。这个代价是真实的，见第 4 节。

### 决策二：每个步骤 2-5 分钟

**选了什么**：把动作拆到"写失败测试""运行它确认失败""写最小实现""运行确认通过""提交"这样的粒度。

**为什么**：意义不在省时间，而在**让误解无处藏身**。

- "实现登录功能" 这样的大步骤可以让执行者带着一堆误解蒙混过关，直到很久以后才爆雷。
- "写失败的测试" 这样的小步骤**无法隐藏误解**——如果执行者没搞懂这一步要干什么，它就卡住了。**卡住是可观测的**，蒙混过关不是。

这是**把隐性错误转成显性阻塞**的设计：让问题在最小代价的位置暴露。

**一个容易忽略的细节**：TDD 的五个动作被拆成了**五个独立步骤**，"运行它，确认它失败"是单独一步，不与"写测试"合并。**为什么**——因为如果合并成一步，执行者很容易只做前半段。拆开之后，"确认失败"成了一个必须显式完成的勾选项。这是**用结构强制流程**，而不是靠执行者的自觉。

**代价**：计划页数急剧膨胀。一个中等功能可能产生几百行计划。

### 决策三：禁止占位符，连"与 Task N 类似"都禁止

**选了什么**：列了一张"计划失败"清单，其中一条是 *"Similar to Task N"（repeat the code — the engineer may be reading tasks out of order）*。

**为什么"类似 Task N"也算失败**：理由不是洁癖，而是**执行模型的现实**——子代理可能
- 一次只拿到一个任务（控制器逐个投喂）
- 按自己认为合理的顺序推进
- 跳读

一旦发生，"类似 Task N"就指向了它没读过的空白。

**为什么"添加适当的错误处理"这类也致命**：它把决策**推迟到了执行时刻**——而执行者恰恰是**上下文最少的那个角色**。计划作者当时知道"适当"指什么，执行者不知道。

这条规则的底层逻辑是：**计划阶段偷的懒，执行阶段会加倍偿还**。因为执行阶段的每一次"自己判断一下"，都是一次可能出错的分叉。

**代价**：写作成本极高。写计划的时间可能接近甚至超过直接实现——尤其当作者其实已经在脑子里把实现想完了，还要逐行誊写出来。

> 但这恰恰是它**最被低估的收益**：**写计划 = 预演实现**。"写计划"时被迫把实现想完，很多设计问题会在这里暴露，而这时修改成本接近零。

### 决策四：先锁文件结构，再定任务

**选了什么**：*"Before defining tasks, map out which files will be created or modified and what each one is responsible for. This is where decomposition decisions get locked in."*

**为什么**：**任务分解的质量上限由文件结构决定**。如果结构没想清楚就直接开始切片，切出来的任务会互相纠缠——两个任务都要改同一个文件、接口在任务之间反复变更。

先把"哪些文件、各自负责什么"定下来，任务就变成了"填充这些边界"的机械工作。原文那句 *"This is where decomposition decisions get locked in"* 用词很准——**锁定**意味着后面的任务只是这个结构的下游产物。

配套的边界原则也在这节：*"Files that change together should live together. Split by responsibility, not by technical layer."*（一起变更的文件放一起，按职责拆而非按技术分层拆。）这是对"按 controller/service/repository 分层"这类传统习惯的**直接反对**——理由是**变更频率**才是内聚性的真正来源。

### 决策五：Run 与 Expected 必须成对

**选了什么**：每个执行命令的步骤都要写 `Run: <命令>` 和 `Expected: <预期输出>`。

**为什么**：如果只给命令不给预期，执行者看到输出**无法判断这是正常的还是异常的**。而这两种情况的处理方式完全相反——正常失败要继续，环境坏了要停下。

这实际上是**把验证的判断标准前置到了计划里**。执行者不需要理解"为什么应该失败"，只需要比对输出与预期是否一致。这又是一次"降低对执行者判断力的依赖"。

原文给的示例很讲究：`Expected: FAIL with "function not defined"` —— 不只是"失败"，而是**失败的具体原因**。因为"测试失败"有很多种（语法错误、导入错误、断言的失败），只有指定了原因，才能确认这个测试失败在**正确地失败**。（这与 `test-driven-development` 里"确认它以预期方式失败"的要求是同一件事。）

### 决策六：自审三项，且明确"不要派子代理"

**选了什么**：写完计划后自查三项——**规格覆盖**、**占位符扫描**、**类型一致性**。原文特别注明：*"This is a checklist you run yourself — not a subagent dispatch."*

**为什么明确禁止派子代理**：这个技能是"写给子代理执行的计划"，如果自审又派子代理，就出现了一个尴尬的递归——**而真正的问题是一致性检查需要的是全局视野**。一个只被喂了部分内容的审查代理，看不出 Task 3 和 Task 7 的命名不一致。

**为什么是这三项**：

| 检查 | 缺陷类型 | 能否靠搜索发现 |
|------|---------|---------------|
| 规格覆盖 | 漏做 | 需要双向对照（规格 ↔ 任务） |
| 占位符扫描 | 没写完 | 可以，靠模式匹配 |
| 类型一致性 | 前后不一致 | **不能**，只能通读比较 |

第三项是唯一**必须把前后文放在一起看**才能发现的。原文给了一个很好的例子：一个函数在 Task 3 叫 `clearLayers()`、Task 7 叫 `clearFullLayers()`——这在交给执行者之后会变成实实在在的编译错误。

**代价**：自查的天花板是模型自己的盲区。同一个模型写、同一个模型审，**它不会发现自己没想到的东西**。这是自审固有的局限，而原文明确拒绝了用子代理来补这个短板。

### 决策七：执行交接时**推荐** subagent-driven

**选了什么**：提供两种执行方式，但把 subagent-driven 标为推荐。

**为什么**：这个推荐是有内在逻辑的，不是偏好——**计划写得如此穷举，正是为了配合 fresh-subagent 执行**。两个设计是配套的：

- 计划自足 → 子代理不需要继承上下文
- 子代理上下文干净 → 不会被主会话的漂移污染

如果改用 inline execution（同会话执行），计划的详细程度就**过剩**了——因为执行者本来就拥有上下文，那些额外说明是浪费。

**代价**：subagent-driven 的成本更高（每任务一个实现代理 + 两个审查代理），且要求宿主平台支持子代理。在不支持子代理的环境里，这份推荐会落空（`executing-plans` 技能里也承认了这一点）。

## 3. 机制如何运转

```
已批准的规格
      ↓
范围检查 ←── 多子系统？先拆成多份计划，一份一个子系统
      ↓
锁定文件结构（谁创建、谁修改、各自负责什么）
      ↓
按结构切任务 ──→ 每个任务：
      │            ├─ Files: 精确路径（含行号区间）
      │            ├─ Step 1: 写失败测试（含完整测试代码）
      │            ├─ Step 2: Run + Expected（确认失败，含失败原因）
      │            ├─ Step 3: 最小实现（含完整代码）
      │            ├─ Step 4: Run + Expected（确认通过）
      │            └─ Step 5: 提交（含 git 命令）
      ↓
自审三项（自查，不派子代理）：规格覆盖 / 占位符 / 类型一致性
      ↓
就地修复
      ↓
交接：推荐 subagent-driven-development，或 executing-plans
```

**最容易违反的两条约束**：

1. **"每一步都给完整代码"** —— 违反的表现是作者写着写着开始偷懒，出现"这里照上面那样写就行"。诱因是真实性：当实现已经在脑子里很清楚时，逐行誊写感觉像纯粹的浪费。
2. **"写计划不需要派子代理自审，但执行时的每个任务都要派"** —— 两者的判断标准不同，容易混。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **计划本身写错** | 错误被执行者**忠实地**贯彻到每个任务，且因为细节到位而**显得可信** | 详尽的计划自带权威感——执行者不会质疑一份写得这么细的计划，审查者也容易放过 |
| 规格**本身有问题** | 计划忠实继承了缺陷，且过程中没有人回头质疑规格 | 计划的输入是规格，它不做上游校验（只有"规格覆盖"检查漏没漏，不检查对不对） |
| **探索性任务**（还不知道怎么做） | 写不出失败的测试，也写不出完整代码 | 整个技能假设"实现路径已知"。spike、技术验证、"先试试看能不能跑通"这类任务**在结构上不适用** |
| 代码库**在计划执行期间变化** | 计划里的行号区间、代码片段过期 | 计划是一份**冻结的工件**，而代码在动；计划越长、执行越久，脱节越严重 |
| 计划**过长** | 控制器读不完，或读到后面忘了前面 | 穷举式详尽的固有代价；而 `subagent-driven-development` 要求控制器**一次性提取全部任务** |
| 2-5 分钟粒度**被执行者机械理解** | 为凑粒度而拆出无意义的步骤 | 粒度是启发式而非硬规则，但写成了看起来精确的数字 |
| 自审**由同一模型执行** | 作者盲区不会被发现 | 自查的天花板是自己的认知边界；原文明确拒绝派子代理来补 |

> **第一、三条最值得琢磨。**
>
> 第一条是这个技能的**反直觉风险**：我们通常认为"计划越详细越安全"，但实际上**详细的错误比粗略的错误更危险**——粗略的错误会被执行者当场发现并追问，详细的错误则会被信任、被贯彻。计划的可信度与它的危险度在这里是正相关的。
>
> 第三条则划出了这个技能的**适用边界**：它要求"实现路径已知"。当你还在探索"这个方案到底能不能行"时，先写测试、再写实现的循环根本无从下手——你会写不出那个测试。这类工作应当先用 `prototype` 之类的方式探索，**探索完了再回来写计划**。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **前置** `brainstorming` | 产出的规格是本技能的唯一输入；brainstorming 的终态就是调用本技能 |
| **后继（二选一）** `subagent-driven-development` | 推荐路径。本计划的穷举式详细正是为它设计的 |
| **后继（二选一）** `executing-plans` | 同会话批量执行 + 检查点。此时计划的详细程度是过剩的 |
| **依赖** `using-git-worktrees` | 隔离工作区应在写计划/执行时已创建 |
| **引用** `test-driven-development` | 计划里那五步结构就是 TDD 的 RED-GREEN-REFACTOR 在任务粒度上的展开 |
| **对照** OpenSpec 的 `tasks.md` | 清单式 vs 穷举式：服务于"同会话执行"和"子代理执行"两种不同模型 |
| **元层面** `writing-skills` | 两者都是"写一份给代理执行的文档"，共享"读者零上下文"的核心假设 |
