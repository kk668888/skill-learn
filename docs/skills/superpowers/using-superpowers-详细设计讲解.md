## 1. 它解决什么问题

它解决的是**技能系统自身的引导问题（bootstrap problem）**。

一套由 14 个技能组成的纪律体系，有一个致命的默认状态：**技能存在，但不等于技能会被使用**。

LLM 处理一个任务时，默认走的是**通用能力**——它已经会写代码、会调试、会规划，不需要任何技能也能给出看起来合理的产出。而"调用某个技能"是一个**额外的、需要主动发起的动作**。于是默认行为永远是"直接用通用能力处理"，除非有一个足够强的理由让它先去查一下。

这个"足够强的理由"不会自己出现。每一条理由都会被 AI 自己反驳掉：

- "这个任务很简单，用不着走流程" —— 最常出现的一条
- "我先看看代码再决定" —— 把检查推后，然后永远推后
- "我记得这个技能讲什么" —— 用记忆代替当前版本
- "我知道 TDD 是什么" —— 知道概念 ≠ 遵循它

**结果是：一整套精心设计的纪律，可能一次都不会被触发。**

**设计立场**：把"检查技能"设为**在任何响应或动作之前的强制动作**，并且明确规定——**包括澄清性提问在内**。同时，把上面那些反驳**逐条预先写死**。这个技能不提供能力，它只负责让其它技能有被用到的机会。

> 用一个比喻：它不是引擎，是**点火顺序**。整套 Superpowers 的价值，取决于这一步是否发生。

## 2. 核心设计决策

### 决策一：做成一个技能，而不是写进系统提示

**选了什么**：把这条元规则包装成一个普通的技能文件（`using-superpowers`），通过 SessionStart 钩子注入。

**为什么**：这是**自我一致**的要求。整套系统的核心主张是"技能是组织指令的正确单位"——如果纪律的总纲反而不以技能形式存在，那就制造了一个例外，而例外会引发它自己的引导问题（谁规定系统提示优先于技能？）。

做成技能还有一个实际收益：**它可以被更新、被测试、被其它技能引用**。`writing-skills` 里那套"跑压力测试找漏洞、再补漏洞"的方法论，因此也能用在这份文件上。

**代价**：它是**每次对话都要加载**的内容，token 成本最高。原文因此在措辞上极度克制（见决策四的代价）。

### 决策二：用 1% 这种极端不对称的阈值

**选了什么**：*"If you think there is even a 1% chance a skill might apply... you ABSOLUTELY MUST invoke the skill."*

**为什么**：关键不在于"1%"这个数字，而在于它**故意放弃了准确性**。

判断"某个技能是否适用"这件事，本身就需要先了解技能内容——而了解内容正是"调用"要做的事。这是一个**循环**：要决定读不读，得先读过。任何"先精确判断再决定"的设计都卡在这个循环里。

1% 阈值的作用是**打破这个循环**：它把判断规则从"这个技能适用吗"降级成"这个技能**可能**适用吗"——后者可以在不读内容、只读 description 的情况下回答。**用一个廉价的近似判断，替代一个昂贵的精确判断。**

这个取舍之所以成立，是因为代价**严重不对称**：

| | 代价 |
|---|---|
| **误调用**（不该调却调了） | 读一段文字，确认不适用，放下。原文明确说了这不构成问题：*"如果调用的技能经确认不适用于当前情况，你不必使用它。"* |
| **漏调用**（该调却没调） | 整条纪律失效——而失效是静默的，你不会收到任何提示 |

**代价**：误调用不是免费的。每一次调用都会把技能正文载入上下文，而上下文是稀缺资源。1% 的阈值意味着**几乎每条消息都会触发一次检查**，在技能库里技能很多的环境下，这会累积成可观的 token 开销和无关内容干扰。

### 决策三：检查必须早于澄清性提问和探索

**选了什么**：红旗表里明确写了——*"技能检查在澄清性提问**之前**"*、*"技能会告诉你**如何**探索。先检查。"*

**为什么**：这是整份文件里**最反直觉的一条**。直觉上，"我还不了解情况，当然应该先问、先看"是完全合理的。但这条规则说的恰恰相反。

理由在于：**澄清什么、怎么探索，本身就是技能要规定的内容**。`brainstorming` 规定了一次只问一个问题、优先给选择题；`systematic-debugging` 规定了第一步是读错误信息、稳定复现、检查最近变更。如果先按自己的直觉问了一轮，你就已经在用一套**未经检验的方法**推进了——之后即使调用了技能，也是在一个已经被自己的提问方式塑造过的语境里。

换句话说：**"先了解情况"这个动作本身也有正确和错误的方式**，而方式归技能管。

**代价**：这条规则导致最前面的几步显得笨拙——用户说了一句模糊的话，AI 却先去"读一段规则"，而不是直接回应。在真正简单、不涉及任何流程的交互里（"这个函数叫什么名字"），这套前置动作是纯开销。原文用"问题就是任务"来堵这个反驳，但那更像是修辞而非论证——**确实存在一些连检查都不必要的交互**。

### 决策四：把合理化逐条写死

**选了什么**：一张 12 行的红旗表，每行是一个具体想法配上反驳；外加正文里那句 *"You cannot rationalize your way out of this."*

**为什么**：这些内容**不是凭空写的**，而是 `writing-skills` 那套方法的产物——先在不提供技能的情况下跑基线，把 AI 实际说出的借口逐字记录下来，再针对这些具体借口写反驳（也就是 RED → GREEN → REFACTOR 在文档上的应用）。

这解释了表格为什么写得这么直白，甚至有点冒犯（"知道概念 ≠ 使用技能"、"这感觉很有产出 → 无纪律的行动浪费时间"）。这不是为了说服你，而是为了**触发自我识别**：当 AI 脑中浮现"这只是一个简单问题"时，它会立刻在表里认出自己。

**代价**：这个方法有一个明确的边界——**它只能防御已经见过的借口**。表里没有的合理化第一次出现时，这一层防御是零。而这张表越长，这份每次对话都要加载的文件就越贵。

### 决策五：显式声明指令优先级

**选了什么**：用一整节写清 `用户指令 > Superpowers 技能 > 默认系统提示`，并给出具体例子（用户说"不要用 TDD"时，遵从用户）。

**为什么**：这是一个**强规则系统的合法性声明**。`using-superpowers` 的措辞极其强硬（"你没有选择"、"不可协商"、"不是可选项"），如果不明确它在权限链上服从于谁，它就会和用户的 `CLAUDE.md` 直接冲突，而冲突的解决方式没有定义。

把自己排在哪里，是这个技能**主动做出**的选择——它把自己放在**用户之下、默认行为之上**。这个位置很关键：**低于用户**，意味着它不能凌驾于人的明确要求；**高于默认行为**，意味着它确实能压过 AI 的舒适区。

> 一个宣称"不可协商"的系统，自己先说清服从于谁——这不是自我削弱，而是它得以被信任的前提。

### 决策六：过程技能优先于实现技能

**选了什么**："我们来做个 X" → 先 `brainstorming`，再实现技能；"修一下这个 bug" → 先 `debugging`，再领域技能。

**为什么**：两类技能管的层次不同。**过程技能决定任务的形态**——brainstorming 可能推翻整个需求，debugging 可能发现你根本修错了对象。实现技能则是在既定形态里填充内容。先跑实现技能，等于在形态还没定的时候就往里填东西。

**代价**：这条规则要求 AI 在"还没开始做"的时候就有能力识别"这是一个什么类型的任务"。而在真实对话里，用户的第一句话常常是模糊的，任务类型要到后来才浮现——此时"先选过程技能"就变成了猜。

### 决策七：`<SUBAGENT-STOP>`——只对主会话生效

**选了什么**：文件开头第一个标签就是——被派来执行具体任务的 subagent **跳过这个技能**。

**为什么**：subagent 的上下文是**由派发者精心构造的**。它存在的全部意义就是"只做这一件事、只知道这些信息"。如果在它运行时注入这套"全局纪律 + 12 条红旗 + 技能优先级"，会做两件坏事：**污染它的上下文**（它不需要知道技能全景），以及**诱使它偏离任务**（它可能开始考虑"我是不是该先 brainstorming 一下"，而它的任务是执行一个已经定好的计划中的第 3 步）。

这条规则与 `subagent-driven-development` 的核心主张完全一致——"它们绝不应当继承你的会话上下文或历史，你要精确地构造它们需要的东西"。

**代价**：见第 4 节第一行。

### 决策八：用 dot 流程图而不是文字描述决策路径

**选了什么**：`The Rule` 一节给了一张 Graphviz 流程图，而不是几段散文。

**为什么**：这条规则本质上是一个**循环**——"收到消息 → 判断是否有技能适用 → 调用 → 发现有清单就建待办 → 执行"。循环用文字描述容易丢失结构（读者会把它读成线性步骤），而流程图天然表达回路和分支。

`writing-skills` 给出的流程图使用判据是：只在"容易搞错的决策点"和"可能停得太早的流程循环"用图，"何时用 A 还是 B"这类分叉也算。这里恰好命中两条。

## 3. 机制如何运转

```
对话开始
   ↓
（SessionStart 钩子）注入 using-superpowers
   ↓
收到用户消息
   ↓
即将进入 PlanMode？
   ├─ 是 → 已经 brainstorming 过？
   │        ├─ 否 → 调用 brainstorming
   │        └─ 是 ↓
   └─────── 否 ────────┐
                       ↓
              有任何技能可能适用？（哪怕只有 1%）
                 ├─ 肯定不 → 直接响应（含澄清提问）
                 └─ 可能 ↓
              调用 Skill 工具
                       ↓
              声明："Using [技能] to [目的]"
                       ↓
              该技能有清单？
                 ├─ 有 → 为每项建 TodoWrite 待办
                 └─ 无 ↓
              严格照技能执行
```

**最容易违反的约束**：整张图里唯一被反复违反的节点是"有任何技能可能适用？"——因为**答案是"没有"的时候，什么都不用做**，而什么都不做不会产生任何可观察的后果。它的正确执行和它的失败执行，在外部表现上完全一样。

**这就是为什么这个技能需要一张 12 行的红旗表**：它为这个不可观察的失败，提供了一套自我检测信号。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **在 subagent 中运行** | 整套纪律对 subagent 完全失效 | `<SUBAGENT-STOP>` 明确要求跳过。纪律只能由**派发者**写进 subagent 的提示词里传递 |
| 技能**很多**的环境 | 每次检查都可能命中，上下文被无关技能正文塞满 | 1% 阈值刻意放弃了准确性，误调用不是免费的 |
| 判断"是否适用"需要先了解技能 | 只能靠 description 猜，而 description 又不许概括工作流 | 循环问题被 1% 阈值绕过，而非解决——近似判断必然有偏差 |
| 任务**真的**很简单 | 前置检查是纯开销，规则显得教条 | "问题就是任务" 是修辞，不是论证 |
| 与用户 `CLAUDE.md` 的**指令冲突** | 理论上用户优先，实践中判断困难 | 优先级规则只解决了"谁赢"，没解决"怎么识别冲突" |
| 技能**改名或不存在** | 检查通过但调用失败 | 规则的措辞是"如果技能存在就用它"，没有存在性校验 |
| 非 Claude Code 平台的**自动注入缺失** | 整个机制不启动 | 它依赖 SessionStart 钩子维持常驻；其他平台靠各自的机制（GEMINI.md 等） |
| AI 谎报**"没有技能适用"** | 无法被发现 | 判断是内部的，外部没有任何可观测信号 |

> **最值得注意的是第一行。**
>
> `<SUBAGENT-STOP>` 和整套系统的执行模型之间存在一个**真实的张力**：
>
> - `subagent-driven-development` 的核心主张是——每个任务派一个**上下文隔离**的 subagent，它"绝不继承你的会话上下文或历史"。
> - `using-superpowers` 说——subagent **跳过这个技能**。
> - 但 `subagent-driven-development` 又要求——subagent 应当遵循 TDD。
>
> **一个不继承上下文、又被要求跳过总纲的 subagent，从哪里知道要用 TDD？**
>
> 答案是：**只能从派发者构造的提示词里**。`subagent-driven-development` 的附属文件里有 `implementer-prompt.md` 等模板，纪律是通过那些模板传递的，而不是通过元技能。
>
> 这意味着一个重要的结论：**这套纪律系统在 subagent 语境下不是自动生效的，而是需要在每一份派发提示词里重新手写一遍**。`<SUBAGENT-STOP>` 是一个合理的决定（避免上下文污染），但它把"纪律的传递"从"元技能自动覆盖"降级成了"派发者的负责任程度"——而后者是一个容易被忽略的、没有预警的失效点。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **被** SessionStart 钩子**注入** | 这是它运行的方式——常驻在每次对话的开头 |
| **为所有其它技能提供入口** | 没有它，其余 13 个技能只是磁盘上的文件 |
| **规定技能调用顺序** | 过程技能（brainstorming、debugging）先于实现技能 |
| **被** `writing-skills` **反向约束** | 这份文件本身也是一个技能，因此也要遵守 `writing-skills` 的写作与测试规范 |
| 与 `subagent-driven-development` 的张力 | 后者依赖上下文隔离，而隔离意味着纪律必须由派发提示词传递（见第 4 节） |
| 与 `grilling` / OpenSpec 的同构 | 三套系统都需要一个"总开关"式的入口机制：Superpowers 用元技能 + 钩子，grill 用薄入口，OpenSpec 用 CLI 生成的命令文件 |
