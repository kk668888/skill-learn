## 1. 它解决什么问题

它专用一个失败模式：**规划产物之间的漂移。**

`proposal.md`、`specs/`、`design.md`、`tasks.md` 是四份**互相引用**的文件——proposal 说"要加暗色模式"，specs 写着"SHALL 检测系统偏好"，design 说"用 CSS 变量"，tasks 说"1.1 添加主题 context"。它们本来是一致的一套。

问题在于**它们会被分开改动**。三种常见情况：

1. **你手工编辑了**其中一份（比如直接把 `design.md` 里的方案从 CSS 变量改成 Tailwind 的 dark: 前缀）
2. **实现过程中发现了新情况**，你想把决策并进计划
3. **用户改了主意**，"顺便把范围也缩小一点"

无论哪种，改完之后那四份文件**不再互相一致**了。而最危险的地方在于：**不一致不会自己报错。** 没有任何工具会告诉你 `tasks.md` 里还写着已废弃的 CSS 变量方案。你会带着一份自相矛盾的规划继续往下走，直到实现到一半才撞见矛盾——那时已经写了不少代码。

**设计立场**：把"保持规划内部一致"当成一个**需要专门执行的动作**，而不是改完顺手就该注意到的事。并且约定这个动作**只在既有文件内部活动**——不向外扩展到代码，不向前扩展到新文件。

## 2. 核心设计决策

### 决策一：双向协调，而不是顺流而下

**选了什么**：改完一处后，检查**所有**其他已有 artifact，且方向不限。

原文的措辞很关键：

> `check every other existing artifact against it - in ANY direction: an edit to a later artifact may require revising an earlier one, not only the other way around. Build order is a useful reading order, not a constraint on which artifacts may be revised.`

**为什么**：因为人的默认假设是**顺流改**。构建顺序（proposal → specs → design → tasks）给出了一条自然的时间线，于是很容易默认"改也从上游改到下游"。

但设计变更常常**从下游被发现**——写 `tasks.md` 时才发现 `specs.md` 里的需求根本拆不成可执行的任务。这时要改的是**上游**。如果技能里没写"方向不限"，执行者会默默遵守顺流假设，然后卡住：明明知道 specs 有问题，却因为"specs 是上游、现在已经到 tasks 了"而不去动它。

**代价**：双向检查的计算量更大（每次改动都要回看全部 artifact），而且会产生**连锁修订**——改 A 导致 B 不一致，改 B 又导致 C 不一致。原文没有给出终止条件或迭代上限，实际依赖 AI 判断"何时算协调好了"。

**备选方案**：
- *只做顺流检查* —— 被否决。它会让"下游发现问题"这类最常见的场景失去出口。
- *机器校验 artifact 一致性* —— 无法实现。一致性是语义问题（"暗色模式"和"dark theme"是不是同一件事？），CLI 只能做文件存在性检查，做不到语义比对。

### 决策二：永不创建新文件——把边界切在"存在"上

**选了什么**：只修订 `existingOutputPaths` 里的文件；需要新 artifact 时，指引用户走 `/opsx:continue`。

原文甚至明确禁止在 glob artifact 下发明新文件。

**为什么**：这是一个**风险切分**决策，切分线画在"文件是否已存在"上。两类操作的风险性质完全不同：

| 操作 | 风险 | 需要什么能力 |
|------|------|-------------|
| 修订已有文件 | 破坏**内部一致性** | 一致性审查（本技能有） |
| 创建新文件 | 走错**构建顺序**、放错位置、用错模板 | schema 顺序知识 + 规则/模板获取（`continue` 有） |

把两者混在一个技能里，会让它同时背两种责任。分开之后，每个技能的护栏都能写得非常硬——本技能就能直接写"不要推进构建前沿"，而不必加一堆例外。

**代价**：一次"既想改又缺文件"的需求要跑两个命令。用户说"把设计改成 X，顺便补一个没写的 artifact"，AI 必须停下来做一半、再让你切到 `/opsx:continue`。**这个摩擦是刻意的。**

### 决策三：默认行为是"一致性审查"

**选了什么**：如果用户只说了"更新"／"弄协调"，就当作一次**协调性审查**——读所有 artifact，互相核对是否存在矛盾、缺口与重复。

**为什么**：因为用户往往**不知道该改哪一份**。他说"更新"时，心里想的可能是"我觉得这个变更哪里不对，但说不上来"。如果技能要求"先告诉我要改哪个文件"，用户就得自己去读四份文档找矛盾——那是 AI 更擅长的事。

这个默认值把"我不知道哪里不对"从一个**无法处理的请求**变成了**本技能最擅长的任务**。

**代价**：审查是**只读且不改变状态**的动作，做完可能结论是"本已协调，无需编辑"。用户会觉得"跑了一趟什么都没干"。原文为此写了明确的一句：`If the change is already coherent, say so and make no edits.`——这是必要的，防止 AI 为了"有点产出"而制造无谓的编辑。

### 决策四：每处编辑都要用户确认

**选了什么**：展示拟议修订及理由，**用户确认后才写入**；被拒绝的就不写。

**为什么**：规划产物的编辑有**不对称的代价**——写入很便宜（几行 Markdown），但影响面很大（下游的 tasks、已写的代码、甚至归档后的历史记录都会受影响）。对这类"低成本、高影响"的操作，逐项确认是合理的。

对比 `apply-change`：那里是"逐任务实现"，节奏是**连续推进**（"keep going through tasks until done or blocked"）。同样是"逐项"，但一个要确认、一个不停步——因为代码改动是可测试、可回滚的，而规划改动的对错**只有你想得清楚**。

**代价**：一次涉及多份 artifact 的协调会产生一串确认，很长。用户如果全部同意，就是在反复按"继续"。

### 决策五：用"意图 vs 细化"决定要不要重开

**选了什么**：如果请求改变的是变更的**intent**（意图）而非 refinement（细化），建议用 `/opsx:new` 从头开始。

**为什么**：变更的名称、proposal、以及归档后的目录名（`archive/2025-01-23-add-dark-mode/`），全都**绑定在它最初声明的意图上**。

把一个"做 A"的变更慢慢改成"做 B"，会污染历史：三个月后你回看那个归档目录，名字说是加暗色模式，内容却在讲别的。**这条判据保护的是历史可读性，不是当前操作的正确性。**

**代价与风险**：这条判据**边界模糊**。"把暗色模式的实现从 CSS 变量改成 Tailwind"是细化（不重开）；"暗色模式改成只做亮色模式的高对比度版本"是意图变更（该重开）。但中间地带大量存在——"把范围从整个应用缩小到只做设置页"算哪一种？原文没给判据，只能靠判断。

## 3. 机制如何运转

```
选择变更（歧义时列出最近修改的前 3-4 个，把最新的标为 Recommended）
      ↓
openspec status --change <name> --json
   ├─ schemaName              决定有哪些 artifact
   ├─ artifacts[].status      done / skipped / ready / blocked
   ├─ artifactPaths.<id>.existingOutputPaths   ← 要编辑的**具体文件**（glob 已展开）
   └─ artifactPaths.<id>.resolvedOutputPath    ← 别写这个（glob 时是模式字符串）
      ↓
理解请求
   ├─ 有具体修订 → 那是起点
   └─ 只说"更新" → 当作一致性审查
      ↓
阅读并双向协调
   ├─ 应用所请求的编辑
   └─ 用它对**其他每一份**已有 artifact 检查（**方向不限**）
      ↓
逐项展示拟议修订 → 用户确认 → 才写入
      ↓
只给建议，不代劳：缺 artifact → /opsx:continue
                  已实现 → /opsx:apply
                  全完成 → /opsx:archive
```

**最容易违反的关键约束**：`Do not advance the build frontier`（不要推进构建前沿）。

它容易被违反，是因为**创建缺失的文件在直觉上是"帮忙"**——你读到了 specs，发现 `design.md` 没写，顺手补上看起来完全是善意的。但"补一个文件"需要知道 schema 的构建顺序、该 artifact 的规则与模板、以及它是否本该被跳过（`skip_specs`）——这些知识在本技能里被刻意排除了。**善意的越界仍然是越界。**

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 用户改的是**意图**，却走了 update | 历史记录失真：归档目录名与实际内容不符 | "意图 vs 细化"的判据边界模糊，靠 AI 判断 |
| 连锁修订没有终止条件 | 编辑来回震荡，或 AI 自己决定"差不多协调了"就停 | 原文没给迭代上限，双向检查天然会产生连锁 |
| glob artifact 下文件名选错 | 创建的 file 不在 CLI 预期位置，状态却不报错 | `resolvedOutputPath` 与 `existingOutputPaths` 的区分是纯技术性警告，容易被略过 |
| 手工编辑后语义漂移（"暗色模式" vs "dark theme"） | 双向协调查不出这类不一致 | 一致性是**语义**问题，技能只能靠 AI 阅读理解，没有机器校验 |
| 用户全部同意、不细看 | 确认环节退化为形式 | 逐项确认的效力依赖用户真的在审 |
| 变更已实现，改完规划后没走 apply | 代码与 specs 静默漂移 | 原文只"建议"走 apply，没有强制，也没有检测 |
| 自定义 schema 的 artifact 名很陌生 | AI 可能仍按 spec-driven 的名字去推断 | 原文反复强调"别硬编码 artifact 名"，但这依赖执行者克制 |

> **最值得警惕的是第二行。** 双向协调在理论上是"改到不再有矛盾为止"，但这是个**没有终止条件的循环**。改为 A 可能让 B 不一致，改 B 又反过来影响 A 的措辞。原文没给收敛判据，实际靠 AI 的"我觉得协调了"。而 LLM 恰恰倾向于**过早宣布完成**——它会在某次检查后说"现在都一致了"，即使还有隐蔽的矛盾留在两份文件的不同措辞里。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **与** `openspec-continue-change` **严格分工** | 分界线画在"文件是否已存在"：**已存在归 update，不存在归 continue**。本技能的护栏里直接写"那是 continue 的活" |
| **与** `openspec-new-change` **是二选一** | 判据是"意图 vs 细化"：意图变了重开走 new，只做细化留在这里 |
| **指向** `openspec-apply-change` | 修订后的计划若涉及代码改动，停下并指向它——本技能**永不编辑代码** |
| **被** `openspec-apply-change` **反向依赖** | apply 允许"实现中发现问题就建议更新 artifact"，那条回头路的落点就是本技能 |
| 与 `openspec-ff-change` 的对照 | ff 是"最快走完构建前沿"，update 是"在原地协调已建成的东西"——一个管**推进**，一个管**一致性** |
| 与 Superpowers 的对照 | Superpowers **没有对应物**。它的 `brainstorming` 只产出一次设计文档，没有多份 artifact 之间的漂移问题（因为只有一份）。update-change 的存在本身就说明 OpenSpec 用**更多份文档**换取了更细的表达能力，同时引入了这个新问题 |
