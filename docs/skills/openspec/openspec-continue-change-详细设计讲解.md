## 1. 它解决什么问题

它的字面职责很朴素：**创建一个缺失的 artifact。** 但真正值得分析的是它给自己套上的一条约束——

> `Create ONE artifact per invocation`（每次调用只创建一个 artifact）

这条约束与"把缺的都补上"这个自然冲动**直接冲突**。如果目标只是"让构建前沿推进到位"，一次创建全部显然更高效。所以这个技能真正要解决的失败模式是：**AI 会抢在你之前把规划做完。**

想象一下这个场景：你的 `proposal.md` 和 `specs/` 写好了，`design.md` 和 `tasks.md` 还空着。你说"继续"。一个没有减速机制的 AI 会立刻把两份都写完——而且**它必须自己决定 design 的内容**。于是设计决策在你没看过一眼的情况下全部拍定，你拿到的是一份"已完成"的规划，和一句"接下来可以实现了"。

问题不是 AI 写得不好，而是**那四份 artifact 之间本该有的四次人工检查，被压缩成了零次**。`.openspec` 那套目录设计的全部意义——"把需求变成可审查的文件"——在这种情况下被架空了。

**设计立场**：**推进构建前沿这件事，必须一个文件一个文件地、在你眼前发生。** 减速不是效率损失，而是这个技能存在的主要理由。

## 2. 核心设计决策

### 决策一：一次只创建一个 artifact

**选了什么**：创建**一个** artifact 后立即停止，并给出"Want to continue?"的提示。

**为什么**：每个 artifact 天然是一个**检查点**。四份 artifact 就是四次机会，让你在错误扩散前看到它。而**批量创建会把检查点全部抹掉**——不是减少，是抹掉，因为四份文档一起交给你，你不可能逐份细读它们之间的一致性。

这也解释了这个技能为什么在创建后**不自动继续**：`STOP after creating ONE artifact`。它把"要不要继续"的决定权显式交回给你，每一轮都是一次微小的确认。

**代价**：
- **慢**。四份 artifact 要四次调用、四次 CLI 查询、四轮对话。
- **摩擦**。你如果说"继续创建"，实际要重复输入四次。
- **失效风险（关键）**：这条约束**极易被稀释**。如果你连说四次"继续"，它实际上就退化成了 `ff-change`——但**没有** ff 那套专门为批量场景设计的正确性保障（构建前沿的传递闭包计算、条件 artifact 的严格判定）。你得到了慢的体验和差的正确性。

**备选方案**：
- *全部创建完再统一展示* —— 这就是 `ff-change`，作为独立技能存在。两者并存的前提是它们**服务不同场景**：continue 用于"我想边看边推进"，ff 用于"我信得过，快速铺完"。
- *加一个参数控制批量* —— 被否决。参数化的开关在提示词场景里几乎不可控——AI 拿不准何时该开，用户也不会记得传。

### 决策二：重新从磁盘读，不信对话记忆

**选了什么**：创建新 artifact 前，读取依赖文件，并且**始终从磁盘重新读取**——即便对话中早先看过。原文在正文和护栏里各写了一遍。

**为什么**：这对抗的是一个非常自然的 LLM 习惯——"这个文件我刚看过，我记得内容"。问题在于：

- **你记得的是上次看到的样子**，不是它现在的样子
- 用户完全可能在两次交互之间**手工编辑过** artifact（OpenSpec 明确支持这种用法）
- 而基于过时内容生成的新 artifact，会**把过时信息固化到下游**——下游 artifact 会成为旧版本的忠实继承者

**代价**：多几次文件读取。在 artifact 很大时这是真实的 token 成本。而且它是**冗余的**——大部分时候文件确实没变。原文选择承担这个成本，因为**过时记忆造成的错误比多余的读取昂贵得多，而且不报错**。

### 决策三：`context` / `rules` 是约束，不是内容

**选了什么**：反复强调这两者是给 AI 的约束，**永远不要**复制进 artifact 文件。

**为什么**：这是一个**已经真实发生过、所以才被反复强调**的错误。`context` 是项目背景（"本项目使用 pnpm，不要用 npm"），`rules` 是 artifact 规则（"每个需求必须有 WHEN/THEN 场景"）。它们的作用是**影响你怎么写**，而不是**属于文档的内容**。

如果被复制进去，artifact 会混入元信息——`specs/theme/spec.md` 里出现"本项目使用 pnpm"这种与主题无关的句子。这在**单次**使用中只是噪音，但在**归档**之后就变成污染：`openspec/specs/` 号称是"系统当前应该做什么"的真相源，里面却塞着构建工具的约定。

**代价**：约束"不要复制"需要 AI 持续区分"我读到的"与"我该写的"，这是一个**容易在长文档生成中逐渐松懈**的区分。原文用了加粗 + 单独小节 + 护栏里再写一遍的三重强调，说明作者知道单靠一次说明不够。

### 决策四：取第一个 `ready` 的 artifact，不挑

**选了什么**：`Pick the FIRST artifact with status: "ready"`。

**为什么**：这个决定只能由 schema 的构建顺序来做，**不能由 AI 挑**。让 AI 在多个 `ready` 的 artifact 里"选一个最重要的"，等于让它参与规划排序——那是 schema 的职责，也是它没有能力判断的事（它不知道后续 artifact 会依赖什么）。

**代价**：如果第一个 `ready` 的 artifact 恰好是你最不想现在写的那个，你没有选择权——只能先写它，或者先手工把前面的处理掉。**这个不灵活是刻意的**：一旦允许挑选，构建前沿的顺序就失去了确定性，`status` 的 `ready`/`blocked` 判定也不再能预测下一步。

### 决策五：委派而非自己写

**选了什么**：如果 `instruction` 字段把创建委派给了某个具体的技能或命令，就调用它，不要自己写文件。

**为什么**：这保持了**schema 对流程的控制权**。某些 artifact 可能需要专门的处理（比如 specs 需要按 capability 拆分、需要生成多个文件）。如果技能硬编码"读到 template 就自己填"，那些特殊流程就丢了。

**代价**：多一跳间接，链路更长；而且技能里写不了"委派之后应该期待什么"——它只能要求"验证文件确实存在于 `resolvedOutputPath`"。

## 3. 机制如何运转

```
选择变更（歧义时列出最近修改的前 3-4 个）
      ↓
openspec status --change <name> --json
      ↓
状态分支 ┌─ isPlanningComplete: true → 道贺 + 建议实现 → 停止
        ├─ 有 status:"ready" 的 artifact → 创建**一个** → 停止
        └─ 全部 blocked            → 异常，展示状态请用户检查
      ↓
openspec instructions <artifact-id> --change <name> --json
   ├─ context / rules     ← 约束，**不写进文件**
   ├─ template            ← 文件结构
   ├─ instruction         ← 权威指引（可能委派给别的技能）
   ├─ resolvedOutputPath  ← glob 时需自己选具体路径
   └─ dependencies        ← 从**磁盘**重读
      ↓
创建文件 → 验证存在 → 展示"创建了什么 / 解锁了什么" → STOP
```

**最容易违反的关键约束**：`Create ONE artifact per invocation`。

它容易违反，是因为**违反它的动机非常正当**——"后面两个也 ready 了，何不一次做完，省得用户再敲一次"。这个"贴心的效率优化"会精确地抹掉技能的**唯一理由**。原文用 `STOP after creating ONE artifact` 这种全大写 + 前置动词的写法，就是在堵这个动机。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 用户连点"继续" | 事实上变成 ff，但**没有** ff 的正确性保障 | 减速机制的全部效力来自"每轮都是一次人工检查"，机械重复会让检查名存实亡 |
| 依赖 artifact 被手工编辑过，但 AI 用了记忆 | 新 artifact 基于过时内容，把过时信息固化到下游 | "从磁盘重读"是倡议，没有机制能验证它真的读了 |
| `context` / `rules` 被复制进 artifact | 归档后污染 `specs/` 真相源 | 区分"读到的"与"该写的"在长文档中容易松懈 |
| `resolvedOutputPath` 是 glob | 可能起错目录名或选错具体路径 | 具体文件名需要 AI 自行判断，而判断依据只有 schema 指引和上下文 |
| 第一个 `ready` 的 artifact 不是用户想写的 | 用户没有选择权 | 刻意的不灵活——一旦允许挑，`ready`/`blocked` 就不再可预测 |
| artifact 很多（如 onboard 场景） | 逐个创建产生大量往返 | 减速设计的固有成本 |
| 扩展 profile 未启用 | 本技能根本不存在，`apply` 的 blocked 出口失效 | 属扩展 profile，默认安装下没有 |

> **第一行是这个技能的根本弱点。** 它的全部价值建立在"每个 artifact 之间有一次真实的人工检查"上，而**这一点无法被技能本身保证**——技能只能做到"创建完就停下"，做不到"确认你真的看了"。一个只是想快点做完的用户，会用它走出 ff 的效果，同时失去 ff 那套专门为批量设计的正确性保障。**这是"用摩擦换检查"这类设计的通病：摩擦可以被用户单方面消除，而检查不会自动回来。**

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **与** `openspec-ff-change` **正面对立** | 同一目标（把 artefact 补到可实现）的两种押注：continue 每次一个（减速、留检查点），ff 一次做完（提速、放弃检查点）。**这是套件内最本质的一对设计分歧** |
| **与** `openspec-update-change` **严格分工** | 分界线画在"文件是否已存在"：**不存在归 continue，已存在归 update**。update 的护栏明确写"不要推进构建前沿——那是 continue 的活" |
| **与** `openspec-new-change` **分工** | new 负责"开一个新变更并产出**第一个** artifact"，continue 负责"在此之后的每一个"。前者要处理命名与意图，后者只处理顺序 |
| **被** `openspec-apply-change` **依赖** | apply 遇到 `state: "blocked"`（缺 artifact）时，唯一的推荐出口就是本技能 |
| 与 `openspec-propose` 的对照 | propose 是"一次性生成全部 artifact"（与 ff 类似但入口不同：从零创建变更），continue 是"在既有变更上逐格推进" |
| 与 Superpowers 的对照 | Superpowers 的 `writing-plans` **一次产出一整份计划**，没有"多份 artifact 逐个确认"的机制。OpenSpec 用更细的粒度换取了更多检查点，代价就是本技能与 ff 必须并存来覆盖两种节奏偏好 |
