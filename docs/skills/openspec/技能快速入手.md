# OpenSpec 技能快速入手

## 适用场景

你有一个小功能想法，希望先把“为什么改、改成什么、怎样做”写成可审查的文件，再决定是否实现。本例为**练习待办应用增加完成状态筛选**，只走到提案完成与人工审查，不修改应用代码。

## 准备条件

- 在一个可随意修改的**练习项目**中操作，项目里已有简单的待办列表，并安装了 OpenSpec CLI 与支持其工作流技能的 AI 工具。不要在本项目仓库里执行下面的练习命令。
- 项目根目录应已有 `openspec/`；若还没有，先在练习项目根目录运行 `openspec init`，按提示选择你的 AI 工具。初始化会生成 OpenSpec 配置和工具指令文件。
- 在同一个项目根目录运行后续命令。本例使用普通本地仓库；若你使用已注册的独立 store，按该技能要求先选定 store，并在适用命令后保持 `--store <id>`。

## 示例输入

在练习项目中对助手发送：

> 请使用 `openspec-propose` 创建名为 `add-todo-status-filter` 的变更：待办列表增加“全部、未完成、已完成”三个筛选项，默认“全部”；切换筛选只影响显示，不删除或改写任务。请生成可审查的规划文件，完成后停下，等我决定是否实现。

## 跟做步骤

1. **创建规划产物。** 助手应先核对项目背景；如果关键行为仍有歧义，先问你，再用 OpenSpec CLI 创建变更并依赖次序写规划文件。**可观察结果：**练习项目里出现 `openspec/changes/add-todo-status-filter/`，其中有 `.openspec.yaml`、`proposal.md`、`tasks.md` 和对应能力域下的增量 `spec.md`。`design.md` 是否需要由该 artifact 的条件决定；小变更可能会有意跳过。这是功能行为变化，不应以 `skip_specs` 跳过规格。
2. **检查状态。** 在练习项目根目录运行：

   ```bash
   openspec status --change add-todo-status-filter
   ```

   **可观察结果：**状态列出提案、规格、设计、任务的完成情况；若某项未完成，按提示回到助手补齐，而不是仅凭目录存在就视为准备好。
3. **人工停点：审查承诺。** 打开 `proposal.md` 看范围，打开增量 `spec.md` 看三个筛选项的可观察行为，再看 `tasks.md` 是否与之相符；若生成了 `design.md`，也审查其技术取舍。不同意默认值、状态名称或其他决定，就让助手修改规划文件。**可观察结果：**你能用这些文件说明本次变更的范围、验收场景与实现步骤。
4. **可选校验。** 运行 `openspec validate add-todo-status-filter --type change --strict`。**可观察结果：**CLI 报告有效或指出需修正的问题；校验通过仍不代替你的内容审查。

## 完成判断

OpenSpec 状态显示本次变更所需的规划产物已齐备，且你已亲自审查范围与行为。`openspec-propose` 到这里必须停下；只有你之后明确启动 `openspec-apply-change`，才进入实现阶段。
