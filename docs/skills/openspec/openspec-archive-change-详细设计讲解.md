# openspec-archive-change · 详细设计讲解

## 1. 它解决什么问题

代码写完了，"变更"这件事却只完成了一半。

OpenSpec 把需求拆成两层：`specs/` 是**系统现在应该做什么**（当前真相），`changes/<name>/specs/` 是**这次要改什么**（增量 delta）。实现完成时，代码变了、tasks 勾完了、delta 写好了——但 `specs/` 里那份"真相"**仍然是旧的**。

于是会出现一种很隐蔽的腐坏：`openspec/specs/` 读起来仍然自洽、格式完好、看起来权威，只是**它描述的是三个月前的系统**。而它恰恰是下一轮变更的起点——下一轮会基于一份过时的真相去写 delta。**错误不会被发现，只会被继承。**

**为什么"提示词写清楚点"解决不了**：这个动作的本质是一次**写入不可逆真相**的操作。它需要的是**仪式**——明确的触发时机、一次显式确认、以及写入后的验证——而不是更清楚的措辞。措辞解决不了"什么时候算改完了""写坏了怎么办"。

**设计立场**：归并是一次**生效（commit）事件**，不是实现完成后的自动副作用。它宁可失败、宁可停下、宁可让人重来，也不允许"半途而废地写了一半"。

> 这个立场和 git 的 `merge` 同构：工作分支上的提交再多，不 `merge` 就进不了 main。而 OpenSpec 特意让这一步**必须由人说出口**。

## 2. 核心设计决策

### 决策一：归档是显式动作，不是自动结束

**选了什么**：实现完成后，delta **不会**自动合并。必须显式触发 `/opsx:archive`。

**为什么**：合并 = "这个变更的需求**正式成为**系统真相"。这个语义太强，不能由"tasks.md 勾完了"这种机械信号触发——因为 tasks 勾完不代表需求是对的。**勾选是主观的，真相是有后果的**，两者之间需要一个人为的确认点。

**代价**：变更会堆积。用户忘了归档，`changes/` 下就躺着一堆已完成但未生效的变更，而 `specs/` 悄悄落后于代码。原文没有机制能发现这种"忘了归档"的状态。

**备选方案**：
- *实现完自动合并* —— 被否决。见上：会把"需求是否正确"这个判断交给一个机械条件。
- *定期批量合并* —— 被否决。合并时机与需求的成熟度解耦，会把未验证的需求写进真相。

### 决策二：合并由 agent 智能完成，而不是机械文本替换

**选了什么**：`openspec-sync-specs` 是 **agent-driven intelligent merge**——由 LLM 读 delta 与主规格，理解语义后重写主规格。

**为什么**：delta 与主规格之间不是机械的文本拼接。举几个机械替换做不到的情形：

- 主规格里已有一条 Requirement，delta 说 MODIFIED 它——需要把 delta 点名的**场景**改掉，而把**其他场景原封保留**。这不是"替换一段文本"，是"在一条需求内部做外科手术"。
- delta 说 REMOVED，但主规格里的对应需求已经被上一轮改写过——需要按**语义**匹配，而不是按原文匹配。
- 一个 capability 被多个变更按顺序改过，主规格的当前形态是多次合并的累积结果——delta 必须理解这个累积状态。

**代价**：**合并变成非确定性操作**。同样的 delta + 同样的主规格，两次运行可能产出不同的主规格。而主规格承载的是"权威真相"的地位，权威性通常要求可复现。这是这套设计里最根本的张力——**用概率性操作维护权威性资产**。

这个代价直接逼出了下面两条设计。

### 决策三：合并后重新全量比对，不信任同步的自报

**选了什么**：同步结束后，对**每一个**有 delta spec 的 capability 重新做一遍比较——**不只是**同步自报触碰过的那些。

**为什么**：既然合并是 agent 驱动的（决策二），那么它说"我做完了"就只是一句**声称**，不是证据。而且这句话特别容易错——LLM 倾向于报告成功。原文的措辞很值得注意：

> *"A successful sync leaves nothing left to apply, so each capability must now read as already synced"*

关键在于它的**判据方式**：不是"同步说了什么"，而是"**主规格现在读起来是不是已经同步的样子**"。验证的对象是**结果状态**，不是**执行报告**。

加粗的"不只是同步自报触碰过的那些"进一步堵住了另一种失败：同步可能**漏掉**某个 capability 却以为自己做完了。只看自报触碰的，就查不出漏掉的。

> 这与 Superpowers 的 `spec-reviewer-prompt.md` 里那句 `CRITICAL: Do Not Trust the Report / The implementer finished suspiciously quickly` 是**同一个设计动作**——都是"不信任 agent 的自报"。区别在于手段：Superpowers 派**另一个 subagent** 去不信，这里用**机械的重新比对**去不信。后者更硬，因为它不依赖第二个 agent 的判断力。

### 决策四：同步必须内联，禁止后台委派

**选了什么**：原文明确要求同步**内联执行并等待结束**，且直接点名了禁止后台委派的理由。

**为什么**：这是一个**真实的竞态条件**，而且是"归档"这个动作天然带有的——它的最后一步 `mv` 会**移走自己的输入**：

```
step 4: sync 读取 changes/<name>/specs/  →  写 openspec/specs/
step 5: mv changes/<name>/ → archive/
```

若 sync 还在后台跑，而 step 5 已经把 `changeRoot` 移走了，结果是：**变更躺在 archive 里显示"归档成功"，而主规格从未更新**。更糟的是这件事**事后无法被发现**——变更已经归档、没了，没人会再去查它有没有生效。

原文的处理是双保险：① 内联执行、等待结束；② 移动之前先验证主规格（决策三）。第 ② 条是第 ① 条失效时的兜底——即使同步以某种方式没写完，验证也会发现"主规格还不是已同步的样子"从而停止归档。

**代价**：同步不能并行化。批量归档时（见 `bulk-archive`），这意味着多变更的合并必须串行，无法利用并发。

### 决策五：两种 lookup 的失败待遇**相反**

**选了什么**：同一个技能里，两次 CLI 查询的失败后果被刻意设计成相反的：

| 查询 | 失败时 |
|------|--------|
| `instructions archive`（第 1 步） | **绝不阻塞**——继续，就当没有额外输入 |
| `instructions specs`（第 4 步） | **必须停止**——在写任何主规格之前 |

**为什么**：判据是**失败后继续的可逆性**。

- `instructions archive` 只提供建议性的提示输入（context / operationGuidance）。它失败，无非是少了一些项目约定——继续归档不会写坏任何东西。
- `instructions specs` 提供的是**合并规则**。它失败意味着**在不知道规则的情况下改写真相**。而主规格是权威资产、写坏了影响面大且难回溯。

**这条对比值得单独记住**：同一套系统可以对同类失败采取完全相反的策略，只要判据是"错了能不能收回"。这比"统一容错策略"更精确——统一反而会在两个方向上同时犯错：该停的没停，该走的停住。

### 决策六：警告不阻塞，错误阻塞

**选了什么**：artifact 未完成、任务未勾完——**只警告、请你确认**，不阻止归档。而同步失败——**直接停止**。

**为什么**：同样是可逆性判据。

- "任务没勾完"或"某个 artifact 缺了"是**主观判断**：也许用户就是想先把变更归档（比如那个 artifact 本来就 plan 了要跳过）。技能的责任是把事实摆清楚（`Don't block archive on warnings - just inform and confirm`），不是替用户否决。
- "同步失败"是**客观错误**，且会造成不可逆的坏结果（真相被写坏或半写）。

**代价**：用户可以带着一堆未完成任务归档，事后无从分辨那个变更是"真的做完了"还是"带着缺口归档的"——原文只在归档摘要里留下一句 `Archived with 2 incomplete tasks`。

### 决策七：日期前缀，且绝不叠加第二个日期

**选了什么**：归档名为 `YYYY-MM-DD-<change-name>`；若名称已有 `YYYY-MM-DD-` 前缀，则**原样使用**。

**为什么**：两条规则各管一件事。

- **日期前缀**：`archive/` 是一个只增不改的目录。在这样的目录里，日期是**唯一有意义的排序键**——你打开 archive 想看"最近归档了什么"，日期顺序就是时间顺序。
- **绝不叠加**：这条看着琐碎，实际防的是一个具体的坏结果。若无此约束，一个已叫 `2025-01-23-add-dark-mode` 的变更被再次归档会长成 `2026-09-14-2025-01-23-add-dark-mode`。规则的真实作用是让**重命名操作幂等**——同一天重复执行不产生新名字。

**代价**：同一天归档两个同名变更会失败（目标已存在）。原文的处理是**报错并让人处理**，而不是自动加序号——宁可让人看见冲突，也不悄悄造出 `-2` 后缀。

## 3. 机制如何运转

```
/opsx:archive <name>
   ↓
1. 选定变更 → 载入 instructions archive（失败无所谓，继续）
   ↓
2. 检查 artifact 完成度 ── 不完整？警告 + 请确认
   ↓
3. 检查 tasks 完成度   ── 未勾完？警告 + 请确认
   ↓
4. 有 delta spec？
   ├─ 无 → 直接进第 5 步
   └─ 有 → 比对 delta vs 主规格，展示合并摘要
            ↓ 用户选择
        ├─ 取消            → 停止
        ├─ 不同步直接归档   → 进第 5 步
        └─ 立即同步
             ↓ 先取 specs 规则快照（失败 → 停止！）
             ↓ 内联跑 sync-specs，等待结束（禁止后台）
             ↓ 重新比对【全部】capability
                  ├─ 有任一不匹配 → 报告差异 + 停止（不归档）
                  └─ 全部匹配    → 进第 5 步
   ↓
5. mkdir archive/ → 生成目标名（不叠加日期）→ 目标已存在？报错；否则 mv
   ↓
6. 显示摘要
```

**最容易违反的关键约束**：第 4 步里"**重新比对全部 capability**"这一步。它看起来很啰嗦——同步刚跑完，为什么要再全查一遍？答案是决策三：同步是 agent 驱动的，它的自报不可信，而漏查一个 capability 的代价是**一个变更被静默吞掉**。这一步是这套设计里最像"多余的谨慎"、实际最不能省的地方。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **两个会话同时归档、且 delta 撞同一 capability** | 后写的覆盖先写的，**先写的那份要求静默消失** | 归档时刻**没有并发锁**，也没有版本检查；两个会话都会报告"归档成功" |
| **delta 只 MODIFIED 一条需求的某个场景** | 未在 delta 中点名的其他场景可能被**整段重写吞掉** | 合并是 LLM 做的，而 LLM 的默认行为是整段重写；原文要求"其余场景原封未动"是需要精细克制的外科手术 |
| **合并结果不确定** | 同样的 delta 两次运行产出不同主规格 | 合并是非确定性操作（决策二的代价）；主规格的权威性因此依赖运气 |
| **同步被委派为后台任务** | 变更显示已归档，主规格**从未更新**，且事后无法发现 | `mv` 移走了同步正在读的目录（决策四）。原文写了这条禁止，但它是**纪律，不是技术强制** |
| **用户在同步失败后中止** | 变更未归档、主规格未动——**这是安全的一侧** | 设计上把失败推向"什么都没发生"，但用户可能误以为已经归档而不再重试 |
| **带着未完成任务归档** | `specs/` 里出现了实际未实现的需求，**真相污染** | 警告不阻塞（决策六）；技能只负责告知，否决权在用户 |
| **忘了归档** | `specs/` 悄悄落后于代码，下一轮基于过时真相写 delta | 没有机制检测"已完成但未归档"的变更 |
| **主规格被手工改过** | 下次合并基于被改过的状态，delta 与主规格可能对不上 | 主规格对用户是可写的；没有校验和或锁来防止带外修改 |

> **最值得注意的是第一、二条。** 它们共同指向同一个根本问题：**合并是一次概率性的、没有并发保护的对权威资产的写入**。原文用"重新全量比对"（决策三）能挡住**漏做**，用"内联执行"（决策四）能挡住**时序错乱**，但挡不住**两个并列写入互相覆盖**——因为这个冲突发生在两次独立的归档之间，任何单次归档内部的验证都看不见它。
>
> 这也是 `bulk-archive` 存在的根本理由：只有把多个变更**放进同一次操作**，冲突才可能被检测到。反过来推论——**逐个归档在冲突这个维度上，比批量归档更危险**，这违反直觉。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **调用** `openspec-sync-specs` | 第 4 步内联执行的合并内核；归档只负责"何时合、合完验、验完搬" |
| **取代** `openspec-bulk-archive-change` | 单变更用本技能；多变更并行**应当**改用 bulk（它多了冲突检测，见失效分析第一条） |
| **被** `openspec-verify-change` **前置** | verify 出报告，本技能决定是否归档；但 verify **不阻塞**归档——是否采纳由用户和本技能各自的守卫决定 |
| 与 Superpowers `verification-before-completion` 的关系 | 同一诉求（证据优于宣称）的两种实现：后者把"不信任"放在**人**（要求跑出证据），本技能把它放在**机器**（重新比对主规格） |
| 与 git merge 的同构 | `specs/` 是 main，`changes/<x>/specs/` 是 feature 分支，archive 是 merge——而这里没有 git 的冲突解决与历史记录 |
