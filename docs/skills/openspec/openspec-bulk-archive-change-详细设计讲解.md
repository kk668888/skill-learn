## 1. 它解决什么问题

它的起因是一个**只有并行工作才会出现的失败**：多个变更同时进行时，它们的 delta 会撞在同一个 capability 上。

设想两个进行中的变更——`add-oauth` 和 `add-jwt`——都往 `identity/user-auth` 这个 capability 里加需求。两者各自看都没问题：delta 合法、tasks 完成、实现都在。问题出在**归档**：主规格只有一份，两个 delta 都要往里合并。

`archive-change`（逐个版本）**看不见这个冲突**。它只处理一个变更，读完自己那份 delta、合并、搬走、报告成功。第二个变更再来一次，同样报告成功。结果主规格里只剩后一次合并的结果——**先归档的那份需求静默消失**，而两次操作都显示"归档成功"、没有任何人知道出了事。

**设计立场**：冲突必须由**代码里实际实现了什么**来裁决，而不是由"哪个变更更新"或"用户更想要哪个"来裁决。原因是——delta 记录的是**意图**，代码才是**事实**。当两个意图撞车时，唯一有裁决资格的是事实。

> 注意这个立场的边界：它假设"实现过的需求比没实现的更重要"。多数时候成立，但当某个需求**故意**还没实现却被归档时（本技能允许带警告归档不完整的变更），这个假设就会给出错误答案——见第 4 节。

## 2. 核心设计决策

### 决策一：冲突的键是**精确完整路径**

**选了什么**：冲突只在两个变更的 delta 落在**完全相同的 `<capability-path>`** 上时成立。`identity/user-auth` 与 `billing/user-auth` 路径末段同名，**不算冲突**。

**为什么**：因为它们本来就是两个不同的 capability，各自有独立的 `spec.md`，互不影响。把末段名当键会产生大量假冲突。

这条规则的深层含义是：**目录层级就是隔离机制**。capability 路径分得越细，冲突面越小、批量归档越安全。反过来——把一切都塞进 `auth/` 这种粗粒度路径，等于人为制造冲突。

**代价**：如果团队对 capability 的划分不一致（有人写 `identity/user-auth`，有人写 `auth`），真实的冲突会被漏检——两个路径指向同一个概念，但字符串不同，检测不到。**判据是字符串，不是语义。**

### 决策二：裁决依据是代码证据

**选了什么**：对每处冲突，去代码库搜索实现证据，据此决定同步哪些 delta。

**为什么**：三种可能的裁决依据里，这是唯一客观的：

| 备选依据 | 为什么否决 |
|---------|-----------|
| 按变更新旧 | 简单，但会把未实现的新变更盖在已实现的旧变更上——用"意图"覆盖"事实" |
| 按用户偏好 | 用户未必知道哪个真做了；等于把技术判断推回给非技术信息 |
| 按 delta 内容质量 | 更主观，且"写得好的 delta"与"已实现的需求"无关 |

**代价**：搜索是启发式的，会误判。需求叫 "OAuth Provider Integration"、代码里却叫 `loginWithGoogle()` 时，搜不到就判"未实现"。而**判错的后果是丢需求**——被判未实现的 delta 会被排除在同步之外，它代表的意图不会进真相。原文对此的处理是"跳过同步并警告用户"，但警告出现在操作完成后的摘要里，那时已经晚了。

### 决策三：都实现 → 按时间顺序，新的覆盖

**选了什么**：两个冲突的 delta 都已实现时，按**变更创建时间**排序，旧的先施加、新的覆盖。

**为什么**：需要一个确定的、可解释的顺序规则。时间顺序是最容易向人解释的："后写的变更代表更新的想法。"

**代价**：**创建时间不等于实现时间，也不等于优先级**。一个先创建、后实现的变更，会被判定为"较旧"从而被覆盖——但事实上它可能才是最新的意图。原文没有提供覆盖这个默认顺序的机制（第 7 步的重新推导只处理"伙伴被跳过"，不处理"顺序不对"）。这是这套设计里一处**无法表达真实优先级**的缺口。

**备选方案**：按变更名里的日期前缀排序。**被否决**（原文未提）——但值得注意，这与归档命名规则（`YYYY-MM-DD-<name>`）并不一致，那个日期是**归档日**，不是创建日。

### 决策四：按 **delta** 而非按 **change** 追踪包含/排除

**选了什么**：每个 delta 独立决定是否同步，并明确警告**不要把一个变更塌缩成一个同步开关**。

**为什么**：一个变更的 delta 可能横跨多个 capability，其中一部分已实现（要同步）、另一部分没有（不能同步）。按变更设布尔开关就只剩两个错答案：要么把未实现的需求也写进真相（污染），要么放弃已实现那部分的同步（漏掉）。

**这是整套技能里最容易被实现错的一处**，因为"按变更"符合直觉、代码更简单、而且**简化后的行为看起来仍然合理**——只是静默丢了正确性。原文用加粗强调，正是为了压住这个冲动。

**代价**：状态空间从 `2^变更数` 变成 `2^delta 数`，报告与实现的复杂度都上一个量级。第 8 步 d 因此要专门区分"归档被跳过"与"delta 同步被跳过"两件不同的事。

### 决策五：原子性**不对称**

**选了什么**：两次前置查询的失败待遇相反，且都写在护栏里：

| 查询 | 失败后果 |
|------|---------|
| `instructions archive`（第 2 步，每批一次） | **绝不阻塞**——没有 context/guidance 也继续 |
| `instructions specs`（第 7 步，每个将同步的变更一次） | **整批原子性停止**——在任何写入或移动之前 |

**为什么**：判据是失败的可逆性，与 `archive-change` 的决策五完全同源。

- archive inputs 只是建议性输入，缺了不写坏任何东西。
- specs 规则是**合并规则**。缺了它去改写主规格，等于在不知道规则的情况下动真相资产。

关键设计是"**在第一次写入或移动之前取齐全部快照**"。如果改成"边查边写"，第一个变更写完了第二个才失败，结果就是一半生效、一半没生效，而且**没有回滚**。取齐才开始，把部分失败的可能性从根上消掉。

**代价**：必须先跑完 N 次查询才能开始第一个写入，批量越大前置延迟越长。而且它牺牲了一种可能性：本来可以先处理那些查询成功的变更（更快的部分进展）。这里选择了"要么全做、要么全不做"。

### 决策六：**ready-only** 选项要重新推导冲突

**选了什么**：用户选择"只归档就绪的变更"时，若某个冲突的两个变更中有一个被跳过，**只用正在归档的变更重新推导该冲突的裁决**。

**为什么**：冲突裁决不是一个"分析结果"，而是**相对于某一批变更集合**的结论。集合一变，结论可能就不再成立。

举例：裁决原本说"两者都已实现，按时间顺序施加 A 然后 B"。现在 B 被跳过（它不完整），冲突的第二个参与者消失了——**冲突本身不存在了**。此时若沿用旧裁决，就会出现"施加顺序里包含一个不在批里的变更"的矛盾状态。

**代价**：重新推导意味着第 7 步要回头改第 5 步的结论，流程不是单向的。这也是为什么原文特意写"按**意图**而非精确字面来路由答案"——用户可能选了标签却理解成了别的意思，而这会直接影响重新推导。

### 决策七：单次确认 + 禁止自动选择

**选了什么**：始终提示选择（`Do NOT auto-select`），然后对整批做**一次**确认。

**为什么**：这是一次**批量破坏性操作**（多次 `mv` + 多次主规格写入）且**没有回滚**。自动选择意味着 AI 替用户决定"哪些算完成了"——这个判断一旦错，用户会在不知情下把未完成的变更推进真相。

**代价**：批量越大，用户越难真正**审阅**那张状态表（10 个变更 6 列）。"单次确认"在提高效率的同时，把"逐项确认"提供的注意力摊薄了。这是拿审阅质量换操作效率的取舍。

### 决策八：单个变更失败不阻断其余

**选了什么**：某个变更因故失败（如归档目录已存在）时，**继续处理其他变更**，最后分类汇报。

**为什么**：与决策五的"整批原子性停止"形成对照——同样是失败，为什么这里不整批停？因为两者失败的**性质不同**：specs 规则查询失败会让**所有**后续写入都不可靠（共享的前置条件缺失）；而单个变更归档失败是**局部**的（它的归档目录撞名了），不影响别人。

**代价**：批量操作结束后可能处于**混合状态**——3 个归档成功、1 个失败、2 个跳过、若干 delta 未同步。而且**已成功的不会因为后续失败被回滚**。用户必须读懂分类摘要才能知道实际发生了什么。

## 3. 机制如何运转

```
/opsx:bulk-archive
   ↓
1. openspec list --json → 无变更则停止
   ↓
2. 用户多选（禁止 auto-select）
   载入 instructions archive（每批一次，失败不阻塞）
   ↓
3. 逐变更收集：artifact 状态 / tasks 完成度 / delta specs（existingOutputPaths 为唯一来源）
   ↓
4. 按【精确 capability-path】建映射 → 2+ 变更撞同一路径 = 冲突
   ↓
5. 逐冲突调查代码库 → 裁决（只一个实现→同步它 / 都实现→时间顺序 / 都没实现→跳过+警告）
   ↓
6. 展示状态表 + 冲突裁决摘要 + 不完整变更警告
   ↓
7. 单次确认（取消 / 全部 / 只就绪）+ 重新推导受影响的冲突
   ↓ 取齐全部 specs 规则快照（任一失败 → 整批停止！）
   ↓
8. 逐变更：a. 内联 sync（只传 includedDeltas，明确忽略 excludedDeltas）
           b. 验证主规格（只验 includedDeltas）
           c. mkdir archive/ + mv
           d. 记录 Success / Failed / Skipped / Sync skipped
   ↓
9. 分类摘要
```

**最容易违反的关键约束**：第 8 步 a 里那句"**明确指示它忽略该变更的 `excludedDeltas`**"。这句听起来多余——都已经只传 included 路径了，为什么还要额外指示"忽略"？

因为合并是 agent 驱动的：同步 agent 会去读变更目录，而那里**躺着全部 delta**（包括被排除的）。只传 included 路径未必挡得住它顺手把整目录都合了。所以必须**显式**说"忽略那些"。这与决策四（per-delta 模型）是一体两面：模型再正确，也必须在调用时把意图传达到位。

## 4. 什么时候会失效

### 4.1 delta 合并本身的脆弱点

这些是它与 `archive-change` 共有的，只在批量下被放大：

| 脆弱点 | 后果 | 原因 |
|--------|------|------|
| **合并非确定性** | 同样的 delta 两次运行产出不同主规格 | `sync-specs` 是 agent 驱动的智能合并，不是机械文本替换。而主规格承载"权威真相"，权威性通常要求可复现 |
| **MODIFIED 需要外科手术式精度** | 未在 delta 中点名的其他场景被整段重写吞掉 | 原文要求"带 delta 点名的场景变更、且其他场景原封未动"；而 LLM 的默认行为是整段重写 |
| **REMOVED 的退役边界** | 空的主规格文件被留下，成为"声称 capability 存在却无需求"的谎言 | 移除最后一个 requirement 时必须**删掉主规格文件**，而不是留一个空的 `## Requirements` |
| **无审计线索** | 主规格里看不出这次归档改了什么 | 合并后唯一的线索是归档目录里的 delta，而它已与主规格分离 |
| **跨会话无锁** | 两个批量会话同时跑，后写的覆盖先写的 | 单次操作内部的验证看不见另一次操作；**批量只能检测批内冲突，跨批冲突完全无保护** |

### 4.2 批量相比逐个**多出**的风险

这几条是**只有把多个变更放进同一次操作才会出现**的：

| 场景 | 后果 | 原因 |
|------|------|------|
| **级联合并把偏差放大** | 同一 capability 被多个 delta 依次合并时，前一次的偏差被后一次继承并叠加 | 每次合并读的是**上一次刚写的主规格**。若第一次把某条需求改错了，第二次基于这个错误状态继续改——错误不会被发现，只会被累积。**逐个归档时顺序由人分次决定，批量则把这一串合并压进一次操作，中间没有任何人看的机会** |
| **合并顺序由"创建时间"决定** | 与真实优先级不符，可能用旧意图覆盖新意图 | 批量必须自己定顺序（决策三）；逐个归档时顺序由人操作的时间决定，天然能反映人的判断 |
| **混合状态更难收拾** | 3 成功 / 1 失败 / 2 跳过 / 若干 delta 未同步，无回滚 | 决策八允许局部失败继续；已移动的 `changeRoot` 不会因后续失败被移回 |
| **裁决对不完整变更给出错误答案** | 某个变更因未实现而被判"排除同步"，但它其实**故意**还没实现、稍后会做 | 步骤 7 允许带着警告归档不完整的变更，而步骤 5 的判据是"代码里有没有实现"——不完整变更天然缺少实现证据，于是被误判为"不该同步" |
| **混合 schema 批次只取一份 context** | 某些变更缺少适用的项目约定 | 步骤 2 只查**一个**变更的归档输入，却让 context 贯穿整批（为了压掉 N 次查询）；混合 schema 时单一来源未必适用每一个 |
| **审阅被摊薄** | 用户对那张 6 列表格实际只扫了一眼就点了"全部归档" | 单次确认（决策七）在提高效率的同时减少了逐项审阅的注意力 |
| **单点失败爆炸半径大** | specs 快照任一失败则整批停 | 决策五的原子性保护；代价是批量越大越容易被一个查询拖住全部进展 |

> **最值得注意的是第一条（级联合并）。** 它是批量**独有**的脆弱点，也是这套设计里最隐蔽的一处：每次合并都单独看都"成功"了，验证也是**逐个 capability** 做的（第 8 步 b 只验证主规格是否呈现已同步的样子），没有任何环节在**全过程结束后**再看一眼最终的主规格是否仍然自洽。
>
> 换句话说：`archive-change` 验证的是"这一步做对了没有"，而批量需要的是"这一串做完之后整体还对不对"——**后者没有任何地方在被检查**。三个 delta 依次改同一条需求时，最终结果可能忠实反映了三次合并中的每一次，却整体违背了最初意图。
>
> 这也解释了为什么这套设计最终仍然要求人读摘要：**串行合并的正确性，无法由串行验证保证**。

### 4.3 通用失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 用户取消后 | 什么都不归档——**这是安全的一侧** | 护栏明确写了"被取消的批量操作什么都不归档" |
| 归档目录撞名 | 该变更失败，其余继续 | 决策八的局部失败策略 |
| 用户忘了归档 | `specs/` 悄悄落后于代码 | 与 `archive-change` 同病；批量只是让积压更快地变成一次大操作 |

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **是** `openspec-archive-change` **的批量版本** | 同一个归并点，多出冲突检测、批量确认、分类汇报。**单变更不要用本技能**（它要求多选、且流程更重） |
| **调用** `openspec-sync-specs` | 第 8 步内联执行，逐变更、逐 delta 调用，且必须显式排除 `excludedDeltas` |
| **依赖** `openspec-verify-change` 的产出视角 | 本技能自己不做完整验证，只做"主规格是否已同步"的机械比对；实现层面的验证是 verify 的职责 |
| **反向教训** `openspec-archive-change` | 逐个归档在**冲突**这个维度上比批量更危险——违反直觉，但这是批量存在的根本理由 |
| 与 git 的关系 | git 的 merge 有冲突标记、有回滚、有历史；OpenSpec 的归档三者都没有。**这是它最大的结构缺口** |
