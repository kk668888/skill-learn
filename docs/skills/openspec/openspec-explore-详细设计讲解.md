# openspec-explore · 详细设计讲解

## 1. 它解决什么问题

它对付一个**时序性的失败**：**在还没想清楚的时候，就开始写东西。**

这个失败之所以危险，恰恰因为它不痛。你在探索阶段随手让 AI 生成一份 `proposal.md`，看起来是进展——你有文件了、有结构了、有产物了。但从此刻起，这件东西**有了重量**：你会不自觉地围着它想，因为"都写了"；你会倾向于修补它而不是推翻它；而如果最初的假设是错的，你会在错的骨架上继续搭。

文档产物的成本不是写在磁盘上的那几个字节，而是**它对后续思考的锚定效应**。

第二个失败模式更隐蔽：**探索被"必须产出"绑架**。绝大多数工作流把探索当作第 0 阶段——它存在，但必须交付一份东西给第 1 阶段。于是探索变成了瀑布的第一步，而不是真的在想事情。

**设计立场**：把"探索"与"承诺"**彻底分开**。探索可以有**零产出**，而且那常常是最好的结果。

> 原文里那句 "Sometimes the thinking IS the value"（有时候思考本身就是价值）不是抒情，而是这个技能的**核心契约**。它明确告诉使用者：这里可以什么成果都没有。

## 2. 核心设计决策

### 决策一：声明自己**不是**工作流

**选了什么**：`This is a stance, not a workflow. There are no fixed steps, no required sequence, no mandatory outputs.`

**为什么一个技能要花篇幅声明"我不是什么"**：因为 LLM 会把**任何带步骤的文档当成必须逐条执行的清单**。这是它读文档的默认方式，不是特例。所以如果这份 SKILL.md 长得像一份流程，它就会被当作流程执行——而那正好违背探索的本意。

原文用了一整套手法来卸掉这种"清单感"：
- 小标题写成 `What You **Might** Do`（"可能会做的事"）
- 单列一节 `What You Don't Have To Do`（"你不必做的事"）
- 立场条目用否定式成对出现（"好奇，**而不是**规定性的"、"打开线索，**而不是**审讯"）
- 收尾强调总结是"可选的"

**代价**：无法验证。一个有步骤的技能可以说"你做了第 3 步吗"，而"保持好奇"没法检查。**这个技能的可遵守性天然低于其他技能**——它依靠的是 AI 的姿态，而姿态无法审计。

**备选方案**：写成一份轻量流程（比如"先列 3 个方案 → 再画图 → 再问 5 个问题"）。**被否决的原因**：那就是它要避免的东西——一旦有清单，探索就退化成填表，而填表产出的是**合规的探索**而不是**真正的思考**。

### 决策二：禁止实现，但**允许**创建 artifact

**选了什么**：`you must NEVER write code or implement features` 与 `You MAY create OpenSpec artifacts (proposals, designs, specs) if the user asks` 并存。

**为什么这条线画在这里**——这是整个技能**最需要精确理解**的一处。两种行为看起来都是"产出东西"，但性质完全不同：

| | 创建 artifact | 写应用代码 |
|---|---|---|
| 性质 | **捕获思考** | **做出承诺** |
| 可逆性 | 高（artifact 随便改，不跑） | 低（代码要能跑、要维护） |
| 所处阶段 | 探索 | 实现 |

**关键在"捕获"二字**：如果一个想法已经成形到能被写下来，那不写反而是浪费——思考的产出应当被保存（这正是 `domain-modeling` 的"即时落盘"纪律在另一个套件里的对应物）。而写代码是不可逆的进一步动作，它把"我们在考虑 X"变成"我们有了 X"。

**代价**：这条线在实践中**比看起来模糊**。写一份 `specs/<capability>/spec.md` 到底算"捕获思考"还是"做出承诺"？规格文本一旦写进 delta，就有了"将被归并进主规格树"的语义。原文用"如果用户开口要求"来兜底——把判断权交给用户，但这并没有消除歧义，只是转移了它。

### 决策三：不自动捕获，只提议

**选了什么**：`Don't auto-capture - Offer to save insights, don't just do it.` 以及对每条洞察都是"提议 → 用户决定 → 走开"的三段式。

**为什么**：**自动捕获等于 AI 替用户决定"什么值得留下"**。而"什么值得留下"恰恰是探索阶段要探讨的问题本身——如果 AI 已经知道答案，那就不需要探索了。这条规则在保护探索的**开放性**：判断权留在用户手上，探索才不会被一个过早的"这很重要"截断。

**代价**：探索的成果可能**流失**。用户聊了两小时，很满意，然后关掉会话——什么都没留下。而探索越久，值得捕获的东西越多，但捕获动作完全依赖用户主动。这是一个**把便利性换成开放性**的典型取舍。

**备选方案**：自动把每次探索都存成 artifact。**被否决的原因**：会产生大量"没到成形程度"的中间产物，而它们会像决策一里说的那样**锚定后续思考**——正好是这个技能要防的病。

### 决策四：状态从 CLI 读，不从对话记忆读

**选了什么**：`openspec list --json`、`openspec status --change "<name>" --json`，并在读取时明确要求"从 `artifactPaths` 读现有文件"。

**为什么**：这与 OpenSpec 整体设计一致（见 [技能原理深度讲解.md](./技能原理深度讲解.md) 第 2 节），但在 explore 里有额外分量——**探索是跨会话的**。你周一聊了一半，周三接着聊，会话已经换了一个。此时"我上次说到哪了"这个问题，靠对话记忆回答必然出错，靠 `status --json` 回答永远准确。

原文里还有一条更细的规定：

> `always re-read them from disk, even if you saw them earlier in the conversation (the user may have edited them)`

**这条是在防"记忆比磁盘新"的错觉**——你在对话里看到的是某个时刻的快照，而用户可能在会话之外手工改了文件。**磁盘永远是权威**。

### 决策五：`context`/`rules` 是约束，不是内容

**选了什么**：`These are constraints for you to follow, not content to reproduce: do NOT copy them into the conversation or into any artifact.`

**为什么**：防一个很具体的坏行为——LLM 拿到项目背景后倾向于**把整段背景原样粘贴进它产出的文件**。后果是每个 artifact 都被同样的样板文字撑大，真正的信息被稀释，而且这些样板会和项目背景**逐渐不一致**（项目背景更新了，artifact 里的副本没有）。

**本质**：这是在区分**读入的上下文**和**写出的产物**。对 LLM 来说这两者在表示上很接近（都是文本），所以需要显式划线。同一句话在 `openspec-propose` 里又说了两遍——说明实践中这个问题反复发生。

### 决策六：变更目录**只能**由 CLI 创建

**选了什么**：`Never create a new change directory under openspec/changes/ by hand.`（在 `## When no change exists` 第 1 步和 `## Guardrails` 里各写了一遍）

**为什么**：`openspec new change "<name>"` 会创建必需的元数据文件 `.openspec.yaml`。手工建一个目录，会得到一个**看起来像变更、但缺元数据**的目录——后续每个 CLI 命令（`status`、`instructions`、`validate`）都读不到它，于是整个工作流在这条变更上静默失效。

**这是一个"一致性由 CLI 单点保障"的设计**：把"变更必须长什么样"的知识收在 CLI 里，而不是散落在各个技能的操作说明中。代价是技能文档必须反复提醒"别绕过 CLI"——因为它给的诱惑很实在（`mkdir` 比记住一条命令简单）。

## 3. 机制如何运转

```
用户进入 /opsx:explore
      ↓
读状态：openspec list --json  →  有没有进行中的变更？
读项目上下文：<root.path>/openspec/config.yaml 的 context / rules
      ↓
┌─────────────────────────────────────────────────┐
│  无固定步骤。三种走向：                            │
│                                                  │
│  ① 没有变更 → 自由思考                            │
│        └ 当洞察结晶 → 提议"要不要开个变更？"        │
│        └ 用户要求捕获 → 走下面第 4 步的捕获流程      │
│                                                  │
│  ② 已有变更 → status --json 读现有 artifact        │
│        └ 在对话里自然引用                          │
│        └ 决策成形 → 按映射表提议捕获到具体文件       │
│                                                  │
│  ③ 用户要比较选项 → 先问上下文，再画约束表          │
└─────────────────────────────────────────────────┘
      ↓
全程护栏：不实现 / 不自动捕获 / 不手工建目录 / 不强行套结构
```

**捕获流程（用户明确要求时）——本技能里唯一有"步骤"的部分**：

```
openspec new change "<name>"                    ← 必须走 CLI（建 .openspec.yaml）
      ↓
openspec status --change "<name>" --json        ← 拿到依赖顺序
      ↓
对每个 ready 的 artifact：
  openspec instructions <id> --change "<name>" --json
      ↓
  用 template 写文件到 resolvedOutputPath
  用 context / rules 约束自己（但不写进文件）
      ↓
  每写一个 → 重跑 status → 继续直到全部 done / skipped
```

**最容易违反的约束有两条**：

1. **手工建变更目录**——`mkdir` 的诱惑太大。后果是静默的：目录存在、文件能写、但 CLI 读不到，后续所有命令在这条变更上失效。
2. **把 `context`/`rules` 抄进 artifact**——这是 LLM 的默认行为，不是偶发失误。原文为此在 `propose` 里重复了两次。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 用户期待**一个答案** | 用户觉得"聊了半天没进展"，转去用 `propose` | 本技能刻意不发散成结论；"没有强制产出"在想要结果的人眼里等于无效 |
| 探索**没有边界** | 永远在探索，从不进入变更 | 它**没有停止条件**——这正是与 `grilling`（"前沿为空"才停）最本质的差别：一个是收敛的，一个是开放的 |
| 探索**跨上下文压缩** | 中间结论丢失，重新开始 | 零产出 = 零持久化。防锚定的设计同时放弃了持久化 |
| 用户**从不主动捕获** | 有价值的探索成果全部流失 | 决策三把捕获动作完全交给用户，而用户往往高估自己的记忆力 |
| **store 粘性被遗忘** | 命令作用到错误的 `openspec/` 根，读到别人的变更 | store 一旦选定要全程携带，但在长对话里很容易漏掉 `--store` |
| **捕获流程的边界情况组合爆炸** | AI 在"条件性跳过 / blocked 依赖 / 未请求的前置项"之间判断失误 | `## When no change exists` 第 2–4 步已经长到需要反复回读；每一条边界规则都是为修补一个真实坑加上的，但它们**相互组合**后的分支数已超出一次阅读能掌握的范围 |
| **终端非等宽 / 窄屏** | ASCII 图错位、失去可读性 | 可视化被写成核心手段，但它依赖等宽字体与足够宽度 |
| **用户手工改了 artifact** | AI 基于对话里的旧快照继续推理 | 原文要求"从磁盘重读"，但这条纪律依赖 AI 自觉执行 |
| **把探索当实现用** | 写出代码，违背技能契约 | "创建 artifact 可以"与"写代码不行"的界线在实践中容易模糊（见决策二） |

> **最有意思的是第二行。** 这个技能的"没有停止条件"是它与同族技能最本质的差异：
>
> | | 停止条件 | 性质 |
> |---|---|---|
> | `grilling` | 前沿为空（依赖穷尽） | **收敛**：可判定何时完成 |
> | `brainstorming` | design doc 获批准 | **收敛**：有明确交付物 |
> | `openspec-explore` | 无 | **开放**：随时可以继续，也随时可以停 |
>
> 开放是刻意的，它换来了"思考本身即价值"的自由；代价是没有东西能告诉用户"够了，该往前走了"。**在实际使用中，这个缺失的停止条件往往由用户自己的耐心来提供**——而耐心不是一个可靠的机制。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **下游** `openspec-propose` | 探索成形后通常流入它，一次生成四件套。但**没有强制衔接**——用户可以探索完直接停 |
| **下游** `openspec-new-change` | 更受约束的开变更方式；explore 是"想清楚再开"，new-change 是"边开边想" |
| **下游** `openspec-apply-change` / `openspec-archive-change` | 通过变更间接衔接（探索 → 提案 → 实现 → 归档） |
| **同族对比** `grilling` | 都在"想清楚"，但方向相反：grilling **收敛**（设计树 + 前沿，穷尽假设），explore **发散**（打开线索，不设漏斗） |
| **同族对比** Superpowers `brainstorming` | 两者都在实现前探索，但 brainstorming **必须产出** design doc 并取得批准；explore **允许零产出** |
| **共同机制** | 三者都遵循同一道规划门禁：探索/设计阶段禁止写应用代码。这是三套系统各自独立发明的同一设计（见 [技能原理深度讲解.md](./技能原理深度讲解.md) 第 3 节） |
