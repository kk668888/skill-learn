## 1. 它解决什么问题

先看 `openspec archive` 到底做了几件事。它把两件**性质完全不同**的动作捆成了一个命令：

| 动作 | 性质 | 可否单独发生？ |
|------|------|---------------|
| 把 delta 规格合并进 `specs/` 真相树 | **状态变更**——系统的"当前真相"被更新 | 可以，而且经常应该单独发生 |
| 把变更标记为完成、移入 `archive/` | **生命周期变更**——这件事被认为结束了 | 只有在实现确实做完时才该发生 |

捆在一起会产生一个具体的坏结果：**只要变更没归档，真相树就得不到更新**。而这个窗口可能很长——一个变更从提出到实现完成跨几天甚至几周是常态。在这段时间里，`specs/` 描述的还是旧世界，任何基于真相树的工作（下游仓库读规格、团队按规格对齐、下一步变更引用当前能力）都在读**过期信息**。

所以这个技能的存在理由，就是**把第一个动作单独暴露出来**：

> 原文 description 的措辞是精确的：*"update main specs with changes from a delta spec, **without archiving the change**"*——重点全在最后半句。

成功输出的最后一句也印证了这个分工：*"Main specs are now updated. **The change remains active** - archive when implementation is complete."*（主规格已更新。变更**保持活跃**——实现完成后再归档。）

**设计立场**：规格的"生效时机"应当与变更的"完结时机"**解耦**。二者常被混淆，因为默认路径（archive）恰好同时做了两件事；但它们是两个独立的问题。

> **同样重要的一层**：它不只是"一个额外入口"，还是**合并逻辑的唯一实现**。原文明确说了 *"Archive does this inline"*——archive 不自己实现一遍合并，而是内联调用同一套流程。这决定了它的失效模式会影响 archive，也决定了修一处即修三处。

## 2. 核心设计决策

### 决策一：agent-driven 智能合并，而不是程序化覆盖

**选了什么**：由 AI 读 delta、读主规格，然后**直接编辑**主规格。原文对此有明确解释：

> *"This allows intelligent merging (e.g., adding a scenario without copying the entire requirement)."*

**为什么**：看规格演进中最常见的操作——"给某条既有 requirement 加一个 scenario"。程序化合并只能做到"用 delta 里那一块替换主规格里那一块"，而 delta 的 MODIFIED 块写的是**改动意图**，不是**合并后的完整形态**。要落成主规格，必须理解"哪些部分该保留、哪些该替换"，这是语义工作。

**代价（很实在）**：可靠性从"确定性"降级为"依赖判断力"。程序化合并的结果可预测、可测试；agent-driven 合并的结果取决于模型这次读得对不对。整个技能后半部分那些密集的护栏（第 3、4 步的大量约束）本质上都是在**为这一个决策补可靠性**。

**备选方案**：
- *程序化合并（CLI 直接算文本差异）* —— 被否决。无法处理"只加一个 scenario、保留其余"这类语义合并，而这是主用法。
- *让 delta 自己写成最终形态（即 delta 就是合并结果）* —— 被否决。那样 delta 会退化成主规格的完整副本，评审时看不出"这次到底改了什么"，delta 作为**精炼 diff** 的价值（OpenSpec 的核心卖点之一）就没了。

### 决策二：delta 路径只能来自 `existingOutputPaths`

**选了什么**：原文措辞是"**唯一来源**"（`as the only source of delta spec paths`），并明令不许从其他 artifact 推断。

**为什么**：这是一个**防止 AI 自作聪明**的条款。AI 看到 `changes/<name>/` 下有 `proposal.md`、`design.md`，很自然能从里面"推断"出可能的 capability 路径——而推断的结果可能对得上、也可能错。错的话，它会写出一份**没人要求存在**的主规格。

护栏的取向很清楚：**宁可报告"没有 delta 规格"然后停下，也不要凭理解补出一个。** 这与 `grilling` 的"事实归我、决策归你"是同一种纪律——只不过这里的边界划在"可读的元数据"（CLI 输出的路径）与"需要推断的语义"之间。

### 决策三：调用方收窄的子集，绝不放宽

**选了什么**：如果调用方给出了一份**显式列举**的路径子集，就只同步这些；原文反复强调 *"never widen it back to the full list"*。

**为什么**：这条护栏服务于一个具体协作场景——**bulk archive**。批量归档时，如果某个 delta 的实现找不到，它会**刻意排除**该 delta 并收窄范围。此时如果 sync 出于"我发现了更多 delta，顺便都同步了吧"的好意把范围放宽回去，就会写出一份**调用方明确不愿写的主规格**——而且是静默的。

**这是"聪明反被聪明误"的典型防御**。它承认了一个反直觉的事实：在自动化流程里，**执行者的主动性有时是风险而非价值**。子集是调用方的**决策**，不是可以优化的**建议**。

**代价**：sync 变得不"方便"——它不能顺手多干点活。而且这条规则完全依赖 AI 遵守，没有任何机制强制（子集信息只在提示词里）。

### 决策四：删除主规格需要六重条件

**选了什么**：废弃一个 capability（即删除整份 `spec.md`）时，必须**同时**满足六条：本次运行移除后不再剩 requirement 块、文件其余部分格式良好（仍有 `## Purpose`）、同步前文件本就不是空的、其余非空行能逐行归账、变更的 `.openspec.yaml` 声明了 `retire_capabilities: true`、路径解析后确实在真正的 specs 根目录内。

**为什么**：这是整个技能里**最不可逆**的动作。前五条各自堵一种误触：

| 条件 | 堵住的误触 |
|------|-----------|
| ① 不再剩 requirement 块 | 文件里还有别的 requirement 却被删 |
| ② 仍格式良好（有 Purpose） | 删完留下结构已经坏了的文件 |
| ③ 本来非空 | "本来就没内容，顺手删掉好了"这种无中生有 |
| ④ 逐行归账 | 文件里还有**我没看懂**的东西就删了 |
| ⑤ 显式声明 `retire_capabilities` | AI 自行决定"这个 capability 该退役了" |
| ⑥ 防符号链接 | 顺着链接删掉仓库外的文件 |

第 ③ 条尤其精妙：它把"**什么都没移除**"这个最常见的情况直接变成"不许删"，一句话堵掉了一大类边界 bug。

第 ④ 条（逐行归账）是最强也最"笨"的一条——它要求把文件里每个非空行都归类到已知的结构成分。**笨，但正是它的价值**：它把"我理解这个文件"变成了可检验的操作，而不是一句自信的断言。

第 ⑤ 条把最终决定权**前置**到配置文件——不是问"你觉得该退役吗"，而是要求人在动手之前就在 `.openspec.yaml` 里表过态。

**配套的兜底**：无论什么情况，*"Never write or leave an empty `## Requirements` section"*。也就是说，宁可停在半路，也不留下一个结构上已经坏掉的主规格。原文还要求：若只缺那个 marker，**要明确告诉用户缺的就是它**——这是"停在半路"之后仍要给出可操作出口。

**代价**：非常麻烦，而且失败时是**部分完成**状态（该 capability 没同步、其他 capability 已同步）。原文用"报告阻塞条件 + 告诉用户如何解除"来收尾，但没有"回滚已同步部分"的机制。

### 决策五：specs 规则快照 fail-closed

**选了什么**：写任何主规格之前取一次 `openspec instructions specs`；若命令非零退出或 JSON 无效，**停止**，且明令 *"Do not treat the failure as an absent rule set."*（不要把这个失败当成"没有规则集"）。archive 内联调用时则复用其快照，避免重复获取。

**为什么**：区分"**没有规则**"与"**取不到规则**"——这两者在结果上都是"没有 rules 可用"，但含义完全不同：前者是配置如此，继续合并是对的；后者是环境出了问题，继续合并等于在**不知道约束是什么**的情况下写文件。

**代价**：多一次 CLI 往返（直接调用时），以及一个可能的硬停——一个本可以绕过的查询失败会让同步彻底停下。

### 决策六：要求幂等

**选了什么**：*"The operation should be idempotent - running twice should give same result."*

**为什么**：agent-driven 合并天然不幂等——AI 每次读写的"理解"可能略有差异。但这条要求实际上不是描述事实，而是**给出一个可检验的质量标准**：如果你合并出的结果在第二次运行时还会变化，说明第一次的合并没做到"保留 delta 未提及的一切、维持既有顺序"（原文 Guardrails 里的那两条）。

**代价**：这是个软要求，无法自动验证，只能靠自觉。

## 3. 机制如何运转

```
选定变更
   ↓
status --json  →  planningHome.root（store-aware 的主规格根）
   ↓
existingOutputPaths  →  delta 路径（唯一来源，或调用方收窄的子集）
   ↓
取一次 specs 规则快照（失败 → 停；archive 内联时复用其快照）
   ↓
对每份 delta：
   ├─ 读 delta，读主规格（可能不存在）
   ├─ 按 ADDED / MODIFIED / REMOVED / RENAMED 智能合并
   │     └─ REMOVED 触及"删整份 spec.md"时 → 六重条件检查
   └─ 主规格不存在 → 创建（Purpose 取自 delta，缺则 TBD）
   ↓
openspec validate --specs   →  失败则报告，不得声称成功
   ↓
摘要（含 TBD Purpose 提醒、废弃的恢复指引）
```

**最容易违反的约束**：第 ④ 步里"**MODIFIED 块必须携带整条 requirement**"（正文 + 所有幸存 scenario）。这一条最容易在细节上出错——AI 很自然只写"改动的那部分"。好在它**有防护**：`openspec validate` 与 `openspec archive` 都会拒绝这种写法。这是设计上的好示范——**把容易犯的错变成会报错的错**。

第二条容易违反的是"**绝不把 delta 文件原样拷进主规格**"。delta 带 `## ADDED Requirements` 这类操作头，而主规格里只能有单一的 `## Requirements`。一旦混入，主规格的**语义就坏了**（状态文件里混进了过程痕迹），且下次同步无法区分"当前真相"与"上次的待办"。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **主规格被人工改过、与 delta 语义冲突** | 合并结果取决于 AI 的判断，可能选错一边 | agent-driven 合并没有冲突检测机制，靠"运用你的判断合理地合并" |
| **子集护栏被静默放宽** | 写出一份调用方刻意扣下的主规格 | 子集信息只在提示词里，无机制强制；纯靠遵守 |
| **规则快照抓取而失败但被当成"无规则"** | 在不知道约束的情况下写主规格 | 原文明确禁止（fail-closed），但仍是依赖遵守的软约束 |
| **废弃条件的判断手软** | 该停的没停，删掉了不该删的 spec.md | 六条里②③④都需要判断，尤其④"逐行归账"很容易被草率带过 |
| **同步中途卡在某个 capability** | 部分完成：该 capability 未同步，其他已同步 | 无"回滚已同步部分"的机制，原文只要求报告阻塞条件 |
| **`validate --specs` 失败但仍宣称成功** | 用户以为规格已生效，实际是坏的 | 原文明令不得声称成功，但这是纪律而非机制 |
| **同一主规格被并发同步** | 后写者覆盖先写者 | 无锁、无版本检查；`specs/` 是普通文件 |
| **变更长期不归档、反复 sync** | 主规格与 delta 长期双写，漂移风险累积 | 解耦的代价：两条路径都可能改真相树，需要人维持一致性 |
| **主规格 `## Purpose` 与 delta 的不同** | 以主规格为准，delta 的 Purpose 被丢弃 | 这是**刻意**设计（与 archive 一致），但在"新 capability"场景下可能丢掉更好的描述 |

> **最值得注意的是第一行。** 这个技能的核心决策（agent-driven 智能合并）同时也是它最大的风险来源：**它把一个需要理解的任务交给了一个可能理解错的执行者**。程序化合并不会"理解错"，只会"覆盖"——后者是可预测的坏，前者是不可预测的坏。
>
> 原文对此的应对方式很有代表性：**不试图让 AI 更可靠，而是加护栏把不可靠的后果限制在可承受范围内**。所以你会看到"只从 `existingOutputPaths` 取路径""不许放宽子集""删除要六重条件""validate 失败不得声称成功"——这些护栏没有一条能让合并本身更聪明，它们只是让**错误更难隐藏**。这是处理"必须依赖判断力"这类问题时的一个通用姿态。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **被** `openspec-archive-change` **内联调用** | archive 不自己实现合并，而是内联走这条流程；原文明确说 *"Archive does this inline"*。改这里即改 archive |
| **被** `openspec-bulk-archive-change` **收窄范围地调用** | 批量归档排除掉"找不到实现"的 delta，以**子集**形式调用本技能；这正是决策三所保护的那个场景 |
| **与** `openspec-verify-change` **互补** | verify 检查"实现是否与 artifact 一致"，sync 负责"把 artifact 的改动落进真相树"。二者都在归档之前，但一个管代码、一个管规格 |
| **与** `openspec-update-change` **方向相反** | update-change 改的是变更内的 delta，sync 把 delta 推出去到主规格。一个向内、一个向外 |
| **前置依赖** | `openspec-propose`（或 `new`/`ff`）必须先产出 delta 规格，否则第 3 步直接报告"没有可同步的内容"并停止 |
| 与 Superpowers 的对照 | Superpowers 没有对应技能——它不维护"真相树"这种持久资产，规划产物（design doc、plan）只服务于当次实现。**这个技能是 OpenSpec"规格资产化"定位的直接体现** |
