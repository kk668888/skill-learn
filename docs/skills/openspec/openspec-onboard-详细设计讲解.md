## 1. 它解决什么问题

先要看清一个结构性问题：**OpenSpec 的价值只有走完一个完整周期才显现。**

单独看某个 artifact 是看不出意义的——`proposal.md` 像一份普通的说明，`specs/` 像一份需求文档，`tasks.md` 像一份待办清单。任何一份单独拎出来，用户都会想"我自己写不行吗"。这套东西的价值在于**它们之间的接力关系**：proposal 定 WHY → specs 定 WHAT → design 定 HOW → tasks 拆分 → apply 实现 → archive 把结果固化回真相树。**这条链只有跑通一次，才从"一堆文件"变成"一套方法"。**

而首跑恰恰是最容易失败的：新人面对 12 个 `/opsx:*` 命令无从下手，选错入口（比如直接用 `apply` 而没有 change）、在某个环节卡住、然后得出"这玩意儿太重"的结论——**他从未见过这套东西跑通的样子，所以无法判断问题出在工具还是出在自己**。

**设计立场**：把"学会"设计成一个**完成态的体验**。不投喂文档，而是带着他**在真实项目上跑完一次**，让抽象概念在具体情境里各自落位一次。

> 这个技能在 12 个技能里是罕见的品类：它**不产出变更、不改规格，它的产物是用户的理解**。所有其他技能都在操作仓库状态，只有它操作的是人。

## 2. 核心设计决策

### 决策一：用真实代码库的真实小任务，而不是玩具示例

**选了什么**：原文 Guardrails 里写得毫无余地——*"Use real codebase tasks—don't simulate or use fake examples."*

**为什么**：玩具示例（todo list、计算器）会把流程教成**脱离语境的仪式**。用户在真实项目里第一次遇到的是"这个 TODO 在我看不懂的那个模块里"，而不是"给 todo 加一个删除按钮"。真实任务是**带着摩擦的**，而这些摩擦正是工作流要处理的东西。

**代价（很实在）**：真实任务会**真的可能卡住**——测试跑不起来、依赖没装、那段代码依赖你没读过的模块。此时"教学"会突然变成"调试"，而调试一条卡住的教学流程，体验很糟。

**备选方案**：
- *内置一个玩具项目* —— 被否决。流程能跑通，但学到的是"这套东西在干净的假项目上可行"。
- *让用户自备任务* —— 部分采纳（Phase 2 的第 4 个选项"别的什么？"），但不作为主路径。因为自备任务常常过大（见决策四）。

### 决策二：强制走完全部 11 个阶段，哪怕改动极小

**选了什么**：*"Don't skip phases even if the change is small—the goal is teaching the workflow."*

**为什么**：这条护栏直接解释了"为什么修一个 console.log 也要走 proposal/specs/design/tasks"——听起来荒谬，但如果因为任务小就省掉 design，用户就**少看到一段**，而那段恰恰是他以后在真实项目里一定会遇到、却从没见人做过的部分。教学的目标是覆盖**整个周期**，不是高效完成这个任务。

**代价**：**"杀鸡用牛刀"的观感**。用户很可能在心里嘀咕"就改一行至于吗"。原文对此的应对是让叙述保持轻量（*"Keep narration light—teach without lecturing"*），但讽刺感不会完全消失。这是刻意接受的成本：用一个荒诞感换一次完整的样貌。

### 决策三：EXPLAIN → DO → SHOW → PAUSE 的节拍，且草案先于落盘

**选了什么**：在每个关键转折点（explore 后、proposal 草案后、tasks 后、archive 后）按"解释 → 做 → 展示 → 暂停"推进；Phase 5-8 反复出现"起草 → 呈现 → PAUSE → 才保存"。

**为什么**：两件事被这个节拍同时解决。
- **教学层面**：EXPLAIN 先给心锚，DO 让它落地，SHOW 让结果可见。PAUSE 则是**把"我懂了"变成一个必须显式表达的动作**——用户不吭声，流程就停在那里。
- **纪律层面**："草案先呈现、认可后才保存"直接呼应 OpenSpec 的规划门禁（`Planning boundary`）：**未经认可的产物不落盘**。用户在第一次使用时就**体验到**这条纪律，而不是读到它。

**代价**：来回次数多，15-20 分钟的估计里相当一部分花在等待确认上。原文对此的反制是 *"don't over-pause"*——但"适度"是判断，没有标准。

### 决策四：范围护栏是**软的**

**选了什么**：任务过大时给出三条出路（切小/换一个/还是要做），并明说 *"Let the user override if they insist—this is a soft guardrail."*

**为什么**：这是本技能与 OpenSpec 其余部分最值得对照的一处设计。**同一套件里，别处用的是硬门禁**——`Planning boundary` 直接禁止未获批准的规划进入实现，`sync-specs` 的废弃条件凑不齐就**必须停**。而这里刻意选了软的。

差别来自**后果的严重性**：

| 场景 | 违规后果 | 该用哪种约束 |
|------|---------|-------------|
| 未批准的规划直接实现 | 污染代码库与真相树，影响共享资产 | **硬**——必须拦 |
| 误删一份主规格 | 不可逆地丢失规格 | **硬**——六重条件 |
| 新手挑了个太大的学习任务 | 只影响他自己的学习体验 | **软**——给建议即可 |

**用硬约束去管只伤害自己的选择，收益为零而体验为负**：新手第一次用这套东西就被系统驳回，学到的是"这工具很烦"，而不是"这工具很严谨"。

> 这条设计的可迁移价值很高：**约束的强度应当匹配后果的严重性**，而不是匹配"我有多希望用户别这么做"。

### 决策五：先扫描代码库生成候选，扫不到才开放提问

**选了什么**：Phase 2 先按六类信号扫描（TODO/FIXME 注释、吞掉错误的 catch、没有测试的函数、`any` 类型、调试痕迹、缺失的输入校验）并给出 3-4 条带**位置与范围估计**的具体建议；只有当什么都没找到时，才退回"你想做什么"。

**为什么**：先扫的价值不在"总能找到"，而在**给出具体的锚点**。用户看到"第 2 条，`src/another/file.ts`，约 15 行"时，判断成本远低于面对一个开放问题。而且六类信号都是**低风险、边界清晰、可独立完成**的——它们被选中，本质上是因为它们**适合当教学样本**（改动小、验收明确、不牵扯架构）。

**代价**：扫描结果可能与用户的真实兴趣无关；用户为了配合流程而选了一个他并不关心的任务，参与感会打折。

**注意兜底**：扫不到时退回开放提问，**而不是硬凑一个建议**。硬凑的任务会让教学变成表演——用户能感觉出来。

### 决策六：内联演示 explore，而不是指路

**选了什么**：Phase 3 花 1-2 分钟**当场**在相关代码上跑一遍 explore 式的调查，而不是告诉用户"另外有个 `/opsx:explore` 你可以去用"。

**为什么**：抽象地知道一个命令存在，和亲眼看到它在**当前这个任务**上跑出结果，是两种完全不同的理解。指路是低成本但低效的——用户不会因为被告知就真的去用。

**代价**：这一段是**一次性的演示**，其分析结论不必然被后续阶段采用（Phase 5 的 proposal 是独立起草的）。也就是说，这一段有"演完就丢"的成分，是一笔纯教学开销。

### 决策七：优雅退出，且"只要命令参考"是正常分支

**选了什么**：两条退出路径——中途想停（告知变更保存在哪、如何恢复）和只想要命令参考（直接给速查表）。Guardrails 里有一条明令：*"neither pressure the user to continue"*。

**为什么**：教学场景里，"施压"是有真实代价的——被追着问"你确定不走完吗"的新手，会把"学这套工作流"和"被人推销"关联起来，之后更难主动回来。所以退出不是失败，是**必须被设计过的正常分支**。

第二条路径还多解决一件事：它把"跳过教程"从"用户不配合"变成了**一个被承认的选项**。这是设计上的成熟——**给用户一条体面的出口，比想办法堵住出口更有效**。

### 决策八：Preflight 检查 CLI

**选了什么**：开始前先跑 `openspec --version`，未安装就停下并告知。

**为什么**：这个技能有**大量 CLI 调用**（`new change`、`instructions`、`archive`…）。如果 CLI 缺失，用户会在 Phase 4 才撞上失败——那时已经投入了几分钟，体验是"走到一半发现不能用"。**把环境检查前置到第一步**，成本一行命令，收益是把失败提前到零成本时刻。

## 3. 机制如何运转

```
Preflight：openspec --version 存在？否 → 停
   ↓
Phase 1  Welcome（说明我们会做什么、耗时）
   ↓
Phase 2  扫描代码库 → 3-4 条候选（含位置与范围估计）
   │          └─ 大任务 → 软护栏（切小/换/还是要做，可穿越）
   ↓
Phase 3  内联演示 explore（1-2 分钟真实调查）   ← PAUSE
   ↓
Phase 4  new change → 展示产出的文件夹结构
   ↓
Phase 5  Proposal   ┐
Phase 6  Specs      │  每个都是：EXPLAIN → 起草 → 呈现 → PAUSE → 保存
Phase 7  Design     │
Phase 8  Tasks      ┘                        ← tasks 后 PAUSE
   ↓
Phase 9  Apply：逐任务实现 → 勾选框 → 轻量叙述
   ↓
Phase 10 archive --yes
   ↓
Phase 11 Recap + 命令参考 + 下一步
```

**最容易违反的约束**：*"Don't skip phases even if the change is small"*。它的压力来自**合理性**——用户自己就会说"就这么点改动，别搞 proposal 了吧"，而答应跳过既省事又显得体贴。AI 在这里很容易顺着用户走。原文的对策是在 Guardrails 里把它写成一条独立的、措辞直白的禁令，而不是藏在某一步的说明里。

**第二条容易违反的**：*"Use real codebase tasks—don't simulate"*。当扫描没找到合适候选、或用户的任务不好下手时，"我举个例子演示一下"是很自然的退路——但那就把整个教学的地基抽掉了。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **代码库无 git 历史、无明显 TODO** | 扫描找不到候选，退回开放提问，教学从"带着做"退化为"你想做什么" | 六类信号都不存在时没有别的选材路径；有兜底但体验明显下降 |
| **真实任务触发真实复杂性**（依赖装不上、测试基础设施缺失） | 卡在 Phase 9，教学变成调试，用户记住的是"卡住了" | 决策一选了真实代码库，代价就是真实摩擦；技能里没有"任务变得不可控时如何降级"的机制 |
| **用户挑了大任务并坚持** | 软护栏被穿越，卡在实现细节里，看不到完整周期 | 刻意设计（决策四）。只伤害自己的选择就该允许——但代价确实会兑现 |
| **AI 在演示中犯了错** | 错误被当成"工作流的一部分"学走 | 教学技能的固有风险：**示范即标准**。学习者没有能力区分"这是工作流的做法"和"这是 AI 的失误" |
| **有经验的人跑它** | 纯浪费 15-20 分钟 | 它没有任何"你已熟悉，是否跳过"的检测，假设读者必是新手 |
| **中途退出** | 仓库里留下一个半成品 change | 有 graceful exit 指引（告知路径与恢复方式），但**变更本身仍挂着**，需要用户自己回来清理或完成 |
| **Phase 3 的演示结论与 Phase 5 的 proposal 不一致** | 用户困惑"刚才不是说 X 吗" | 演示是一次独立即兴调查，proposal 是重新起草的，两者不共享结论 |
| **用户跟完但没懂 WHY** | 产物是"会敲这几个命令"，不是"理解这套工作流" | 技能的产物是理解，而理解无法被验证——走完全部 11 个阶段只证明流程通了，不证明学会了 |
| **在已有大量 OpenSpec 变更的项目里跑它** | 新建一个 change，可能与既有进行中的工作冲突 | 没有"这个项目已有活跃变更"的检查 |

> **最值得注意的两条是第三和第四条，它们指向同一个结构性风险：教学质量无法被验证。**
>
> 其他技能的产出是可检查的——`validate --specs` 会告诉你主规格对不对，`--version` 会告诉你环境行不行。而这个技能的全部产出是**用户脑子里的模型**，磁盘上留下的痕迹（一个改好的小任务 + 一条归档记录）与"他学会了"之间没有必然关系。他完全可能全程跟着走、每步都按确认键、最后什么也没理解——而流程看起来**完全成功**。
>
> 原文对这个根本局限的应对方式，是**把所有能确定的环节都设计成不依赖理解的**：脚本化的阶段顺序（不会跳）、脚本化的暂停点（必须确认）、脚本化的检查（CLI 必须在）。但"懂了没有"这一层，它终究交付给了用户自己——这也是为什么 Phase 11 的收尾是 *"Try `/opsx:propose` on something you actually want to build. You've got the rhythm now!"*：**真正的验收在教程之外**。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **内联演示** `openspec-explore` | Phase 3 借用它的方法论做一次短调查，但不真正调用它 |
| **顺序覆盖** `propose` / `apply` / `archive` 的全过程 | 它把常规工作流的每一步都手工走一遍。**它不调用这些技能**——而是自己重演它们的阶段，因为教学需要每一步都带解释和暂停 |
| **与** `openspec-new-change` **的关系** | `new` 是"逐个 artifact 推进"的常规版本；onboard 教完之后用户手上就是这样一条节奏，但 `new` 没有教学性的暂停与叙述 |
| **结尾推荐** `openspec-propose` | Phase 11 的"下一步"推荐的是 `propose`（一次性生成全部 artifact）——从"跟着走"过渡到"自己走" |
| **前置依赖** | 必须先装好 openspec CLI（Preflight 检查），且需要一个有代码的仓库（Phase 2 扫描的前提） |
| 与 Superpowers 的对照 | Superpowers **没有**对应技能。它的技能假设使用者已在体系内（`using-superpowers` 是元规则，不是教程）。OpenSpec 因为有"12 个命令 + 目录约定 + 两种 profile"这些需要被传授的外部知识，才需要专门的教学入口——**需要教多少，取决于有多少东西是必须被知道而不能被推断的** |
