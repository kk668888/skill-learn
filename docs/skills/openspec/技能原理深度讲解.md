# OpenSpec 原理拆解

> 本地版本：`@fission-ai/openspec` v1.8.0（全局 npm 包，`C:\Software\AllSoftware\nodejs\node_modules\@fission-ai\openspec\`）
> 官方定位：*"The most loved spec framework"*——给 AI 编码加上一层轻量规格（spec）层。

## 0. 一句话原理

**把"需求"从聊天记录里搬到磁盘上：AI 和你先就一组可审查的 Markdown 规格达成一致，代码才开始写；规格像代码一样有版本、有增量、可归并。**

README 里的问题陈述就是出发点：

> *"AI coding assistants are powerful but unpredictable when requirements live only in chat history."*

（当需求只存在于聊天记录里时，AI 编码助手强大但不可预测。）

## 1. 核心数据结构：openspec/ 目录

OpenSpec 的主角不是流程，是**磁盘上的数据结构**。`openspec init` 后：

```
openspec/
├── specs/                        ← 【当前真相】系统现在应该做什么
│   ├── todo-management/
│   │   └── spec.md               ←   按 capability（能力域）组织
│   └── user-auth/
│       └── spec.md
├── changes/                      ← 【进行中的变更】
│   ├── add-dark-mode/            ←   一个变更 = 一个文件夹
│   │   ├── .openspec.yaml        ←   变更元数据
│   │   ├── proposal.md           ←   为什么改、改什么
│   │   ├── specs/                ←   规格增量（delta）
│   │   │   └── theme/
│   │   │       └── spec.md       ←   ADDED/MODIFIED/REMOVED Requirements
│   │   ├── design.md             ←   技术方案
│   │   └── tasks.md              ←   实现清单
│   └── archive/                  ← 已归并的历史变更
│       └── 2025-01-23-add-dark-mode/
└── AGENTS.md 等 AI 指令文件       ← init 生成，随工具而异
```

**关键设计：delta（增量）规格。**

进行中的变更不重写主规格，而是写"增量"——只写这次变更**新增/修改/删除**了哪些 Requirement。归档（archive）时才把增量合并进 `openspec/specs/` 的主规格树。

**为什么是 delta 而不是直接改主规格**：
- 变更评审时看到的就是纯净的需求 diff，一眼看清这次到底改了什么行为
- 变更可以废弃（整个文件夹删掉），主规格毫发无损
- 和 git 的分支模型同构：`specs/` 是 main，`changes/<x>/specs/` 是 feature 分支，archive 是 merge

## 2. 工作流：opsx 四部曲

```
/opsx:explore ──→ /opsx:propose ──→ /opsx:apply ──→ /opsx:archive
  想清楚           生成四件套         实现任务         归并回主规格
 (可选,无副作用)    (规划,不写码)      (写码)           (delta → 真相)
```

### /opsx:explore —— 为什么要有"无赌注思考"

还没想清楚时的思考伙伴：读你的代码、权衡方案、塑形一个计划，**不落任何文件、无副作用**。

**为什么**：把"探索"和"承诺"分开。探索期不应该被迫产生 artifact（产生 = 承诺），否则你会因为"都写了"而将错就错。

### /opsx:propose —— 一次生成四件套

输入一个变更名或想法，AI 创建 `changes/<name>/` 并生成四件套：

| Artifact | 回答的问题 | 模板结构 |
|----------|-----------|----------|
| `proposal.md` | 为什么改？改什么？影响哪？ | Why / What Changes / **Capabilities**（新增/修改的能力域路径）/ Impact |
| `specs/<capability>/spec.md` | 系统必须做到什么？ | **Requirement**（用 SHALL）+ **Scenario**（WHEN/THEN）|
| `design.md` | 技术上怎么做？ | 技术方案、取舍 |
| `tasks.md` | 分几步做？ | 任务组 + checkbox 清单 |

生成指令里有一条和 Superpowers 的 HARD-GATE 异曲同工的硬边界（源码原文）：

> **Planning boundary**: ... authorizes planning only, even if it asks to build or fix something. **Do not edit project code.** After the planning artifacts are complete, stop. Do not start implementation in the same response, even if the initial request asks for it.

（规划边界：即使你的请求说要构建或修复，也只授权规划。不要动项目代码。规划产物完成后就停。即使用户要求也不要在同一响应里开始实现。）

**为什么**：同样的病，同样的药——对抗"拿到需求立刻开写"。规划态和执行态必须分离，中间隔一道人工审查。

**规格为什么用 Requirement + SHALL + WHEN/THEN 这种刻板格式**：

```markdown
### Requirement: Theme selection
The app SHALL let users switch between light and dark themes,
defaulting to the system preference.

#### Scenario: User toggles dark mode
- **WHEN** the user clicks the theme toggle
- **THEN** the app switches to dark mode and persists the choice
```

- **SHALL**（必须）：RFC 风格的规范性语言，排除"最好""尽量"这种弹性措辞——需求要么满足要么不满足
- **WHEN/THEN Scenario**：每个场景天然映射为一个验收测试。规格写完，测试用例的骨架已经在那了
- **结构化换来机器可处理**：CLI 能 `openspec validate` 检查变更是否合法（比如零 delta 的纯重构变更必须显式标记 `skip_specs: true`，不许为了过校验而编造需求——连"应付校验的作弊"都被预案了）

**Capabilities（能力域）是什么**：规格的组织维度。`user-auth`、`todo-management` 这样的 kebab-case 路径，每个 capability 一个 spec.md。**为什么**：按业务能力而不是按代码模块组织需求，brownfield（存量）项目也能渐进采用——先把已有行为补写成规格，再往上叠变更。

### /opsx:apply —— 实现任务

`/opsx:apply <change>` 按 tasks.md 逐项实现。关键机制：它不靠 AI 自己"记住"流程，而是**每一步都向 CLI 要结构化状态**：

```bash
openspec status --change "add-dark-mode" --json      # 变更当前状态
openspec instructions apply --change "..." --json    # 此刻该干什么、读哪些文件
openspec list --json                                   # 有哪些进行中变更
```

**为什么这聪明**：
- **状态放在磁盘/CLI，不放在对话记忆里**。对话会压缩、会漂移、换个会话就没了；`status --json` 永远返回当前真相。这也解释了 README 那条 Usage Note：*"OpenSpec benefits from a clean context window"*——它的设计本来就不依赖长上下文。
- 指令里明确处理各种状态（blocked→建议 continue、歧义→必须问用户），AI 不是在即兴发挥，而是在执行一个状态机。

### /opsx:archive —— 归并点

任务完成后 `/opsx:archive`：把 `changes/<name>/` 移入 `archive/<日期>-<name>/`，**把 delta 合并进 `openspec/specs/` 主规格树**。

**为什么归并是显式动作**：合并 = "这个变更的需求正式成为系统真相"。这是个该由人确认的仪式，不是实现完自动发生的副作用。

## 3. 生效机制：CLI 如何让 30+ 工具的 AI 都听话

OpenSpec 支持的不是某一个 AI，而是 30+ 编码工具。它怎么做到的？

**`openspec init` 时**：检测你选的工具（Claude Code、Cursor、Codex...），把 `/opsx:*` 工作流**生成为该工具能理解的文件**（Claude Code 是技能/命令文件，别的工具是各自的指令格式）。`openspec update` 重新生成。

源码里能看到精心的防漂移设计：

> *The instruction text itself is shared, so the two cannot silently drift.*（技能和命令两个表面的指令文本共享同一份，所以不会悄悄漂移。）

**和 Superpowers 的机制对比**：

| | Superpowers | OpenSpec |
|---|---|---|
| 分发方式 | 插件市场安装 | CLI 往项目里**生成**命令文件 |
| 约束的载体 | SKILL.md 正文（对话纪律） | 磁盘 artifact + CLI 状态机 |
| 对抗开写冲动 | `<HARD-GATE>` 标签 | `Planning boundary` 段落 |
| 状态存于 | design doc / plan 文件 + TodoWrite | openspec/ 目录 + JSON API |

注意一个细节：**两套系统各自发明了一个功能相同的硬门禁**（HARD-GATE / Planning boundary），措辞几乎互相独立。这本身就说明"规划态与执行态分离"是这个问题的收敛解——第三次对比时值得写进文档。

## 4. 哲学（README 原文）

```text
→ fluid not rigid        流动而非僵化（任何 artifact 随时可改，无阶段闸门）
→ iterative not waterfall 迭代而非瀑布
→ easy not complex       简单
→ built for brownfield not just greenfield  为存量项目而生
→ scalable               个人项目到企业都适用
```

**fluid not rigid 值得展开**：README 专门对比 Spec Kit（GitHub 官方的 spec 工具）——*"Thorough but heavyweight. Rigid phase gates... OpenSpec is lighter and lets you iterate freely."* OpenSpec 的任何 artifact 都可以中途修改、可以回到前面的 artifact 改了再继续。**为什么**：规格本身也是认知过程，写错了规格不丢人，锁死在阶段闸门里才误事。

## 5. 一图总结两套的本质分工

```
        "做什么"（需求真相）          "怎么做"（工程纪律）
        ┌─────────────────┐          ┌─────────────────┐
        │ OpenSpec 主场     │          │ Superpowers 主场  │
        │ specs/ 主规格树   │          │ 设计对话质量       │
        │ delta 变更       │          │ 计划零占位符       │
        │ archive 归并     │          │ TDD/评审/验证      │
        └─────────────────┘          └─────────────────┘
              产物：可审查的需求文档          产物：按纪律生成的代码
              状态：活在磁盘上               状态：活在流程里
```

重叠区（两次"先设计后编码"、两次任务清单）是真实的；互补区（规格资产化 vs 工程纪律）也是真实的。**孰取孰舍还是配合，留给实验后你自己写对比文档来回答**——第三次会话见。

## 6. 斜杠命令与技能对照

openspec 的每个工作流都有两个"面"：`/opsx:*` **斜杠命令**（你敲的入口）与**同名技能**（AI 执行的内容）。源码注释说明了二者的关系：

> The apply workflow instructions, authored once and rendered by both the skill and command surfaces. The surfaces are intentionally distinct, but they differ only in how they are invoked.

（指令只写一份，由技能面与命令面各自渲染。两个面刻意保持不同，但差别只在于**如何被调用**。）

| 斜杠命令 | 对应技能 | 作用 |
|---------|---------|------|
| `/opsx:explore` | `openspec-explore` | 进入探索模式——想清楚想法、调查问题、澄清需求（无副作用） |
| `/opsx:propose` | `openspec-propose` | 提出一个新变更，一次性生成全部 artifact |
| `/opsx:new` | `openspec-new-change` | 用 artifact 工作流新起一个变更（OPSX） |
| `/opsx:continue` | `openspec-continue-change` | 继续某个变更——生成下一个 artifact |
| `/opsx:ff` | `openspec-ff-change` | 一次生成实现所需的全部 artifact（fast-forward） |
| `/opsx:update` | `openspec-update-change` | 修订既有规划 artifact 并保持彼此一致 |
| `/opsx:apply` | `openspec-apply-change` | 实现变更里的任务（**唯一允许动代码的阶段**） |
| `/opsx:verify` | `openspec-verify-change` | 归档前验证实现与变更 artifact 是否一致 |
| `/opsx:archive` | `openspec-archive-change` | 归档一个已完成的变更（delta 合并进主规格） |
| `/opsx:bulk-archive` | `openspec-bulk-archive-change` | 一次性归档多个已完成变更 |
| `/opsx:sync` | `openspec-sync-specs` | 把变更的 delta 规格同步回主规格 |
| `/opsx:onboard` | `openspec-onboard` | 引导式上手——带讲解走完一个完整的 OpenSpec 工作流周期 |

> 命令文件在源码 `skills/openspec/commands/opsx/`，**不单独建档**——命令与技能共享同一份指令文本，技能文档已覆盖其内容。
