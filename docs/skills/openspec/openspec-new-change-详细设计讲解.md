## 1. 它解决什么问题

它解决的是 `openspec-propose` 的**反面问题**。

`propose` 一次生成四件套，快，但代价是**把用户排除在规划之外**。用户说一句"加暗色模式"，然后拿到四份成品——他在规划阶段**没有介入点**。如果他对第一份文档的范围判断不认同，那个判断已经传染给了另外三份。

而规划恰恰是**最需要用户在场**的阶段。写代码可以外包，因为代码的对错有客观标准（测试、编译、运行）；而"这个范围对不对""这条需求是不是我想要的"**没有客观标准**，只有用户知道。

**设计立场**：规划不是一件可以一次外包出去的事，而是一件**需要逐步参与**的事。所以这个技能的核心不是"更快"，而是**在正确的时刻把控制权交回去**。

> 注意它的 description 自我标注为"实验性的"，且它不在 `openspec init` 的**默认 profile** 里（默认只有 6 个工作流）。作者对它的定位很清楚：这是一个**可选的、还在演化的**节奏，不是主路径。主路径是 `propose` 的"快"。

## 2. 核心设计决策

### 决策一：**主动停止**就是功能本身

**选了什么**：第 6 步没有动作，只有一句 `**STOP and wait for user direction**`。护栏进一步封死："**不要**越过'展示第一个 artifact 模板'这一步。"

**为什么这是本技能最核心的设计**：把它和 `propose` 并排看，两者前五步几乎一样，**唯一的实质差别就是"停不停"**。

```
propose:     new change → status → 生成全部 artifact → 停下等 apply
new-change:  new change → status → 展示第一个模板 → 【停】
```

所以这个技能的价值**不在它做了什么，而在它不做什么**。停止把一个"AI 替你想清楚"的流程，变成了"AI 陪你逐步想清楚"的流程。

**代价**：来回成本显著上升。每个 artifact 都要一次"继续"、一次确认。对于一个需求已经很清楚的中型变更，这套节奏是纯粹的开销——用户会希望直接用 `propose`。

**备选方案**：让 `propose` 加一个 `--interactive` 参数。**被否决的原因**（推测）：参数化的交互模式会让同一个技能承担两种截然不同的行为，而技能是**靠 description 自动路由**的——"一次生成"和"逐步生成"在语义上差异足够大，值得是两个技能。这也解释了为什么 `new-change` 会重复 `propose` 的前五步文本，而不是共享一个实现。

### 决策二：只展示模板，不创建 artifact

**选了什么**：`Do NOT create any artifacts yet - just show the instructions.`

**为什么**：模板是**"即将发生的事情"的预览**。让用户在投入之前先看到形状——"哦，proposal 要写 Why / What Changes / Capabilities / Impact 这四块"——他可以在这个时刻说"等等，我想要的不止这些"。

**这是一个廉价的检查点**：展示模板几乎零成本，而如果模板结构不对，纠正的代价也极低（还没写任何东西）。这与 `propose` 的"先全部写完再说"形成对照。

**代价**：多一个来回。而且它依赖用户**真的会看模板**——如果用户直接回一句"继续"，这个检查点就白设了。

### 决策三：用"停住"代替"声明边界"

**一个观察**：`openspec-propose` 有那段明确的 **Planning boundary**——"只授权规划、不要编辑项目代码、即使用户要求也不要在同一响应里开始实现"。而 `openspec-new-change` **没有对应的段落**。

它的护栏是另一种表述："还不要创建任何 artifact"、"不要越过展示第一个模板"——这些约束的是**推进流程**，不是**编辑项目代码**。

**两种做法的对比**：

| | propose | new-change |
|---|---|---|
| 边界的表述 | **显式规则**："只授权规划，不要改代码" | **隐式结构**：流程在第 6 步就停了，够不到写代码那一步 |
| 优点 | 规则独立于流程，即使流程被绕过也成立 | 更简洁，不必声明一条够不到的禁令 |
| 风险 | 啰嗦 | **一旦"停住"被绕过，没有任何东西兜底** |

**这不是缺陷，是一个取舍**：new-change 用流程结构代替了显式规则。它在正常情况下更优雅——不写一句你做不到的事。但它把安全性**绑在流程的完整性上**：只要第 6 步被跳过（比如用户说"别停，全部做完"），那条边界就不再有任何表述来支撑。

> 这也从侧面说明 `propose` 为什么要写得那么啰嗦（那句 `even if it asks to build or fix something` 就是在堵"用户说了要做"这个理由）——**当一个技能会走到"可能开始写代码"的位置时，它就必须显式地把门关上**。

### 决策四：与 `propose` 共享前置步骤，但**复制**而非复用

**选了什么**：`new-change` 完整地重复了 `propose` 的前五步——store selection 段落（同一段长文字）、Input、schema 判定、`openspec new change`、`openspec status --json`。

**为什么这样是合理的**：这两个技能的前半段确实是**同一件事**，重复保证了行为一致——用户无论走哪条路，脚手架和状态读取的方式都一样。

**代价**：**文本漂移**。同一段 store selection 说明在两个文件里各存一份，哪边改了另一边不会跟着改。这类重复是模板生成的常见后果，而它的后果通常在几个版本之后才显现（两处说明开始互相矛盾）。

**备选方案**：把公共前缀抽成一个共享片段。**为什么在这里不好做**：技能是**独立分发的单元**（`install-skills.mjs` 逐个目录复制），一个技能目录里不能引用另一个技能的文件。所以"复用"在这套架构下意味着"要么重复，要么在 CLI 里生成时拼接"——OpenSpec 选了前者。

### 决策五：命名校验与同名检测作为护栏

**选了什么**：两条护栏——"如果名字不是 kebab-case，要求一个合法的名字"、"如果同名变更已存在，建议改为继续那个"。

**为什么**：这两条都在保护**磁盘数据结构的一致性**。kebab-case 是变更目录名的约定（它来自你的自然语言描述，需要被规范化）；同名检测防的是**两个变更争抢同一个目录**——那会让 `status`/`archive` 指向不明。

**代价**：几乎没有。这是低成本的防御，且失败模式（名字不合法、目录冲突）都是当场可发现的。

## 3. 机制如何运转

```
用户：/opsx:new add-dark-mode
      ↓
① 无清晰输入 → 追问想构建什么 → 推导 kebab-case 名字
      ↓
② 确定 schema（默认；用户点名或问"有哪些工作流"时才变）
      ↓
③ openspec new change "<name>"      ← 走 CLI（建 .openspec.yaml）
      ↓
④ openspec status --change "<name>" --json
      ↓                              ← 拿 planningHome / changeRoot /
                                         artifactPaths / nextSteps
⑤ 找第一个 status=ready 的 artifact
   openspec instructions <id> --change "<name>"
      ↓                              ← 输出模板 + 上下文
⑥ ══════════ 停下，等用户指示 ══════════
         ▲
         └── 这个"停"就是本技能的终点，也是它的全部价值
```

**最容易违反的约束**：**别越过第 6 步**。护栏专门写了这条（"不要越过'展示第一个 artifact 模板'这一步"），因为它是最自然的越界——AI 拿到了模板，下一步就会想去填它。而填它正是 `propose` 的活。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **第 6 步被绕过**（用户说"别停，全做完"） | 退化成 `propose`，且**失去了 `propose` 的显式规划边界** | 本技能用"停住"代替"声明边界"（决策三）。界线一旦越过，没有规则兜底 |
| 用户**不看模板** | 检查点白设，等于多花一个来回 | 决策二依赖用户真的审阅预览，而这个动作是纯靠自觉的 |
| 变更**本身很简单** | 来回成本大于收益，用户烦躁 | 逐步节奏的价值与"需要介入的程度"成正比；简单需求的介入需求为零 |
| **`continue-change` 未启用** | 停在第一个模板后，用户不知道下一步该走哪个命令 | 本技能只负责"开个头"，推进依赖扩展 profile 里的 `continue-change`；两者必须同时启用才闭合 |
| **与 `propose` 的共享文本漂移** | 两条路径的 store/schema 说明渐渐不一致，行为出现分歧 | 决策四：复制而非复用。技能是独立分发单元，共享片段在架构上做不到 |
| **标记为 experimental** | 接口可能变；依赖它的自动化会碎 | 作者明确标注了成熟度（description 与 profile 位置）。这是诚实的代价，不是缺陷 |
| 用户**默认 profile** 下 | **用不到这个技能** | 它不在默认的 6 个工作流里；必须先 `openspec config profile` 切到扩展 profile |

> **第一条与第三条构成本技能的核心张力**：它存在的理由是"让用户在规划中在场"，而它的失效方式是"用户要求跳过在场"。这两件事在**同一类用户**身上同时成立——目标明确的人既希望参与规划，又讨厌被逐步拦停。
>
> 所以它的适用场景其实很窄：**需求已有大致方向、但细节需要边聊边定**的中型变更。需求极清楚（用 `propose`）或极不清楚（用 `explore`）时，它都不是最优解。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **同级替代** `openspec-propose` | 同一阶段的两条路径：propose = 一次生成（快），new-change = 逐步（稳）。**用户按"需求清楚程度"选择** |
| **下游** `openspec-continue-change` | 本技能停在第一个模板；推进由 `continue-change` 接手。**两者必须同时启用**（同在扩展 profile） |
| **下游** `openspec-ff-change` | "fast forward"——另一个推进节奏的变体 |
| **下游** `openspec-apply-change` / `openspec-archive-change` | 全部 artifact 完成后进入实现与归档 |
| **上游** `openspec-explore` | 需求极模糊时的前置，与 `propose` 共享同一上游 |
| **共同机制** | 与 `propose` 一样走 `openspec new change` 脚手架（不手工建目录），状态一律取自 CLI |
