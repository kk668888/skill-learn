## 1. 它解决什么问题

"实现完了"是一句**声称**，不是**证据**。

而且这句话特别容易说得出口——AI 尤其如此。它写完代码后倾向于报告完成，因为这个报告很难被证伪：没人会去逐条核对 tasks 是否勾对了、delta 里的每个 Requirement 是否真在代码里、design.md 里的决策是否被遵守了。

真正难处理的是：**这三类问题的性质完全不同，却都伪装成同一句话"做完了"。**

- 任务勾完了，但有一个**没做**
- 都做了，但某个需求**实现得不对**
- 都对，但实现方式**和 design.md 里定的方案矛盾**，或和项目既有模式不搭

如果只输出一句"通过/不通过"，这三类问题的**可操作性**就全丢了：未完成的任务要去做，偏离的实现在 review，模式不一致只需知晓——它们的处理方式、紧急程度、责任人都不同。

**设计立场**：验证的产出不是**判决**，而是**分类过的线索**。它的职责是把事实摆得足够清楚，让**人**能做决定——而不是替人做决定。这个立场贯穿全部设计，尤其体现在下面决策六（它不阻塞归档）。

> 隐含前提：**验证者（AI）没有能力做真正的证明**。它只有代码搜索和常识推理。整个技能是围绕这个自我限制定制的。

## 2. 核心设计决策

### 决策一：三个维度，而不是一个结论

**选了什么**：Completeness（完整性）/ Correctness（正确性）/ Coherence（一致性），每维独立出结论。

**为什么**：三维分别回答三个不同的问题——

| 维度 | 问题 | 判据 | 可执行性 |
|------|------|------|---------|
| Completeness | 说要做的事**都做了吗**？ | 复选框、需求列表（客观） | 去补做 |
| Correctness | **做对了吗**？ | 需求/场景与代码的对应（半客观） | 去 review |
| Coherence | 做法**自洽吗**？ | 与 design.md、与项目模式的比对（主观） | 去知晓 |

关键在于三者的**证据强度递减**：Completeness 是查清单（几乎确定），Correctness 是搜关键词（可能错），Coherence 是主观判断（经常可争议）。把三者混成一个结论，就等于用最弱的那一环去决定整个结果。

**代价**：报告更长，用户要多读几行。但换来的是"该去做什么"一目了然。

### 决策二：公开承认自己是启发式，不是证明

**选了什么**：原文在「验证启发式」一节里明说："使用关键词搜索、文件路径分析、**合理推断**——不要求完全确定的证据"。

**为什么**：这是整套设计里**最诚实的一处**。它等于在说：这份报告的结论可能是错的。

为什么值得这么写？因为**不这么写的后果更糟**。如果技能暗示自己能给出确定结论，用户就会按"确定"来对待它——把 CRITICAL 当成真理、把"全部通过"当成保证。而实际上：

- 需求名叫 "OAuth Provider Integration"，代码里的实现可能叫 `loginWithGoogle()`——关键词搜不到，于是误报"未实现"。
- 反过来，搜到了同名函数但行为完全不同——于是漏报。

公开承认启发式之后，才能引出下面那条真正重要的规则。

### 决策三：不确定时**向下降级**

**选了什么**：`When uncertain, prefer SUGGESTION over WARNING, WARNING over CRITICAL`。

**为什么**：这条规则的目的不是"谦虚"，而是**保护信噪比**。

一份验证报告的全部价值，取决于它列在"必须处理"里的条目**是否真的必须处理**。一旦 CRITICAL 里混进误报，用户试过两次"这个其实没问题"之后，就会开始**整体忽略这份报告**——而那时真正致命的遗漏也一起被忽略了。误报的危害不是"多花时间看了一条"，而是"训练用户不再看"。

所以宁可把不确定的东西放在低级别：CRITICAL 只留给查清单得出的确定结论（未完成任务、需求列表里有但代码里完全找不到），其余全部降级。

**代价**：真正的严重问题若证据不够直接（比如"实现可能存在但行为偏离"），会被降成 WARNING 从而**可能被拖延**。这是拿"不误报"换"可能漏掉严重项"的取舍——作者选了前者，理由是对"报告被整体忽略"的恐惧大于对"单条被拖延"的恐惧。

### 决策四：每条问题必须可执行

**选了什么**：`Every issue must have a specific recommendation with file/line references where applicable`，且明文禁止 `consider reviewing` 这类措辞。

**为什么**：含糊的建议等于没有建议。"建议审查一下认证模块"——审查什么？谁审查？审出什么算完？这类建议的唯一效果是把工作**推回给用户**，同时还让他以为已经有人看过了。

禁止它的方式和 TDD 技能里那张「合理化对照表」是同一手法：**把常见的偷懒话术直接点名封死**，而不是依赖执行者自觉。

### 决策五：优雅降级

**选了什么**：按实际存在的 artifact 决定验证范围——只有 tasks 就只查任务；有 tasks+specs 就查两维；全有才查三维。且**必须注明跳过了什么、为什么**。

**为什么**：因为 `design.md` 是可选 artifact（纯重构变更常常没有）。如果技能假定三个都在，遇到缺 design 的情况就会要么报错、要么**悄悄跳过却不说明**——后者更坏，因为用户会以为三个维度都查过了。

原文的规则是"跳过可以，但必须显式说明"。这条和决策三同源：**不能让缺失伪装成通过**。

### 决策六：它不阻塞归档

**选了什么**：本技能**只产出报告**，没有任何阻止归档的机制。甚至发现 CRITICAL 时，最终判定也只是 `Fix before archiving` ——一句建议。

**为什么**：这是"验证"与"守门"的**职责分离**。归档是否放行，由 `archive-change` 自己的守卫决定（它检查 artifact 完成度、tasks 完成度、以及同步是否成功）。本技能只负责把证据交上去。

这个分开是有道理的：验证器一旦同时是守门人，它就有了"为了拦住而夸大问题"的动机；而且验证的标准（启发式，可能误报）不足以支撑一个硬性否决权。**把判决权留给可逆性判据更清楚的环节**（能不能写坏主规格），而不是留给一个靠关键词搜索的判断。

**代价**：CRITICAL 可能被无视。用户可以直接跳过 verify 去 archive——**原文没有任何机制阻止这件事**。这是一处刻意的、代价明确的开放性。

> **与 Superpowers 的对照**：`verification-before-completion` 对同一诉求（证据优于宣称）的处理截然相反——它写着 `NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE`，把"没有证据不许宣称完成"定成铁律，并且**定性地把违规称为不诚实**而非草率。
>
> 两套的差别在于**证据的来源**：Superpowers 要求**跑命令看输出**（客观、机器产生、不可辩驳），所以敢下铁律；OpenSpec 这里只能**搜关键词做推断**（主观、AI 产生、可错），所以只能给建议。**证据的强度决定了规则的硬度**——这是这两套系统放在一起看时最清楚的一课。

## 3. 机制如何运转

```
/opsx:verify <name>
   ↓
1. 选定变更（只列带 tasks 的）
2. openspec status --json      → 知道 schema 与存在哪些 artifact
3. openspec instructions apply → 拿到 contextFiles（要读哪些文件）
   ↓
4-7. 按 artifact 实际情况验证（优雅降级）
   ├─ Completeness：数复选框、提取 "### Requirement:" 列表、搜代码
   ├─ Correctness ：逐需求搜实现证据；逐 "#### Scenario:" 查覆盖与测试
   └─ Coherence  ：比对 design.md 的决策；扫项目模式
   ↓
8. 出报告：记分卡 + CRITICAL/WARNING/SUGGESTION 分组 + 每条附建议
   ↓
（结束——不阻塞任何后续动作）
```

**最容易违反的关键约束**：决策三的**降级纪律**。默认冲动是"发现了可疑之处就报高severity"，因为报高显得尽责。而正确做法恰恰相反——**证据不足时降级**。这一步没有任何机制强制，完全靠执行者理解"误报会训练用户忽略报告"这件事。

另一处易违反的是决策五的"**必须说明跳过了什么**"。跳过检查在报告里不留痕迹时，报告看起来和"全部查过且通过"一模一样。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **需求名与代码标识符不对应** | 误报"未实现"，或漏报（搜到同名但不同的东西） | 唯一手段是关键词搜索；自然语言需求名 ↔ 代码命名之间没有映射关系 |
| **delta spec 没按模板写 Requirement 标记** | 提取到 0 条需求，**整维静默通过** | 提取依赖字面标记 `### Requirement:`；格式一破，检查就空转且不报错 |
| **需求实现存在但行为偏离** | 判为 WARNING 而非 CRITICAL，**可能被拖延到上线** | 证据是间接的，按决策三降级；这是"不误报"的代价 |
| **CRITICAL 里混入误报** | 用户开始整体忽略报告，真问题随之被忽略 | 报告的价值取决于"必须处理"的纯度；一次误报就损耗一次信任 |
| **verify 被跳过** | 未完成任务、未实现需求直接进入 `specs/`，真相被污染 | 本技能**不阻塞**归档（决策六），且原文无任何机制强制先跑 verify |
| **规格本身写错了** | 全部通过，但通过的是错的规格 | 三维只验证"实现 vs 规格"，**从不验证规格本身对不对**——这是本技能的能力边界 |
| **验证之后代码又被改** | 报告过时，无人知晓 | 验证是一次性快照，没有回归保护、没有重跑触发 |
| **Coherence 维度被忽视** | design.md 与实际实现长期分叉，design 文件沦为装饰 | 该维最主观、证据最弱、最容易被当成"风格问题"跳过；而"不要对风格吹毛求疵"这条纪律无从强制 |

> **最值得注意的是第二条和第六条。**
>
> 第二条是一种**静默失效**：格式一破，检查不会报错，只会查到 0 条需求然后判定通过。这类"输入不符合预期时静默放行"的行为，比明确的失败危险得多——因为报告上写着"通过"。
>
> 第六条则划出了这个技能的能力边界：它验证**一致性**，不验证**正确性**。一套写得漂亮、实现得忠实、内部完全自洽的规格，如果它本身描述的是错误的需求，本技能会全部通过。**规格的正确性只能由人负责**——这个技能能做的只是确保"实现没有偷偷偏离规格"，从而让人只需审一处、而不是审两处。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **前置** `openspec-archive-change` | 归档前跑它拿报告；但本技能出的是**建议**，归档放行由 archive 自己的守卫判定 |
| **验证对象** `openspec-apply-change` | 它验证的正是 apply 阶段的产出（实现是否落在代码里） |
| **读取** `openspec-propose` 的产物 | 读 delta specs / tasks / design——这三样是 propose 阶段生成的 artifact |
| 与 Superpowers `verification-before-completion` 的分歧 | 同诉求、两种硬度：Superpowers 靠**可执行的证据**下铁律；这里靠**启发式推断**给建议（详见决策六的对照） |
| 与 Superpowers `requesting-code-review` 的关系 | 都是"在问题级联放大之前抓住它"；区别是评审对象——后者看**代码质量**，本技能看**需求与实现的一致性** |
