## 1. 它解决什么问题

它是 OpenSpec 十二个技能里**唯一被授权修改代码**的那一个。

这听起来像是"它就是干活的那个"，但真正的设计问题在别处：**规划一旦结束，代码开始写，最大的风险是什么？**

风险是**规划与实现之间的那道墙被无声地拆掉**。想象一下没有这个技能的约束会怎样：你在 `/opsx:propose` 之后直接说"开始实现吧"，AI 一边读着 `tasks.md` 一边写代码——然后发现第 3 个任务描述得不够清楚。它会怎么办？很可能会**顺手替你把设计补全**：按最合理的猜测实现，然后继续。你没有看到任何提示，但事实上它已经**在实现阶段做了规划决策**，而这个决策没有经过你、也没有落进 `specs/`。

所以这个技能要解决的不是"怎么把代码写出来"，而是**如何在放手让 AI 写代码的同时，保住"规划决策必须显式发生"这条线**。

**设计立场**：实现阶段允许"停下来"，但**不允许"猜过去"**。原文用六条暂停条件（任务不清晰、暴露设计问题、错误、阻塞、用户打断、需求不明）把"停下来"制度化，并在护栏里直接写死一句 `don't guess`。

## 2. 核心设计决策

### 决策一：唯一授权改代码，其余阶段一律禁止

**选了什么**：`apply` 是权限反转点——`propose` 阶段明令"不要编辑项目代码"，`apply` 阶段才允许。

**为什么**：这不是"分工"，而是**用一个可检查的边界替代一个不可检查的判断**。"现在该不该写代码"如果交给 AI 临场判断，它会倾向于"用户看起来很想看到进展，那就写吧"。而一旦把这个判断变成**阶段属性**（这个技能允许、那个技能不允许），判断就从模糊的意图识别变成了确定的状态查询。

**代价**：你必须显式地从一个阶段切到另一个。规划做完了但你没说 `/opsx:apply`，代码就不会被写——**技能不会主动越界来帮你**。

**备选方案**：
- *不做权限划分，让 AI 判断何时可以写代码* —— 被否决。这正是它要解决的问题本身。
- *用一个标志位而不是独立技能来控制* —— 被否决。标志位是隐藏状态，无法通过"我现在在哪个技能里"被用户直接看到。

### 决策二：`context` 与 `operationGuidance` 被定义为"契约而非检查"

**选了什么**：把这两个外部注入的字段逐条限定——不是完成证据、不替代内建指令、不许绕过 blocked、冲突时保留控制值，并且**明确承认"这些是 prompt 级行为契约，不是可强制执行的检查"**。

**为什么**：这是全文最诚实的一段，它处理的是一个**真实的权限模糊**。`context` 来自项目配置，`operationGuidance` 来自 CLI——两者都是"外部权威"，但外部权威可能和当前状态冲突。如果不预先划界，AI 面对冲突时会随机选择一方（通常是更晚看到的那一方）。

**这段的价值在于它列出了四种具体的越权方式**，而不是笼统地说"要尊重指令"：① 把 context 当完成证据（看到"任务已完成"之类的描述就以为可以收工）；② 用 guidance 替代内建指令；③ 拿 guidance 去绕过 blocked；④ 冲突时不报告而自行取舍。

**代价与风险**：作者自己点破了——**这段约束无法被验证**。它写在提示词里，靠执行者自觉。所以它是一份"君子协定"，而不是护栏。这一点反而让它可信：**一份假装自己有强制力的约束，比一份坦白自己没有强制力的约束更危险**。

### 决策三：进度记在磁盘上，不记在对话里

**选了什么**：任务完成通过在 `tasks.md` 里把 `- [ ]` 改成 `- [x]` 来标记。进度、状态一律来自 `openspec status --json`。

**为什么**：让**状态活在文件里而不是对话里**。对话会压缩、会漂移、换个会话就没了；而 `tasks.md` 的勾选框和 `status --json` 的输出永远返回当前真相。

这条设计与 OpenSpec README 的那句 Usage Note 是同一件事的两面：*"OpenSpec benefits from a clean context window."*（OpenSpec 受益于干净的上下文窗口。）它敢这么说，是因为**它本来就不依赖长上下文**——状态在磁盘上。

**代价**：多一次 CLI 调用；并且 checkbox 是**文件存在性级别**的粗糙指标（谁勾上就算完成，没有验证）。这个粗糙性在 ff-change 里会变成一个具体的陷阱（见该技能）。

### 决策四：明确拒绝阶段锁定

**选了什么**：`Fluid Workflow Integration` 一节主动声明"可随时调用""允许更新 artifact""不做阶段锁定"。

**为什么**：因为**实现必然会暴露设计问题**。如果流程锁死"规划阶段完成后不许再碰规划产物"，那么实现中发现设计问题时，AI 只有两个选择：绕过流程偷偷改，或者停下来告诉你"流程不允许我改，你得重新走一遍 propose"。前者破坏流程，后者惩罚诚实。

**代价**：回头改 artifact 会让**之前基于旧 artifact 做的实现可能作废，而技能里没有任何机制追踪这种作废**。原文只说了"允许更新"，没说"更新后如何回溯已实现的部分"。这是这个决策的未偿成本——它被下推给了 `update-change` 技能（那个技能确实要求"实现已完成的变更被改写后，建议走 `/opsx:apply` 把 delta 带进代码"）。

### 决策五：把"停下来"制度化为六个具名条件

**选了什么**：任务不清晰、暴露设计问题、错误或阻塞、用户打断、需求不明——逐条列为暂停触发条件，并配 `don't guess`。

**为什么**：LLM 的默认倾向是**填充空白并继续前进**。"停下来问"对它而言是反直觉的——它倾向于把提问视为"没做好"。所以不能只说"遇到问题要问"，必须**把"什么算问题"逐条列举出来**，让它可被对照检查。

**代价**：暂停会打断你的节奏；如果条件判得太松，一个琐碎的不确定就停下来问，会让流程变得啰嗦。原文用 "Task is unclear"（不清晰）这种较严的措辞来收紧，但**边界最终还是靠判断**。

## 3. 机制如何运转

```
选择变更（含歧义时必须问用户）
      ↓
openspec status --change <name> --json     ← 拿到 schema、路径、编辑约束
      ↓
openspec instructions apply --change <name> --json
      ↓
状态分支 ┌─ blocked  → 建议 /opsx:continue，停止
        ├─ all_done → 祝贺 + 建议归档，停止
        └─ 其他     → 继续
      ↓
读 contextFiles 里的每一个文件（不假定文件名）
      ↓
展示进度（N/M）
      ↓
┌─→ 逐任务实现
│     - 改动最小化、限定在任务范围
│     - tasks.md：- [ ] → - [x]
│     - 六个暂停条件任一命中 → 停
└── 直到全部完成或暂停
      ↓
展示状态：本次完成项 / 总体进度 / 下一步建议
```

**最容易违反的关键约束**：`Do not use context or operation guidance as proof that a task is complete.`（不要把 context 或 operation guidance 当作任务已完成的证据。）

这条之所以容易违反，是因为违反时**感觉非常合理**——如果 context 里写着"本项目的任务清单在 tasks.md，勾选即代表完成"，AI 很容易把"我读到的说明"与"我确实完成了"混为一谈。而这个技能的完成判定**只认 CLI 的进度数字和 tasks.md 的勾选框**，不认任何叙述性文本。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| `tasks.md` 的勾选框被手工改动，或与真实进度不符 | 进度数字失真，AI 会跳过未做的任务或重做已做的 | 勾选框是**文件存在性级别**的指标，没有验证机制 |
| 任务描述本身有歧义，但 AI 判断为"清晰" | 按猜测实现，规划决策被悄悄下移到代码里 | 六个暂停条件全部依赖 AI 判断"是否清晰"，`don't guess` 是倡议而非检查 |
| 一次实现里顺手改了任务范围之外的代码 | 改动超出 tasks 边界，评审时难以归因 | 护栏写了"改动最小且聚焦"，但没有范围校验 |
| 实现中发现问题却**不**回头改 artifact | 代码与 specs 静默漂移，下次读 specs 的人被误导 | 决策四打开了回头路，但**走不走这条路由 AI 主动提议**，它可能选择"先绕过去" |
| 回头改了 artifact，但不重跑 apply | 已实现的部分与新规划不一致，无人追踪 | 技能内没有"规划变更 → 实现作废"的追踪机制 |
| 自定义 schema 里没有 tasks artifact | 步骤 2/6 假定存在承载任务的文件 | 原文说"哪个 artifact 承载任务随 schema 而定"，但实现循环的结构仍围绕任务清单 |
| `blocked` 状态下 `/opsx:continue` 未安装 | 只能退回到手敲 CLI 命令查下一个 artifact | 原文对这一点给了降级路径，但用户容易以为流程断了 |

> **最值得警惕的是第二行。** 整个技能的防线建立在"AI 能识别出自己不懂"这个前提上。但 LLM 的失效模式恰恰相反——**它对自己的理解程度评估得很差**，越是不懂的地方越容易给出流畅的猜测。所以 `don't guess` 这条护栏的实际效力，取决于一件它无法保证的事。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **被** `openspec-propose` / `new-change` / `ff-change` / `continue-change` **指向** | 那四者产出 artifact，完成后都提示"运行 `/opsx:apply` 或让我实现" |
| **指向** `openspec-continue-change` | 状态 `blocked`（缺 artifact）时的唯一推荐出口 |
| **指向** `openspec-archive-change` | 状态 `all_done` 时的推荐出口 |
| **与** `openspec-update-change` **互补** | 实现暴露设计问题时：update 负责改 artifact，apply 负责把改动带进代码——两者构成一个闭环 |
| 与 Superpowers 的对照 | `apply` 对应 Superpowers 的**执行阶段**，但它**内置了 TDD 与评审**吗？没有——它只要求"改动最小、遇歧义暂停"。TDD、两阶段评审、subagent 隔离这些在 Superpowers 里是**独立技能**，在 OpenSpec 里**根本没有对应物**。这是两套体系最实质的能力差异之一 |
