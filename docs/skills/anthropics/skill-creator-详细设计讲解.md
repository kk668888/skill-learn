# skill-creator · 详细设计讲解

> 本文回答「这个技能**为什么这么设计**」。原文说了什么，见 [skill-creator · 中文版](./skill-creator-中文版.md)。

## 1. 它解决什么问题

**失败模式：写技能靠直觉，评技能靠自我感觉。**

写一个 SKILL.md 很容易——把工作流写成 Markdown 而已。难的是回答两个事后问题：

- 这段 description 到底会不会在正确的时候触发？
- 技能正文真的让模型做得更好了吗，还是只是「看起来更专业了」？

一个人凭直觉写完技能，自己读一遍觉得挺好，就上线了。没有对照（不知道无技能时模型表现如何）、没有基准（不知道好多少）、没有触发测试（不知道什么时候会失灵）。这和「不做测试就上线的代码」是同一种病——只不过病灶是自然语言写的提示词，所以「看起来能跑」的错觉比代码更强：文字总能读通，但读通不等于有效。

「提示词写清楚点」解决不了这个问题，因为清楚≠有效。description 写得再清楚，如果不覆盖用户真实的说法，模型照样不触发；指令写得再清楚，如果没有对照实验，你无法知道它带来的是提升还是干扰。**技能需要的是实证方法，不是更好的文笔。**

隐含的设计立场有三条：

1. **技能是软件**，需要测试、基准、回归——所以整套技能围绕 eval 循环组织，附带 schema、评分、汇总脚本，俨然一个小型测试框架。
2. **人是最终的评估者**——定量断言只能覆盖可客观验证的部分，输出质量的最终裁判是坐在浏览器查看器前的用户。模型自评不可信。
3. **元技能本身也要符合它宣扬的价值观**——「泛化、精简、解释 why」既是它教别人写技能的准则，也是它自己行文的准则（整份 SKILL.md 几乎没有 ALL-CAPS 命令，大量解释为什么）。

## 2. 核心设计决策

### 决策一：with-skill 与 baseline 双跑对照，且同一轮启动

**选了什么**：每个测试用例跑两次——一次挂技能，一次作为基线（新技能的基线是无技能，改进技能的基线是旧版快照）；且必须在同一轮启动全部运行。

**为什么**：没有基线，「挂技能后输出变好」无法归因——可能模型本来就做得到。基线语义随任务类型切换，保证归因对象始终是「这次改动」。同一轮启动则是控制时间混杂：分两批跑，可能赶上不同的系统负载或模型状态，对照就不干净了。

**备选方案**：只跑 with-skill，靠人的印象判断提升。否决原因：印象会把「技能写得好」和「模型本来就行」混为一谈，而这个混淆恰恰是本技能要消灭的。

**代价与风险**：成本直接翻倍（每个 eval 两次 subagent 运行），对 Token 敏感的用户不友好。原文用「可选的盲评」把进一步加码（更多对照）隔离在进阶区，算是给了成本逃生口，但主循环的双跑没有降级选项——Claude.ai 环境下只能整个砍掉定量基准。

### 决策二：人类评审查看器（viewer）优先于模型自评，且必须在 Claude 自查之前生成

**选了什么**：跑完测试先启动 HTML 查看器把输出递到用户眼前，用户看完给反馈，Claude 才开始改技能。Cowork 一节甚至全大写重申：**GENERATE THE EVAL VIEWER *BEFORE* evaluating inputs yourself**。

**为什么**：模型评审自己的产出有系统性偏袒（它倾向于认为自己的输出合理）；而且用户与测试例朝夕相处，识别「这不是我要的」比任何 rubric都快。原文明说浏览器评审器在 Claude.ai 场景下可以退化成对话内展示，但「人先看」这个次序在任何环境都不可让步。

**备选方案**：模型先自评、筛掉明显问题，再交人工复核。否决原因：自评会先入为主地给输出「圆谎」，污染后续的人类判断；且省下的那点时间远不值得引入的偏差。

**代价与风险**：把用户变成了循环的阻塞点——每轮迭代都要等人看完。对想全自动跑的用户，这套流程显得啰嗦（所以原文要留「just vibe with me」的灵活出口）。

### 决策三：断言在跑批等待期起草，而非看到结果之后

**选了什么**：Step 1 启动全部运行后，Step 2 明确要求「趁运行进行中」起草断言。

**为什么**：一半是流水线优化——subagent 在后台跑，主会话闲着，断言起草恰好不需要运行结果。另一半是方法论约束：断言必须在看到结果**之前**定型。先看到输出再定标准，就是先射箭再画靶，基准失去意义。

**代价与风险**：要求主会话有较强的多任务调度能力（通知驱动、时机把握）；如果运行秒完，这条时序约束就形同虚设，断言起草自然滑到结果之后，偏倚风险回归。

### 决策四：改进以泛化为纲，明令禁止过拟合补丁

**选了什么**：改进技能时第一原则是「从反馈中泛化」——用户抱怨的是这几个例子，但你修的是要用一百万次的技能；顽固问题建议换比喻、换工作模式，而不是打补丁。

**为什么**：技能和模型微调一样存在过拟合——在迭代用的几个测试例上越来越好，换个说法就失灵。测试集小（2-3 条），过拟合风险天然放大，必须靠价值观层面的约束来对冲，仅靠「别改得太具体」这种软提醒不够。

**代价与风险**：「换个比喻试试」的成功率不稳定，可能要多轮试错才找到对的表述方向；对比之下，打补丁虽然丑但见效快。这条原则牺牲了局部收敛速度，换全局泛化性——对急着的用户是逆风。

### 决策五：解释 why 取代 ALL-CAPS 命令，ALL-CAPS 是黄色警报

**选了什么**：写作风格一节明确要求向模型解释每条指令背后的原因；发现自己在大写 ALWAYS/NEVER 或堆僵硬结构时，视为黄色警报，重新组织并讲清推理。

**为什么**：现代 LLM 有良好的心智理论，理解了「为什么」就能在未覆盖的边界情况上做出正确推断；而 ALL-CAPS 命令只在字面匹配的场景有效。硬压式指令是「用关键词补丁弥补指令失败」——本质还是过拟合。

**代价与风险**：解释要花更多 Token（SKILL.md 变长，渐进式披露的第二级成本上升）；对真正需要刚性约束的场合（输出模板、字段名），「解释 why」不如直接给模板有效——所以原文自己在定义输出格式时也照样用了 ALWAYS 大写，实践与理念有微妙的自相矛盾。

### 决策六：description 优化用 60/40 切分 + near-miss 负例 + 按 test 分数选优

**选了什么**：20 条触发 eval 查询切成 60% 训练 / 40% 留出测试；负例必须是「共享关键词但意图不同」的 near-miss；每条查询跑 3 次取可靠触发率；最多迭代 5 轮，最终按**测试集**分数选 `best_description`。

**为什么**：description 优化是最容易过拟合的环节——它可以无限逼近训练集里那几条说法。切分 + test 选优是直接搬机器学习的标准防过拟合手段；near-miss 负例则是保证负例真的有区分力（全无关的负例谁都能答对，指标虚高）；每条跑 3 次是因为触发本身有随机性，单次测量噪声太大。

**代价与风险**：成本可观（20 条 × 3 次 × 5 轮 ≈ 300 次触发测试），所以原文把它放在技能完成之后、并要求用户确认状态良好再跑。小样本（8 条测试查询）下的「防过拟合」只是缓解，不是免疫。

### 决策七：按运行环境优雅降级（Claude Code / Claude.ai / Cowork 三套说明）

**选了什么**：同一个核心循环，三种环境的机制差异各写一节：Claude.ai 没 subagent 就自跑自评、砍掉定量基准；Cowork 没浏览器就用 `--static` 出独立 HTML；description 优化没 `claude` CLI 就跳过。

**为什么**：技能被设计为跨环境分发的资产，如果假定单一环境，一半用户拿到手就残废。逐节降级说明把「哪些环节依赖什么能力」显式化，让模型在任何环境都能找到可行的退路。

**代价与风险**：SKILL.md 膨胀到 485 行（逼近自家建议的 500 行上限）；三套说明有重叠，维护时容易漂移不同步。这是「一份技能服务所有环境」路线固有的税——按环境拆分技能又会让分发和版本管理碎片化，两害相权取了前者。

### 决策八：盲评对比做成可选的进阶功能，且评审与归因分离

**选了什么**：严格的 A/B 对比拆成两个独立角色——comparator 盲评（不知道哪个输出来自哪个技能），analyzer 事后揭盲归因（读双方的技能与转录，分析为什么赢）。

**为什么**：盲评消除的是「知道出处后的偏袒」（品牌效应）；揭盲归因则是把「谁赢了」升级为「为什么赢」——后者才能喂回下一轮改进。两个角色分离，各自保持单一职责，也避免评委给自己找理由。

**代价与风险**：需要 3 次 subagent（两跑一评）起步，成本又上一层；rubric 是 comparator 现场生成的，评分尺度跨轮不稳定。原文自己承认「大多数用户用不上，人类评审循环通常就够了」——把它收进 Advanced 区是清醒的成本/收益标注。

## 3. 机制如何运转

主循环是一个「实证驱动的提示词开发流水线」：

```
            ┌────────────────────────────────────────────────┐
            │                  迭代循环                       │
            │                                                │
  捕获意图   ▼                                                │
┌──────────┐ 草稿    ┌──────────────────────────────────┐      │
│ 访谈/调研 │──────▶│ Step 1  同一轮启动 N 个测试 × 2 跑  │      │
└──────────┘ SKILL.md│  (with_skill + baseline)          │      │
      ▲             └──────────────┬───────────────────┘      │
      │                            │ 后台运行中                 │
      │                            ▼                          │
      │             ┌──────────────────────────────────┐      │
      │             │ Step 2  趁等待起草断言（先于看结果） │      │
      │             └──────────────┬───────────────────┘      │
      │                            ▼                          │
      │             ┌──────────────────────────────────┐      │
      │             │ Step 3  通知到达即存 timing.json   │      │
      │             └──────────────┬───────────────────┘      │
      │                            ▼                          │
      │             ┌──────────────────────────────────┐      │
      │             │ Step 4  grader评分 → 汇总benchmark │      │
      │             │         → 分析师检查 → 启动viewer   │      │
      │             └──────────────┬───────────────────┘      │
      │                            ▼                          │
      │             ┌──────────────────────────────────┐      │
      │             │ Step 5  人类在viewer评审           │      │
      │             │         → feedback.json           │      │
      │             └──────────────┬───────────────────┘      │
      │                            ▼                          │
      │             ┌──────────────────────────────────┐      │
      └─────────────┤ 泛化式改进技能（非打补丁）           │──────┘
                    └──────────────────────────────────┘

循环收敛后：description 优化（触发测试循环）→ 打包交付
```

时序上有两条容易违反的关键约束：

1. **断言必须先于看到结果定型**（Step 2 与 Step 1/4 的时序关系）。违反它，基准就变成「为已有输出找理由」，全部定量数据失去意义。这是整套机制里最脆弱的一环——没有任何强制手段，全靠模型自律遵守时序。

2. **查看器必须在 Claude 自己评估输出之前生成**（Cowork 一节的全大写叮嘱）。违反它，Claude 会先入为主地自行「修正」，人类的评审权被架空，human-in-the-loop 退化成 human-as-rubber-stamp。原文用「GENERATE THE EVAL VIEWER *BEFORE*」这种它自己都称为黄色警报的大写来强调，可见真实运行中这条被违反的频率之高。

外围还有一条数据流纪律：`grading.json` 的字段名（`text`/`passed`/`evidence`）是硬契约，查看器按名字解析——中间产物的 schema 漂移会静默破坏下游，这也是 `references/schemas.md` 独立成文件的原因：让所有环节对着同一份契约写。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 输出主观的技能（文风、设计、艺术） | 定量基准无处着力，硬套断言产生假精度 | 断言依赖「客观可验证」前提；主观质量只能靠人类定性评审，循环退化为纯人工 |
| 目标任务太简单（"读这个PDF"） | 触发优化失真——好 description 也测不出触发 | 技能触发机制只对模型独立搞不定的复杂任务生效，简单查询永远绕过技能 |
| 无 subagent 环境（Claude.ai） | 定量基准整个砍掉，自跑自评引入作者偏差 | 双跑对照与并行运行都依赖 subagent；跑技能的和写技能的是同一个上下文 |
| 用户赶时间（"vibe with me"） | eval 循环被跳过，技能质量回到「写完即上线」 | 人类评审是循环的阻塞点，用户可以随时合法地拆掉整套安全网 |
| 测试集只有 2-3 条 | 「泛化」保障形同虚设，改进实质上是在过拟合 | 样本量撑不起「跨无数提示词泛化」的声明，只是缓解 |
| 触发优化负例写得简单 | 指标虚高，优化出的 description 实战判别力差 | 全无关的负例任何 description 都能答对，训练信号没有区分力 |
| 断言起草晚于结果到达 | 基准失去方法论意义，变成事后合理化 | 「先定标准再看结果」的时序约束无强制机制，依赖模型自律 |
| Cowork 等环境模型忘记生成 viewer | 用户没看就进入下一轮，评审权被架空 | 原文自述该环境下 Claude 系统性不愿生成查看器，只能靠大写叮嘱 + TodoList 提醒对抗 |
| 迭代多轮后基准波动大 | 难以判断新版本是否真的更好 | 每配置样本量小（每 eval 一跑），噪声未被平均；analyzer 只能标记无法消除 |

总规律：**失效集中在「客观可验证」与「人类在环」两个前提被抽掉的时候**——前者塌掉定量半边，后者塌掉定性半边，剩下的是一套仪式感大于判别力的流程。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| 与 superpowers 的 writing-skills | 同为「造技能的技能」，但方法论对立：writing-skills 是**规则驱动**（TDD 式——先写测试再写技能，由约束推导内容），skill-creator 是**实证驱动**（先写草稿再跑对照 eval，由数据迭代内容）。前者适合流程类、可静态检验的技能；后者适合输出质量依赖模型的技能 |
| 与 brainstorming / grilling | skill-creator 的 Capture Intent + Interview 阶段承担了轻量的需求澄清职能，但不做「一次一问」的深挖——它假设意图可以在 4 个标准问题内收敛，更复杂的需求澄清应交给专门的提问类技能先行 |
| 与被创建的技能（父→子） | 本技能是生产者，产物是新技能。它对子技能的全部要求（pushy description、渐进式披露、解释 why）实际上定义了一套「技能质量标准」——读它可以反推官方对好技能的审美 |
| 与 skill 生态的 description 触发机制 | 它是极少数把「description 是执行代码」当作一等公民来对待的技能——专门的优化循环、评测 schema、HTML 评审工具链，全都围着触发率这一个指标转 |
| 环境技能（`/skill-test` 等） | 被明确排除：原文点名「不要用 `/skill-test` 或其他任何测试技能」——自带工具链自成闭环，避免外部测试技能的流程与本技能的产物契约（目录结构、schema）冲突 |
