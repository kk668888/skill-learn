## 1. 它解决什么问题

这个技能本身**不解决实际问题**——它只有一行字。它要解决的是**一个关于其它技能的问题**：拷问该由谁发起？

拷问是一种**侵入性极强**的交互。它会连续向你抛出成批问题，打断你手上的任何事，并要求你逐条作答。如果这种交互可以被 AI 自主启动，后果是：你只是随口说"我最近在想换个博客框架"，AI 立刻开始盘问你——而你可能完全没有被拷问的意愿。

**设计立场**：把"发起权"和"执行逻辑"**拆开**。发起权必须在你手上；执行逻辑放在别处，供多方复用。

> 这个技能几乎没有实现，全部价值在于**一条元数据声明**（`disable-model-invocation: true`）加上**一行转发**。这是一个"靠声明而非靠代码"解决问题的设计。

## 2. 核心设计决策

### 决策一：用 `disable-model-invocation: true` 关闭自动触发

**选了什么**：在 frontmatter 里声明本技能**只能手动调用**。

**为什么**：`description` 是 Claude Code 的路由键——AI 判断"要不要用某个技能"完全靠读它。`grill-me` 的 description 写的是"一场不留情面的访谈，用于打磨计划或设计"，这个语义**很容易被误匹配**：你提到"我在琢磨一个方案"，AI 就可能认为该拷问你。

所以这里不能靠"把 description 写得更窄"来解决——因为窄了又会漏掉真正想用它的场景。**正确做法是把判断权整个收回来**：关掉自动触发，由你用 `/grill-me` 显式表达意图。

**代价**：你必须记住命令名。忘记的话，这个技能永远不会被触发，你会以为它坏了。

**备选方案**：
- *让 description 更精确* —— 被否决。语义匹配天生模糊，"想被拷问"和"在琢磨事情"在文本上难以区分。
- *保留自动触发，但让 AI 先征求同意* —— 被否决。多一层交互确认，体验更啰嗦；而且在用户明确想用时也增加摩擦。

### 决策二：正文只做转发，不实现逻辑

**选了什么**：`Call the Skill tool with "grilling".`——一行，把控制权交给 `grilling`。

**为什么**：这是整个技能集合**可组合性**的根基。看它的实际收益：

```
grill-me         = grilling
grill-with-docs  = grilling + domain-modeling
```

假设当初把拷问逻辑直接写进 `grill-me` 里，那么要做"带文档的版本"时，唯一选择是**复制一份再改**。两份拷贝此后会各自演化、各自修 bug，逐渐漂移。而现在加一个变体的成本是**一行**，且 `grilling` 一个字都不用动。

额外收益：因为逻辑不在入口里，**内核可以被单独使用**——你可以在不发起拷问的情况下单独触发 `domain-modeling`（比如只是改 `CONTEXT.md` 时）。这在"入口即全部逻辑"的设计下做不到。

**代价**：多一跳间接。读 `grill-me` 的源码看不出它能干什么，必须再去看 `grilling`。

**备选方案**：
- *入口内联全部逻辑* —— 被否决。见上。
- *用参数传递模式* —— 被否决。增加了一个需要文档化的接口，而"组合两个技能"用现成的技能机制就能表达，不需要自造参数系统。

### 决策三：入口与内核的触发策略**不同**

**选了什么**：`grill-me` 禁止自动触发，`grilling` 允许自动触发。

**为什么**：这不是疏漏，而是刻意的分层——
- **入口管用户意图**：你要不要被拷问 → 必须由你决定
- **内核管触发语义**：这套方法论什么时候适用 → 交给语义匹配

如果内核也禁止自动触发，那么任何想复用它的技能都必须靠人工中转，组合性就断了（这正是决策二收益的前提）。

> **跨 harness 印证**：`agents/openai.yaml` 里同样写了 `allow_implicit_invocation: false`。同一个决策在两个平台的技能格式里各写了一遍——说明"入口禁止自动发起"是这套设计的**本质要求**，不是某个平台的偶然约定。

## 3. 机制如何运转

```
你输入 /grill-me
      ↓
Claude Code 载入 grill-me/SKILL.md
      ↓
正文只有一行：调用 grilling
      ↓
grilling 载入，开始第一轮拷问
```

关键约束在于**你无法通过自然语言触发它**——`disable-model-invocation: true` 意味着即使 AI 判断"现在该拷问用户了"，它也只能建议你手动调用，不能自己发起。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 你**忘了命令名** | 技能永远不会被触发，形同不存在 | 自动触发被关闭，唯一入口是人手输入 |
| `grilling` 被**改名或删除** | 入口变成死链，调用报错 | 正文硬编码了 `"grilling"` 字符串，没有校验机制 |
| 误用于**编码场景** | 拷问完成了，但设计决策没有落盘 | 它不含 `domain-modeling`，那是 `grill-with-docs` 的职责 |
| 环境**不支持技能机制** | 完全不可用 | 它没有任何独立实现，100% 依赖宿主平台 |

> 第二个失效场景值得留意：**薄入口是零冗余的**。`grill-me` 里没有任何"我依赖 grilling"的声明，只有一句自然语言。改名不会触发任何报错提示，只会静默失败。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **调用** `grilling` | 唯一依赖。非编码场景的拷问逻辑全部来自它 |
| **被** `grill-with-docs` **取代** | 编码场景应改用后者（额外叠加领域建模，产出会落盘） |
| 与 `install-skills.mjs` 的关系 | 脚本把它打平装到 `~/.claude/skills/grill-me/`，`disable-model-invocation` 等 frontmatter 原样保留 |
