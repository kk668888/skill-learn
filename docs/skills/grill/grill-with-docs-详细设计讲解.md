## 1. 它解决什么问题

`grill-me` 能把设计想清楚，但它有一个**时间维度的漏洞**：拷问结束后，那些被敲定的决策住在哪里？

答案是——住在**对话记录**里。而对话会压缩、会丢上下文、换个会话就没了。于是会出现一个荒诞的场景：你花了一小时想清楚了整套设计，三天后打开新会话，AI 对一切一无所知，你得从头再讲一遍。**想清楚的价值被易逝性吃掉了。**

同时还有一个更隐蔽的问题：**术语漂移**。拷问过程中你会反复使用某些词，而这些词的含义往往在追问中被悄悄修正过——"取消"到底是取消整个订单还是部分？如果没人记下来，下次讨论时同样的歧义会再来一遍。

**设计立场**：把"想清楚"这件事的**产出**也当作一等公民。不只是过程要严谨，产物必须**落到磁盘上**。

> 注意它的取舍：它假设**这个项目值得留下文档**。如果是快速试验、一次性脚本、或者你只是想临时理清思路，`grill-me` 更合适——`grill-with-docs` 会持续要求你停下来写文件。

## 2. 核心设计决策

### 决策一：用"调用两次"实现组合，而不是复制

**选了什么**：正文全部内容就是 `Call the Skill tool twice, for "grilling" and "domain-modeling".`

**为什么**：这是整个 grill 系列里**最能说明薄入口价值**的一处。对比两种做法的长期演化：

```
方案 A（组合，实际采用）
  grilling          ← 拷问逻辑，一份
  domain-modeling   ← 文档逻辑，一份
  grill-with-docs   ← 一行："都调一下"

方案 B（复制）
  grilling          ← 拷问逻辑，一份
  domain-modeling   ← 文档逻辑，一份
  grill-with-docs   ← 拷问逻辑副本 + 文档逻辑副本  ← 两份要各自维护
```

方案 B 的问题不是"多写一次"，而是**两份拷问逻辑会各自演化**：在 `grilling` 里修了一个提问题路的 bug，`grill-with-docs` 那份不会跟着修。时间越久，两者行为差异越大，而没有任何机制能提醒你。

方案 A 的代价是**多一跳间接**，以及**两个内核的节奏可能互相干扰**（见第 4 节）——这个代价是真实的，但远小于维护两份拷贝。

### 决策二：为什么选这两个内核，而不是别的

**选了什么**：`grilling` + `domain-modeling`。

**为什么是 `grilling`**：编码场景和`grill-me`面对的是同一个问题——设计未经验证就开写。所以拷问内核完全复用。

**为什么是 `domain-modeling`**：因为在所有"该留下什么文档"的选项里，术语表和 ADR 是**最容易在拷问中被敲定、也最容易丢失**的两类：

- **术语**在对话中被反复修正，修正过程本身就是最容易丢的信息
- **取舍理由**（为什么不用方案 B）是拷问的核心产出，但常规文档只记"用了 A"，不记"为什么不是 B"

**备选方案**（为什么没选）：
- *加一个"写设计文档"的技能* —— 被否决。设计文档的内容其实就是拷问过程的记录，而`grilling`已经把决策逐条问清楚了，再写一遍是重复劳动。
- *只用 `grilling`，让用户事后自己写* —— 被否决。"事后自己写"在实践中等于"不写"，语境一过就写不出当时的精确含义了。

### 决策三：入口同样禁止自动触发

**选了什么**：`disable-model-invocation: true`（与 `grill-me` 一致）。

**为什么**：理由与 `grill-me` 相同——拷问是侵入性的，发起权必须在用户手上。而且这一版更重（会持续要求写文件），被 AI 自主启动的代价更大。

### 决策四：不为"带文档的拷问"写任何专属逻辑

**选了什么**：这个技能里**没有一行**是关于"什么时候写文档""写什么格式"的。

**为什么**：全部交给 `domain-modeling`。这保证了整套设计里**关于"文档"的规则只有一个来源**（`domain-modeling` 的 SKILL.md）。如果这里再写一遍"术语敲定时要记下来"，一旦规则演进（比如 ADR 判据改了），就有两个地方要改，而且迟早会不一致。

**代价**：读 `grill-with-docs` 的源码完全看不出文档是怎么产生的，必须跨到 `domain-modeling` 才能理解完整行为。

## 3. 机制如何运转

```
你输入 /grill-with-docs <想讨论的事>
      ↓
同时载入两个内核
      ↓
grilling 驱动主循环（设计树 × 前沿 × 轮次）
      │
      └── 每当某个术语被敲定 / 某个取舍被确定
              ↓
          domain-modeling 判定是否落盘
              ├─ 术语 → 更新 CONTEXT.md（即时，不攒批）
              └─ 难逆转的取舍 → 提议 ADR（须过三判据）
      ↓
前沿为空 → 你确认共识 → 结束（文档已在过程中写好）
```

关键点：**文档不是收尾动作，而是贯穿过程中的副作用**。`domain-modeling` 明确要求"不许攒批"，所以落盘发生在拷问途中，而不是结束后补记。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| **两个内核的节奏互相干扰** | 拷问的流畅性被打断，或文档被"等会儿再写"拖掉 | `grilling` 追求"整条前沿批量推进"，`domain-modeling` 要求"术语敲定**当场**落盘"——一个要连贯，一个要随时叫停 |
| 项目**没有代码可对照** | `domain-modeling` 的"与代码交叉验证"这一招失效 | 该纪律依赖"代码是领域模型的第一手证据"，纯文档/纯构思项目没有这个锚点 |
| 讨论的是**一次性议题** | 产出大量没人再看的文档 | 设计立场假设"这个项目值得留档"。快速试验应该用 `grill-me` |
| 术语**反复变更** | `CONTEXT.md` 频繁改写，或留下过时条目 | 即时落盘在术语不稳时会产生震荡 |
| 你在**多人协作项目中** | 你的 `CONTEXT.md` 与团队既有词汇表可能冲突 | 该技能假设术语表由你单方维护，没有"与他人协商"的机制 |

> **第一个场景是这套组合的固有张力**，也是最值得注意的。两者都是成熟设计，但优化目标不同：`grilling` 优化**信息采集效率**（少来回），`domain-modeling` 优化**信息保存时机**（趁语境新鲜）。叠在一起时，你可能正在答第 4 个问题，AI 突然说"等一下，我先把刚才那个术语记下来"。这个打断是**必要**的——因为拖到最后写不出准确含义——但确实牺牲了拷问的连贯性。

## 5. 与其他技能的协作

| 关系 | 说明 |
|------|------|
| **调用** `grilling` | 主循环驱动，决定问什么、按什么顺序问 |
| **调用** `domain-modeling` | 落盘逻辑，决定写什么、何时写、要不要立 ADR |
| **取代** `grill-me` | 编码/需要留档的场景用它；纯思辨场景仍用 `grill-me` |
| 与 Superpowers 的关系 | 功能上覆盖 brainstorming + writing-plans 的"想清楚"部分，但**不产出实现计划**、不管 TDD 与评审——那部分留给 Superpowers |
