# grill 系列技能原理拆解

> 源码：`~/.claude/skills/`（来自 [mattpocock/skills](https://github.com/mattpocock/skills)，作者 Matt Pocock）
> 涉及技能：grill-me、grilling、grill-with-docs、domain-modeling
> 仓库定位：*"Skills for real engineers — not vibe coding"*——小、可改、可组合。

## 0. 一句话原理

**用穷举式的结构化访谈，在行动之前消灭所有未经验证的假设——并把过程中敲定的术语和取舍沉淀为磁盘资产。**

它对抗的 LLM 缺陷：拿到模糊想法就开始干活，把"我以为你想要"伪装成"理解了需求"。

## 1. 架构：薄入口 + 内核分离

四个技能分两层：

```
【入口层】用户手动触发（disable-model-invocation: true）

  grill-me ────────────┬──→ 【内核层】可被组合、也可独立触发
   （非编码用）          │
                       ├──→ grilling         拷问方法论（设计树 × 前沿 × 轮次）
  grill-with-docs ─────┤
   （编码用，多文档）     └──→ domain-modeling 领域建模纪律（术语表 + ADR）
```

入口的正文只有一行，例如 grill-me：

```markdown
Call the Skill tool with "grilling".
```

**为什么这样设计**：

- **组合性**：grill-with-docs = grilling + domain-modeling，一行转发实现组合，零复制。想加一个"grill 加自动实验"的变体，再写一行入口即可。
- **内核独立可用**：domain-modeling 平时单独触发（改 CONTEXT.md、写 ADR 时），不必捆绑在拷问里。内核的 description 写成允许自动触发（"Use when... uses any 'grill' trigger phrases"）。
- **为什么入口禁止自动触发**（`disable-model-invocation: true`）：拷问是高强度打断式交互——AI 不该自作主张开始盘问你。**入口管用户意图（你要不要被拷问），内核管触发语义（什么时候这套方法论适用）**。两层各管一件事，职责干净。

## 2. grilling 内核：设计树 × 前沿 × 轮次

三个核心概念（技能原文的定义）：

| 概念 | 定义 |
|------|------|
| **Design tree（设计树）** | 每个决策分支出挂在它下面的决策 |
| **Frontier（前沿）** | 前置决策已全部敲定的决策集合 = 此刻**能问**的问题（不用猜还没听到的答案） |
| **Round（轮次）** | 一轮问完整条前沿（每题编号 + 给推荐答案），等回答，重算前沿，再下一轮 |

```
Round N:  问 Q1 Q2 Q3（整条前沿，各带推荐答案）
             ↓ 用户回答
          树被重塑：已敲定的决策解锁下游问题
Round N+1: 新前沿 = 刚解锁的问题 ∪ 未解决旧问题
             ↓
          前沿为空 → 拷问结束 → 用户确认共识 → 才许行动
```

### 每个机制为什么存在

**为什么按树组织而不是线性问卷**：
问题的答案决定后续问题该不该问、怎么问。线性问卷必然问出"依赖未定答案"的问题——那是让 AI 瞎猜。依赖关系被显式建模后，"哪些问题现在还不能问"就有了精确的定义（不在前沿上的问题不许问）。

**为什么一轮问完整条前沿（而不是一次一问）**：
这是和 Superpowers brainstorming 的直接分歧点——brainstorming 铁律 *"Only one question per message"*，grilling 却批量问。两种解法针对同一矛盾：**用户注意力 vs 依赖正确性**。grilling 的立场：编号 + 每题带推荐答案已足够控制认知负载，而批量能一次消化整层依赖、少跑几个来回。哪个对？看你被打断的耐受度——这正是对比实验该记录的观察点。

**为什么每题必须带推荐答案（➡️）**：
- 迫使提问者**表态**。没有立场的开放提问是把设计工作甩回给用户。
- 用户可以一键同意（决策杠杆：推荐对，回个"同意"就推进），也可以推翻——推荐错了，分歧点立刻暴露，比开放问答精确得多。
- 推荐答案本身就是一次假设检验：AI 敢不敢基于现有信息下判断？

**事实与决策的分工（原文最硬的一条）**：

> *"Finding facts is your job, never the user's."*

能自己查的（文件系统、工具状态、代码现状）绝不问用户——派 sub-agent 去查。**决策**才是用户的。且探索不阻塞访谈：sub-agent 未返回时，只有依赖它的下游问题等待，前沿上其余问题照问——依赖树天然支持并行。

**为什么完成条件是"前沿为空"而不是"聊得差不多"**：
"前沿为空"是可判定的数学条件：决策树每个分支都被走过，**nothing left silently assumed**（没有沉默的假设）。模糊的"聊透了"无法判定，也无法阻止过早收工。

**为什么最后还要用户确认共识**：
原文：*"Do not act on it until the user confirms you have reached a shared understanding."*——这是你见到的**第三处规划门禁**（HARD-GATE → Planning boundary → shared understanding confirmation）。三套系统独立发明了同一个闸门：共识必须显式确认，行动不许自动接续。

## 3. domain-modeling 内核：术语表 + ADR 纪律

定位（原文的自我区分，很精确）：

> 主动构建和磨尖领域模型是 **active** 纪律；仅仅读 CONTEXT.md 拿词汇表用是任何技能都能做的 passive 习惯。**这个技能管"改模型"，不管"消费模型"。**

### 五个动作

1. **对照术语表质疑**——用户用词和 CONTEXT.md 冲突时当场叫停（"你的术语表定义 cancellation 是 X，你现在说的像 Y，到底是哪个？"）
2. **磨尖模糊词**——"account 是指 Customer 还是 User？这是两个东西"：一个规范词 + 一串 `_Avoid_` 同义词
3. **编造边界场景压测**——用具体极端场景探概念边界，逼用户精确
4. **与代码交叉验证**——用户陈述和代码矛盾时当面摆出来（"你说支持部分取消，但代码取消的是整个 Order，哪个对？"）
5. **即时落盘**——术语敲定当场写进 CONTEXT.md，*"Don't batch these up"*

### 每条纪律为什么存在

| 纪律 | 为什么 |
|------|--------|
| CONTEXT.md **只是术语表**，"nothing else" | 范围蔓延保护：术语表一旦开始存决策、计划、实现细节，就变成没人读的杂物间 |
| 规范术语 + `_Avoid_` 弃用词 | 同义词漂移是沟通噪音之源；**opinionated**（选一个最好的），弃用词列出来防复发 |
| 定义紧凑、只收本领域术语 | 通用编程概念（timeout、repository pattern）不入表——它们不需要本项目特有定义 |
| **惰性创建**（第一个术语敲定才建文件） | 不产出空脚手架；文件的存在本身就代表"这里有真东西" |
| **即时落盘，不许攒批** | 术语敲定的语境是易逝的，拖到会话末尾就写不出当时的确切含义了 |
| ADR **三判据**全满足才写：难逆转 + 无上下文会奇怪 + 真实取舍 | ADR 膨胀 = 没人读。多数决定不配 ADR；判据把"值得记录的取舍"和"日常选择"分开 |

### ADR vs 术语表的分工

- **术语表**记"我们管这个东西叫什么"（高频、易变、轻）
- **ADR** 记"我们为什么选了这条难回头的路"（低频、持久、重）
- 两者都是**磁盘资产**——这一点和 OpenSpec 的 `specs/` 同构：对抗聊天记录的易逝性，把共识变成文件。对话会压缩、会丢失、换会话就没了；文件不会。

## 4. 三套系统的收敛与分歧

| | grill 系列 | Superpowers | OpenSpec |
|---|---|---|---|
| 访谈前置 | grilling：设计树 × 前沿，批量问 | brainstorming：一次一问 | /opsx:explore：无副作用探索 |
| 行动门禁 | shared understanding 需用户确认 | `<HARD-GATE>` | Planning boundary |
| 磁盘资产 | CONTEXT.md（术语）+ ADR（取舍） | design doc + plan | specs/ 主规格 + changes/ 增量 |
| 适应场景 | 任何想法（含非编码） | 编码工程纪律 | 需求资产管理 |
| 粒度哲学 | 穷举（前沿空才停） | 过程完整（链路走完） | 流动（随时可改任何 artifact） |

**收敛点**（三个独立发明的同构物，说明是这类问题的稳定解）：

1. **访谈先于行动**——三套都拒绝"拿到就做"
2. **行动门禁**——三套都要显式确认才放行执行
3. **共识落盘**——三套都把对话产物写成文件对抗易逝性

**分歧点**（对比实验的核心观察对象）：

- 提问节奏：一次一问（brainstorming）vs 整前沿一批（grilling）
- 完成判定：过程走完（Superpowers）vs 依赖穷尽（grilling）vs 用户满意即止（OpenSpec fluid 哲学）

## 5. 与你的关联（L2 自检素材）

你在这个项目里**完整亲历过一次**：Round 1（定主题）→ Round 3（钉 L2、共存/取舍）→ Round 4（方式/产出/验收/范围四连问，每题带推荐答案）→ Round 5（实验需求、节奏）→ 前沿清空 → 共识总结 → 你确认 → 才开始写文档。期间我查了 `learn` 技能、OpenSpec 安装位置（事实自己查），没问过你任何能自己查的东西；CONTEXT.md 现有 9 个术语、按惰性+即时纪律维护；没写任何 ADR（学习方法决策不满足三判据——不难逆转）。

**自检题**（不翻文档回答，答得上就是 L2 达标）：

1. 为什么 grilling 的入口技能要 `disable-model-invocation: true`，内核却不要？
2. "整条前沿一批问"和"一次一问"各自押注什么？什么情况下你会反过来选？
3. ADR 三判据为什么缺一不可？只满足两条会发生什么？
