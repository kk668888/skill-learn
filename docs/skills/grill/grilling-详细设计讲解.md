## 1. 它解决什么问题

LLM 面对一个模糊想法时的默认行为是**立刻开始产出**——写代码、写方案、写文档。而它填充空白的方式是**用最可能的推测代替确认**。

这个推测过程完全不可见：你看到的是一个自信、完整、结构良好的产出，看不到底下垫了多少个"我猜他大概是想要…"。等到发现猜错，成本已经付出。

更麻烦的是，**这个错误不来自模型能力不足，而来自信息不足**——换个更强的模型也一样猜错，因为它同样没有那些信息。所以这不是"提示词写清楚点"能解决的问题，而是**流程结构**问题：在产出之前，必须有一个强制把假设暴露出来的环节。

`grilling` 就是那个环节：一场结构化的、以穷尽假设为目标的访谈。

> **设计立场**：它假设"用户心里其实有答案，只是没说清楚"，而不是"用户也不知道自己想要什么"。这个假设决定了整套机制是**追问式**的（逼出已有信息）而非**发散式**的（帮你创造信息）。后者是 brainstorming 的活。

## 2. 核心设计决策

### 决策一：用树建模，而不是用清单

**选了什么**：把待定事项组织成一棵**设计树**——每个决策分支出挂在它下面的决策。

**为什么**：因为决策之间有**依赖**。问"A 还是 B"和问"选 A 的话 X 怎么配"是两个问题，后者在前者未定之前没有意义。清单结构无法表达这种关系，于是必然出现两种坏情况：要么问出带着臆想前提的问题，要么漏问。

树结构把"哪些问题现在可以问"变成**可计算**的——那就是前沿的定义。

**备选方案**：线性问卷（一份固定的问题清单）。**被否决的原因**：同样的清单对不同项目问出的问题质量天差地别，且无法表达依赖。

### 决策二：一轮问完整条前沿，而不是一次一问

**选了什么**：把所有当前可问的问题**一次性**列出，每题编号并附上推荐答案。

**为什么**：这是整套设计里最反直觉的一条，因为它和人类访谈的直觉相反（人类访谈讲究一次一问、慢慢来）。理由在于**等待成本**：一次一问意味着用户答完一轮、AI 消化、再出下一题——每个来回都有固定的交互开销。而前沿上的问题是**同层**的，彼此无依赖，用户完全可以在一次阅读中处理完。

**它赌的是什么**：赌用户能承受一次读 4-6 个问题。用编号和每题的结构化排版来降低认知负载，换取更少的来回。

**这个赌注的代价**：问题一多，用户容易只答前两个、忽略后面的，或者回答质量下降。

> **对比**：Superpowers 的 `brainstorming` 在同一个问题上做了**相反**的赌注——它的铁律是 *"Only one question per message"*（一条消息只问一个问题）。两套系统都是成熟设计，分歧点在于对"用户注意力 vs 交互次数"的权重判断不同。**这是 grill 与 Superpowers 最实质的设计差异**，也是学习这两套时最值得琢磨的一处。

### 决策三：每题必须给推荐答案

**选了什么**：每个问题后面都要有 `➡️` 推荐的答案，不允许裸问。

**为什么**：三重作用。
1. **逼提问方表态**。没有立场的开放提问，本质是把设计工作又推回给用户——用户请你来是想听判断，不是想做题。
2. **降低回答成本**。推荐对了，用户回一个"同意"就能推进；推荐错了，分歧点会以最快速度暴露。这比开放问答的收敛速度快得多。
3. **推荐本身就是一次假设检验**。AI 敢不敢基于现有信息下判断，会立刻暴露它的理解程度。

**风险**：如果 AI 的推荐被用户无脑同意，这个机制就退化成了"AI 单方面决策"。所以它依赖用户**真的会推翻**错误推荐。

### 决策四：事实归 AI，决策归用户

**选了什么**：凡是可以从环境查到的东西（文件系统、代码现状、工具状态），**禁止问用户**，派子代理去查。

**为什么**：这是防止 LLM 懒惰的关键条款。**把该自己查的东西包装成问题丢给用户**，表面像征求意见，实质是转嫁工作量——而且比直接偷懒更隐蔽，因为它伪装成了"尊重你的意见"。

它同时也是**依赖树的一个应用**：探查本身就是前沿上的一个未定项，只有它下游的问题需要等，其余问题照常推进。这条"不要阻塞"的补充，让并行成为可能。

### 决策五：完成条件是"前沿为空"

**选了什么**：结束的标志是前沿为空（每个分支都走到、没有沉默的假设），**不是**"聊得差不多了"。

**为什么**：停止条件必须**可判定**，否则无法阻止过早收工。LLM 有强烈的"我觉得我懂了"倾向，"聊透了"这种模糊标准会被它轻易自我说服。

**这一点与 TDD 的"先看测试失败"是同一思路**：把主观判断换成客观条件。区别只是 TDD 用"测试是否由红转绿"，这里用"前沿是否为空"。

### 决策六：用户确认前不得行动

**选了什么**：即使前沿已空，也要等用户明确确认共识，才允许据此行动。

**为什么**：前沿为空只保证"问题都问过了"，不保证"答案都被理解了"。确认这一步是让人来检查**理解**，而不是检查**覆盖面**。

> **跨套件观察**：`Superpowers` 用 `<HARD-GATE>` 标签、`OpenSpec` 用 `Planning boundary` 段落、`grilling` 用"确认共识"这一步——**三套系统各自独立发明了同一道规划门禁**。同一个问题被三个不同作者独立用三种措辞解决，说明这不是巧合，而是这类工作流的**收敛解**：规划态与执行态必须分离，且中间需要一道人工闸门。

## 3. 机制如何运转

```
Round N
  ├─ 计算前沿：前置条件已全部敲定的决策
  ├─ 整条前沿一次性提出（编号 + 推荐答案）
  └─ 等待用户回答
       ↓
  用户回答重塑树：已敲定的决策解锁下游
       ↓
Round N+1  重新计算前沿 → 循环
       ↓
前沿为空 → 请用户确认共识 → 才允许行动
```

关键点在于**每轮结束后树发生了变化**——不是简单地"删掉已回答的问题"，而是"解锁了新问题"。这就是为什么不能预先写一份完整问卷：问题集合是随答案演化的。

另一条约束：**依赖本轮未决问题的问题，属于后面的轮次**。这条规则容易被违反，而违反的后果很严重——AI 会基于臆想的答案提问，而带着错误前提的问题，用户的回答也失去了意义。

## 4. 什么时候会失效

| 场景 | 后果 | 原因 |
|------|------|------|
| 决策之间**没有依赖** | 退化成一份普通问卷，树的建模白费 | 前沿永远等于全部剩余问题，批量问的优势不再明显 |
| 用户**自己也不知道想要什么** | 无法给出答案，推荐答案成了 AI 的单方面决策 | 设计立场假设"用户心里有答案"，这个前提不成立 |
| 用户**无脑同意推荐** | 拷问变成 AI 自问自答 | 决策三的机制依赖用户真的会推翻 |
| 问题空间**过大** | 前沿永远清不空，或问题粒度失控 | 缺少"先分解成大块"的上游步骤——这需要人先做范围切分 |
| AI **不查事实** | 把能查到的东西问给用户，浪费轮次 | 决策四要求 AI 主动判断"这是事实题还是决策题"，判断错了就破功 |

> 最后一条尤其值得注意：**"事实 / 决策"的边界需要判断力**。"你想要什么颜色"是决策，但"项目里现在用的是什么 UI 框架"是事实——AI 必须能分清，否则会问出大量本可自查的问题。
