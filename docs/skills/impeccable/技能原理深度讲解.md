# Impeccable · 技能原理深度讲解

> **来源**：`skills/impeccable/impeccable/`，上游 `pbakaus/impeccable` 版本 4.5.2。  
> **范围**：解释整套 Impeccable 如何把前端设计从一次性提示，组织成可延续、可检验的工作流。单个命令的原文和设计取舍见下方技能文档。

## 一条主链路

```mermaid
flowchart LR
    A[用户任务] --> B[产品与既有界面取证]
    B --> C[判断页面目的与任务范围]
    C --> D[选择或继承视觉方向]
    D --> E[按任务手册实现]
    E --> F[检测、实际渲染与复核]
    F --> G[记录可复用的设计事实]
```

这条链路的核心不是多做几轮视觉润色，而是让每次设计决定有来源、有适用范围、有可对照的结果。上游虽然提供多种命令，安装时仍是**一个技能**：共同规则由入口承载，具体任务通过参考手册展开。命令是进入同一条主链路的不同切口，并不各自发明一套产品事实。

## 为什么每一步都存在

### 先取证：防止模型把缺失文档误认成空白项目

技能先读取 `PRODUCT.md`、`DESIGN.md`、页面简报、源码与已有视觉素材。产品事实回答“这是什么、为谁服务”；已建成的界面回答“哪些选择已经成为现实”。即使项目没有 `DESIGN.md`，代码里的颜色、排版、组件与品牌素材仍可能形成明确的视觉体系。新功能应继承它；真正的重设计才有权替换它。

启动器的 `context` 把这一步变成可重复入口。其价值是降低会话间遗忘和凭空补全的概率；其代价是它本身与项目文档都可能过期。因此技能另设 `doctor` 处理漂移，并规定不要把漂移修复偷偷混入一次设计任务。

### 再判范围：防止局部优化扩张成全站改版

一个页面可能承担说服、操作、阅读或体验任务；一款产品也可能同时包含四种页面。按页面目的选模式，可以让操作界面优先考虑可扫读与状态，营销界面优先考虑注意力与行动，文档优先考虑理解。随后再判断请求是局部修补、在既有体系内扩展，还是建立或替换整套视觉世界。

范围判断控制后续工作的力度。局部优化直接继承现有体系；开放的新页面需要确定构图；替换视觉体系才需要更完整的候选方向与设计选择。这个分流放弃了“一套重流程包办所有请求”的整齐性，换取对用户时间和项目稳定性的尊重。

### 先决定方向：避免在既成页面上反复找审美理由

对开放的新作品，Impeccable 从受众熟悉的文化、物件与视觉传统推导候选体系，再把选中的方向记录为页面简报里的开发契约。这样代码有了可检验的目标：首屏组成、视觉语言、用户理解路径及完成条件都可以与实际渲染比较。

候选方向和随机抽取机制针对的是生成模型的“收敛”：即使明确要求独特，模型也容易回到同类产品常见的版式。机制强迫它走出第一反应，同时仍由用户选择。它牺牲了直接开工的速度，也不保证随机抽中的方向一定好；真正的质量仍取决于受众证据、候选方案质量和后续判断。

### 再实现：把共同底线与任务手册分开

入口技能保留通用原则，具体工作按命令读取对应参考手册：规划、评审、审计、排版、色彩、动效、性能、浏览器迭代等各有路径。`craft-floor` 在动手前加载，规定真实内容、对比度、状态、响应式、浏览器默认元素等共同底线。这样的渐进加载能让当前任务看到需要的规则，又避免每次把全部参考资料塞进上下文。

底线不负责决定审美方向。用户明确给出的简报和已确定的视觉体系应先于常见模式警告。否则检测器容易把“少见但有意为之”误判成问题，把所有作品再次推回同一种安全风格。

### 最后验证与记录：让成果能跨会话延续

检测器和钩子擅长找机械问题，截图与人工复核负责判断层级、情绪、构图和真实使用情境。两类证据互补。技能要求成批检查、成批修复，并为整轮验证设置退出上限，避免把无限微调当作质量。新视觉体系交付后，`DESIGN.md` 应从实际建成的界面中总结，而不是在实现前写一份随后硬要代码服从的愿望清单。

这一步形成反馈回路：已交付的界面成为下一次设计的证据，持久文档为后续代理提供记忆，诊断工具则提醒记忆何时与现实分离。若真实内容、关键状态或运行环境缺席，验证结论必须相应收窄，不能把漂亮的单张截图当作完成证明。

## 整套设计哲学

Impeccable 同时反对两个极端：只靠模型即兴发挥，以及只靠自动规则拼出合规页面。前者会重复训练数据中最熟悉的模板，后者会丢掉受众、品牌和意图。它用产品事实限制想象的边界，用方向选择扩大想象的空间，再用实现与渲染证据检验结果。

它也把“事实归项目、选择归用户、执行与核验归工作流”分开：事实应有来源，开放的视觉方向需要选择，执行者负责完成并检验。整套机制的成本是更多上下文文件、命令手册与评审步骤。因此它最适合视觉品质有明显价值的前端工作；对极小且要求明确的修改，应使用其局部路径，避免把完整设计仪式强加给简单任务。
