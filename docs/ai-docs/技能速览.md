## openspec（12 个）

> 技能全名 `openspec-xxx`，日常以 `/opsx:xx` 命令形态使用

| 技能 | 干什么 | 怎么喊 |
|------|--------|--------|
| `opsx:new` | 开新变更，逐个 artifact 交互式创建（把关型） | 斜杠 |
| `opsx:propose` | 一句话需求一步生成全套提案，拿去即可开工 | 斜杠 |
| `opsx:ff` | 跳过分步交互，快进建完实现所需全部 artifacts | 斜杠 |
| `opsx:explore` | 探索模式：想法与需求的思考伙伴 | 斜杠 |
| `opsx:continue` | 变更进行中，补建下一个缺失 artifact | 斜杠 |
| `opsx:update` | 修订既有规划 artifacts 并保持互相一致（永不碰代码） | 斜杠 |
| `opsx:apply` | 按变更的 tasks 清单实现 | 斜杠 |
| `opsx:verify` | 验证实现与 artifacts 一致 | 斜杠 |
| `opsx:archive` | 归档完成的变更，delta 合入主规格 | 斜杠 |
| `opsx:bulk-archive` | 批量归档多个并行变更 | 斜杠 |
| `opsx:sync` | **不归档**，只把 delta 同步进主规格 | 斜杠 |
| `opsx:onboard` | 带解说的完整工作流上手巡回 | 斜杠 |

## 容易混的几组

- **openspec 三种开工**：`opsx:new` 逐步把关｜`opsx:propose` 一句话换全套提案｜`opsx:ff` 跳过分步快进——要交互质量用 new，需求已想清用 propose，嫌逐步慢用 ff
- **写计划**：`writing-plans`（superpowers，产出计划文件）vs `opsx:new`（openspec，产出 proposal+spec+tasks）——同为规划门禁，产物形态不同
- **执行计划**：`executing-plans`（独立会话）vs `subagent-driven-development`（当前会话子代理）vs `opsx:apply`（按 tasks 清单）
- **审查**：`requesting-code-review`（管流程：请谁看）vs `ponytail-review`（管内容：看什么）
- **写技能**：`writing-skills`（superpowers 规范）vs `skill-creator`（官方工坊）
- **收尾**：`finishing-a-development-branch`（git 层面）vs `opsx:archive`（规格层面）vs `opsx:sync`（只同步不归档）
