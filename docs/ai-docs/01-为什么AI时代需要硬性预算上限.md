# 为什么 AI 时代需要「硬性预算上限」

原文：[We’re going to need default hard budget caps on pretty much everything](https://simonwillison.net/2026/Oct/3/default-hard-budget-caps/)｜Simon Willison，2026 年 10 月 3 日。

## 先用一句话理解

当 AI 编程助手能替你创建程序、调用收费 API 和部署服务时，**「花到 50 元就自动停止」比「花到 50 元时发邮件提醒」更能保护你**。Simon 认为，按量收费的平台应该默认提供前一种硬限制。

## 作者到底在担心什么

过去，你通常会亲手写程序、配置服务器，花钱的动作有一定门槛。现在，你可能只说一句「帮我做个能每天整理新闻的网站」，AI Agent 就能接着写代码、连接模型 API、部署应用。程序可能持续运行，即使你已经关了电脑或者睡觉了。

按量收费的服务通常按调用次数、处理的 token、计算时间或存储量计费。一个循环错误、被人滥用的接口，或者一个持续重试的任务，都可能迅速增加账单。文章的核心担忧是：**自动化降低了创建服务的门槛，也降低了意外花钱的门槛。**

## 三个术语

1. **API**：程序调用另一家服务的接口。例如，你的网页调用大模型接口生成摘要。一次调用可能很便宜，但大量重复调用会累积费用。
2. **软性预算提醒（soft cap）**：达到你设定的金额后，平台通知你，但程序仍继续运行、仍可能继续计费。它像汽车的油量警示灯。
3. **硬性预算上限（hard cap）**：达到金额后，平台拒绝后续请求，或暂停相关服务。它像电路断路器，损失被限制在可预期范围内。

## 用一个例子走一遍

假设你部署了一个 AI 摘要网站，设定每月最多花 100 元。

- **只有提醒**：某个接口因错误一分钟调用数百次。平台在达到 100 元时给你发邮件；你早上才看到。期间的请求仍可能产生费用。
- **有硬上限**：达到 100 元后，新的收费请求被拒绝。网站的一部分功能可能暂时不可用，但账单不会随这个错误无限增长。

所以这里有一个真实的取舍：硬上限可能让服务暂时停止；没有硬上限则可能出现超出预期的账单。Simon 的观点是，对大多数个人开发者和很多企业来说，默认先限制损失更合理；确实需要持续运行的人可以主动选择取消限制。

## 文章提到的行业变化

Simon 在文中指出，AWS 当时推出了针对部分新体验的项目支出限制，Google Cloud 也推出了针对项目中部分服务的 Spend Caps。他欢迎这些变化，同时提醒读者：**某项功能存在，不等于你的账号、地区、服务和现有项目一定适用**。文章发表时，AWS 文档还说明有关体验在逐步开放。

把这点迁移到你的项目：不要仅因为控制台写着「预算」就以为会自动停费。要看清楚它是提醒还是拦截、覆盖哪些资源、有没有不受限制的费用。

## 程序员可以学到什么

这篇文章表面讲云账单，本质讲**把风险控制写进系统默认行为**。当你让 AI Agent 工作时，除了描述「它要完成什么」，还应定义「它最多能消耗多少资源、失败时何时停止」。例如：

- 给试验项目使用单独的云项目或 API Key，便于隔离费用。
- 设置明确的调用次数、并发数和重试次数。
- 对按量计费服务检查是否有真正的硬限制；仅有邮件提醒时，降低权限或缩小实验规模。
- 在本地先用少量样本测试，再扩大任务。

这些是从作者观点推出来的工程实践，并非文章列出的固定操作步骤。

## 15 分钟练习

列出你目前可能使用的三种计费资源（例如模型 API、云服务器、对象存储）。对每项回答：**谁能触发费用？达到预算后是通知还是停止？任务失控时怎样手动关掉？** 不知道答案的地方先标成「待核实」。完成这张小表，比盲目开一个新服务更有用。
