# Python 3.15 发布：从开源维护者的角度看新版本

原文：[Hello Python 3.15, goodbye 3.10, and now I can use 3.11](https://simonwillison.net/2026/Oct/12/python-3-15/)｜Simon Willison，2026 年 10 月 12 日。

## 先用一句话理解

Simon 一边介绍 Python 3.15 的新能力，一边解释一件开源维护者很在意的事：**当最老的受支持版本从 3.10 变成 3.11，项目就能放心使用 3.11 已有的特性，同时仍要测试最新的 3.15。**

这篇主要是传统软件工程文章，AI 只是其中一个应用场景。它适合练习「看到新版本时，怎样判断它对现有项目有没有价值」。

## 为什么标题同时出现 3.15、3.10 和 3.11

Simon 的开源项目尽量支持所有仍受官方维护的 Python 版本。Python 3.15 发布后，文章说 3.10 退出了官方支持范围。因此，项目可以不再为 3.10 保持兼容，代码的最低版本可以考虑提高到 3.11。

想象你写一个应用，需要让旧手机和新手机都能运行。只要承诺支持旧手机，你就不能直接依赖新手机才有的功能。等旧手机退出支持范围，你才能简化代码，采用较新的系统能力。Python 项目也是同样的道理。

这**不意味着所有项目都必须立刻放弃 Python 3.10**。企业内部系统、用户部署环境和依赖库的限制可能不同；Simon 描述的是他自己维护项目的政策和选择。

## Python 3.15 有哪些值得注意的变化

### 1. 显式延迟导入（lazy import）

通常程序启动时会执行 `import`，把相关模块加载进来。若某个插件依赖一个很大的库，即使这次任务根本用不到它，启动也可能变慢。显式延迟导入表示：先声明这个模块，真正用到相关对象时才加载。

Simon 提到自己的 `LLM` 命令行工具有插件系统。以前安装了依赖很重的插件，就可能拖慢每次命令启动。延迟导入给这类工具提供了直接的优化手段。小白可以把它理解为：**先把书名登记在借书单上，真的要读时再去书架取书。**

### 2. 推导式里的展开写法

Python 3.15 增加了更直接地把多个列表、集合或字典展开合并的写法。文章展示了把 `[[1, 2], [3, 4]]` 摊平成 `[1, 2, 3, 4]` 的例子。对新手而言，重点不是记住语法，而是理解「把多层容器里的元素汇集成一个容器」这个常见任务。

### 3. 标准库内置采样性能分析器

当程序慢时，开发者需要知道时间究竟花在哪个函数。采样分析器会定期观察正在运行的程序，记录它当时执行到哪里，再汇总热点。它通常比每一步都记录的追踪方式开销更低。

文章中的新工具能附着到运行中的 Python 进程，并生成类似火焰图的结果。**火焰图**不是温度图；它用横向宽度表示某条调用路径占用的时间或样本比例。你应先找最宽的区域，再决定是否值得优化。若大部分时间只是程序在等待输入，盲目重写业务函数通常没有用。

## 为什么「新版本」不等于「明显更快」

Simon 引述的测试显示，Python 3.15 在所测场景中与 3.14 的性能总体接近；实验性的 JIT 在特定测试中有提升。JIT 可以粗略理解为运行时把某些代码编译成更快执行的形式。

这里要学会看测试范围：**一个 Fibonacci 测试变快，不代表你自己的 Web 服务、数据处理脚本或 AI 应用都会按同样比例变快。** 真正的升级决策应基于项目自己的测试、依赖兼容性和部署环境。

## 文章中的升级动作意味着什么

Simon 用 `uv` 安装和切换 Python 版本，并更新部分项目模板的测试范围。`uv` 是一个 Python 环境与包管理工具；模板则是创建新项目时重复使用的骨架。他还列出 3.11 中现在可以直接依赖的能力，例如 `tomllib`、异步任务管理工具以及 SQLite 接口改进。

对开源维护者来说，升级通常不是只改一个版本号，而要连续回答：

1. 使用者还需要哪些旧版本？
2. 依赖库是否支持新版本？
3. 自动化测试是否覆盖新的最低版本和最新版本？
4. 新语法是否真的能删掉旧的兼容代码？
5. 性能变化是否经过本项目的测量？

## 30 分钟练习

找一个自己的 Python 项目，先不要升级它。查看 README、项目配置和 CI（持续集成）文件，写下它声明支持哪些 Python 版本。再挑一个脚本，测一次启动时间或运行时间。这样以后读到新版本文章时，你能判断「这项变化是否解决我的真实问题」，而不是只追逐最新版本号。
