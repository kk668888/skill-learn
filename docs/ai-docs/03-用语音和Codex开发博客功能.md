# 用语音和 Codex 开发博客功能：一场真实的 AI 编程实验

原文：[A new feature for my blog, built using my voice](https://simonwillison.net/2026/Oct/9/built-using-my-voice/)｜Simon Willison，2026 年 10 月 9 日。

## 先用一句话理解

Simon 一边做晚饭，一边通过语音与 Codex 沟通需求，让它为自己的 Django 博客开发「Newsletter 归档页」。**语音让需求沟通更方便，但最后的代码审查、接口选择和上线判断仍由人完成。**

## 他想做什么功能

Simon 有两类 Newsletter：一种在 Substack 上发布，另一种是提供给赞助者的月度内容。他希望自己博客新增一个页面，统一展示它们，并让归档、搜索和已有页面之间的关系符合博客现有规则。

如果你不熟悉 Django，可以把它理解为 Python 的网站开发框架。这次功能涉及几个典型的网站组成部分：

- **数据模型**：网站如何存放 Newsletter 的标题、日期、来源等信息。
- **数据库迁移**：给现有数据库增加存放新数据所需的结构。
- **导入脚本**：从 Substack、GitHub 等来源取回已有内容。
- **页面与模板**：把数据展示成归档页。
- **搜索与分类规则**：决定这些内容在哪里出现、哪里不出现。

所以这不是让 AI 生成一张静态网页，而是在一个真实项目里增加一套与旧功能协作的新功能。

## 实际流程，按顺序看

**第一步：先启动本地预览。** Simon 在本地项目里让 Codex 启动开发服务器并打开浏览器。这样后续不仅能听模型说「做好了」，还可以亲眼看页面。

**第二步：通过语音提出和修正需求。** 他边做饭边说话，过程中有停顿、改口和反复思考。例如，他讨论 Newsletter 是否应该出现在标签页、首页和按日期排列的归档页。这里最重要的不是说得像正式需求文档，而是把实际业务规则讲出来。

**第三步：Agent 写代码和导入脚本。** 大约半小时的语音交互后，功能已包含新数据模型、迁移、管理界面、多个来源的导入、归档页以及站内搜索集成。文章列出了具体完成的部分。

**第四步：人来检查尚未解决的细节。** 其中一个数据源在私有 GitHub 仓库里，需要处理访问凭据。Simon 没有把敏感凭据随意放进对话。他后来回到键盘前，要求把某个通过 Git 子进程导入数据的方案改成基于 API 的方案。

**第五步：通过 PR 审查并收尾。** PR（Pull Request）可以理解为一份待审查的代码变更。Simon 在 GitHub 里看代码，提出修改，再花约半小时用文字沟通和调整，满意后才将功能上线。

## 这篇最值得程序员学的三个细节

### 1. AI 能处理不完美表达，但业务规则仍由你负责

口头说话有重复和改口，Agent 仍能提取需求。这说明你不必等到写出完美提示词才开始。但如果你自己没想清楚「新内容应该出现在什么页面」，模型也无法替你决定最终产品规则。先给具体例子、再不断澄清，往往比堆砌提示词技巧有用。

### 2. 用可见结果和代码共同验收

一个页面看着正常，导入脚本却可能不稳；代码能运行，页面也可能不好用。Simon 同时看本地预览和 PR 代码。他发现 Git 子进程方案与自己的部署需要不匹配，于是更换实现。这是「能跑」到「能维护、能上线」之间的一步。

### 3. 语音适合大方向，精确修改适合文字

Simon 的结论不是所有开发都应该靠说话完成。他觉得语音适合边做别的事边讨论、提出想法；到了错误信息、代码片段和精确反馈阶段，打字和粘贴更有效。这是根据任务选择交互方式，而不是追求全程语音。

## 如果你是小白，怎样复刻这个方法

不必先做复杂网站。选一个小需求，例如「给自己的笔记目录做一个按月份浏览的页面」。按下面顺序让 Coding Agent 协作：

1. 描述现有目录和你想看到的页面，给两三个真实样例。
2. 说清楚边界：哪些文件要显示，哪些不要显示；是否只读；是否需要搜索。
3. 让它先展示本地预览，再看关键代码和数据处理逻辑。
4. 用你的样例逐个验收；发现差异就指出具体页面和现象。
5. 最后要求它总结改了什么、做了哪些验证，以及尚未确定的地方。

**动手目标**：在 60～90 分钟内做成一个你自己会使用的小功能，并能用两句话解释它的数据从哪里来、错误时会怎样。这个练习比连续观看十个「AI 一句话建站」视频更接近真实开发。
