## Context

现有离线发行由 `offline-inputs.json` 锁定输入树，准备脚本验证上游文件，制包脚本生成含逐文件摘要的 `manifest.json`，安装器先统一校验再按套件执行。现有安装方式覆盖插件、项目 CLI、引擎和技能目录，尚无用户级独立可执行程序。参见 [proposal.md](proposal.md) 与 [RTK 增量规格](specs/offline-skill-distribution/spec.md)。

## Goals / Non-Goals

**Goals:**

- 让维护者用已下载的官方 `v1.1.0` Windows x64 ZIP 重建可验证的 RTK 离线输入，不在内网阶段联网。
- 让两种宿主的向导共用同一份 RTK 安装逻辑，并能独立选择、预览及重复运行。
- 将程序置于 `%LOCALAPPDATA%\Programs\rtk`，在当前用户 PATH 中登记该目录。

**Non-Goals:**

- 不调用 `rtk init`，也不修改 Claude Code 或 Codex 的 hook 配置。
- 不加入其他架构、操作系统或 RTK Proxy。
- 不接管系统级或其他来源的 RTK 安装。

## Decisions

### 官方 ZIP 作为唯一上游输入

准备命令接受显式 `--rtk-archive` 路径，先核对官方 `checksums.txt` 中 `rtk-x86_64-pc-windows-msvc.zip` 的 SHA-256，再解压 `rtk.exe`、`LICENSE`、`LICENSE-ENGINE` 到输入树，最后计算固定输入树摘要。清单同时记录版本、发布页与双许可证信息。相比直接收一个任意目录，此方式能证明二进制与上游固定发行物一致；代价是版本升级必须同步更新摘要、清单与测试。

### 新增独立程序安装策略

为清单增加专门的可执行程序安装方式，由安装器在统一校验后处理。安装路径固定在当前用户的 `%LOCALAPPDATA%\Programs\rtk`，不受技能的项目级或用户级 `--scope` 影响。状态检查比较目标目录的预期文件内容并检查用户 PATH；不同内容或非预期条目为冲突，同内容可补登记缺失的 PATH。相比放在解压目录，固定位置允许用户移动或删除发行 ZIP；相比安装到项目，每个宿主和项目共用一份程序。

### PATH 与命令解析

只修改当前用户的 PATH，按路径大小写不敏感和规范化后的值去重；保留其余原有条目、空段和结尾分隔符。读取 `HKCU\Environment` 中未经展开的原值，并保留原来的 `REG_SZ` 或 `REG_EXPAND_SZ` 类型，防止已有 `%USERPROFILE%` 等引用在写回时失效。预检检查有效 PATH 中是否已有其他位置的 `rtk.exe`，避免“已安装但实际运行了另一份程序”。如已有其他来源，报告冲突并要求人工处理。写回后向 Windows 广播环境变更，并提示新终端才能读取新环境。相比修改系统 PATH，此选择不需要管理员权限，影响范围也更小。

### 写入顺序与可恢复性

安装前完成包校验、目标目录及 PATH 冲突检查。首次安装先复制文件，再登记 PATH；若 PATH 写入失败，报告失败并保留已复制文件，重试可从同内容状态继续补登记 PATH。避免自动回滚时误删目标中由用户后来放入的文件。预览和状态命令只读，不创建目录、不更新环境。

## Risks / Trade-offs

- **用户 PATH 很长或由外部工具并发修改** → 写入前重读用户 PATH，去重后写回；写入失败时明确报告并允许重试。
- **系统 PATH 中已有另一个 RTK** → 预检报告冲突，避免安装成功但命令仍解析到旧程序。
- **官方发布物采用 Apache-2.0 与 BUSL-1.1 双许可证** → 包内保留两份许可证，清单标明两者，不将默认二进制误写成纯 Apache-2.0。
- **固定目录已有其他内容** → 不自动覆盖或清理，交给用户决定迁移方式。

## Migration Plan

维护机下载并校验 `v1.1.0` ZIP，执行新增准备参数，重新生成 `offline/inputs` 与 `offline/kit`，运行离线测试及完整包验证后发布。旧版离线 ZIP 保持原样；若需回退，重新发布旧版 ZIP。已安装的 RTK 可由用户手动从固定目录移除并从用户 PATH 删除相应条目。
