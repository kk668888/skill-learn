## Context

参见 [proposal.md](./proposal.md)。当前 [Vite 配置](../../../viewer/vite.config.ts) 只在 `configureServer` 中挂载 Express API，`viewer/package.json` 没有生产构建或启动命令。扫描器和上传逻辑都以项目根相对路径访问 `skills/`、`docs/skills/`、`docs/ai-docs/`、`docs/collections/` 与根级 Markdown。上传 API 当前只接受 `localhost` Host 及同源 Origin；Portainer 的局域网 IP 会触发 403。行为边界以两份 [增量规格](./specs/) 为准。

## Goals / Non-Goals

**Goals:**

- 镜像在不运行 Vite 开发服务的情况下提供页面与 API，并继续复用现有扫描、阅读、搜索、上传实现。
- 容器内项目根路径稳定，只有两个普通文档目录需要宿主机可写挂载；其他资料成为镜像内容快照。
- 保持现有本机开发路径与上传路径 ID，允许通过运行时配置指定 Portainer 的局域网访问地址。

**Non-Goals:**

- 不增加登录、密码、用户权限或多用户隔离；Portainer 自身的登录不会保护查看器端口。
- 不自动推送镜像到仓库，不配置 HTTPS 网关或公网入口，也不自动执行 Git 操作。
- 不在容器中安装 Git 或把整个仓库挂为可写目录。

## Decisions

### 1. 使用生产服务入口，共享现有 Express API

新增生产入口，先注册 `createApiApp`，再提供前端构建产物和页面回退；未知 `/api/` 路径不得回退成 HTML。新增明确的前端与服务端构建命令：前端由 Vite 构建，服务端 TypeScript 打包为 Node 可运行的模块，运行时仅需生产依赖。Docker 使用多阶段构建，最终阶段复制构建产物、生产依赖及项目资料，不运行 `vite dev`。生产服务在容器内监听 `0.0.0.0:5188`；本机 `npm run dev` 保持原行为。

备选是直接在镜像里执行 `npm run dev -- --host 0.0.0.0`。这会把开发服务器、热更新与开发依赖留在长期运行的容器中，并使产物依赖源码布局，因此不选。服务端入口应使用显式项目根配置或固定容器布局，避免打包后 `import.meta.url` 位置改变导致扫描错误。

### 2. 将外部访问地址作为运行时配置

Portainer Stack 提供一个完整的 `VIEWER_PUBLIC_ORIGIN`，例如 `http://192.168.1.20:5188`。服务端启动时验证它是合法的 HTTP Origin，上传时以其协议、Host 和端口作为明确允许值；不从任意请求的 Host 或 `X-Forwarded-*` 头推断信任来源。容器模式缺少或误配该值时应明确报错。本机开发模式继续采用现有 localhost 行为。

备选是放开 Host 校验或允许任意 Origin。那会使其他网页更容易向局域网查看器发起跨站上传，因此不选。Origin 校验只防浏览器跨站提交，不是身份认证；没有登录的 Portainer 部署仍允许能直接访问端口的局域网用户读写。

### 3. 镜像包含只读资料，两个普通文档目录使用宿主机绑定挂载

以仓库根作为 Docker 构建上下文，把 `skills/`、`docs/skills/`、根级 Markdown 和查看器产物放到固定容器项目根。Portainer Stack 将宿主机项目里的 `docs/ai-docs/` 与 `docs/collections/` 分别绑定到容器中同名目录；部署前创建后者，确认两个目录可由容器运行用户写入。这样已有 AI 文章和自建分组继续使用原路径，容器重建只替换程序与只读资料，上传文件仍留在宿主机供 Git 管理。

备选的 Docker 命名卷虽能持久化，但文件不直接落在项目目录，不符合宿主机 Git 管理需求。把整个项目仓库挂成可写目录则扩大了上传服务接触技能源码与规划文件的范围。镜像中 `docs/ai-docs/` 的副本会被绑定挂载遮住，宿主机目录是容器运行时的权威内容；技能资料更新需要重新构建镜像。

### 4. 交付 Portainer Stack 示例与部署检查

提供镜像构建命令、Stack 示例、两个宿主机绝对路径占位值、外部 Origin、端口映射和健康检查。镜像可在 Portainer 所管理的同一 Docker Engine 上本地构建；若 Portainer 管理另一台主机，文档说明先把镜像推送到用户选择的镜像仓库，再让 Stack 拉取。示例不写死用户的局域网 IP 或宿主机路径。

备选的项目内自动发布流水线需要镜像仓库与凭据，当前没有这些约定，因此留待单独变更。

## Risks / Trade-offs

- [免登录局域网部署] → 能访问发布端口的设备可以读写文档。文档明确只在受信任局域网使用，并提示不要将端口映射到公网；需要访问控制时另立变更。
- [HTTP 明文传输] → 局域网流量未加密。本次没有账号密码可泄露，但文档内容仍可能被网络观察者读取；未来可在受信任反向代理后接入 HTTPS。
- [宿主机绑定挂载的权限或路径错误] → 上传可能失败或看不到已有文档。启动和验收步骤检查目录存在、可写，并区分宿主机路径与容器路径。
- [镜像资料快照与挂载内容来源不同] → 更新技能或技能文档需重建镜像；普通文档直接在宿主机更新。部署说明明确两类内容的更新方式。
- [构建上下文夹带本地文件] → `.dockerignore` 排除 `.git`、依赖、缓存、安装副本、环境文件及其他不应入镜像的内容；保留必要的项目资料。

## Migration Plan

1. 在 Docker 宿主机准备项目的 `docs/ai-docs/` 和 `docs/collections/`，确认已有文章仍在前者；不要搬迁文件。
2. 构建镜像，使 Portainer 所管理的 Docker Engine 能找到该镜像；在 Stack 中填写宿主机绝对路径与局域网 Origin 并启动。
3. 从局域网浏览器验证阅读、搜索、上传和宿主机落盘；用相同挂载重建容器验证持久化。
4. 回滚时恢复旧镜像或停用 Stack；宿主机两个文档目录保留，容器删除或重建不删除上传文件。
