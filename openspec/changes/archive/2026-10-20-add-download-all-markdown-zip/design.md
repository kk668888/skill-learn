## Context

参见 [proposal.md](./proposal.md)。现有 `scanProject(root)` 是目录、读取和搜索 API 的共同收录边界，返回排序后的项目根相对路径。开发服务由 Vite 挂载 `createApiApp`，Docker 生产入口也复用它；下载接口放在同一 Express API 中即可保持两种运行方式一致。界面左侧边栏已有上传与主题操作区，适合放置下载入口。

## Goals / Non-Goals

**Goals:**

- 将扫描结果作为唯一文件清单，不在下载功能里重新定义目录范围。
- 归档条目使用扫描器返回的正斜杠相对路径，直接保留原始字节，并支持中文文件名。
- 在生成大 ZIP 时避免服务端把整份归档常驻内存；失败时让前端能识别。

**Non-Goals:**

- 不提供按分组、搜索结果或单篇文档下载，不导出渲染后的 HTML。
- 不加入定时备份、历史版本、服务端持久化 ZIP 或 Git 操作。
- 不改变现有免登录局域网访问范围；下载的数据本来就可由同一查看器逐篇读取。

## Decisions

### 1. 由服务端按当前扫描结果生成 ZIP

新增 `GET /api/download`。请求开始时调用 `scanProject(root)`，以该次结果确定条目集合；对每个路径做常规文件与可读性检查，再交给流式 ZIP 库，以路径本身作为归档内名称，不增加顶层文件夹。成功响应使用 `application/zip` 与固定的附件文件名。ZIP 仅通过响应传送，不写入项目目录。开发和生产入口均通过现有 `createApiApp` 获得接口。

备选方案是在浏览器逐篇调用 `/api/doc` 再打包，但它会把所有内容与 ZIP 都留在浏览器内存，并将大量请求的失败处理分散到前端；因此采用单次服务端下载。另一个备选是直接把 `docs/` 打包，无法覆盖根级和技能文件，也会包含查看器不可见的资料。

### 2. 共用扫描边界并保留原始文件

ZIP 仅使用 `scanProject` 返回的路径，归档前确认路径仍指向项目内的普通文件；不接受客户端传入路径。文件内容由二进制读取流进入 ZIP，避免文本解码、换行或 BOM 被改写。空扫描结果生成有效的空 ZIP。上传后再次请求会重新扫描，因此新文档自然纳入。

备选方案是复用 `/api/doc` 的 JSON 内容，但那会重新编码 UTF-8 文本，无法保证归档字节与源文件完全一致。

### 3. 前端等待完整响应后触发保存

边栏增加“下载全部 Markdown”按钮。点击后请求同源 API，并在响应完整到达后把 ZIP Blob 交给浏览器下载；请求期间禁用重复点击，完成后释放对象 URL。HTTP 错误或响应流中断时显示提示并恢复按钮状态。按钮始终作用于全量扫描结果，不读取当前过滤或搜索状态。

备选方案是直接导航到下载 URL，浏览器能更早开始保存且内存开销较低，但页面难以获知 HTTP 错误或中途断流，无法可靠显示失败反馈。这里优先满足明确的失败反馈要求。

## Risks / Trade-offs

- [文件在扫描后被删除或改写] → 归档前预检，流式读取期间出错时终止响应；前端仅在完整收到响应后触发保存。并发修改仍可能让 ZIP 中的内容反映读取时刻而非请求开始时刻，不能承诺跨文件的原子快照。
- [大量文档使浏览器持有较大 Blob] → 服务端流式生成并保持只读；前端需要接收完整 ZIP 才能显示可靠的失败反馈。若以后数据量超出浏览器内存预算，再单独设计下载传输方案。
- [无登录的局域网用户可批量取得资料] → 保持现有访问模型，并在界面与部署说明中沿用“仅受信任局域网”的约束；本变更不扩大可读取的文件集合。
- [ZIP 库增加生产依赖] → 选用维护中的流式库，固定锁文件，并通过构建、解压和 Docker 运行测试检查兼容性。

## Migration Plan

新增只读 API 与按钮，不涉及已有文档迁移。部署时重新构建查看器或 Docker 镜像；回滚旧版本即可移除下载入口和 API，不影响宿主机 Markdown 文件。
