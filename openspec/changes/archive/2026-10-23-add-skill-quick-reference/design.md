# 设计：技能速览文档

## Context

见 proposal.md 的 Why。现状约束：文档将放在 `docs/ai-docs/`（手写文章的家，已被 viewer 扫描收录）；`docs/collections/` 是上传功能的自建分组目录，不放手工内容；`docs/skills/<套件>/` 受项目规则限制只允许四类文件。

## Goals / Non-Goals

**Goals**

- 一页速查：39 个技能按套件分组，每行「技能名｜干什么｜怎么喊」，只留区分词
- 集合恒等由测试守护，新增/删除技能后速览漂移会直接红

**Non-Goals**

- 不做自动生成（脚本生成引入构建步骤，且一句话职责需要人工提炼，机器拼不出区分词）
- 不做 viewer 特殊入口（不与 SDD 入门指南争 WelcomePanel 唯一入口）
- 不做英文版（本项目文档定位全中文）
- 「怎么喊」列不做机器校验（见决策 3）

## Decisions

### 1. 守护测试只解析表格首列，不解析散文

- **选择**：测试从文档的 markdown 表格中提取首列技能名（约定：技能名一律用反引号包裹），与 `skills/**/SKILL.md` 的 `name` 集合双向比对
- **为什么**：「容易混的几组」对照区块里也会出现技能名（如 `writing-plans` vs `opsx:new`），若全文提取会把对照引用误判为「虚列条目」。表格首列是条目的唯一权威位置，语义清晰且解析稳定
- **代价**：文档作者必须遵守「条目只出现在表格首列」的约定；测试失败信息需列出缺失/多余名单，否则作者无从下手

### 2. opsx 短名用显式别名表，不做推导

- **选择**：测试内置 12 条显式映射（`opsx:new` → `openspec-new-change` 等）
- **为什么**：推导规则 `opsx:<x>` → `openspec-<x>-change` 对 `openspec-propose`、`openspec-onboard`（无 `-change` 后缀）不成立，规则会带特例，不如直接列全表
- **代价**：openspec 套件新增技能时需同步别名表——但那本身就是「新增技能」动作的一部分，测试会兜底提醒

### 3. 「怎么喊」列不进守护测试

- **选择**：触发方式（自动/手动/斜杠）是编辑判断，测试只守护集合恒等
- **为什么**：`disable-model-invocation` 可判定「手动」，但 ponytail 一族「模型可调但实际按需」属于灰区，机器校验会把编辑判断变成格式游戏
- **代价**：触发列写错不会被发现，接受（速查表是给自己看的，错一次自己就改了）

### 4. 测试落 `viewer/tests/`，与既有守卫测试同家

- **选择**：`viewer/tests/skill-quick-reference.spec.ts`（vitest，node 环境读文件即可，无需 jsdom）
- **为什么**：FOUC 键名守卫、production 路由测试都在这里，读仓库文件的测试已有先例；根目录 `tests/` 是安装脚本的家，语义不符

## Risks / Trade-offs

- [文档格式微调导致测试误红] → 首列 + 反引号的约定足够简单稳定；失败信息输出缺失/多余名单，修复路径明确
- [一句话职责的质量无测试守护] → 明确接受：集合恒等归测试，行文质量归「逐行对照中文版精修」的实现步骤
- [技能数量继续增长，表格变长] → 接受：速查表本就是扫视用途，一屏滚动 39 行仍是优势；真到上百行再考虑分套件拆页

## Migration Plan

纯新增（两个新文件 + CLAUDE.md 一句增补），无迁移；回滚 = 删除文件、撤销增补句即可。
