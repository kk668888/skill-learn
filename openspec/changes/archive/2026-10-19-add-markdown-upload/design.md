## Context

查看器由 Vite 开发服务承载 React 页面，并通过同进程的 Express 中间件提供只读 API。`scanner.ts` 目前扫描 `skills/`、`docs/skills/`、`docs/ai-docs/` 和根级 Markdown；`tree-builder.ts` 将 AI 文章作为独立分组，其余两类目录按技能文档约定组树。`App.tsx` 只在挂载时获取一次目录树。参见 [proposal.md](./proposal.md)；行为边界以 [上传规格](./specs/markdown-document-upload/spec.md) 为准。

## Goals / Non-Goals

**Goals:**

- 在现有本地服务中完成一次上传、落盘、更新目录与打开文档的闭环，继续复用现有读取和搜索接口。
- 保持上传目标的严格白名单，使普通文档入口不能写入技能源码、技能文档或任意项目路径。
- 新增分组和文件的可见性来自实际磁盘内容，不维护另一份数据库或浏览器索引。

**Non-Goals:**

- 不提供独立的空分组管理、批量上传、编辑、删除或覆盖。
- 不增加 Git 暂存／提交操作，也不为静态构建增加可写后端。
- 本次不提供 Docker 镜像；只保持路径相对项目根，便于以后挂载文档目录。

## Decisions

### 1. 保留 AI 文章目录，自建分组使用固定根目录

继续以 `docs/ai-docs/` 对应“AI 文章”；扫描 `docs/collections/` 下的一级子目录，每个子目录对应一个普通文档分组。`tree-builder.ts` 依据这些路径生成与“AI 文章”同级的分组节点，并保持现有文件路径 ID。上传目标使用稳定的分组标识，由服务端映射到这两种允许的路径；请求不能直接提供任意目标目录。

备选是把 AI 文章迁到统一目录，或允许选择 `docs/` 下任意目录。前者会改变现有路径、链接与 Git 历史，后者容易碰到 `docs/skills/` 的严格文档结构，因此均不采用。新增分组只允许一层，以减少命名和树形交互复杂度。

### 2. 使用带大小限制的 multipart 上传，服务端保存原始字节

前端通过 `FormData` 提交一个文件、目标文件名以及“已有分组标识／新分组名称”。服务端增加单个上传接口，在内存中接收最多 5 MiB 的文件，使用严格 UTF-8 解码校验，再将原始字节写入磁盘。选用成熟的 multipart 解析中间件及其类型定义，避免自行处理分段边界；相比先把文件转成 JSON 字符串，这一方式可保留换行和可选 BOM 等原始字节，并能直接约束文件数量与大小。前端也先检查扩展名与大小，服务端重复校验，服务端结果为准。

接口成功时返回新文档的项目根相对路径，供前端刷新树和导航；无效输入返回 400，文件过大返回 413，同名文件或新分组名冲突返回 409，写入失败返回 500。错误响应沿用现有 `{ error }` 格式，并给出用户可处理的中文提示。

### 3. 名称校验、冲突处理与写入保持一致

服务端只接受单级文件名和分组名，拒绝空白、`.`／`..`、路径分隔符、控制字符、隐藏名称及跨平台不安全名称；目标文件名必须以小写 `.md` 结尾。新分组名还不能与“AI 文章”同名。查找现有分组和文件时按 Unicode 规范化及不区分大小写的键比较，避免 Windows 与未来 Linux 容器出现不同的冲突结果。

服务端先验证输入，再解析允许目录，并拒绝符号链接目录；对同一分组的写入串行化，在检查同名文件后以排他创建方式写入目标文件。写入失败时删除本次产生的不完整文件；若同时新建了目录，只清理本次创建且仍为空的目录。备选的直接覆盖写入更省步骤，但会破坏已有 Git 文件并使冲突提示失效。

### 4. 上传后复用目录树与文档路由

上传控件放在普通文档可见的界面入口，包含文件选择、已有分组选择／新建分组、可编辑的目标文件名和明确的成功或错误反馈。`App.tsx` 在上传成功后重新请求 `/api/tree`，保留已展开节点，并展开目标分组，然后按服务端返回的路径走现有文档路由。搜索继续每次按 `scanProject` 读取磁盘，因此无需新增索引更新协议。上传失败则保留所选源文件与目标文件名，方便改名重试。

## Risks / Trade-offs

- [multipart 新依赖和内存缓冲] → 限制一个文件与 5 MiB，校验请求体大小，避免无界内存占用。
- [不同文件系统的名称规则和大小写行为不同] → 服务端统一验证并做不区分大小写的冲突检查，同时使用排他创建；按分组串行化本进程并发请求。
- [目录被替换成符号链接或保存中断] → 写入前核实真实目标目录，排他创建并清理失败产生的文件；只在允许目录内操作。
- [Git 仓库会出现用户上传的未提交文件] → 界面说明文件已保存到项目目录；不暗示已自动提交。
- [未来 Docker 容器重建可能丢失容器层文件] → 未来打包时为文档目录配置宿主机挂载或持久卷；本次不改变本地路径约定。

## Migration Plan

无需迁移现有文章或修改其路径。新增 `docs/collections/` 可在首个自建分组上传时创建；旧版本查看器仍可读取 `docs/ai-docs/`，但不会展示新目录。回滚应用代码不会删除已上传的 Markdown 文件，必要时可由用户直接在项目目录管理这些普通文件。
